# Kalshi Arbitrage Bot — Claude Context

This is a **production prediction-market pair-trading bot** (the "Kalshi Arbitrage Bot" is its product name; the same-title strategy is a near-arbitrage, the time-series strategy is a directional bet) that trades real money via RSA-signed Kalshi REST API calls. Read this file in full before making any changes to trading, fee, or order-submission logic.

---

## What This Is

The bot finds two types of mispriced binary contract pairs on Kalshi, sizes positions using the Kelly criterion, and submits fill-or-kill orders leg-by-leg (there is no batch order endpoint), unwinding the first leg if the second doesn't fill. A separate backtesting pipeline replays the same strategy on the full history of settled markets.

**Time-series pairs:** Two contracts asking the same question at different deadlines (e.g. "Will BTC exceed $80k by March?" vs. "by June?"). `market_a` is always the EARLIER contract — earlier by `close_time`, except for a same-event ladder (DR-73), where it is earlier by STATED deadline and the pair carries that gap on `CandidatePair.stated_gap_days`. A later deadline can only add probability, so the later contract's YES ask normally sits above the earlier's, and the gap `pB − pA` is the market-implied probability that the event first happens *between* the two deadlines. The bot disputes that number when it is large: when `pB − pA >= min_price_diff_for_gap(gap_days)` it buys YES on the earlier contract (at `pA`) and NO on the later one (at `nB`). Exactly three settlement cells exist: the event happens by the earlier deadline (A=YES ⇒ B=YES; the YES on A pays), it never happens by the later deadline (A=NO, B=NO; the NO on B pays), or it happens in between (A=NO, B=YES; both legs expire worthless — the full stake is lost). A=YES with B=NO is impossible for a cumulative-deadline pair. **That premise is now screened on WORDING at pair formation (a heuristic) rather than assumed (DR-67):** both finders refuse a pair unless both legs' WORDING states a cumulative "by <date>" deadline and the two deadlines DIFFER — `scanner.deadline_phrasing` / `scanner.cumulative_deadline_pair`, one definition shared by `find_time_series_pairs` and `backtester._extract_pairs` (see the cumulative-deadline gotcha below). The backtester still treats a pair that settled A=YES/B=NO as a premise violation and excludes it with a counted WARNING, never pays it — but that counter is no longer the ONLY signal, it is defence in depth behind a text heuristic, and a non-zero count now means one of the WARNING's named causes fired — most likely a wording false negative, though legs ordered on an early REALIZED close (cross-event pairs only — a same-event ladder is ordered on its stated deadlines), or strike-blind grouping on a cache without subtitles, can also produce it (DR-72 widened the WARNING beyond "the wording screen missed it" — see the strategy-change gotcha below for the full cause list). A wording heuristic has residuals: recurring rolling-window series ("before <date>" families that publish a new deadline every week) pass the screen without genuinely nesting, but checked against real prices they are co-quoted only in the earlier leg's final hours at a YES ask near $0.01, where the trade reduces to a NO bet on the later window regardless — measured harmless; see the Known residuals list in the cumulative-deadline gotcha below. This is a **directional bet, not an arbitrage**: at market prices its expected value is zero minus fees, and it only profits if the market systematically overstates the in-between mass. Kelly sizes it with `config.time_series_profit_prob(pA, pB)` = `1 − k·(pB − pA)`, where `k = TIME_SERIES_INTERVAL_PROB_DISCOUNT` (0.75) is the fraction of the market-implied in-between mass the operator believes ("prices converge by 25%") — an operator-tunable estimate, not a measured quantity. Two contracts are only "the same question at two deadlines" when they ask about the same OUTCOME, so the grouping key is `scanner.time_series_group_key(pair_key(m), m.subtitle)` — the date-stripped `event_title | market_title` PLUS the market's outcome label — not the title alone: a daily price family lists dozens of strikes under ONE title and differs only in the subtitle (DR-01, see the cross-strike gotcha below). Two contracts of ONE event ticker were refused outright until DR-73, on the rationale that a shared event is a multi-choice OPTION set; that is true of an MVE event's labels and false of a deadline LADDER, so `config.TIME_SERIES_SAME_EVENT_LADDERS` (shipping OFF) admits two dated cumulative rungs of one event, ordered and tiered on their stated deadlines — see the same-event-ladder gotcha below. And two contracts whose RAW wording is identical — same `title`, same `subtitle`, same event title — across two event tickers of ONE series are not a cumulative-deadline pair at all: the deadline lives outside the wording, so they are two instances of one recurring fixture and the finder skips them (DR-02, DR-54 — see the one-series gotcha below). This conjunct lives in the time-series finder as well as the same-title one because gating only the latter would merely relabel the trade.

**Same-title pairs:** Two contracts with identical title + subtitle on different event tickers of DIFFERENT series; two events of one series are two instances of one recurring fixture and are never paired (DR-02, DR-54 — see the one-series gotcha below). Any divergence of 5% or more is anomalous (the code rejects `pA - pB < SAME_TITLE_MIN_PRICE_DIFF`, i.e. `>=` qualifies, not a strict `>`); the bot exploits it assuming 95% co-resolution probability. The subtitle is the intra-title outcome discriminator and is sourced from the API's `yes_sub_title` field (see the subtitle-drift gotcha below) — it is load-bearing, not cosmetic, and since DR-01 it discriminates in BOTH finders: the same-title key `(event_title, title, subtitle)` and the time-series key `scanner.time_series_group_key`.

**Multivariate (MVE) markets:** Both pair types include MVE markets (option markets within a multi-choice event, e.g. "Trump" inside "2024 Election Winner") when `INCLUDE_MVE_MARKETS=True` in `config.py`. Pairs are grouped by `event_title + market_title` (see `scanner.pair_key`) so option labels like "Trump" or "Above $80k" can't false-positive across unrelated events; the time-series finder keys on that PLUS the subtitle (`scanner.time_series_group_key`), which still leaves one option label at two deadlines in a single group but splits two different labels. Since DR-54 no same-title pair is ever formed between two MVE combo events: Kalshi lists combos under several series prefixes, all beginning `KXMVE` (`KXMVECROSSCATEGORY`, `KXMVESPORTSMULTIGAMEEXTENDED`, `KXMVECROSSCATEGORY0`, `KXMVENBASINGLEGAME`), and since DR-55 `scanner.event_series` collapses that whole family onto one series (`config.MVE_SERIES_FAMILY_PREFIX`) so the one-series rule treats any two combo tickets as two instances of one recurring fixture — a combo ticket's wording names its legs but never its date, so one wording recurs across fixture instances and two tickets with identical leg wording are two DIFFERENT tickets. That is a pairing rule, not an ingest exclusion — MVE markets are still fetched, grouped and traded as time-series pairs and against non-combo same-title counterparties. **DR-73 does not open MVE option labels to pairing either, and for the same reason the cumulative-deadline rule does not: it turns on WORDING.** Two markets of one event pair only when both are worded as cumulative deadlines reading to two DIFFERENT calendar dates, which an option set ("Trump" / "Harris" under one election event) never is — so the branch admits a deadline ladder and still refuses the multi-choice options this exclusion was written for. **The cumulative-deadline rule (DR-67) does not change that, because it turns on WORDING rather than on a market being MVE:** an MVE market whose sub-contract label carries a "by <date>" deadline ("$80,000 by June 30") is eligible like any other, and so is one whose parent EVENT title carries it ("Presidential Election Winner by March 2026") — those two routes are pinned by `tests/test_scanner.py::TestOutcomeDiscriminator::test_dated_outcome_label_is_one_key` and `::test_mve_option_label_at_two_deadlines_still_pairs`. The event-title route survives DR-69's deciding-field spans because there the event title IS the deciding field (the option label and title carry no marker), so it supplies the spans itself (`tests/test_scanner.py::TestSpansFromDecidingField::test_mve_event_title_route_still_pairs`). What that rule does refuse is the narrower case of a combo/parlay ticket whose wording names its legs but no date at all ("Parlay" / "All legs hit"), which classifies `unknown` and fails closed — correct, since such a pair never had a cumulative-deadline premise either. That refusal is theoretical on the LIVE path today: live combo ingest currently returns zero nested markets (see the SDK-response-model drift gotcha, which records that the prod MVE listing returns zero nested markets regardless of `with_nested_markets`), so no live combo ticket reaches this rule to be refused by it. The CLASSIFIER does run routinely in the BACKTEST — cached day slices do carry combo records, and `_extract_pairs` classifies every member of a >=2-member time-series group up front, combo or not — but no combo PAIR ever reaches this refusal there either: two combos landing in one time-series group are always identically-worded duplicates of one KXMVE ticket, so the one-series conjunct (checked first) drops them a line earlier, before `cumulative_deadline_pair` is ever asked (measured on the 2026-09-08/09 day slices: 0 of 856,513 combo records share a group key with a differently-worded combo or with any non-combo). Since DR-68 the classifier does read combos worded "by Decision" (fight-method legs), which used to read as a "by Dec" deadline — on those same slices that was every one of the 525 combo records classified cumulative, and none remains. On those same 2026-09-08/09 day slices, the time-series pairs DR-67 removes from `main`'s set were mostly snapshot families (97.3% of 943,450 non-MVE pairs, per the verifier), plus dateless non-MVE look-alikes (2.7%) — combos contributed ZERO time-series candidates before and after this change (DR-02/54/55 already excluded them). Set `INCLUDE_MVE_MARKETS=False` to fall back to binary-only behaviour. With the flag off, event titles are still resolved and attached in both the scanner and the backtester — the flag narrows which markets are fetched, never how the remaining ones are grouped.

## Run Commands

All commands must be run from the **repo root**:

```bash
# One-time setup (Python >= 3.11)
pip install -e ".[dev]"

# Sandbox simulation with virtual $1k balance
python3 -m kalshi_betting.main --mode dev --sandbox-balance 1000

# Sandbox simulation, dry-run (no orders submitted)
python3 -m kalshi_betting.main --mode dev --dry-run

# Production live trading
python3 -m kalshi_betting.main --mode prod

# Production discovery only, no orders
python3 -m kalshi_betting.main --mode prod --dry-run

# Live trading (either mode), only consider markets closing within 14 days from now
python3 -m kalshi_betting.main --mode dev --max-horizon-days 14

# Backtest from 2024-01-01 with $10k starting balance
python3 -m kalshi_betting.backtest --start-date 2024-01-01 --balance 10000

# Backtest forcing fresh API fetch (ignores disk cache)
python3 -m kalshi_betting.backtest --no-cache

# Backtest, only enter trades whose later-closing leg is within 14 days of the simulated entry date
python3 -m kalshi_betting.backtest --max-horizon-days 14

# Backtest at a specific time-series interval discount k (this run only; live sizing always reads config.py)
python3 -m kalshi_betting.backtest --interval-discount 0.60

# Backtest without the k-grid re-simulation (dashboard's k selector offers one point; the empirical-k calibration report still runs;
# with the band sweep on — the default — each band is simulated at the primary k only, so the scenario explorer's heatmap has a single k column)
python3 -m kalshi_betting.backtest --no-sweep

# Backtest with same-event deadline ladders forced on/off for THIS run only
# (default: config.TIME_SERIES_SAME_EVENT_LADDERS; never reaches the live finder,
#  which binds that constant at import — this is how the ladder k-hat is measured)
python3 -m kalshi_betting.backtest --same-event-ladders
python3 -m kalshi_betting.backtest --no-same-event-ladders

# Backtest at a specific PRIMARY-scenario time-series spread band on pB - pA
# (backtest only; live trading reads no band value — config.min_price_diff_for_gap's
#  spread_min keyword is never passed outside config/backtester/backtest/dashboard)
python3 -m kalshi_betting.backtest --spread-min 0.30 --spread-max 0.60

# Backtest without the band x k x population scenario sweep (band sweep is ON by
# default in the CLI; the primary scenario still runs, but the dashboard's
# Scenario Explorer section has no grid to show)
python3 -m kalshi_betting.backtest --no-band-sweep

# Weekly scheduler daemon (runs prod every Monday 09:00)
python3 -m kalshi_betting.scheduler

# Live verification of the V2 order mapping + transfer unit (~1c of real money, prod account)
python3 -m kalshi_betting.v2_probe --ticker <TICKER> [--step no-mapping|unfillable-ask|transfer] [--dest-shard N] [--yes]

# Run tests
python3 -m pytest tests/ -v

# Lint check
python3 -m ruff check kalshi_betting/
```

## CI and Packaging

- `.github/workflows/ci.yml` runs two jobs, **Lint (ruff)** and **Test (pytest)**, on every push to `main` and on every pull request regardless of base branch (the `pull_request:` trigger carries no branch filter). Both must pass before merging — run them locally first.
- `pip install -e ".[dev]"` installs the packages CI needs. Backtests additionally benefit from the optional `perf` extra (`pip install -e ".[dev,perf]"`), which adds `orjson` to speed up settled-market JSON parsing — never required, and the on-disk cache format is identical with or without it.
- `pyproject.toml` declares `requires-python = ">=3.11"` and pins `kalshi-python-sync==3.2.0`. Do NOT bump the SDK pin to 3.13.0 — that version's own metadata requires Python >= 3.13 and breaks `pip install -e ".[dev]"` on 3.11 (i.e. breaks CI).
- Tests live in `tests/` (`test_auth.py`, `test_backtest.py`, `test_backtester.py`, `test_config.py`, `test_dashboard.py`, `test_historical.py`, `test_http.py`, `test_main.py`, `test_reporter.py`, `test_scanner.py`, `test_scheduler.py`, `test_strategy.py`, `test_trader.py`, `test_v2_probe.py`, plus the non-test helper `dashboard_golden.py` and its `fixtures/` directory) and run fully offline against `MagicMock` clients.
- `tests/test_dashboard.py::TestGoldenSections` pins the seven dashboard sections that predate the scenario explorer to SHA-256 digests captured on `main` @ `fe0a758` (`tests/fixtures/dashboard_golden_main.json`, rendered and normalised by `tests/dashboard_golden.py`). A deliberate change to any of those seven sections fails it until the golden is re-captured, by the recipe in `tests/dashboard_golden.py`'s module docstring. When a digest diverges in a plotly/pandas/numpy environment other than the captured one (plotly 6.9.0, pandas 3.0.3, numpy 2.4.6), the test SKIPS rather than fails. `pyproject.toml` pins none of the three exactly, so a CI skip there is not a pass: read the skip reason.

## Key Patterns — Always Follow These

**Constants live in `config.py` exclusively.** Never hardcode `0.07` (fee rate), `0.20` (Kelly cap), `0.15`/`0.30` (tiered time-series price thresholds — always go through `min_price_diff_for_gap()`), `0.75` (the time-series in-between discount `k` — `TIME_SERIES_INTERVAL_PROB_DISCOUNT`; always go through `time_series_profit_prob()`), `(0.0, 1.0)` (the BACKTEST's default time-series spread band on `pB − pA`, i.e. no band — `BACKTEST_DEFAULT_SPREAD_BAND`; read only through `time_series_spread_band()`, whose floor `backtester._find_entry` passes to `min_price_diff_for_gap(gap_days, spread_min=…)` (so it also sets that pass's leg-price-sum ceiling, `1 −` the raised floor) and whose ceiling it tests per Monday through `time_series_spread_too_wide()` — time-series pairs only, a Monday above the ceiling is skipped rather than ending the scan, and the default band reproduces the live rule; the live path reads no band value: its only `min_price_diff_for_gap` calls, scanner's three (the finder's floor, `_pair_max_sum`, enrichment's `ref_yes is None` fallback), pass the gap alone, and no module outside `config`, `backtester`, `backtest` and `dashboard` may reference a band helper or band constant, import one of those three modules, or pass `min_price_diff_for_gap` more than the gap — a deny-by-default walk of the package pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_live_path_reads_no_band`), `(0.0, 0.20, 0.25, 0.30, 0.35, 0.40)`/`(0.50, 0.60, 0.70, 0.80, 0.90, 1.00)` (the band grid for the backtest's band × k scenario sweep — `SPREAD_BAND_SWEEP_FLOORS`/`SPREAD_BAND_SWEEP_CEILINGS`; read only by `backtester._sweep_from_candidates`, reached through `run_backtest_sweep(band_sweep=True)` — the CLI's default — which crosses all 36 bands with `INTERVAL_DISCOUNT_SWEEP`'s 13 `k` values into 468 `population="all"` scenarios, plus a standalone time-series (ladders + cross-event, same-title excluded), ladder and cross-event simulation per non-empty cell, a split-half out-of-sample check per "all" and per time-series cell and an excluding-top-event concentration check per "all" and per time-series cell that traded at least one event, all over the ONE fetch `_prepare_candidates` already ran, and with ONE full `_find_entry` pass — at the no-band band, every other band rescanning only the pairs that entered there; measured 2026-09-23 on the DR-73 calibration corpus (10,733 time-series pairs, 10,530 with candles on both legs, start 2020-01-01, ladders on) at 26.4–26.6 s for the whole sweep (4,590 simulations, 3.2–3.3 s of it the entry passes; **Return `None` for validation failures; don't raise.** `compute_trade()` returns `None` when there's no edge. Both finders drop markets with a missing/unparseable `close_time` in the shared `scanner._filter_active_markets()` they each call first — reported as one summary WARNING carrying the count (silent at zero) — once per RUN, not once per finder: both run modes call `_filter_active_markets` on the SAME list twice, so `find_same_title_pairs`, always the second to run, passes the keyword-only `warn_missing_close=False`. The flag suppresses only the REPORT; the markets are dropped either way, and any standalone caller keeps the default `True` (TS-22). **Two-stage fee calculation:**
1. `fee_per_pair_approx(price_a, price_b)` — continuous approximation over the two LEG prices (`scanner.leg_prices(pair)`: `(nA, pB)` for same-title, `(pA, nB)` for time-series); use during pair *filtering* before the integer contract count `n` is known.
2. `fee_leg_exact(n, p)` — ceiling-rounded exact fee; use for *final validation* once `n` is determined.
Never swap these — the approximation underestimates and will let bad trades through if used for final validation.

**Retry pattern:** Use `api_call_with_retry()` from `_http.py` for all new market-data API calls (this includes read-only portfolio calls like the balance read in `auth.verify_auth()` and `get_held_tickers`; both now go through `fetch_json_page` on the SDK's raw `*_without_preload_content` variant rather than the modeled call — see the shard-balance gotcha). It handles HTTP 429 and 5xx with exponential backoff doubling 2s → 32s across 6 attempts (`_MAX_DELAY = 60s` is only a defensive ceiling). It ALSO retries status-less transport failures — `urllib3.ProtocolError`, `ReadTimeoutError`, `http.client.IncompleteRead`, and the builtin `ConnectionError`/`TimeoutError` — matched through a bounded `__cause__`/`__context__` walk (`_is_transient_network_error`), because urllib3 wraps the real error (a `ProtocolError: Connection broken: IncompleteRead` from `resp.read()` killed a multi-hour backtest fetch on 2026-08-03; it carries no `.status`, so the old status-only classifier treated it as fatal). Retrying these is safe *because* every caller of this wrapper is a read-only GET. Do NOT add retry logic to order submission in `trader.py`, on EITHER order path, NOR to the collateral transfer POST — `_submit_order` (legacy) deliberately calls `fetch_json_page` directly and `_submit_order_v2` / `_execute_transfer` deliberately call `_http.signed_request_json` directly (which itself contains no retry logic, precisely so those call sites stay single-shot); a failed leg means the price moved, not a transient error, and a retried transfer moves the money twice. `trader._position_count()` **is** wrapped (it's a read-only GET like the rest): the no-retry rule covers submission only, and an unretried transient 429 there reads as "fill state unknown", escalating a recoverable ambiguity into a rollback or `manual_review`. Don't "unify" `_position_count` with `_submit_order`/`_submit_order_v2`/`_execute_transfer` in either direction — the asymmetry is the rule, and `trader.py` therefore DOES import `api_call_with_retry` (for the position lookups only); the no-retry rule is asserted per-function on the submission/transfer sources, never as a module-wide import ban. The position reads that are deliberately unretried go through `trader._position_count_once`, and both sit inside the window where the NO leg MAY be filled (on the re-read path that is exactly what is being determined) and is certainly unhedged, because the YES leg has not been submitted: `_confirm_v2_no_mapping`'s mapping check (see the V2 backstop bullet) and `_execute_one`'s NO-leg ledger-lag RE-READ (DR-64 — see the delta bullet). It shares `_read_position`'s parse with `_position_count`, so only the retry policy differs; the YES-leg re-read is deliberately the RETRIED reader, because the first read beside it is already retried and a single-shot re-read that fails yields an unknown delta, i.e. `manual_review`, which leaves the NO leg unhedged INDEFINITELY — strictly worse than a bounded wait followed by a correct unwind. The accepted residual is that in the branch where the YES leg genuinely did not fill, that retried re-read can hold the loss-floored unwind for up to ~62s of backoff on top of the 1s pause, which can turn a `rolled_back` into a `rollback_failed` orphan; the pre-existing read beside it already carried that same exposure. One consequence to respect: the cause-chain walk means anything raised *inside* an `except` block that is handling a `TimeoutError` inherits it as `__context__` and is misclassified as transient, so `_execute_one` takes its post-failure position snapshots **outside** the `except` clause (on the NO leg and the YES leg alike) — otherwise a fatal lookup error stalls an urgent decision for the full ~62s backoff.

**Pair dedup prefers same-title.** When both scanners detect the same ticker pair, `main._dedup_pairs(same_title_pairs, time_series_pairs)` keeps the same-title entry — a same-title pair is a near-arbitrage (both legs pay under co-resolution, assumed at 95%), whereas the time-series copy of the same tickers is a directional bet on the in-between mass sized by an operator estimate (`k`). This matches `strategy.select_portfolio()`'s same_title > time_series tie-breaker. Don't flip the argument order. **Dedup is not a safety net, and DR-02 is why.** It only ever drops a time-series copy when a same-title copy EXISTS, so a rule that removed the same-title copy alone would hand the identical trade straight through as a time-series bet — which is exactly why the one-series rule is applied inside BOTH finders (see the one-series gotcha below) rather than here. Since DR-02/DR-54 dedup never sees the one shape it was load-bearing for: an identical-wording pair on two event tickers of ONE series is now dropped by BOTH finders, so there is no same-title copy for dedup to prefer and no time-series copy for it to drop. **Since DR-67 the finders cannot produce a cross-type collision on the same ticker pair at all**: a same-title pair requires identical wording, a time-series pair requires two DIFFERENT stated deadlines, and identical wording states identical spans, or none — never two different ones. Dedup stays as a guard for a collision that could arise another way, and its argument order still matters.

**Directional, deadline-gap-tiered price filter.** `find_time_series_pairs()` requires `pB - pA >= min_price_diff_for_gap(gap_days)` (the LATER-deadline leg's YES ask priced HIGHER than the earlier's by at least the tier) — not `abs(pB - pA)`. A pricier EARLIER contract is never a candidate: the strategy disputes an outsized in-between mass, and a pair with no in-between mass has nothing to dispute (`time_series_profit_prob` clamps that gap at zero, so such a pair would model as riskless — reintroducing `abs()` would size real trades on it). `gap_days` comes from `scanner.deadline_gap_days(market_a, market_b)`, which is order-independent (`abs(close_b − close_a).days`), so the tier never depends on which market was passed first — except for a same-event ladder (DR-73), whose gap is the one between its two STATED deadlines and is carried on `CandidatePair.stated_gap_days`. Downstream of pair formation there is exactly ONE reader of either, `scanner.pair_gap_days(pair)`, and both sites that re-derive the tier (`_pair_max_sum` and enrichment's `ref_yes is None` fallback) go through it; calling `deadline_gap_days` there would re-tier a ladder whose rungs share a `close_time` from 0.70 down to 0.85. The threshold is tiered by the deadline gap between the two legs: 15% (`MIN_PRICE_DIFF_SHORT_GAP`) when the deadlines are ≤ 15 days apart (`SHORT_DEADLINE_GAP_DAYS`, inclusive), 30% (`MIN_PRICE_DIFF_LONG_GAP`) for 16–30 days; gaps over `MAX_DEADLINE_GAP_DAYS` (30) are never candidates — a wider gap leaves more room for the event to genuinely land between the deadlines, so more of the market-implied in-between mass is real rather than mispricing, and a bigger gap must be demanded before disputing it. **`min_price_diff_for_gap()` also takes a BACKTEST-only `spread_min` keyword** (`config.min_price_diff_for_gap(gap_days, spread_min=None)`), which layers a spread-band floor on top of the tier as `max(tier, spread_min)` — `backtester` is the only module that ever passes one: `_find_entry` uses it to filter, and `_interval_calibration(spread_min=…)` uses it only to label each gap band's tier with the floor its entries cleared. The primary band is resolved by `config.time_series_spread_band()`, from the tuple `backtest.py` builds out of `--spread-min`/`--spread-max`, or from `config.BACKTEST_DEFAULT_SPREAD_BAND` when none is given; each grid band of a band sweep goes through the same function. Every LIVE call — the finder's own floor test here, `_pair_max_sum`, and enrichment's `ref_yes is None` fallback — passes the gap alone and reads no band value at all: pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_live_path_reads_no_band`, a deny-by-default AST walk that refuses a second positional or any keyword argument to this helper outside `config`/`backtester`/`backtest`/`dashboard`. See the "Interval-discount calibration" gotcha below for the full backtest-only band × k × population sweep this floor feeds; it changes no live behavior. The same tier drives the orderbook price-sum ceiling (`1 - threshold`, i.e. 0.85 / 0.70) via `scanner._pair_max_sum()` in both `enrich_with_orderbook_prices()` and `validate_pair_price()`; the ceiling applies to the LEG prices (`pA + nB` for time-series, `nA + pB` for same-title — `scanner.leg_prices(pair)`), not to the YES-ask gap, and it already implies an executable gap of at least the tier. The backtester's `_find_entry` mirrors all of it, including the DR-73 same-event-ladder gap (DR-73c), which it reads through the same `scanner.same_event_ladder` behind the same switch. Never bypass `min_price_diff_for_gap()` with a flat threshold — a flat 15% admits wide-gap pairs whose in-between mass is largely genuine. **The post-enrichment tradeable check carries a direction conjunct, tested against a REFRESHED reference quote (TS-34).** `enrich_with_orderbook_prices` used to rewrite only the two LEG prices and leave the non-leg YES ask — `pB` for time-series, `pA` for same-title — at its scan-time value, so `strategy._kelly_p` subtracted a scan-time `pB` from a depth-weighted `pA`; once the fresh `pA` reached the stale `pB`, `time_series_profit_prob`'s `max(0, pB − pA)` clamp returned `p = 1.0`, the pair modelled as RISKLESS and Kelly sized it at the `BUDGET_FRACTION` cap — the same failure the `abs()` warning above describes, reached from the other end. `scanner._reference_yes_ask(pair, ob_a, ob_b)` now re-derives that quote from the book already in hand and enrichment writes it back beside the leg fills (only when that side had resting bids — otherwise the scan-time value is kept, never overwritten with `None`). The refresh costs ZERO extra API calls: in each pair type `_leg_ask_levels` consumes only one side of each book, and the fetched-but-unused side is exactly the one whose complement is the reference ask (`ob_b["no"]` for time-series, `ob_a["no"]` for same-title). The guard itself is ONE expression for both pair types — `reference > avg_yes` — because `avg_yes` is always the YES leg's fill and the reference always the other market's YES ask, so there is no polarity to get backwards; it drops the pair rather than sizing it. With a refreshed reference the guard is IMPLIED by the ceiling on an UNCROSSED book: every qualifying level satisfies `avg_yes + avg_no <= 1 − tier`, the NO leg always sits on the reference market so `avg_no >= 1 − max(YES bid there)`, hence `avg_yes <= max(YES bid) − tier <= reference − tier`. So it can only fire on a crossed book, or when the reference side was empty and the scan-time quote is still in play — a burst of its WARNINGs on a healthy exchange is a stop-and-report signal, not something to tune away. Keep the strict `>` rather than re-asserting the full tier (a float-boundary pair at exactly the tier must not be rejected), and do NOT add a matching check to `validate_pair_price`: it reads none of `pA/nA/pB/nB`, re-fetches both books and re-applies the same ceiling, which already implies the direction.

**Time-series legs and submission order.** Which side each leg buys is a property of the pair type, read through exactly one helper chain: `config.SAME_TITLE_LEG_SIDES` `("no", "yes")` / `config.TIME_SERIES_LEG_SIDES` `("yes", "no")` — `(side bought on market_a, side bought on market_b)` — exposed as `scanner.leg_sides(pair_type)` (anything but the exact string `"time_series"`, including `None` or a mock's auto-attribute, resolves to same-title, so an unknown pair type can never be traded as the directional bet), `scanner.leg_prices(pair)` (`(nA, pB)` for same-title, `(pA, nB)` for time-series — the two prices everything sizes, fees and submits against; it reads `nB` directly with no default, so any time-series stub must carry a real float `nB`), and `trader._ordered_legs(spec) -> (no_leg, yes_leg)` (frozen `trader._Leg` records: `market`, `side`, `price_dollars`, `count`, `label`). `market_a` is the pricier side by YES ask for same-title and the EARLIER contract for time-series; `nA` is still read for time-series (reporting only — it keeps the prod-log "nA (NO ask)" column meaningful) and `nB` is populated fail-soft (0.0) for same-title (reporting only, never priced). The trader always submits the NO leg first and it is the leg that gets unwound — `market_a` for same-title (today's wire behaviour, byte-identical), `market_b` for time-series — then the YES leg; rollback, the position-delta signs (a NO fill reads as `−count`, a YES fill as `+count`) and the once-per-process V2 NO-mapping backstop all operate on "the NO leg", never on "market_a". Never hardcode `spec.pair.market_a` as the NO leg anywhere — `_ordered_legs` is the only source of truth, and every builder and rollback-price helper (`_build_no_order[_v2](leg)`, `_build_yes_order[_v2](leg)`, `_build_rollback_order_v2(no_leg)`, `_rollback_floor_cents(no_leg)`, `_v2_rollback_price(no_leg)`) takes a `_Leg`, not a spec (`_v2_top_of_grid_price(market)` alone stays market-taking). Label rule for logs and rows: "A"/"B" always mean `market_a`/`market_b` (keep the `(A=%s B=%s)` ticker labels), "NO leg"/"YES leg" always mean submission legs; trader execution and dry-run logs list legs in SUBMISSION order (NO first), while `main`'s pairs table, `_print_portfolio` and the reporter rows list MARKET order (A then B) with the side rendered next to each count (`"5× YES(A) + 5× NO(B)"`). `TradeSpec.x`/`y` are the counts on `market_a`/`market_b` (both `n`), and `TradeSpec.cost_with_fees_a`/`_b` are MARKET_A's/MARKET_B's leg costs whatever their sides — `trader._required_cents_by_shard` pairs them with `market_a`/`market_b.exchange_index`, so that invariant is load-bearing for collateral. The backtester's `_settlement_receipt(n, outcome_a, outcome_b, pair_type)` pays `n` per leg whose market resolved to the side that leg bought (via `leg_sides`; the same-title table is unchanged, the time-series table has exactly three cells and raises `ValueError` on the impossible A=YES/B=NO cell as a defensive guard behind `run_backtest`'s exclusion), and `backtester._leg_prices_for(pair_type, pA, nA, pB, nB)` is the dict-world mirror of `leg_prices`.

**Kelly's denominator is the dollars AT RISK, and the fee is one of them (DR-62).** `b = net_spread / (price_a + price_b + fee_per_pair_approx(price_a, price_b))` — the fee sits in the DENOMINATOR as well as the numerator, because fees are cash out the door at execution and the losing cell loses `total_cost_with_fees` in full, exactly as `TradeSpec.min_payoff`'s docstring and the time-series settlement table already said. With the fee-less `(price_a + price_b)` the gate passed whenever `p·net_spread > q·(price_a + price_b)`, while true positive EV needs `p·net_spread > q·(price_a + price_b + fee)`: **the gate overstated EV by exactly `q·fee` on every pair**, so `f* > 0` did NOT mean positive expected value. Reproduced on a time-series pair the scanner admits (pA 0.16, nB 0.21, pB 0.98): `f*` +0.0113 as coded, −0.0099 fee-fair, true EV −0.0060 against a modelled +0.0069. **Quote the population figure with the grid it came from — it is strongly grid-dependent** and two independent measurements disagreed by 4x on differently-delimited grids: on a whole-cent grid over the short-tier admissible region (`pA`, `pB`, `nB` each 0.01–0.99, `pB − pA >= 0.15`, `pA + nB <= 0.85`, `net_spread > 0`), 2,748 of the 132,179 specs the OLD gate admitted — 2.1% — had non-positive true EV; at the 0.30 tier, 1,992 of 82,715 (2.4%). Replaying the 22 `Trade computed` lines of the 2026-09-16 22:56:53 prod dry run at their logged 2-dp precision: **0 of 22 were EV-negative** (the closest, the FIDE pair, lands at `f*` +0.0011 under the new gate and survives), against an aggregate EV overstatement of $1.56 on a modelled $17.47, spread over the $190.32 of contract cost those 22 computed trades represent (the run then SELECTED 8 of them, $61.68 fee-inclusive — quote whichever denominator you mean, and do not invent a third). That is small next to the operator's own `k` uncertainty (a pooled empirical `k̂` measured against a configured 0.750 — the figure once quoted here was measured pre-DR-67 on strike-blind, wording-unscreened data and is void; see the DR-67 gotcha's dormancy note); the point is that the gate now means what it says. **Same-title is nearly immune** — `q` is the fixed `1 − SAME_TITLE_CO_RESOLVE_PROB` = 0.05, so `q·fee` is small and the fraction barely moves; a verdict flips on roughly 0.3% of admissible whole-cent price points (measured: 12 of 4,465), always accept → reject — while the time-series bet moves far more, because `q = k·(pB − pA)` routinely exceeds 0.5 on exactly the wide-gap pairs the strategy targets. **The gate is strictly TIGHTER**: every size is the same or smaller and a small number of marginal time-series pairs are now correctly rejected, so **any backtest baseline taken before this change is not comparable**. The oversizing bias was `q·fee/net_spread` — that is the ABSOLUTE drop in `f*`, not a percentage of anything, and the two readings must not be conflated: across those 22 trades the absolute drop runs 0.009–0.030, which is a 6%–96% RELATIVE cut with a median near 8% (the near-cap wide-gap pairs move least; marginal pairs move most — the FIDE pair loses 96% of its fraction). **`f* > 0` means positive expected value under the CONTINUOUS fee approximation, which is what the gate prices with — not on the spec's own exact-fee fields.** `fee_per_pair_approx` underestimates the ceiling-rounded `fee_leg_exact` that `min_payoff` and `total_cost_with_fees` are built from, so a spec within roughly `q·(exact − approx fee)/net_spread` of the boundary can still be marginally EV-negative at single-digit `n` (measured at a $10,000 balance: pA 0.12 / pB 0.33 / nB 0.70 accepts at n=30 with `p·min_payoff − q·total_cost_with_fees` = −$0.005). `compute_trade`'s `min_payoff > 0` check bounds that small-`n` rounding residual; it does not eliminate it. Do not restate the guarantee without that qualifier — an over-charitable reading of exactly this shape ("a negative result means negative expected value") is what hid DR-62 in the first place. **Kelly's `b` and the REPORTED `profit_ratio` are deliberately DIFFERENT quantities and must not be collapsed back together**: `TradeSpec.profit_ratio` keeps the fee-less denominator as a return-on-contract-cost figure, because it feeds `monthly_profit_ratio` — `select_portfolio`'s ranking key — and the prod Excel log's Profit Ratio column, and changing the ranked value would change which trades are preferred. The Kelly quantity is named `kelly_b` in `strategy._evaluate_size`, `kelly_b_entry` in `backtester._simulate_at_discount` (whose `profit_ratio_entry` likewise stays fee-less and still drives `entry_monthly_ratio`), and the local `b` in `dashboard._kelly_fraction`. **All three carry the same arithmetic and must move together** — the backtester replays the live admission rule, which is why no backtest could ever have surfaced this, and a dashboard left on the old formula would plot a model the live sizer no longer uses. **The AST parity pins do NOT check this arithmetic** (they only pin WHICH helper each sizer calls), so it is pinned by VALUE in `tests/test_strategy.py::TestKellyRiskIncludesFees`.

**Budget fitting in `compute_trade()`.** After Kelly sizing, `n` is shrunk until the fee-inclusive total cost fits within the Kelly-capped budget. Don't remove the shrink loop — sizing on price alone systematically overshoots `BUDGET_FRACTION`. If the shrink moved `n` and the pair carries a book, the leg prices are then re-derived at the final `n` (a smaller `n` reaches fewer, cheaper levels, so the fee-inclusive cost stays inside the budget and the loop needs no second pass); `p`, `profit_ratio` and `kelly_fraction` are deliberately left at their pre-shrink values, since they are reporting/ranking figures and recomputing them would reopen the non-monotone Kelly question below for no gain.

**Marginal fill pricing — every stage prices the quantity it is actually reasoning about.** Enrichment used to collapse the book to two scalars: a quantity-weighted average over the ENTIRE qualifying book. One pair is capped at `BUDGET_FRACTION` of the balance and Kelly usually sizes well under that, so on a liquid market that average covered depth no single trade could reach — it inflated the fill price, and both the profitability gate in `enrich_with_orderbook_prices` and the Kelly gate in `compute_trade` then killed pairs with a genuine edge in their top few levels. Two halves now fix it, and neither may be removed without the other:
- **`scanner.enrich_with_orderbook_prices(client, pairs, balance_cents)`** bounds its average at `config.max_affordable_pairs(balance_cents, best level's price sum)` — the largest fraction (`BUDGET_FRACTION`) over the cheapest possible prefix sum, hence an upper bound on any `n` the sizer can return, so the price written here is never optimistic relative to the one finally traded. `balance_cents` is REQUIRED, not defaulted: a default would silently restore whole-book pricing on a real-money path with no signal. It also stores the qualifying levels on the pair as `CandidatePair.depth_levels` — `(price_a, price_b, qty)` triples in MARKET order, ascending by combined price, oriented once via `leg_sides` so readers need no pair-type logic — and sets `max_contracts` to that bounded count, i.e. **how many contracts the written prices are valid for**.
- **`strategy.compute_trade`** then solves size and price together over those levels. `_evaluate_size(pair, levels, n, balance_cents)` prices `n` contracts via `scanner.prefix_fill_prices` and runs EVERY gate at that price; `_solve_marginal_size` binary-searches `[1, max_contracts]` for the largest `n` that is *supported* (gates pass at the price of `n`, and Kelly at that price still affords at least `n`). The solved prices are written back onto a `dc_replace` copy of the pair through the same `leg_sides` mapping, so `leg_prices(spec.pair)` — the documented single source of truth for what a leg costs — hands the marginal price to `trader._ordered_legs`, `_v2_limit_price`, `_buy_max_cost_cents`, `_rollback_floor_cents` and the prod trade log with no changes of their own.

Four things are load-bearing. (1) **It is a SEARCH, not a descent from the top,** because the gates bite hardest at the top: a pair can have a comfortably positive Kelly fraction at a realistic size and a NEGATIVE one at full book depth (the "a wide book drives Kelly negative and the pair is skipped" case), so evaluating only the seed and aborting throws away exactly the pairs this mechanism exists to rescue. (2) **Safety rests on verification, not on monotonicity.** The supported set is NOT downward-closed, and this is measured rather than suspected: for a time-series pair a larger `n` raises `pA`, which shrinks `pB - pA` and therefore RAISES `p` while `b` falls, so `f*` does not move in one consistent direction; and once the reachability gate is included the set can have an outright HOLE — on a NO ladder of 0.30@1000 then 0.33@600 it is `[1, 1000]` and `[1501, 1600]` with `[1001, 1500]` unsupported between them. The guarantee is instead that a count is only ever returned after being DIRECTLY verified, so a search that lands low under-sizes rather than mis-prices. One consequence is worth knowing before anyone re-tunes the search: a bisection converges to the top of the LOWEST island and cannot land above a hole, so it UNDER-sizes on such a book rather than mis-pricing — which is also why `compute_trade`'s post-shrink reachability snap has never been observed to fire (118,726 randomized two-level ladders x balances found no case). Keep the snap: that behaviour is an accident of bisection, not a guarantee, and the invariant is what the money depends on. `SIZE_SOLVE_MAX_ITERATIONS` (64) is pure paranoia: a bisection of `[1, max_contracts]` closes in ~log2 passes (~20 for a million-contract book), and on exhaustion the already-verified best is returned with a WARNING. (3) **`depth_levels` is read by TYPE (`strategy._depth_levels`), never truthiness** — a `MagicMock` standing in for a pair answers with a truthy auto-attribute that iterates into nonsense, and a pair whose book we cannot read must be priced on its scalars rather than a guess; same fail-safe rule `leg_sides` applies to an unknown `pair_type`. A pair with no book takes the single-shot path **unchanged**, which is what keeps `tests/test_backtester.py::TestKellyShrinkParity` (which builds a bare pair on purpose) meaningful. (4) **`max_contracts == 0` now means only "not enriched".** Enrichment never writes 0 — a book holding under one contract, or a budget that cannot afford one, drops the pair with its own INFO line instead, closing the sub-one-contract hole that overloaded sentinel used to have.

`main._compute_trade_specs` still keys `{id(candidate_pair): spec}`, but `display_specs` must be built FROM that dict (filtered by which specs were selected), never as `{id(s.pair): s for s in portfolio}` — `compute_trade` returns a re-priced COPY of the pair, so `id(spec.pair)` matches no candidate and every selected row silently renders `—` in the pairs table while the trade itself executes normally. `print_pairs_table` reads its price columns from `spec.pair` when a spec exists, so the prices and the trade on a row describe the same thing. **Measured on live sandbox books (2026-09-13, same command before and after): 12 of 37 pairs priced cheaper, 25 identical, 0 dearer, improvements from 0.03c to 1.99c per pair.**


**The sized count must be depth the FoK can REACH, not depth that merely clears the gap (TS-08).** A V2 taker order is ONE fill-or-kill limit per leg, so it buys only the depth resting at or below its own limit — and that limit is a PER-CONTRACT cap derived from the leg price (`scanner.v2_limit_price`), while the leg price is the quantity-weighted average of a MULTI-LEVEL prefix. An average over a ladder sits BELOW that ladder's top level, so the top of the very prefix being priced can rest above the cap it produces and the order is killed, reported as `status="failed"` / "NO leg FoK not filled" — indistinguishable from a genuine price move. Measured post-#51 on a same-title pair with NO asks 0.32@300 / 0.37@300 against a flat YES 0.30@600: the sizer returned n=600 at a NO leg price of 0.3450, whose cap is 0.3600, which reaches only 300. Put the ladder on the YES leg instead and it is worse than a skipped trade — the NO leg is submitted first and FILLS, then the YES leg is killed and the pair unwinds.

`strategy._reachable_contracts(pair, levels, price_a, price_b)` is the single definition of "how many contract pairs this order can actually buy": it derives each leg's cap through `scanner.v2_effective_cap` — the SAME arithmetic the order body carries, including the NO leg's complement round-trip, which can TIGHTEN the effective NO cap on a sub-cent grid — and sums the depth at or below both. **Never re-derive the cap anywhere else**; the whole finding is that the size and the cap disagreed, and a second copy of the formula guarantees a second disagreement. That is also why the arithmetic LIVES in `scanner.py` (`ceil_to_tick`, `v2_limit_price`, `v2_effective_cap`) and is only re-exported by `trader.py` under its historical private names: `trader` imports both `scanner` and `strategy`, so neither may import `trader`.

It is applied in three places and gated on `ORDER_API_VERSION == "v2"` in all of them — the legacy `buy_max_cost` is a TOTAL-COST cap that CAN sweep a ladder, so narrowing there would shrink legacy sizes for nothing. (1) `strategy._evaluate_size` rejects any `n` whose own price cannot reach `n` contracts, which makes `_solve_marginal_size`'s existing bisection converge on the largest self-consistent size — no separate fixed-point loop, and the empty case needs no `tradeable=False` writeback because an unreachable `n` is simply never selected. (2) `compute_trade`'s post-shrink snap is a BACKSTOP: the fee shrink decrements `n` outside `_evaluate_size`, and reachability is genuinely not downward-closed (on NO 0.30@1000 / 0.33@600 the supported set is [1,1000] and [1501,1600] with a hole between). It has never been observed to fire, because `_solve_marginal_size` bisects and therefore converges to the top of the LOWER island and cannot land above the hole — but that is an accident of the current solver, not a guarantee, so the invariant is enforced rather than assumed. Do not delete it as dead code. (3) `validate_pair_price` counts reachable depth against `spec.x` using the caps derived from `leg_prices(spec.pair)` — the price the trader is ABOUT TO SUBMIT, not a freshly recomputed average — because the question that matters pre-execution is whether the order we are about to send will fill. Its WARNING says "reachable at the FoK limit" on the V2 path and "at gap" on legacy, so the first live reachability rejection is not misdiagnosed as thin depth.

**Enrichment is NOT involved.** `max_contracts` keeps the meaning #51 gave it — the affordability-bounded count the written prices are valid for, and the upper bound of the search — and nothing overwrites it with a reachability count.

**Compare prices with `config.PRICE_EPSILON`, never bare (TS-09).** Every price is a float parsed from a cent-quantized dollar string, so `0.35 - 0.30 == 0.04999999999999999` and a bare `< 0.05` rejects pairs that sit exactly on a documented threshold — measured over live books: the same-title 5c test rejected 50 of 94 qualifying pairs, the 15c tier 21 of 84, the 30c tier 15 of 69. `PRICE_EPSILON` is `1e-6`, at most 1% of the finest tick ($0.0001), so it can only absorb representation noise, never a real one-tick difference. **Do not tune it upward** — it is an ABSOLUTE tolerance, so its weight relative to the compared quantity grows as that quantity shrinks. Seven scanner comparisons carry it: both finders' threshold tests, enrichment's and `validate_pair_price`'s qualifying filters, the `ref_yes is None` fallback's tier test, DR-67's reject-side `pA + nB >= 1.0 - PRICE_EPSILON` guard in `find_time_series_pairs`, and `validate_pair_price`'s reachability-cap check (its two epsilon terms, one per side of the book, are one logical comparison: is this level reachable at the FoK limit). Four of the seven subtract rather than add — both finders' threshold tests, the `ref_yes is None` fallback's tier test, and the pA+nB guard — but they don't all move the same way: the first three subtract on the KEEP side of a reject test (`pB - pA < tier - PRICE_EPSILON`, `pA - pB < SAME_TITLE_MIN_PRICE_DIFF - PRICE_EPSILON`, `(pB - avg_yes) >= tier - PRICE_EPSILON`), which LOOSENS acceptance — a boundary pair is kept rather than dropped, which is the whole point of TS-09. The pA+nB guard subtracts from the reject side's own bound (`pA + nB >= 1.0 - PRICE_EPSILON`), which TIGHTENS it — a sum that is really 1.0 but evaluates a shade under it must still be refused (see the pA+nB skip note above). Do not "fix" any of the three keep-side subtractions to an add: that would re-narrow the keep bound and reintroduce the measured TS-09 rejections above. `backtester._find_entry` mirrors it at three: `gap < threshold` and `price_a + price_b > 1 - threshold` directly, and the backtest-only spread-band ceiling through `config.time_series_spread_too_wide` — the one place that ceiling's epsilon lives, on the keep side like the floor's (`0.90 - 0.30 == 0.6000000000000001` is kept at a 0.60 ceiling). **The AST parity pins do NOT check this constant**, so a missed mirror is silent divergence between live and backtest.
**Use `pathlib.Path` for all file paths.** Never `os.path` or string concatenation.

**Monetary values:** Three units, not two. Contract prices are **dollars** (float, or `Decimal` on the V2 order-price path, range 0–1). Balances and order costs are integer **cents** — except that inside `auth._balance_cents_by_shard()`'s per-shard `balance_breakdown`, the API's own `"balance"` field is a fixed-point **dollar string** (converted with `Decimal`, floored not rounded — see the shard-balance gotcha); only the top-level legacy `"balance"` field and the sandbox fallback are plain integer cents. The collateral-transfer endpoint's `amount` is **centicents** (1/100 of a cent), converted only by `trader._cents_to_centicents()` — see the collateral-transfer gotcha. Don't mix units, and don't assume every "balance" field on the wire is the same shape.

**Process exit-code contract (BS-14).** `main()`'s process exit code is the only signal `scheduler.run_job()` — a separate subprocess — has for what happened in a run, beyond generic pass/fail. `_run_prod`/`_run_dev` return one of four `config.py` codes instead of a bare `None`: `EXIT_OK` (0, the normal case), `EXIT_SKIPPED_LOW_BALANCE` (10, the balance-below-minimum short-circuit — this used to `return` and exit 0 just like a clean run, silently burying the reason nothing happened), `EXIT_TRADES_NEED_ATTENTION` (20, any `execute_trades()` result with status `"rollback_failed"` or `"manual_review"`), and `EXIT_NO_TRADEABLE_SHARDS` (30 — NOTHING was scanned: every advertised shard reported `trading_active=false` so ingest dropped every market (TS-01), or ingest produced zero markets for a cause `/exchange/status` could not name (VI-02); both are decided by the single helper `main._blind_run_reason`, which both run modes call). `main()` ends with `sys.exit(code)`; an unhandled exception is not covered here and still propagates to the interpreter's normal exit 1. `scheduler.run_job()` maps all four to a distinct log level and message so a skipped or attention-needed run is visible in the scheduler's own log, not just buried in `kalshi_arb.log`. Don't collapse these back into a bare `return`/exit 0 — that's exactly the bug this fixed. **30 is deliberately not 0.** An exchange-wide halt (observed live 2026-09-03 00:29 PDT) makes `inactive_shard_indexes` return every shard, `fetch_open_events_with_markets` drop every market, and both loops of `check_shard_coverage` run empty — so it returned `([], [])`, which `_log_shard_coverage` read as success and reported as `Full shard coverage: shards [...] scanned`, indistinguishable from a healthy full ingest. Both run modes therefore short-circuit with 30 on `main._blind_run_reason(markets, shard_statuses, inactive_shards)` (placed after the markets fetch, which is where `inactive_shards` and the ingest census exist, and, in prod, after the `MIN_BALANCE_CENTS` gate, which still runs first, and BEFORE the held-ticker and horizon filters, which legitimately empty the list on a healthy exchange). That helper keeps the halt test — `shard_statuses and inactive_shards == set(shard_statuses)` — as its OWN disjunct and adds a second one, `not markets`, rather than replacing it with the census: the two are NOT equivalent, because a halt that still leaves one stray market ingested (one tagged with a shard `/exchange/status` does not advertise — `scanner._shard_index` only defaults a MISSING index to `DEFAULT_EXCHANGE_INDEX`) would pass a bare census test while every advertised book is shut, carrying the run into pair discovery, sizing and, on a live Monday run, order submission during an exchange-wide halt. The `not markets` disjunct exists because `fetch_shard_statuses` is fail-soft and returns `None` on ANY internal failure, which makes the halt test unevaluable exactly when something has gone wrong: a run that ingested zero markets then exited 0 claiming a clean scan (VI-02). A blind DEV run short-circuits before `write_dev_simulation` on both causes — the empty simulation file records a run that SCANNED and found no pairs, never one that never looked. Independently of the gate, `_log_shard_coverage` claims coverage only over shards that were actually scannable (`trading_active is not False`, so a `None` flag still counts as scanned) — the "Full shard coverage" line names those shards, not every advertised one. On the scheduler side, 30 is the one code that does NOT satisfy the weekly slot. Because 30 now covers both causes and the exit code alone cannot separate them, `scheduler.py`'s retry WARNING and give-up ERROR name both possibilities and point the operator at `kalshi_arb.log`, where `_blind_run_reason`'s line says which one fired — they must never assert the halt as the cause (`tests/test_scheduler.py::TestBlindRunRetry` pins that wording). `run_job(retries=0)` registers a one-shot retry on the `schedule` library's global scheduler (`_blind_retry`, which returns `schedule.CancelJob` so it can never become a recurring job — and, since DR-59, is registered through `scheduler._guarded_job` with `on_error=schedule.CancelJob`, because a retry that RAISES returns nothing and would otherwise stay registered, re-fire on every poll tick and never advance the cap) every `SCHEDULER_BLIND_RETRY_SECONDS` (3600), at most `SCHEDULER_BLIND_MAX_RETRIES` (4) times, and `_maybe_catch_up` re-runs a slot whose recorded attempt exited 30 — its old test was purely temporal and never read the exit code. The cap is enforced by the `retries` argument each attempt carries, never by the caller, because a retry that exits 30 again schedules its own successor; it is persisted as `scheduler_state.json`'s optional `"retries"` key, which pre-existing state files lack and every reader treats as 0 (`_load_state` now also validates the optional `retries`/`exit_code` keys, degrading a bad value IN PLACE rather than discarding the whole state the way an unparseable `last_slot` does: a PRESENT but non-int `retries` — a hand-edited string, `null` — degrades to 0 with a WARNING instead of reaching `_maybe_catch_up`'s `retries < SCHEDULER_BLIND_MAX_RETRIES` comparison unvalidated and raising `TypeError` out of `main()` before the weekly job was ever registered (DR-24); a non-int `exit_code` is typed to `None` the same way, which is hygiene rather than a crash fix — its `==` comparison never raised, it only ever compared unequal and left the slot unretried. `main()` additionally runs the whole startup catch-up check through `_startup_catch_up()`, a `try`/`except Exception: logging.exception(...)` guard around `_maybe_catch_up()`, as a backstop for whatever else that check might still raise). A run that merely FAILED still does not reopen its slot — that is BS-17's deliberate behaviour.

## Known Gotchas

**Every scheduled job is registered through `scheduler._guarded_job` (DR-59, fixed 2026-09).** `schedule.Job.run()` assigns `self.last_run` and calls `self._schedule_next_run()` only AFTER `job_func()` **RETURNS** (verified against the installed library's source), so an exception that ESCAPES a job leaves `next_run` in the past. `scheduler.main()`'s poll loop catches it (`Scheduler tick raised — daemon continues`) and keeps the daemon alive, but the job is still overdue — so `run_pending()` re-enters the SAME job on the very next 60-second poll tick, turning a weekly production trading run into a once-a-minute one for as long as the fault persists. `run_job` really can raise: the slot-CLAIM `_save_state()` sits OUTSIDE its `try`, the finalizing `_save_state()` sits after that `try` has closed, its two `except` clauses (`TimeoutExpired`, `OSError`) are scoped to the `subprocess.run` call alone, and `subprocess.run(..., capture_output=True, text=True)` decodes the child's streams strictly, so one non-UTF-8 byte raises `UnicodeDecodeError` (a `ValueError`, matching neither clause). The same mechanism defeats the blind-retry one-shot contract: `_blind_retry` signals "run me once" by RETURNING `schedule.CancelJob` — `schedule._run_job` cancels on the value RETURNED to it, never on the identity of the registered function — so a retry that raises returns nothing, is never deregistered, AND never advances the `SCHEDULER_BLIND_MAX_RETRIES` cap, which rides solely on the `retries` argument each attempt hands its successor. **The guard sits at the REGISTRATION boundary, not inside any one helper**, which is what makes it cover every escape path a job has rather than the ones an individual helper happens to know about; `.do(_guarded_job, job, *args, **kwargs)` forwards everything after the first argument through `functools.partial`, so the wrapper is transparent on the healthy path. Two registration sites, and both must stay wired: `main()`'s `schedule.every().monday.at("09:00").do(_guarded_job, run_job)` (no `on_error` — a RECURRING job must be rescheduled by a failure, never cancelled by one) and `run_job`'s blind retry `.do(_guarded_job, _blind_retry, retries + 1, on_error=schedule.CancelJob)` (a ONE-SHOT must deregister itself even when it raises). `_save_state`, `_load_state`, `_maybe_catch_up`, `_startup_catch_up`, `run_job`'s body, the exit-code mapping, the retry cap and BS-17 slot accounting are all deliberately unchanged — in particular `_save_state()` still RAISES, so a failed slot CLAIM still prevents the subprocess spawn (a real-money run with no recorded slot would break BS-17's invariant that a claimed slot always has a record). `KeyboardInterrupt`/`SystemExit` are not `Exception` subclasses and are deliberately not caught, so Ctrl-C still stops the daemon. **The weekly wiring is pinned by AST, and must stay pinned:** `main()` spawns a real prod run and is never invoked by the suite, so no runtime test can reach that line — without `tests/test_scheduler.py::TestGuardedJobRegistration::test_ast_weekly_job_is_registered_through_the_guard` (and its `on_error` sibling for the retry), an edit reverting to `.do(run_job)` restores DR-59 with a green suite. On a healthy host nothing changes; the only behaviour change is that a raising job abandons its slot and waits for the next scheduled fire instead of re-firing every minute. **That trade-off is deliberate and is the accepted cost:** a TRANSIENT fault at 09:00 that the old code would have re-entered 60 seconds later now costs the whole Monday slot, and a raising blind retry ENDS the retry chain for that slot (`on_error=CancelJob` deregisters it) — either is recoverable only by `_maybe_catch_up` on a daemon RESTART, never while the daemon keeps polling. It is still strictly better than the alternative it replaces, which is a real production trading run every 60 seconds for the duration of the fault.

**Strategy change (2026-09) — the time-series bet was inverted.** Until 2026-09 `find_time_series_pairs` fired when the EARLIER-closing contract was priced higher than the later one (`pA - pB >= tier`) and bought NO on the earlier (`market_a`) and YES on the later (`market_b`), on the reasoning that a cumulative-deadline pair must satisfy P(A) ≤ P(B) so a pricier earlier contract is a mispricing with three profitable cells. The bot now trades the opposite anomaly: the LATER contract priced at least the tier ABOVE the earlier (`pB − pA >= min_price_diff_for_gap(gap_days)`), buying YES on the earlier (`pA`) and NO on the later (`nB`), on the reasoning that an outsized `pB − pA` is the market overstating the probability that the event first happens between the two deadlines. `market_a` is still the earlier contract; only the sides and the direction of the filter flipped. Three consequences are real-money facts. (1) **It is a directional bet, not an arbitrage.** Three settlement cells exist — event by A (A=YES ⇒ B=YES, the YES on A pays), never by B (A=NO, B=NO, the NO on B pays), in between (A=NO, B=YES, both worthless — the whole stake is lost). At market prices its expected value is zero minus fees; it only profits if the market systematically overstates the in-between mass. "Risk-free"/"guaranteed" wording is gone for time-series everywhere; same-title keeps its co-resolution framing and its wire bytes unchanged. (2) **The Kelly model is `p = 1 − k·(pB − pA)`** (`config.time_series_profit_prob(pA, pB, k=None)`, the single definition that `strategy._kelly_p`, `backtester._simulate_at_discount` and `dashboard._kelly_fraction(pA, nA, pB, nB, pair_type, k=None)` all call — pinned by value and by a two-link AST chain, see the calibration note below), with `k = TIME_SERIES_INTERVAL_PROB_DISCOUNT = 0.75`: the operator believes 75% of the market-implied in-between mass ("prices converge by 25%"). This is an operator-tunable ESTIMATE. With `k = 1` (take the market at face value) or an independence model of the new loss cell, Kelly is ≤ 0 for every time-series pair and nothing ever trades (illustrative fixture 0.30 → 0.60, NO ask 0.40: `k=1` ⇒ p 0.70, f* −0.12; independence ⇒ p 0.58, f* −0.56; `k=0.75` ⇒ p 0.775, f* +0.16). Leaving the LITERAL old expression `1 − pA·(1−pB)` in place would NOT have disabled trading — it would have modelled the impossible A=YES/B=NO cell and sized real trades on it, which is why the formula is pinned rather than merely retuned. (3) **Kelly, not the 20% cap, now sizes typical pairs.** With `k=0.75`, reading off an earlier contract at `pA` = 0.30 on a tight book (`nB = 1 − pB`), the uncapped fraction is ≈ 0.05 at the minimum short-tier gap and ≈ 0.16 at a 0.30 gap, so `BUDGET_FRACTION` (0.20) only binds for gaps of roughly 0.45 or more; **name the reference `pA` whenever quoting these** — the fraction is strongly `pA`-dependent (at the same 0.15 tier it is ≈ 0.14 at `pA` 0.10, ≈ 0.08 at 0.20, ≈ 0.03 at 0.40); a wide book (large `pA + nB` for the same YES-ask gap) drives Kelly negative and the pair is skipped (the same fixture with the later NO ask at 0.50 instead of 0.40 returns `None`). And because a pricier later contract is NORMAL term structure, far more time-series groups qualify than before (one best pair per normalized title+outcome key still applies — `scanner.time_series_group_key`, see the cross-strike gotcha — keyed on the largest `pB − pA`, which no longer bounds a whole daily family to one pair). **What to look for in outputs:** the prod Excel log keeps 18 columns but its x/y headers are now "x — A leg"/"y — B leg", its "Total Cost ($)" column is "Total Cost incl. fees ($)" and its "Min Profit ($)" column is "Profit if won ($)" (headers on new workbooks only — an existing shared `trade_log.xlsx` keeps its old header row, since `_append_locked` writes headers only when creating the file; the VALUES change in every workbook) and every row's Notes cell is prefixed `[<pair_type>: <SIDE_A> A / <SIDE_B> B[ nB=0.xxxx] fees=$x.xx] ` — the `fees=` suffix is what makes a row readable under an old header, since the cost beside it is now fee-inclusive (TS-12); for time-series rows the retained "nA (NO ask)" column is A's best NO ask (reporting only, not a traded price) and the traded `nB` lives in Notes. The dev-simulation candidates sheet gains an "nB (NO ask)" column (13 headers) and its "Price Diff" is `pB − pA` for time-series, `pA − pB` for same-title; `main.print_pairs_table` gains an "nB (NO)" column and its "Min Profit" header is now "Profit (win)" (and, from DR-17, "Outcome A"/"Outcome B" columns carrying each leg's subtitle). `BacktestTrade` carries `entry_nB` (from the candle's `no_ask_close` — old caches need no refresh and there is no `SETTLED_PREFILTER_CACHE_TAG` bump) and `deadline_gap_days` (the calendar-day gap between the two legs' DEADLINES that `_find_entry` selected the price tier and applied the `MAX_DEADLINE_GAP_DAYS` cutoff on, carried out rather than recomputed — the legs' `close_time` gap for a cross-event pair, the two STATED deadlines' gap for a same-event ladder (DR-73), which for a ladder routinely differ (measured on a 1,506-market archive corpus: 101 of 408 ladder pairs have a ZERO-day close gap, 37 closing at the identical instant, while every stated gap is in [1, 30]); it is also what `_interval_calibration` bands `k̂` on, through `_TimeSeriesOutcome.gap_days`; `None` for same_title, which has no deadline-gap concept, and for any trade built without it, e.g. test fixtures — reporting only, nothing sizes, prices or settles on it), its `profit` is negative only in the in-between cell, and its `slippage` for time-series is zero in both win cells and negative in the loss cell (there is no positive-slippage cell). `run_backtest` SKIPS (never trades or pays) any time-series candidate that settled A=YES/B=NO and logs ONE summary WARNING with the count (silent at zero): most likely a wording false negative — a snapshot family, or a recurring window worded "before <date>", read as cumulative — though DR-72 widened the WARNING to also name legs ordered on an early REALIZED close (cross-event pairs only — a same-event ladder is ordered on its stated deadlines), and strike-blind grouping on a cache without subtitles, rather than pointing at the wording heuristic alone. **Since DR-67 that is no longer the only signal** — both finders screen the legs' wording first (`scanner.cumulative_deadline_pair`), so the counter is defence in depth behind a heuristic and a non-zero count means one of those causes fired, most likely the wording one. Expect it at or near zero on a post-DR-67 run. That signal is only trustworthy because `_find_entry` orders a time-series pair's legs on the close **DATETIMES**, like the live finder's `scanner.find_time_series_pairs` sorting its group members on `m.close_time`: two contracts closing on the same UTC date at different times of day are a valid zero-day-gap pair, and deciding the swap on the parsed DATES made them a tie, leaving "market A" as whichever the group list held first — so the pair was either dropped (the direction test goes negative) or replayed with its legs inverted, whose genuine in-between settlement then read as the impossible A=YES/B=NO cell and was booked as a *false* premise violation, corrupting the interval-discount calibration's denominator too (TS-06, fixed 2026-09). **That parity is on the DATETIME-vs-DATE fix only, not on what `close_time` means.** The two paths read the same field name on the close datetimes, but not the same MOMENT: live reads the SCHEDULED close of a still-open market, while the backtest reads the REALIZED close Kalshi recorded for a settled one, which for an event that resolved early (a sports market decided before its listed deadline) can sit before the original schedule. It used to send each ticker's whole window as ONE request, and `_fetch_candles_parallel` opened every window at the run's global `--start-date`, so on a window longer than ~207 days every ticker closing later than that got no candles and could never enter — visible only in `_fetch_candles_parallel`'s `N of M tickers returned no candles` line — and the explorer, like every other strategy figure, described a truncated population (the default `--start-date 2024-01-01` is far past it). `fetch_candlesticks` now pages any window longer than `config.CANDLESTICK_MAX_CANDLES_PER_REQUEST − 1` candle periods (`historical._candle_request_windows`: requests of at most that many periods, overlapping by one period so the merged result equals one uncapped request whichever way the endpoint treats a window's ends) and merges them ascending by timestamp with the overlap's repeats dropped (`_merge_candle_pages`). A window that fits is still one request with the same parameters. `_fetch_candles_parallel` also opens each ticker's request at the later of `--start-date` and that market's own `open_time`, floored to the hour (`backtester._candle_window_open`; a missing or unreadable `open_time` — every cache record written before `_market_to_dict` carried it — keeps `--start-date`), so a market that opened after the window began costs one request for its own life instead of several for months of candles it never had. That is result-neutral: across the 573 cached series of the DR-73 calibration corpus whose request opened before the market did, no candle ends at or before the start of the hour the market opened in; the open is floored because 58 of 1,093 series requested from an off-the-hour `open_time` start later than the opening hour, and a request starting on the boundary gets that hour's candle however the endpoint reads a mid-period `start_ts`. PB7's `dashboard._candle_cap_notice` (a red header line, repeated as the explorer banner's first line) described exactly this defect and was removed with it. **One caveat the fix does not reach:** the DR-73 calibration corpus the explorer is read against (`.git/dr73-calib/candles_ts_all2.json.gz`) was fetched outside the production path, one request per leg from the leg's own `open_time`, so it still lacks candles for the 115 of its 3,704 legs whose own open-to-close-plus-a-day span exceeds the cap (up to 15,527 hours); refetching them through the paged `fetch_candlesticks` would fill it. **Picking a scenario here changes nothing the live bot does:** live trading has no band setting at all, and `k` and the ladder switch stay whatever `config.py` says. Applying a chosen band and `k` live is a separate change that must add live enforcement first.

**The equity curve is a PORTFOLIO VALUE, not a cash balance — open positions are carried at COST (DR-61, fixed 2026-09-16).** `backtester._build_equity_curve` used to accumulate cash alone (`-= total_cost + fees` on the entry date, `+= actual_payoff` on the exit date), so an open position was carried at **ZERO** for its whole holding period and the curve dived on entry and recovered at settlement *whether the trade won or lost*. It now tracks cash PLUS the cost basis of everything still open, which leaves a trade exactly two moves: **`-fees` on the entry date** (cash falls by `total_cost + fees`, the contracts enter at `total_cost`) and **`+(actual_payoff − total_cost)` on the exit date** (the position is written off at cost, the gross receipt credited). The two sum to the trade's own `profit`, so **`total_return`, the final balance and the trade list are identical to within float noise — only the PATH between entry and settlement moves.** ("Identical to the last cent", not literally byte-identical: the position accumulator adds `+cost` on entry days and `−cost` on exit days, so when entries and exits interleave the pair need not cancel to exactly `0.0` in IEEE754. Fuzzed worst case ~4e-12 on a $10,000 balance — under a ULP of the rendered `%.2f`, which is why the parity test uses `pytest.approx(abs=1e-9)` rather than `==`.) That endpoint invariance has one unstated precondition: every trade must settle inside `[start_date, today]`. It does in production — `exit_date` comes from the `settlement_ts` of two already-settled markets — but a trade exiting past the curve's last row would stay carried at cost forever, ending at `initial − fees` where the cash-only curve ended at `initial − cost − fees`. Fees are deliberately NOT capitalised into the carrying value: they buy nothing that can be sold on, so they land on the day they are charged. **Why it mattered:** that series is the sole input to the "Max Drawdown" KPI, the "Drawdown (%)" chart, `_sharpe`/`_sortino` (via the derived `daily_return` column), the per-`k` sweep table's drawdown and Sharpe columns, and the benchmark row that sits in the SAME COLUMN as `^GSPC`'s genuine mark-to-market drawdown — so every one of them was reporting capital DEPLOYMENT as loss. The real 2026-05-01 run is the proof: its **`k = 1.00` point had 3 trades, all 3 profitable and a +4.8% return, and rendered "Max Drawdown −60.0%"**, while its `k = 0.40` point rendered **−100.0% (total ruin) against a final balance of $4,655.87**; the decoded `k = 1.00` trace was flat at $10,000 through 2026-05-24, ONE declining step to $4,001.03 on 2026-05-25 (a pure deployment day), then monotonically non-decreasing. The primary `k = 0.750` card meanwhile showed Sharpe 0.73 and Sortino 2.09 beside a Total Return of −27.0% — the same inversion from the other end. **The accepted cost** is that carrying at cost is not a true daily mark-to-market: an unrealized swing inside the holding period is invisible, so the reported drawdown is REALIZED drawdown and a lower bound on the intraperiod one. Mark-to-market was considered and rejected as materially larger, but **not because the data is missing**: `backtester._fetch_candles_parallel` already fetches each leg's WHOLE hourly series (from the later of `start_date` midnight UTC and the market's own `open_time`, floored to the hour, through one day past its close) and disk-caches it per ticker (a window longer than Kalshi's 5,000-candle-per-request cap is paged — see the scenario-explorer paragraph above). What mark-to-market actually costs is PLUMBING plus a policy — `_find_entry` returns entry-checkpoint prices only, so `candles_by_ticker` lives on the `_Candidates` object only until the last entry pass (it dies with `_prepare_entries` on `run_backtest`'s path, and `_sweep_from_candidates` deletes it before its first simulation), and a per-day series would have to be threaded through `raw_entries` and `_simulate_at_discount` into `_build_equity_curve`, with a rule for the days a leg has no candle. Price it as a data-threading change, never as a new multi-hour fetch. Cost-basis carry is the minimal change that makes each metric mean what its label says; if it is ever revisited, the direction is a strict refinement of this, not a return to cash-only. **DR-03 is untouched and is the constraint any future change here must keep**: the curve still opens one day BEFORE `start_date` at the untouched initial balance, and that row is still what keeps the `cummax` peak at the initial balance rather than at the already-charged day-0 value (see the DR-03 sentences above for the measured before/after). **Every backtest drawdown, Sharpe and Sortino figure ever recorded before this change measured peak deployment and does not reproduce** — including the DR-03/DR-56 fixture log in the paragraph above, which is now marked historical. `_simulate_at_discount`'s own `cash`/`checkpoint_cash` Pass-2 accounting is SIZING and is deliberately untouched: the equity curve is reporting-only, and the two must not be unified.

**Live fetching bypasses the SDK's response models (2026-07 API drift).** The Kalshi API (a) rejects events page sizes above 200 with HTTP 400 (`MARKET_PAGE_SIZE` is now 200 and must stay ≤ 200), and (b) no longer populates the legacy integer fields the pinned SDK's response models type as required: markets lost `yes_ask`/`no_bid`/… (prices now only in `*_dollars` strings) and positions lost `position`/`market_exposure`/… (count now in the `position_fp` string) — so modeled calls that deserialize nested markets, any non-empty positions page, or any order (`Order` lost `yes_price`/`fill_count`/…) raise pydantic `ValidationError`. Therefore `scanner.fetch_open_events_with_markets()`, `scanner.get_held_tickers()`, `trader._position_count()`, and `trader._submit_order()` call the SDK's `*_without_preload_content` raw-response variants and parse the JSON themselves (markets into `scanner.ApiMarket` dataclasses). Order submission is the highest-stakes case: the modeled `create_order` raises AFTER the order is placed, which would shove every real fill into the ambiguous-exception path and unwind successfully filled legs. Two rules: (1) the raw variants do NOT raise on 4xx/5xx, so every raw call must go through `_http.fetch_json_page()`, which re-raises non-2xx as `ApiException` to keep prior error semantics (`api_call_with_retry`'s 429/5xx backoff for market data; order submission stays retry-free per the rule above); (2) don't "simplify" back to the modeled calls (`client.get_events(...)`, `client.get_positions(...)`, `client.create_order(...)`) — they crash on live responses. **Event listings drifted too (2026-08).** They were previously safe through the modeled calls (no nested markets), but the live API now sends `category: null` on some events while the pinned SDK types `EventData.category` as a required `str` — so `get_events` and `get_multivariate_events` raise pydantic `ValidationError` mid-listing. Verified 2026-08-03: this killed a backtest *after* a successful 28-minute fetch. `historical._load_or_build_event_titles` therefore uses `get_events_without_preload_content` / `get_multivariate_events_without_preload_content` through `fetch_json_page` for BOTH bulk listings; the modeled `get_event` (singular) was already unusable — it embeds nested `Market` models — so the per-ticker fallback continues to use a raw GET. There is now no modeled SDK call left in the codebase at all — `verify_auth` (`auth.py`) was the last one, migrated to `get_balance_without_preload_content` for the same reason (BS-10); don't reintroduce a modeled call anywhere. Related drift: the MVE events listing is effectively unbounded (hundreds of thousands of auto-generated collection events) and on prod currently returns zero nested markets regardless of `with_nested_markets` — the MVE pull in `fetch_open_events_with_markets()` bails out after `MVE_MAX_EMPTY_PAGES` (25) consecutive pages that contribute no ACTIVE nested market, and the backtester's title lookup caps its MVE scan at `MVE_TITLE_LOOKUP_MAX_PAGES` (500); without those caps the scan hangs for hours (this is likely why the 2026-07-06 prod run logged nothing after auth). Don't remove the bail-outs. **Every cursor loop in `scanner.py` is bounded twice over (TS-05)** — the two in `fetch_open_events_with_markets()` and the one in `get_held_tickers()`: each keeps a `seen_cursors` set, so a keyset that CYCLES (`A, B, A, B, …`) and therefore never repeats *consecutively* is caught as well as the plain stuck cursor the old `new_cursor == cursor` guard proved; and each stops unconditionally at `SCANNER_MAX_PAGES` (config.py, 5000 — ~1M markets at `MARKET_PAGE_SIZE`, against a ~135k-market prod ingest), which bounds the walk against any cursor pathology whether or not anyone enumerated it. These were the last unbounded scans in the ingest path, and `get_held_tickers` runs before any pairing, so an unbounded walk there means the run never scans at all. The MVE loop's `MVE_MAX_EMPTY_PAGES` productivity bail-out is independent of both and keeps its own counter and reset semantics — don't fold them together. The warning text still contains `cursor did not advance` (now "(repeated)"), which tests pin. **The counter must track productive (active-market) pages, not raw nested-market presence (fixed 2026-08, found live in sandbox).** The bail-out originally reset on the raw `len(markets)` per page regardless of status; on sandbox, the MVE listing serves thousands of pages whose nested markets exist but are all non-active (closed/settled/determined) — those pages kept resetting the counter forever, so the bail-out never fired and a sandbox validation run paged 4,600+ times flat at the same appended-market count. On prod this bug was invisible because prod happens to return zero nested markets per page either way. The fix counts only markets actually appended (status == "active") toward the reset decision. Same drift hits the orderbook: `scanner._fetch_orderbook()` also uses a raw GET, and the book arrives in one of two **matched** key generations tracked by `scanner._ORDERBOOK_SIDE_KEYS`, where each container key owns an ordered tuple of candidate `(yes_key, no_key, unit)` side-key sets and is NEVER read with another container's sets:
- `orderbook_fp` ⇒ `yes_dollars`/`no_dollars` only, **dollar strings**. This is what production actually receives today; its handling must stay behaviour-identical (a prod dry-run should log zero mismatch warnings).
- `orderbook` ⇒ `yes_dollars`/`no_dollars` (**dollars**) if present, else `true`/`false` (**integer cents**). Both shapes come straight from the pinned SDK's `models/orderbook.py`: the `Orderbook` model *requires* `yes_dollars`/`no_dollars` and aliases its legacy int arrays as `"true"`/`"false"` — it never had `yes`/`no`, which the table wrongly assumed until this was corrected (BS-03).

`_fetch_orderbook` picks the container by key *presence* (not truthiness), then takes the first candidate set of that container whose **both** keys exist — a set is only ever taken whole, so a unit can never be inferred from the wrong keys. Cents levels are validated (whole cent in `[1, 99]`) and converted `/100.0` to dollars **before** `_bids_to_ask_levels`, which stays dollars-only by contract; an invalid level is dropped with a WARNING naming the ticker and the raw value, because cents fed straight through that parser yield `1 - 45 = -44` and get silently discarded, turning a full book into a *silent* empty book (BS-12). Degenerate containers: present but `None` or `{}` ⇒ an **empty book** `{"yes": [], "no": []}` (a market with no resting bids, not drift — no warning, BS-28); a side key present but empty/`null` ⇒ that side has no resting bids, also fine; a **non-empty** container matching none of its own candidate sets (or a non-dict value) is logged as a **potential key mismatch** and returns `None` (fail-closed) rather than cross-reading another generation's keys. Don't collapse this back to a flat `data.get("orderbook_fp") or data.get("orderbook")` with an independent `yes_dollars or true` side lookup: that decoupling is exactly the cross-generation read this guards against. `TestFetchOrderbookKeyMapping` in `tests/test_scanner.py` pins every generation, unit, and degenerate container above against the SDK-documented shapes. **Context (from `main`, 2026-03-12):** Kalshi removed every legacy integer price field from its REST/WS payloads that day, and production serves `orderbook_fp` only — so the `orderbook` container and its cents arrays are not expected on the wire today. They are kept as SDK-shape-derived DEFENSE, not as a live code path (the pinned SDK still models exactly those shapes, and the alternative to parsing them correctly is not "no code" but a silently empty book, BS-12). Nothing about that weakens the fail-closed rule: an unknown container, or a known container matching none of its own candidate sets, still returns `None` with a mismatch warning.

**Exchange sharding — ingest tags every shard; only trading-inactive shards are dropped.** Kalshi has partitioned the exchange into parallel shards identified by an integer `exchange_index` on market payloads, in the account balance breakdown, and in `GET /exchange/status`'s `exchange_index_statuses` array. Each shard has its own markets, order books, and slice of account funds. **Market data is cross-shard** — the events/markets/orderbook endpoints return every shard's markets, tagged — so ingest LABELS and keeps them: `scanner._shard_index()` reads the field fail-safe (missing/null/unparseable => `config.DEFAULT_EXCHANGE_INDEX`, since absence is the pre-sharding/sandbox shape and must never empty the market list) and `scanner._market_from_dict()` stores it on `ApiMarket.exchange_index`. The sole ingest-time shard exclusion is `inactive_shards`, passed into `scanner.fetch_open_events_with_markets(client, inactive_shards=...)` by both `main._run_dev` and `main._run_prod` from `scanner.fetch_shard_statuses()` — and forwarded by `find_time_series_pairs`' own no-`markets` fallback fetch, which used to pass none (TS-27; that fallback is DEAD CODE today, unreachable in production and in the suite, so this closes a trap for a future caller rather than a live hole): nothing on a shard the exchange itself reports `trading_active=false` for can be traded, nor should it linger as a stale candidate. **`trading_active` is TRI-STATE on the parsed statuses — `True`, `False`, or `None` when the payload carried no such key — and only a `false` drops a shard at ingest (TS-04).** An absent or renamed field is "unknown", never "halted": coercing it to `False` (the old `bool(entry.get(...))`) marked every shard inactive, dropped every market, and still exited 0 claiming full coverage, so a single renamed field emptied the whole ingest — the same drift class that already hit markets, positions, orders, events and balance, and the same fail-safe policy `_shard_index` applies to a missing `exchange_index`. `fetch_shard_statuses` logs one summary WARNING naming how many shards carried no flag (silent at zero), and every consumer — `inactive_shard_indexes`, `check_shard_coverage`, `main._log_shard_coverage` — tests `is False` / `is not False`, never truthiness; one leftover truthiness test silently reintroduces the bug. `trader._transfers_active` reads a different key (`intra_exchange_transfers_active`) and keeps its `bool()` coercion, because a missing transfers flag correctly means "don't move money". **Absence is not the only drift shape: a RE-TYPED flag must keep its meaning too (TS-04b).** A JSON boolean that arrives as its string form is truthy in Python — `bool("false") is True` — so the old bare `bool()` coercion read a HALTED shard as open and kept scanning and trading it. Every flag in the parse therefore goes through `scanner._status_flag(raw)`, which resolves, in order: a real bool; the numeric spellings `0`/`1`; then, for strings, the closed token sets `config.EXCHANGE_FLAG_NULL_TOKENS` / `EXCHANGE_FLAG_FALSE_TOKENS` / `EXCHANGE_FLAG_TRUE_TOKENS` (stripped, lower-cased), where a stringified null (`"null"`, `"none"`, `"nil"`, `"undefined"`) reads as unknown rather than as open. An UNRECOGNISED value resolves by truthiness, in the one direction that cannot break a reading that is correct today: a falsy one (`0.0`, `""`, `[]`, `{}`) keeps the `False` that `bool()` already gave it — un-dropping a halted shard is the one change this must never make — while a truthy one (`2`, `"maybe"`) becomes `None`, which every `trading_active` consumer already treats exactly as it treated `True` (the shard stays ingested, audited and scannable). Do NOT "clean this up" into "any non-bool is unknown": that is a no-op for the drifted `"false"` (`None` and `True` are indistinguishable at every consumer, all of which test `is False`) AND it un-drops every falsy non-bool. The three flags then differ in what UNKNOWN means, which is why the final step is deliberately not uniform: `trading_active` stores the tri-state verdict as-is (unknown keeps the shard in the ingest — TS-04), while `exchange_active` and `intra_exchange_transfers_active` store `_status_flag(...) is True`, so anything but a recognised true — absent, null, false or unreadable — is stored as `False` and fails closed. That asymmetry is why the money flag matters at all: `trader._transfers_active` reads `intra_exchange_transfers_active`, and a drifted `"false"` read as `True` fires a real, non-idempotent, never-retried collateral POST at a shard whose transfers the exchange has disabled; `scanner.fetch_shard_statuses` is the single parse boundary, so the value reaching `trader` is always a real bool and the `bool()` there is a no-op on it. A second summary WARNING (separate from the absent-flag counter, silent at zero) names each drifted shard, flag and raw value, with the value's `repr` bounded by `config.EXCHANGE_FLAG_DRIFT_REPR_MAX_CHARS` so one drifted array cannot put a multi-KB line in the log on every run (the TS-02 failure class). The absent-flag counter still counts only genuinely ABSENT keys — a key that is present but unreadable is named by the drift line instead. A non-zero skip count logs `Skipped %d markets on trading-inactive exchange shards %s` (silent at zero), and the per-shard ingest census `Ingested markets by shard: {...}` is logged on EVERY fetch — it is the only signal of which shards a run actually saw, and is what makes a category migration visible. There is no `_on_routable_shard` any more; do not reintroduce a drop-at-ingest shard filter. **Migration facts:** shard 0 and shard 1 were both observed live on 2026-08-14; all combo/MVE markets moved to shard 1 on 2026-08-17; crypto moved to shard 2 and tennis/baseball to shard 3 on 2026-08-24. A shard-0-only scanner is therefore blind to most of the exchange — that is what this flip fixes.

**Coverage is audited, never assumed.** `scanner.check_shard_coverage(advertised, market_shards, balance_shards)` is a PURE comparison (no I/O, no logging) returning `(critical, warnings)`; `main._log_shard_coverage()` is the only thing that decides how loudly to report them and is called from both run modes immediately after the fetch, BEFORE held-ticker/horizon filtering (a blind spot must be measured against what ingest actually saw). The severity split is deliberate: an advertised `trading_active` shard that produced ZERO ingested markets is **CRITICAL** when it also holds account funds — money on a shard whose book we never scanned is a real blind spot — and only a **warning** when it holds none, because an advertised-but-empty shard is expected during the rollout and must not critical-alert every week. Markets ingested from a shard `/exchange/status` does not advertise are always critical (the two data sources disagree); funds on an unadvertised shard are a warning. A shard whose `trading_active` is explicitly `false` is never flagged — its ingest drop already warned — but a shard whose flag is absent (`None`, TS-04) IS still audited, because it stays in the ingest. `advertised is None` (sandbox / pre-sharding / any failure inside `fetch_shard_statuses`, which is fail-soft by design) returns `([], [])` and logs "coverage not assessable". **The check NEVER aborts a run** — it reports and trading continues on whatever was covered; the one run-ending verdict, the all-shards-inactive `EXIT_NO_TRADEABLE_SHARDS` short-circuit (TS-01), is decided in `main._run_dev`/`_run_prod`, never inside this pure helper. `balance_shards` must be pre-filtered to shards with a NONZERO balance by the caller (`{s for s, c in shard_balances.items() if c > 0}`); the function only tests set membership.

**Sizing is cross-shard; collateral is made fungible before execution.** `auth.verify_auth()` returns `dict[int, int]` (exchange_index -> cents) and `main._run_prod` sizes Kelly on `sum(...)` of it — the portfolio-wide total, not any one shard — because `trader.ensure_shard_collateral(client, portfolio, shard_balances, shard_statuses, dry_run=...)` runs after `pre_execution_check` and moves cash onto the shards the selected legs actually settle against (each leg charges its own market's shard). It degrades, never aborts: no deficit => untouched portfolio and zero API calls; `dry_run` => plan logged, never POSTed; transfers inactive on either endpoint shard, a failed POST (single-shot — the transfer endpoint is NOT idempotent, so never retry it), or funds that don't settle within `TRANSFER_SETTLE_TIMEOUT_SECONDS` => only the trades needing that shard are dropped, and `_run_prod` early-returns when nothing is left.

**Order routing is per leg.** On the V2 path each order body carries ITS OWN market's `exchange_index` (each `_Leg.market.exchange_index`: the NO leg's market for the NO leg and its rollback — `market_a` for same-title, `market_b` for time-series — and the YES leg's market for the YES leg), so a pair whose legs sit on different shards is now tradeable. It is always explicit and **never the `-1` auto-route sentinel**: an explicit shard makes the exchange reject loudly if our notion of a market's shard is wrong (rather than silently settling against an unmodelled shard), and it bills only that shard's rate-limit bucket where auto-route bills every nonzero shard's. The legacy `/portfolio/orders` endpoint has no shard-routing parameter at all, so while `ORDER_API_VERSION="legacy"` is in force `trader._legacy_routable(spec)` turns away any pair with a leg off `DEFAULT_EXCHANGE_INDEX` — after sizing, immediately before submission. That guard is the legacy path's whole shard story and outlives the migration with it; `main.print_pairs_table`'s "Shards" column (`a/b`) is what explains such a rejection at a glance. The backtest path stores but does not filter: `historical._market_to_dict` passes `exchange_index` through raw into cache records (pre-existing caches read back `None`) so backtest data can distinguish shards, but no historical/backtester code drops markets by shard — all historical markets are shard 0, and filtering would silently change backtest results with no live-safety gain.

**The balance read is raw, shard-aware, and returns PER SHARD — callers sum for gate/sizing (2026-08-14).** `auth.verify_auth()` no longer calls the modeled `client.get_balance()` — that deserializes through the pinned SDK's strict pydantic model (`balance`/`portfolio_value`/`updated_ts` all required ints), the exact drift-fragile pattern that already broke events, orders, and positions. It now calls `get_balance_without_preload_content` through `_http.fetch_json_page()` (wrapped in `api_call_with_retry`, since it's a read-only GET), so non-2xx still raises `ApiException` and bad credentials still fail loudly. Don't "simplify" it back to the modeled call. `verify_auth()` returns `dict[int, int]` — spendable cents keyed by `exchange_index` — not a scalar. `auth._balance_cents_by_shard()` builds that dict from the raw body: (1) every parseable `balance_breakdown` entry, keyed by ITS OWN `exchange_index` (no shard-0 preference — a later collateral-transfer planner and a shard-coverage check both need every shard's balance, not just the routable one); (2) only when the breakdown is missing or entirely unparseable, top-level `balance_dollars` (the cross-shard aggregate) attributed to `config.DEFAULT_EXCHANGE_INDEX`; (3) same fallback tier, legacy top-level integer `balance`, also attributed to `config.DEFAULT_EXCHANGE_INDEX` — this is the sandbox shape. A breakdown that exists but yields no parseable entries at all logs a WARNING and falls through to the aggregate rather than reading `$0` (a false `MIN_BALANCE_CENTS` abort); a malformed or non-dict breakdown entry is skipped rather than aborting the scan of the good ones. If nothing parses, it raises `ValueError` — a deliberate loud-failure carve-out to the return-`None`-on-validation-failure convention, because sizing real trades against an unknown balance is worse than aborting the run. **There is deliberately no scalar-returning wrapper.** A single number would hide funds parked on other shards, and every caller's actual need — the `MIN_BALANCE_CENTS` gate, Kelly sizing, a future shard-coverage check, a future collateral transfer — is either the full per-shard map or its sum, never one shard in isolation; a dual API would invite a future caller to size against the wrong (single-shard) number. `main._run_prod()` reads `shard_balances = verify_auth(client)` and sizes on `balance_cents = sum(shard_balances.values())` — sizing is portfolio-wide because collateral is made fungible across shards by pre-execution transfers (a later commit); the post-trade balance line for the Excel log sums the same way. **Same-key-different-units trap:** inside a `balance_breakdown` entry, `"balance"` is a fixed-point DOLLAR STRING (live: `"1.1407"`); at the TOP level, `"balance"` is legacy INTEGER CENTS (live: `114`). Never route the top-level field through `auth._dollar_str_to_cents()` and never return an entry's field as-is. Within an entry the field is chosen by **presence, not truthiness** (`"balance_dollars" in entry`, never `a or b`): a numeric `0` is a real answer, and an `or` would discard it and read the stale legacy field, reporting a genuinely-empty shard as funded — the one OVER-statement this function can produce, against the flooring and drop-with-a-WARNING rules that exist to guarantee the opposite (TS-16). A repeated `exchange_index` keeps the last entry and WARNs; silently last-winning hid a changed payload shape. Dollar strings are converted with `Decimal` and **floored, not rounded** (`ROUND_FLOOR`), so the bot is never told it holds a sub-cent it cannot spend; float parsing would reintroduce the truncation noise the `*_dollars` fields exist to avoid.

**Collateral transfers are centicent-denominated, asynchronous, and never retried.** Kelly sizing is portfolio-wide (the SUM of every shard's balance) but an order settles against its own market's shard only, so `trader.ensure_shard_collateral()` moves cash onto the shards a selected portfolio actually draws from before execution: it totals each shard's requirement from the legs' `cost_with_fees_a`/`cost_with_fees_b` (`_required_cents_by_shard`, `math.ceil(round(cost * 100, 6))` — ceiling because under-funding a shard by a fraction of a cent gets the order rejected for insufficient collateral, while over-funding by a cent costs nothing; the `round()` first stops binary float noise claiming an extra cent, same idiom as `fee_leg_exact`), plans a pure deterministic greedy fill out of surplus shards (`_plan_transfers` — deficits in ascending shard order, sources ranked by largest REMAINING surplus, so the number of non-idempotent POSTs is minimized), POSTs each planned transfer to `config.TRANSFER_PATH`, and confirms it actually settled. Three rules are load-bearing. (1) **Centicents are the codebase's THIRD money unit** — the endpoint's `amount` field is 1/100 of a cent (dollars for contract prices, integer cents for balances and `buy_max_cost`, centicents here and nowhere else). The conversion lives ONLY in `trader._cents_to_centicents()`; never inline the factor, because a missing ×100 moves 1% of the intended collateral (surfacing much later as an unexplained insufficient-funds rejection) and a doubled one moves 100× out of a shard. (2) **A 2xx means accepted, not settled** — the endpoint is asynchronous, so an order submitted immediately after could still be rejected for insufficient collateral. `_await_transfer_settlement()` re-reads the per-shard balance through `auth.read_shard_balances` — the SINGLE-SHOT (retry-free) variant of `verify_auth`'s parse, because `verify_auth`'s `api_call_with_retry` backoff could hold one read for ~60s and silently stretch the "bounded" wait — every `TRANSFER_POLL_INTERVAL_SECONDS` (2) against a `time.monotonic` deadline of `TRANSFER_SETTLE_TIMEOUT_SECONDS` (30); a balance read that raises is treated as "nothing observed", never as success, and the await targets ONLY the shards accepted transfers were headed for (an unfundable deficit shard must not burn the timeout or miscast settled transfers as in-flight). `trader.py` imports the reader at module scope — layering-legal (`config`/`_http` → `auth`/`scanner` → `strategy` → `reporter` → `trader`) — and tests substitute it by monkeypatching `trader.read_shard_balances`. (3) **A retried transfer moves the money twice** — the endpoint is not idempotent, so `_execute_transfer` submits through `_http.signed_request_json` (single-shot by construction, never `api_call_with_retry`, which `_execute_transfer` deliberately does not use — `trader.py` DOES import `api_call_with_retry` at module scope, for the retried `_position_count` reads; the no-retry rule is asserted per-function on the submission/transfer sources, never as a module-wide import ban) and one failed POST is logged and abandoned, never re-sent. An **accepted-but-unparseable** response is NOT a failed POST: `_check_and_parse` validates the status before parsing, so a `JSONDecodeError` out of that call proves a 2xx and therefore that the money moved. `_execute_transfer` catches it, logs `logging.critical` naming MONEY IS IN FLIGHT, and returns `None` — the value that already means "accepted, id unknown" — so the shard is still awaited and still eligible for the in-flight critical. Letting it propagate instead reported a FAILED POST, skipped the settlement poll entirely and suppressed that critical (TS-17). Nor is an **accepted-but-non-object** response a failed POST: `_check_and_parse` does not narrow the parsed body to a `dict` (both `_http.fetch_json_page` and `_http.signed_request_json` are annotated `-> Any` and say so in their Returns), so a 2xx body of `"accepted"`, `[]`, `123`, `true` or a literal `null` reaches `_execute_transfer` as a `str`/`list`/`int`/`bool`/`None` and `data.get("transfer_id")` raised `AttributeError` into the very same generic handler — the same misreport, one exception type over (DR-05). An `isinstance(data, dict)` guard now logs its own MONEY IS IN FLIGHT critical (naming the type, so payload-shape drift is distinguishable from a parse failure) and returns `None` on the same in-flight contract; an id-less but genuine JSON OBJECT is untouched and still returns `None` with no critical. The other readers of a 2xx body are deliberately left loud, for two different reasons. The read-only ones have moved no money by the time they parse: the `.get(...)` readers (`auth._balance_cents_by_shard`, `scanner.fetch_open_events_with_markets` and the other scanner cursor loops) raise the same `AttributeError`, and `historical`'s subscripting `/historical/cutoff` read (`cutoff["market_settled_ts"]`) raises `TypeError`. The ORDER-submission readers **in `trader.py`** are the exception to that rationale and still must NOT get this guard: a 2xx there can mean a FILL, so money HAS moved — `_submit_order` (legacy) subscripts `data["order"]["status"]` and raises `TypeError`, `_submit_order_v2` reads through `_v2_fill_status`'s `data.get("order")` and raises `AttributeError`, and both stay loud precisely because raising is what routes `_execute_one` into its ambiguous-submission path, where the outcome is resolved against the account's position DELTA — a stronger remedy than an in-flight critical. **`v2_probe.py` is the named carve-out to that carve-out and DOES get the guard (DR-58).** Its submissions are order submissions, but nothing resembling `_execute_one` sits above them: the probe IS the top of its own call stack, so raising resolves nothing and merely kills the process mid-step — after a real ask has been submitted, before the position read, before any "FLATTEN IT MANUALLY" line, and (in `_step_no_mapping`, the only step that has one) before the reduce-only close, leaving a real position open with nothing to tell the operator it exists. `v2_probe._non_object_body_fail` therefore guards both submission-response READERS — `_step_no_mapping`'s NO buy and `_step_unfillable_ask`'s ask — printing a FAIL that names the body type, reading the position and telling the operator what to flatten. **READERS, not submissions: the probe makes THREE submissions and only two of them read their body.** `_step_no_mapping`'s reduce-only NO CLOSE needs no guard because its 2xx body is only handed to `_emit` (typed `Any`, it just pretty-prints) and the verdict comes from `trader._position_count`, so there is no `.get(...)` on it to raise — add a guard there only if a future edit starts reading fill fields off `close_data`. `_non_object_body_fail` **re-reads once on a flat OR unreadable first read**, which EXTENDS DR-21 rather than restating it: DR-21's own re-read fires only on an exactly-zero read, and a bare truthiness test here would collapse `None` (lookup failed) into `0` (genuinely flat) in exactly the window where both are expected — the three outcomes stay distinguishable in the output. It deliberately does NOT submit the close: that order rests on the mapping the unreadable body proves nothing about, so the position is left for a human, as a disproven mapping already leaves it. The probe's own read-only 2xx readers (`_fetch_market`'s `data.get("market")`) stay loud like every other read-only one — nothing has been submitted by then. So: three call sites carry the guard across two modules — `trader._execute_transfer` and `v2_probe`'s two submission readers; `_execute_transfer` is the one site in the PIPELINE with neither property — no ledger reconciles a transfer after the fact, and its caller's generic handler would report a FAILED POST. Do not generalise the guard to any of the others. `_check_and_parse` itself keeps raising on an empty 2xx: returning `{}` there would make `trader._read_position` answer "account flat" when the truth is unknown, and would make every cursor loop read a falsy page as a clean finish. Every failure mode **degrades, never aborts the run**: a shard whose `intra_exchange_transfers_active` is false (checked on BOTH endpoints of a transfer, and a shard absent from `scanner.fetch_shard_statuses()` counts as inactive) warns the operator to move the funds manually in the Kalshi UI; a failed POST logs an error; an accepted transfer whose money is not OBSERVED to arrive logs `logging.critical` naming the in-flight `transfer_ids`. **That critical's trigger is the settlement OBSERVATION, never a shard's membership in `accepted_cents` (DR-65).** `ensure_shard_collateral` compares each still-unfunded shard's `confirmed` balance against `awaitable` — the same `min(required, prior + moved)` map the settle wait targeted, i.e. exactly what the accepted transfers could deliver. Below it, cents were accepted and did not land, so the critical fires; at or above it the money demonstrably arrived and the shard is still short — because a planned leg was blocked, its POST failed, or there was no surplus to cover the rest — which gets a WARNING naming the shortfall instead. **The warning reports only what was observed and asserts no cause**, because the code observed exactly one thing (`confirmed >= awaitable`) and knows nothing about why the shard is still short, nor about transfers whose POST raised — a raised POST the server had already accepted leaves that shard out of `accepted_cents` entirely, so an affirmative "nothing is in flight" there would be a false denial. The two verdicts partition the unfunded shards an accepted transfer was headed for, and no shard is ever reported both ways; a shard whose transfer was never accepted is in NEITHER and was already warned about at its skip or POST-failure site. Do not "simplify" `settled_short` to `unfunded - in_flight` — that would tell the operator a never-sent transfer had "SETTLED". One known residual: "landed" is inferred from a balance THRESHOLD against the run's opening `shard_balances`, so an unrelated credit to the deficit shard of at least the accepted cents, arriving inside the poll while the transfer is genuinely stuck, would suppress the critical (the inverse, a debit, only over-reports, which is the safe direction). The membership test fired the critical on a plan that settled in full and in zero wait, with the same log line's own `confirmed` map showing the money had arrived — telling the operator funds were unaccounted for when none were. In every case only the specs whose shards remain unfunded are dropped — a spec dies if EITHER leg's shard is short, since a funded NO leg with an unpayable YES leg is precisely the unhedged half-fill the rollback machinery exists to avoid — and the rest execute normally. `dry_run` plans and logs but NEVER POSTs, returning the portfolio unchanged. The zero-deficit fast path keys off the deficit set, not off the plan being empty: an empty plan is ambiguous ("nothing needed" vs. "nothing movable"), and reading it as the former would let underfunded specs sail through. `main._run_prod` wires it in right after `pre_execution_check` — but first calls `trader.drop_legacy_unroutable()`, which (on the legacy path only) drops statically-unroutable specs BEFORE any money moves, so collateral is never stranded on a shard the legacy endpoint cannot trade against.


**A time-series pair must be two CUMULATIVE-deadline markets, not two snapshots (DR-67, fixed 2026-09).** The bet buys YES on the earlier contract and NO on the later one. That is only coherent when both contracts ask "will X happen **by** \<date\>", because only then does the earlier deadline's event nest inside the later one's — which is what makes the FAIR VALUE of YES-A + NO-B at most $1 (not a guarantee about the quoted asks: a wide book can still quote pA + nB >= 1 on a genuine ladder), gives the pair exactly three settlement cells, and rules out A=YES/B=NO. Kalshi also lists **snapshot** markets — "what is X **on** \<date\>", "X **in** \<Month\>" — whose probabilities do not nest at all: SOL ≥ $180 on Sep 14 does not imply SOL ≥ $180 on Sep 18. Before this, the codebase asserted the premise and never checked it, and said so in four places (this file three times, README once): "the live scanner cannot tell them apart from prices… this counter is the only signal". **The exposure was real and measured against the repo's own `_DATE_PATTERNS`:** `"Bitcoin price on Sep 15, 2026?"` and `"…on Sep 18, 2026?"` both normalize to `bitcoin price on ?`, so a dated snapshot family landed in ONE time-series group and was eligible to be sized and traded. The same holds for `"Solana price on Sep 14/18, 2026?"` (`KXSOLD`), `"Highest temp in NYC on Oct 1/Oct 2"`, `"Will the Fed cut by 50 bps in December/November 2026?"`, and — from the other direction — `"after March 1, 2026"` against `"after June 1, 2026"`, where probability DECREASES with the date so the earlier/later leg assignment means the opposite of what it says. Only the year-less full-month shape (`"on June 30"` vs `"on July 1"`) stayed split, which is the one shape `tests/test_scanner.py`'s snapshot pin covers. DR-01's own worked example is one of these families.

**The fix is one classifier on both paths.** `scanner.deadline_phrasing(event_title, title, subtitle)` returns `"cumulative"` / `"snapshot"` / `"unknown"`; `scanner.deadline_profile` pairs that verdict with the deadline phrases spelled out by the one field that decided it (DR-69, see detail (1)); `scanner.cumulative_deadline_pair(profile_a, profile_b)` is the eligibility predicate, and BOTH `scanner.find_time_series_pairs` and `backtester._extract_pairs` call it (pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_apply_the_cumulative_deadline_rule` and `::test_ast_the_deadline_classifier_has_one_definition`). Only the FIELD EXTRACTION differs between the paths — attributes live (`scanner._market_deadline_profile`), cache-dict keys in the backtest (`backtester._deadline_profile_dict`, reading every key as `.get(...) or ""` because a cached `subtitle` is legitimately `None`). Eight details are load-bearing.

(1) **The three fields are scanned SEPARATELY and combined by MOST-SPECIFIC FIELD WINS — `subtitle` → `title` → `event_title`** — with a snapshot marker beating a cumulative one *within* a field. They are never concatenated: joining them can manufacture a match across a field boundary (a title ending "…on" beside a subtitle beginning "June 30"). The subtitle leads because it is the **sub-contract**, the thing that actually resolves, so its wording is the most authoritative statement of what the contract settles on and must be able to override a parent event title. That is what keeps an MVE market whose sub-contract is a "by \<date\>" label eligible even under a snapshot-titled parent event. It does NOT weaken the snapshot refusals, and the reason is structural rather than lucky: in the `KXBTCD`/`KXSOLD` families the subtitle is a bare strike ("$82,750 or above") carrying no marker, so the verdict falls straight through to the title, where "price **on** \<date\>" lives. **Since DR-69 the deadline spans come from that same deciding field and no other** — `scanner._deciding_field` is the one field walk, read by both `deadline_phrasing` (the verdict) and `deadline_profile` (the verdict plus the deciding field's spans), pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_the_deadline_classifier_has_one_definition`. Before it, the verdict came from one field while the spans were gathered from all three, and fixing that moves pair ELIGIBILITY (`cumulative_deadline_pair`) in BOTH directions — never a phrasing verdict, since the field walk itself is unchanged — each pinned by `tests/test_scanner.py::TestSpansFromDecidingField` and its backtester mirror: it can refuse a pair whose deciding field states one or no deadline while another field carries distinct dates (an "At any time" subtitle no longer borrows the event titles' "by Sep 14" / "by Sep 18"; a shared "$1 by 2027" sub-contract is one deadline stated twice, whatever the titles say), and it can admit a pair whose deciding fields differ while other fields restate both (each title stating its own deadline, each event title the other's). DR-69 changes the outcome for a stale sub-contract label only toward refusal (seen once in cache: APPLEFOLD-26DEC31); under either rule a stale label can still make one deadline read as two. Measured on the 2026-09-22 live snapshot (113,303 markets): zero verdict flips; spans changed on 558 markets (493 cumulative, 65 snapshot), every one a strict SHRINK to the deciding field's own phrases and none leaving a cumulative market spanless; and zero eligibility flips among the 13,096 time-series candidates the finder compares (52 eligible before and after). (2) **"by" must be followed by a DATE token** — since DR-68 a narrowed set: a month name ending at a word boundary, a weekday (with any following month-name date), a calendar m/d not followed by vote/majority/of, a 2020–2099 year, an ISO date, or a Q/end-of noun form — or "cut **by** 50 bps", "win **by** 10 points" and "pass **by** a 2/3 majority" read as deadlines; the first of those is a real Kalshi shape whose two months merge into one normalized group. (That last example is stopped by the article "a" alone; the m/d token's vote/majority/of lookahead is what stops the article-less "pass by 2/3 majority".) (3) **A bare CLOCK TIME is deliberately not a date token**, so "$82,750 or above by 5pm" is not cumulative — with the subtitle leading, an intraday snapshot family would otherwise fail OPEN through its own sub-contract label instead of falling through to its title. (4) **The date token must cover the NOUN forms** (`Q1 2026`, `end of [the] year`, `year-end`, `EOY`). `_DATE_PATTERNS` already strips `Q1 2026` and `end of [the] year`, so a table accepting only `by <Month>` would refuse markets the grouping key already treats as deadline-dated; `year-end` and `EOY` are NOT in `_DATE_PATTERNS` at all — they are covered here for the same reason as the rest of the token, coverage of common Kalshi phrasings, not because the grouping key needs them. (5) **`after <date>` is a REJECT marker and requires a date token of its own**, or "Will BTC top $100k by Dec 31, 2026, after the halving?" is wrongly refused. (6) **`in <Month>` / `in <Year>` is a WINDOW, not a deadline** — top-10 in October does not nest inside top-10 in November (the FIDE markets this file already names). (7) **The month fragment takes an optional day AND year, with `(?!\d)` on the day group.** Without it "by March 2026" captures only "by march 20" — the day group eats half the year — and every deadline in one month looks identical, which silently refuses genuine pairs; `"by Dec 31"` vs `"by Dec 20"` must read as two different deadlines. (8) **Fails CLOSED**, like `_same_series`: `unknown` wording is refused, and so is a cumulative leg whose DECIDING field names no comparable date ("within 30 days"), even if a less specific field of that leg does (DR-69), because two deadlines that cannot be shown to differ are not a two-deadline pair. Deadline phrases are compared as normalized strings, never as parsed calendar dates: one deadline spelled two ways reads as two ("Oct 1, 2026" vs "October 1, 2026"). Two deadlines truncated to one span read as one: fixed for a weekday plus month-name date by DR-68, other truncations remain (Known residuals below).

**DR-68 tightened the date tokens (fixed 2026-09).** A month name must end at a word boundary on the cumulative side (`_DEADLINE_MONTH_FULL`'s `\b`) and at the next LETTER on the snapshot side (`_SNAPSHOT_MONTH`, used by the `on <Month>` and `on the <Month> <day>` entries and by the `after` marker, which also inherits the `\b`-bounded month through the shared `_DEADLINE_DATE_TOKEN`), so "wins **by Dec**ision", "produced **by Mar**vel Studios", "land **on Mar**s" and "**after May**or Adams resigns" are no longer dates, while an unspaced "on Sep30" / "after Sep30" still fires its reject marker; a calendar m/d must be a real month (1–12) and day (1–31) and must not be followed by vote/votes/majority/supermajority/of, so "by 2/3 vote", "ratified by 3/4 of states" and "by 3/2027" are not deadlines; a bare year must be 2020–2099, so "decrease by 2000" is an amount; `\bever\b` is no longer a cumulative marker (it fired on names — "Chaco For Ever", "Worst Neighbor Ever" — and on "the hottest year ever"); a weekday keeps a following month-name date, so "by Friday, Sep 19, 2026" and "by Friday, Sep 26, 2026" are two deadlines rather than one truncated "by friday" stated twice (a genuine pair used to be refused); "on **the** \<Month\> \<day\>" is a snapshot like "on \<Month\> \<day\>" (the CFP-rankings families), but only with a day, and `(?!\d)` keeps that day from eating a year; and the dotted clock forms ("at 5 p.m. ET") no longer need a following word character. The two older REJECT markers deliberately keep their DATE alternatives as wide as before DR-68 — `after <date>` keeps the wide numeric alternatives (any m/d, any `20xx`) beside the tightened token, and both it and `on <Month>` end a month at the next letter rather than at `\b`, so an unspaced genuine date still matches — because narrowing a reject marker for a GENUINE date fails OPEN: snapshot → cumulative, the one direction this rule must never move for a genuine date. What DR-68 does narrow on the snapshot side, deliberately, is month-prefixed NON-date words: "land on Mars", "decide on declaring", "after Mayor Adams resigns", "after Marvel's release" and "after Decision Day" move snapshot → cumulative, because none of them names a date (detail (5) already requires `after` to be followed by one); the Mars, declaring and "after Mayor" rows of `TestDateTokenBoundaries` pin that move. Measured on the 2026-09-22 live snapshot (113,303 markets): 65 verdicts cumulative → unknown (KXMOVIECAST 27, KXPERFORMROLEBPANTHER 10, KXUFCMOV 10, KXUFCVICROUND 5, KXUFCMOF 5, KXARGNACBGAME 3 — the "Chaco For Ever" club — KXGTEMP 2, KXDTEMMYS 1, KXHMONTH 1, KXVMA 1), 1,060 unknown → snapshot (KXNCAAFTOPCFPPOLL 760, KXNCAAFCFPPOLL 300), **zero** snapshot → cumulative and no other flip, three span-only changes (two KXNHSPLTRBREAK markets lose `'by dec'`, KXGOVTCUTS-26-2000 loses `'by 2000'`), and zero eligibility flips among the 13,096 time-series candidates the finder compares (52 eligible before and after); on the 1,004,591 records of the 2026-09-08/09 day slices, 545 cumulative → unknown — every one a "by Decision" leg, 525 of them combo fight-method tickets (every combo record that read cumulative) — and nothing else. Other deliberate changes (fail closed): "by Friday at 5 p.m. ET" now reads snapshot (the dotted clock fires); "by 12/31 of this year" reads unknown (the `of` lookahead); an m/d followed directly by a word character ("by 6/30th", "by 6/30pm") reads unknown (the m/d token's trailing `\b`); and an unspaced month-name date on the CUMULATIVE side ("by Sep30") reads unknown (`_DEADLINE_MONTH_FULL`'s `\b` — the snapshot side still reads it). No deadline preposition directly followed by either of the last two shapes occurs on the 2026-09-22 snapshot or in those day slices. Tests: `tests/test_scanner.py::TestDateTokenBoundaries` — a regression row per tightened token (each calendar range, month and day, on its own row), plus controls that each name the over-tightening, reject-narrowing or over-widening mutant they kill; the one surviving mutant, a letter lookahead in the `on the` branch, is equivalent, because that branch's required day already excludes a letter after the month — and its finder-level mirror in `tests/test_backtester.py::TestDateTokenBoundaries`.

**The classifier is computed ONCE PER MARKET, never per pair, and that is a hard constraint.** A group of N markets produces O(N²) candidate pairs; `tests/test_backtester.py::TestExtractPairsPerformanceSmoke` sweeps a 50,000-member group under a 30-second budget, and measured on the real tables (on that synthetic 50k fixture, 2026-09-19, before DR-68/DR-69/DR-70), classifying per pair costs **14.08s** against **0.47s** per market — about 47% of the whole budget before the sweep does any work of its own. That is a 30× TIME ratio on that fixture, even though per-pair classification makes about **60× more CALLS** (2 legs × ~31 in-window neighbours per member); quote the two separately. `find_time_series_pairs` memoizes by ticker across the run; `_extract_pairs` memoizes positionally **per group** and drops it with the group, because a corpus-wide ticker→verdict map would add residency in exactly the place TS-07 did work to remove it, and `_extract_pairs` is called twice per run. Measured after, on the same synthetic 50k fixture (2026-09-19): the 50k sweep runs in 7.8s and still emits 1,549,504 pairs. **DR-70 then made each classification cheap (fixed 2026-09).** `_field_phrasing` tests each table with ONE precompiled alternation (`scanner._ANY_SNAPSHOT` / `_ANY_CUMULATIVE`) instead of searching every entry in turn, and `_deciding_field` skips a field identical to the one scanned just before it (every combo record's title repeats its subtitle verbatim). Table entries must stay alternation-safe — zero capturing groups and no inline flags — or "some entry matches" stops equalling "the alternation matches"; `tests/test_scanner.py::TestPhrasingTableInvariants` pins that, and `::TestAlternationEquivalence` checks both alternations against the per-pattern lists (which stay, for `_deadline_spans`' index 0 and as that reference) over 112 distinct wording strings — those of the classifier's parametrized DR-67/DR-68 tests, read off the tests' own parametrize marks so the reference cannot drift from them, plus eight capitalisation cases that no table spells. Measured 2026-09-22 through `deadline_profile` on the first 200,000 records of the 2026-09-08 day slice: **45.7 → 12.3 µs/record** (the alternation alone 23.0, the skip alone 23.9); output identical on all 113,303 markets of the 2026-09-22 live snapshot and, by SHA-256 over the profiles, on the 1,004,591 records of the 2026-09-08/09 day slices. The outcome-label census's own cost is this classifier, not its walk (12.5 vs 0.3 µs per record on the same sample). Since SS-1 the census rides `backtester._index_eligible_keys`, `_prepare_candidates`' first walk over the corpus (fed through `_OutcomeLabelTally.add`), and that walk also computes both grouping keys per eligible record — on a combo-heavy corpus the time-series key dominates it (~135 µs/record, `normalize_title` on long combo titles, measured on the 2026-09-17 7-day window), so there the census is the smaller share.

**What this deliberately does NOT touch.** `_DATE_PATTERNS` and both grouping keys are unchanged — a snapshot family still GROUPS, it is refused at PAIR time — which keeps the blast radius to eligibility and avoids the pattern list this file already flags as regression-prone. The phrasing tables are a SEPARATE structure and must not be merged into `_DATE_PATTERNS`: that list exists to ERASE dates so two deadlines collapse onto one key, these exist to READ the surrounding preposition and decide what kind of question it is. The same-title finder is untouched (no deadline concept), and so is `_extract_pairs`' same-title branch — that function serves both types and dispatches only on `isinstance(key, str)`, so the rule goes on the string-keyed branch ONLY. `_can_ever_enter` is untouched, so **`config.SETTLED_PREFILTER_CACHE_TAG` is NOT bumped** (same precedent as DR-02); do not "optimise" the rule into that predicate, which is the one placement that would silently corrupt every assembled cache on disk. Kelly, `k`, fees, tiers, leg sides, enrichment, `_settlement_receipt` and the trader are all unchanged.

**Two consequences to expect.** (a) **The two finders are now MUTUALLY EXCLUSIVE on one ticker pair.** A same-title pair requires identical wording; a time-series pair requires two DIFFERENT stated deadlines; identical wording cannot state two of anything. So the cross-type collision `main._dedup_pairs` and `backtester._drop_cross_type_duplicates` exist for can no longer arise from the finders. Both helpers stay — they are still right if a collision ever arises another way — and `tests/test_backtester.py::TestRunBacktestCrossTypeDedup` now pins the exclusivity instead of the drop, alongside `tests/test_scanner.py::TestDeadlineGuardFinders::test_dated_identical_wording_is_same_title_only` and its backtester mirror `tests/test_backtester.py::TestRunBacktestCrossTypeDedup::test_dated_identical_wording_is_same_title_only`, which pin the same exclusivity on a fixture whose legs DO each carry a "by \<date\>" deadline stated identically (not the deadline-less class-level `_MARKETS` fixture, titled "Q", that `TestRunBacktestCrossTypeDedup`'s OTHER tests use). (b) **Skipping is not only subtractive**, exactly as for DR-02: both finders keep ONE best pair per group, so refusing a group's widest candidate PROMOTES the runner-up, and a diff of two runs' pairs tables is not a pure deletion.

**Observability, because this rule can empty the strategy.** Absence of a warning must never be the only signal (DR-66). The live finder logs a per-market census on EVERY run — `Deadline phrasing of actively priced markets: N cumulative, N snapshot, N unknown` — plus, since DR-72, THREE silent-at-zero skip counts for refused candidates split by REASON (`scanner.deadline_pair_refusal`, over `REFUSED_SNAPSHOT` / `REFUSED_NO_STATED_DEADLINE` / `REFUSED_SAME_DEADLINE`) rather than one folded count: a leg's deciding field is snapshot wording; a leg's deciding field carries no recognised deadline wording or no comparable date; or the two deciding fields state the same deadline, or truncate to one. A fourth silent-at-zero line covers candidates that WERE worded as two different cumulative deadlines but were refused only for sitting more than `MAX_DEADLINE_GAP_DAYS` apart ("... refused at the %d-day gap cap (tier and price not evaluated): %d") — the live signal that cumulative families exist but sit too far apart to trade, distinct from the three wording refusals, which mean no genuine two-deadline pair was ever established. And another silent-at-zero line for the `pA + nB >= $1` guard. `backtester._extract_pairs` mirrors the three wording-refusal lines (worded "... within the deadline-gap window, before price filters" — it has no gap-cap line of its own, since its close-time sweep window is a performance bound, not a reported filter); The backtest's outcome-label census (counted by `backtester._OutcomeLabelTally` inside `_prepare_candidates`' first walk over the corpus and reported through `_report_outcome_label_coverage`; `_log_outcome_label_coverage` is the one-shot composition of the two) censuses the same three phrasing-bucket counts over the eligible corpus in that single pass and carries them on `OutcomeLabelCoverage` (fields appended after `below_floor`, since it is frozen and not `kw_only`) out to `dashboard._deadline_phrasing_html`. That render is DESCRIPTIVE with **no floor and no banner**, deliberately unlike the subtitle census: the cumulative FRACTION has no healthy baseline — most Kalshi markets are not deadline markets at all — so any threshold would be arbitrary and would fire on every run. The reading that IS actionable needs no threshold, and gets its own sentence on the page: **zero cumulative markets on a non-empty corpus means the run could not have produced a time-series trade at all** — but ONLY when the three counts actually sum to the corpus (DR-71, fixed 2026-09): a mismatched or hand-built coverage instead renders its raw counts plus "(counts do not sum to the corpus — not a verdict)" rather than asserting a verdict its own numbers cannot support. The two refusal reasons are reported SEPARATELY rather than folded into one sentence, because they are refused for different reasons: snapshot wording is refused because such probabilities need not nest ("after \<date\>" nests the wrong way; a shared-start "after X and before Y" window CAN nest — a known, accepted over-refusal), while unrecognised wording is refused because nesting simply cannot be shown. DR-71 also made the three `OutcomeLabelCoverage` phrasing fields REQUIRED, with no default — see the DR-01 paragraph's correction to the DR-66b "one remaining place an omission is possible" sentence for why. One divergence no AST pin can catch: `event_title` reaches essentially every LIVE market but only a small fraction of CACHED ones, so a market whose deciding field is its event title (no marker in its subtitle or title) reads as its event title's verdict live (cumulative for a "by \<date\>" event title, snapshot for an "on \<date\>" one) and as unknown in backtest. At the phrasing-rule level, where the cache carries subtitles, the backtest's profile equals the live one or is unknown (DR-69: the spans come only from the deciding field, so a blank cached event title cannot change a profile the subtitle or title decided — before DR-69 the live spans also folded in the event title's dates, and the two paths could differ in either direction). That is not a pipeline guarantee: a blank cached event_title changes the time-series group key itself.

**`find_time_series_pairs` skips candidates whose leg ASK prices already sum to $1 or more, explicitly rather than emergently.** A win pays only $1, so such a pair cannot profit in any cell. It is not impossible: wide books quote it even on genuine ladders (KXDEFAULT-28DEC31/-29DEC31 at 0.11 + 0.96 on 2026-09-21) — nesting makes the FAIR VALUE of YES-A + NO-B at most $1, not the quoted asks. The skip was previously only IMPLIED by the `tradeable` flag, which meant a violating pair was still constructed and could win its group's one-pair slot ahead of a sound runner-up; the explicit skip only changes which NON-tradeable row represents such a group, since `tradeable` already requires `1 - pA - nB > fee`. **The epsilon runs the OPPOSITE way from every other price filter here** and the comment says so: the qualifying-level tests ADD `PRICE_EPSILON` to a keep bound so a level exactly on the bound is not dropped for noise, whereas this is the REJECT side of a strict `< 1`, so it SUBTRACTS — a sum that is really 1.0 but evaluates to 0.9999999 must still be refused. It tightens by at most 1e-6, two orders of magnitude below the finest tick, so it can never reject a genuinely sub-$1 pair, and TS-09's "never reject for representation noise" rule is honoured rather than broken — in practice it is defensive and inert on every Kalshi grid (4-dp prices; complementary pairs sum to exactly 1.0).

**Any backtest baseline taken before this change is not comparable** — fewer time-series candidates and therefore different trade counts, returns, equity curve and drawdown; on the 2026-05-01 cache the empirical `k̂` population isn't merely smaller, it is now EMPTY (see the dormancy note below). The pooled `k̂` figures quoted elsewhere in this file predate it and are void.

**Dormancy, measured 2026-09-21.** After this rule shipped, the time-series leg forms 0 pairs live, and the 2026-05-01 backtest cache's surviving time-series candidates are recurring windows (weekly "before \<date\>" families) the backtest cannot enter — see the Known residuals list below for why they are harmless rather than fixed. Genuine cross-event cumulative families exist live (e.g. Premier League managers "cease to be manager before Jan 1 / Jun 1, 2027"), but every one measured spans more than the 30-day gap cap; the real cumulative opportunity sits in same-event deadline ladders (Kalshi listing a question's several deadlines as separate markets inside ONE event). **DR-73 built that expansion and ships it OFF** (`config.TIME_SERIES_SAME_EVENT_LADDERS`), so the leg is still dormant by default and the dormancy above is unchanged — with the switch on, the same 2026-09-22 snapshot emits 24 ladder pairs in 24 events. It is off because enabling it means betting the operator's belief against real scheduled-event information and needs its own backtest and calibration first; see that constant's comment for the measured exposure and the calibration that gates the flip. The pooled `k̂` 1.114 quoted elsewhere in this file, measured on the strike-blind 2026-05-01 cache, came from 35 observations on pairs this rule refuses (snapshot or unknown wording) and is void; on that same cache the calibration population is now empty.

**Known residuals of the DR-67 wording rule.** Recorded here, each with its measured bound, rather than fixed.
- **Date-token residuals (DR-68):** season ranges ("2018-19 through 2025-26" reads `'through 2025'` — can turn a verdict cumulative; 1 live instance, KXNBANEWCHAMPION-27-Y); 2020–2099 quantities ("increase by 2030 units"); fractions before other nouns ("by 1/2 point"); month-named proper nouns ("by April Ryan", "Mar-a-Lago"); end-of-period nouns without a trailing boundary ("by the end of the weekend" reads `'by the end of the week'`). Each of these can produce a false cumulative verdict or span; none has a live time-series partner (re-checked on the 2026-09-22 snapshot: no eligible candidate's span rests on one of these shapes). Separately, the snapshot-side `on m/d` and `in/during/for 20xx` tokens were deliberately left wide: they can only produce a false SNAPSHOT verdict — never a span, since spans come only from `_COMPILED_CUMULATIVE[0]` — which fails closed.
- **Weekday + numeric date (DR-68):** a weekday keeps only a following MONTH-NAME date, so a numeric one is still truncated. With no year or a 2-digit one ("by Friday, 9/19", "by Friday, 09/19/26") the two titles do not share a time-series group; with a 4-digit year ("by Friday, 9/19/2026") or an ISO date ("by Friday, 2026-09-19") they do, both legs span `'by friday'`, and `cumulative_deadline_pair` refuses the pair as one deadline stated twice — the weekday-truncation false refusal DR-68 fixed for month-name dates, still present for these. It fails closed (a missed trade, never a false one); a deadline preposition followed by a weekday and a numeric date occurs 0 times on the 2026-09-22 snapshot and in the 1,004,591 records of the 2026-09-08/09 day slices.
- **Recurring rolling windows** ("Will Trump say X before May 11 / before May 18", weekly GPU "Up or Down by", weekly eliminations) pass the wording screen but do not genuinely nest — each is its own week, not a cumulative deadline on one question. Checked against real prices rather than assumed harmless: measured 2026-09-21 on the 2026-05-01 backtest cache, of 1,612 such pairs, 1,448 were never listed together (the backtest's entry rule cannot open a trade on them) and 164 overlapped only in the earlier leg's final 2–10 hours. In 96% of co-quoted admissible hours the earlier leg's YES ask was 0.01, so the pair is effectively a NO bet on the later window regardless of nesting, and nesting does not change the payoff. Kelly would have sized 49 of them: 29 won, 20 lost, net positive. Live scheduled runs (Monday 16:00 UTC) fall after the overlap window closes. Revisit only if a series is found co-listing mid-window rather than only in its final hours.
- **Level at one instant** ("SOFR above X by end of \<period\>"): a value observed at a single moment, worded with a deadline preposition, reads cumulative though it does not nest. Held back today only by the quarterly cadence of the one live family (`KXCREDITC`) — its two nearest quarters are more than `MAX_DEADLINE_GAP_DAYS` apart. A monthly family of the same shape would pass the 30-day gap and needs its own fix (a predicate classifier, not yet designed).
- **Non-monotone predicates** ("exactly N", "remain until \<date\>"): also read cumulative though the underlying condition is not monotone in time. Stopped first by the one-series rule (most instances are same-event ladders) and then by the 30-day gap: the monthly `KXPARDONSTRUMP` windows open only when the previous one closes, so consecutive instances are never co-tradeable.
- **Recall misses that fail closed:** a deadline whose only qualifier is a non-date period ("before Week 4 of the 2026-27 season") names no date token, so it reads `unknown` and the pair is refused — a missed trade, never a false one. A deadline FOLLOWED by a clock time ("before Dec 31, 2026 at 4pm EST") reads `snapshot`, which also refuses. **Kalshi's shared-start template "after issuance and before \<date\>" is a different case and is deliberately ADMITTED** (it reads `cumulative` with the "before \<date\>" span): two windows that start at issuance and end at different dates DO nest, which is exactly the premise the rule screens for. Measured on the 2026-09-22 snapshot, of the 150 markets whose wording mentions issuance, 100 read cumulative, 40 snapshot and 10 unknown — and none of them reaches a pair while `config.TIME_SERIES_SAME_EVENT_LADDERS` is off, because those families list their deadlines inside ONE event ticker and are dropped by the different-event rule, not by the wording rule (see the Dormancy sentence above). **With the ladder switch ON they do pair, and one of them is in the emitted set** — `KXALBUMRELEASEDATE-NEWDRA` ("Will Drake release new album after issuance and before Sep 26, 2026") is 1 of the 24 pairs the 2026-09-22 snapshot emits — which is the intended outcome, not a regression: two windows that both start at issuance and end at different dates DO nest. An earlier version of this bullet claimed all three shapes read `unknown` and were refused; that was false of the code and is corrected here.
- **Realized-close ordering in the backtest:** `_find_entry` reads the REALIZED close of a settled market where the live finder reads the SCHEDULED close, so an event that resolved early can compress or invert the measured deadline gap for a genuine cumulative pair. Backtest-only, and **CROSS-EVENT-only since DR-73c**: a same-event ladder is ordered and gapped on its two STATED deadlines, which is span-date parsing off the wording applied to exactly the population where realized close is worst (681 of 1,821 archive same-event pairs have a close gap of ZERO days; on the 101-slice sub-corpus, 101 of 408 ladder pairs, 37 of them closing at the identical INSTANT — the zero-DAY reading is the one that matters, since `_find_entry`'s cross-event branch orders on close DATETIMES). A cross-event pair still needs a scheduled-close field (a refetch) or the same parsing extended to it — see the TS-06 note above.
- **Strike-blind legacy caches:** a backtest day slice written before the 2026-08 subtitle fix carries `subtitle=None` and groups strike-blind. Remedied by the documented cache refresh (delete `backtest_cache/archive_days/` and `backtest_cache/live_days/`, then re-run with `--no-cache`) — see the subtitle-drift gotcha below. **Since DR-73 the same blank subtitle also changes WHICH LADDERS EXIST, in BOTH directions**, because DR-69 makes the subtitle the deciding field and `scanner.stated_deadline` cross-checks all three: blanking it moves the decision to the TITLE, so a rung reads a DIFFERENT day rather than none, and it disarms a cross-check the live path applies. Measured on the 2026-09-22 snapshot (113,303 actively-statused markets, 378 live ladder pairs): the blank-subtitle shape flips 649 markets to undated, 53 the other way and **9 to a different day**, and forms 246 ladder pairs — 136 of the live 378 missed AND **4 admitted that the live finder refuses**. A `k̂` measured on such a corpus is therefore not measuring the live ladder population; see `backtester._stated_deadline_dict`'s docstring for the per-ticker evidence, and the plan's "prove the corpus before spending on it" step. (The `event_title` divergence is far smaller and had no pair-level effect at all on that snapshot: 71 markets narrow, 1 wide — `KXACAREPEAL-29-29JAN20` — 0 dated differently, 378 ladders either way.)

**Two rungs of ONE event's deadline ladder are a time-series pair, behind a switch that ships OFF (DR-73, live path 2026-09).** Kalshi lists a question's several deadlines as separate markets inside a SINGLE event — "Will SpaceX launch another Starship before Sep 23, 2026?" and "… by Oct 16, 2026?" are both `KXSPACEXSTARSHIP-14`. Both finders refused every same-event candidate from the first commit on a one-line rationale, "options within a multi-choice event". That is right for an MVE event's option labels and wrong for a dated ladder, whose two rungs are the cumulative-deadline premise itself. `config.TIME_SERIES_SAME_EVENT_LADDERS` (default `False`) admits them; **read that constant's comment before flipping it** — it carries the nesting evidence (0 of 1,821 archive same-event pairs settled in the impossible A=YES/B=NO cell, against 2,872 of 22,080 = 13.01% cross-event), the live funnel, and the measured exposure (on the 2026-09-22 snapshot, 24 pairs → 6 selected trades deploying $9,803.66 = 98% of a $10,000 balance at −31% market-implied EV, four at the `BUDGET_FRACTION` cap, the five largest losing together 12.7% of the time under the model's own probabilities). Eight things are load-bearing.

(1) **A ladder is ordered and tiered on its two STATED deadlines, never on `close_time`.** A settled or single-instant event closes every rung together: in the archive 681 of 1,821 dated same-event pairs have a close gap of ZERO days and 13 are ordered the wrong way round by realized close. The arithmetic is DR-73a's `scanner.stated_deadline` (wording → the last calendar day the deadline includes, cross-checked across the market's own fields) and `scanner.same_event_ladder` (two days → `(swap, gap_days)`, the `SAME_DAY` sentinel, or `None`). **Branch on `is None` / `is SAME_DAY`**: `SAME_DAY` is a non-empty string, so `if ladder:` is true for it and `swap, gap = ladder` would unpack eight characters and raise. (2) **The stated gap travels with the pair and has exactly one reader.** `CandidatePair.stated_gap_days` is the gap that ordered the legs, chose the tier and was checked against `MAX_DEADLINE_GAP_DAYS`; `scanner.pair_gap_days(pair)` returns it when it is a real `int` — by TYPE, since a genuine 0-day gap is falsy and `bool` is not an `int` here, the fail-safe rule `leg_sides` follows — and falls back to `deadline_gap_days`. Both downstream re-derivations of the tier go through it (`_pair_max_sum` and enrichment's `ref_yes is None` fallback; `validate_pair_price` reaches it through `_pair_max_sum`, and no other site re-derives it), pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_pair_ceiling_reads_the_pair_gap`, which asserts the *absence* of a direct `deadline_gap_days` call in both. A missed site re-tiers a one-instant ladder from the 0.70 ceiling to 0.85. (3) **The loop variables were renamed to `m_outer`/`m_inner` and each candidate binds `mA, mB = m_outer, m_inner`.** A ladder may SWAP its legs, and `mA` used to BE the outer loop variable, so an in-place swap would have leaked into every later `m_inner` of that iteration; `find_same_title_pairs` already used fresh locals for exactly this reason. Pinned by `tests/test_scanner.py::TestSameEventDeadlineLadders::test_a_swap_does_not_leak_into_later_candidates`. (4) **The branch keeps its OWN counters** (`ladder_disabled_skips`, `ladder_no_event_skips`, `ladder_identical_wording_skips`, `ladder_snapshot_skips`, `ladder_no_deadline_skips`, `ladder_same_deadline_skips`, `ladder_undated_skips`, `ladder_field_conflict_skips`, `ladder_same_day_skips`, `ladder_gap_cap_skips`, `ladder_price_sum_skips`), each on its own silent-at-zero INFO line, and its gap cap sits INSIDE the branch so `gap_cap_skips` keeps counting exactly the cross-event candidates it counted before. Folding them into the DR-72 counters was measured to move `snapshot_skips` 13,043 → 13,055 and `price_sum_skips` 0 → 2 — precisely the blurring DR-72 had just split apart. `ladder_identical_wording_skips` is the LARGEST single ladder refusal on the 2026-09-22 snapshot (502 of 3,354), so leaving it as a bare `continue` dropped 15% of the branch's input out of the funnel with nothing in the log to reconstruct it from. `ladder_disabled_skips` stays FIRST, ahead of the empty-ticker and identical-wording checks, deliberately: it is the funnel's first arrow (3,354) and an operator must be able to read that number off a switch-OFF log — it says what the switch held back, not that every one of them would have paired. The undated/conflict split is made by re-reading the rung with the cross-check disarmed (`stated_deadline(profile, "", "", "")`, which reads only the three FIELD arguments), so there is no second copy of the reader. (5) **One always-logged line while the switch is on** — "Same-event ladder pairs among the time-series pairs: %d", zero included — because a switch that silently produces nothing must be distinguishable from one that is working and finding nothing (DR-66). (6) **Fails CLOSED at every step**, like the wording rule it sits behind: an empty shared event ticker, identical wording (both now counted on their own lines), a non-cumulative verdict, a deadline that states no placeable day, fields that name irreconcilable days, both rungs naming ONE day, or a stated gap over the cap all refuse the pair. (7) **Admitting is not purely additive.** Both finders keep ONE best pair per group, so a ladder can DISPLACE a cross-event candidate by having the wider `pB − pA` — a diff of two runs' pairs tables is not purely an insertion. No cross-event pair is ever re-priced or re-ordered by this change (verified: with the switch off the 2026-09-22 snapshot replays byte-identically through this tree and its parent, same pair lists and same log lines but for the new disabled-count line, `gap_cap_skips` still 52 and `snapshot_skips` still 13,043; with it on the same replay emits 24 pairs in 24 events, all tradeable). (8) **The deadline the outputs RENDER is still `close_time`.** The prod log's and the dev simulation's "A Deadline"/"B Deadline" columns and `main.print_pairs_table`'s render `market_*.close_time`, which for a ladder is the exchange close rather than the stated deadline the pair was ordered and tiered on — already true of 1 of the 24 (`KXMEDIARELEASEDATEAHS-26`, stated gap 8, close gap 7). That is a reporting gap, not a pricing one: nothing sizes or settles on those cells.

**The backtester mirrors it (DR-73c), and one run can override the switch.** The wording and one-series rules are on both paths precisely so the backtest cannot replay a defect the live path has (see the What NOT To Do bullets); a ladder-enabled LIVE run measured by a backtest that still refused every same-event pair would measure the wrong strategy. **One standing caveat the code already records** (at `_simulate_at_discount`'s one-best dedup): the two paths keep one pair per group by DIFFERENT rules — the live finder ranks tradeable-first then largest `pB − pA`, this one by largest `entry_monthly_ratio` — so they can replay different rungs of the same ladder; on the 2026-09-22 snapshot the live funnel narrows 87 eligible ladder candidates to 24 emitted, so that contest decides 63 of them. **And the setting now reaches the dashboard too, not just `kalshi_backtest.log`**: a later commit (the scenario-explorer PR) added `dashboard._run_settings_html(sweep)`, one line printed under the page's "Period:" header — `Primary spread band: … | same-event ladders: on / off / not recorded` — read straight off `BacktestSweep.same_event_ladders` and `primary.spread_band`, so a ladder-enabled run's dashboard is no longer indistinguishable from a switch-off one and no longer needs hand labelling. Both settings shape the population every section reports on (the ladder switch decides which pairs exist, and the band decides which of them are ever entered — it acts inside `_find_entry`, after pair extraction), so, like DR-66b's strike-blind notice, they belong in the header every section is read beneath, not only inside the scenario explorer. "not recorded" prints rather than a guess whenever the sweep carries no value at all — no sweep (the four-positional `generate_dashboard` call) or a hand-built one. Six things are load-bearing on that side. (a) **`backtester._extract_pairs(groups, *, same_event_ladders=None)` forms ladders in a SEPARATE per-event sub-pass**, not by relaxing the windowed cross-event sweep, which keeps its own `continue` on equal event tickers unchanged — so the two populations cannot overlap and no cross-event pair is re-ordered or re-counted. The buckets carry POSITIONAL indexes into the sorted `dated` list, because `group_profiles` is positional. (b) **The sub-pass is deliberately UNWINDOWED.** The close-date window exists because `_find_entry` caps a CROSS-EVENT pair on its close gap, while a ladder is capped on its STATED gap: in the archive 463 pairs would be admitted on their close gap with a stated gap beyond the cap, and exactly 1 sits the other way — inside the cap on its stated gap while its realized closes are further apart — which a windowed sub-pass would silently drop. Pinned by `tests/test_backtester.py::TestExtractPairsSameEventLadders::test_a_35_day_close_gap_with_a_20_day_stated_gap_is_still_formed`. (c) **It is O(B²) per event bucket, not the sweep's O(N·window)**, and a canary covers ONE runaway bucket: a single same-event bucket past `LARGE_GROUP_WARN_THRESHOLD` logs a WARNING naming the event. Measured bucket sizes (2026-09-22): max 26 on the live snapshot's 113,303 markets (`KXNHLHART-27`; 3,704 same-event candidate pairs in all) — counted over every actively-STATUSED market, which is what `_extract_pairs` sees, where `config.TIME_SERIES_SAME_EVENT_LADDERS`' live funnel quotes 3,354 and max bucket 21 for the same snapshot AFTER the live price filter, so the two pairs of numbers describe two populations rather than disagreeing — max 3 on `live_days/2026-09-08.json.gz` (391,609 records, 6 candidates), max 75 on a strike-blind legacy slice where a blank subtitle collapses a daily strike family onto one key — `archive_days/2026-05-01.json.gz` reaches 615,266 candidates that way. **The canary would stay silent through an exact repeat of that 615,266 figure** (its largest bucket is 75, against a 1,000-member threshold): the AGGREGATE cost is bounded by measurement instead, and it is small — that whole sub-pass costs +0.3 to +0.5 s against a ~19 s switch-off call (measured 2026-09-23), paid only with the switch on. A per-call aggregate guard is the alternative and is deliberately not built. (d) **With the switch OFF the sub-pass does NO pairwise work at all**, not even the bucketing, which is why that 615,266 figure cannot be paid on a switch-off run; the disabled census (`ladder_disabled_skips`) therefore stays LIVE-only, where the memoized profiles make it free. The backtest also has no `ladder_price_sum_skips` — `_extract_pairs` applies no price filter of any kind — and its always-logged line counts CANDIDATES ("Same-event ladder candidates among the time-series candidates: %d") because the one-best contest happens later here, in `_simulate_at_discount`. (e) **`_find_entry` gains a ladder branch gated on the SAME flag, never on `event_ticker` equality alone** — a caller that builds a same-event pair itself must not get ladder semantics from a switched-off tree. It orders and gaps on the stated deadlines and returns `None` when either cannot be read or both name one day, and it classifies PER PAIR: a deliberate, commented exemption from DR-70's once-per-market rule, bounded by the ladder pair count (975 over the whole 284-slice archive at ≤ 30 days, ~12.3 µs each) and impossible to memoize in a function that receives two dicts. `scan_end` and the `max_horizon_days` check still read `close_time` ON PURPOSE: they bound when candles exist and when a market is open, which is an exchange fact about the listing, where the stated deadline is a fact about the question. (f) **The flag rides UNRESOLVED through `_prepare_candidates(..., same_event_ladders=None)` — which hands it to both `_extract_pairs` calls and stores it on the returned `_Candidates` — into every `_entries_for_band` pass's `_find_entry` calls** (`_prepare_entries` composes those two halves directly; `run_backtest_sweep` composes `_prepare_candidates` with `_sweep_from_candidates`, which runs the `_entries_for_band` passes) — one resolution, at call time, and the same one on both sides only while `backtester.TIME_SERIES_SAME_EVENT_LADDERS` is not rebound between the halves (see `_Candidates`); a def-time default would freeze the constant at import and ignore both a monkeypatch and a run-level override. **What that call-time lookup resolves is `backtester.TIME_SERIES_SAME_EVENT_LADDERS`, the module's own by-value binding of the config constant — patching `config.TIME_SERIES_SAME_EVENT_LADDERS` is a silent no-op here, exactly as it is for `scanner`.** It is NOT the `time_series_profit_prob(k=None)` idiom, which works only because that helper lives in `config.py` and reads config's own global: `scanner.py`, `backtester.py` and `backtest.py` each bind this constant at import, so a test or harness patches the MODULE it is exercising (the suite does: `backtester.…` and `backtest.…`, never `config.…`), and a backtest's supported lever needs no patching at all. `run_backtest_sweep(..., same_event_ladders=None)` passes it through and logs the resolved value WITH ITS SOURCE; `run_backtest()` keeps its exact signature and passes nothing, so it reads the config; and `backtest.py --same-event-ladders / --no-same-event-ladders` (`BooleanOptionalAction`, `default=None`, echoed beside `k` in the pre-fetch summary) is how the k̂ the flip gate demands gets measured without flipping the switch — `scanner.py` binds the constant at import, so a backtest override can never reach the live finder. **The AST pin is now both-sided:** `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_apply_the_same_event_ladder_rule` asserts the two `scanner.find_time_series_pairs` calls, the two `backtester._extract_pairs` calls, `_stated_deadline_dict`'s single call to `stated_deadline`, and `_find_entry`'s calls to both helpers. **A ladder-enabled backtest is not comparable to any baseline taken without it** — different pairs, so different trade counts, returns, equity curve and drawdown — and `_simulate_at_discount`'s premise-violation counter can only RISE, never fall. The sub-pass is purely ADDITIVE — no cross-event pair is re-ordered, so none stops violating — and every ladder pair that clears the Kelly gate and settles A=YES/B=NO is a new count. Measured on a 1,506-market archive corpus: switch off 1,490 pairs, switch on 1,898, the off list an exact ordered subsequence of the on list (0 reversed, 0 lost, 408 added), and **0 of those 408 ladder pairs settle the impossible cell** against 207 of the 1,490 cross-event ones (13.89%) — so on that corpus the counter does not move at all.

**Cross-strike time-series pairs — the group key must carry the outcome label (DR-01, fixed 2026-09).** A Kalshi daily price family lists dozens of strikes under ONE market title (event `KXBTCD-26SEP1517`: 80 markets, all titled "Bitcoin price on Sep 15, 2026?", the strike only in the subtitle — "$67,500 or above" … "$87,250 or above"). While the time-series key was `normalize_title(pair_key(m))`, every strike of every deadline in such a family landed in ONE group, and the one-best-pair rule (tradeable first, then largest `pB − pA`) then selected the highest earlier strike against the lowest later one: two different questions sized and traded as one cumulative-deadline pair, with no in-between cell at all. Measured on the 2026-09-15 prod dry run's market snapshot, roughly 974 of 979 tier-qualifying combinations in one BTC group were cross-strike; a second read of that snapshot counted 1,021 of 1,027, the two differing in how the group was delimited rather than in the finding — both are over 99%, and it is the proportion, not the count, that the fix rests on. And **four of the six trades that dry run selected were cross-strike** (a fifth was the same-series pair DR-02 names); the six together were ~98% of the cash balance. No money was lost only because the scheduler daemon has never been started. **The fix is one helper on both paths.** `scanner.time_series_group_key(combined_title, subtitle)` returns `"<normalize_title(pair_key)> | <normalized subtitle>"` (the title alone when the subtitle is empty, `""` when the title itself normalizes away), and BOTH `scanner.find_time_series_pairs` and `backtester._group_by_normalized_title` call it — the latter, since SS-1, through `backtester._ts_group_key`, the backtester's one definition of the key, which `_index_eligible_keys` also reads to decide which records are materialized for grouping at all — pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_group_through_the_shared_key_helper` (a two-link chain on the backtester side), because the backtester previously keyed the same wrong way and therefore reproduced the defect rather than detecting it. Three details are load-bearing. (1) **The subtitle is normalized by `scanner._normalize_subtitle`, NOT `normalize_title`.** That pass strips any bare `20xx` token as a year, and a subtitle is exactly where a bare 4-digit strike ("2050 or above") lives — running it over an outcome label would merge every strike in 2000–2099 into one key, reintroducing DR-01 through the subtitle. `_normalize_subtitle` strips only the unambiguous DATE shapes — `_EXPLICIT_DATE_PATTERNS`, every entry taken BY INDEX from `_DATE_PATTERNS` so a copy can never drift: the month-name / abbreviated-month / numeric / ISO shapes that carry a year, the deadline-anchored month + day shape from detail (2), and the pre-existing bare abbreviated month + day — plus trailing punctuation, so "$80,000 by June 30" and "$80,000 by July 31" are one strike at two deadlines and "Donald Trump" and "Donald Trump." are one option label. Whitespace and punctuation are trimmed in ONE `rstrip`, because a stripped date leaves a space in FRONT of any trailing punctuation ("$80,000 by June 30." → "$80,000 by .") and trimming them in sequence left that space in the key, silently dropping a genuine same-strike pair. (2) **`_DATE_PATTERNS` gained ONE shape — deadline preposition + full month name + day ("by June 30") — placed AHEAD of the `by/before/until/through/after <Month>` clause** — that clause's optional day group only matches when a year follows, so from behind it consumed "by June" and stranded the day, leaving "30" against "31" to split two titles that differ only in their deadline. **It is anchored to the preposition deliberately.** A bare `<Month> <day>` also erases the date from SNAPSHOT titles ("... on June 30"), which would put two snapshot markets of one family into a single time-series group — the shape DR-67 now screens at pair formation on the legs' wording, with the backtester's counter as defence in depth. Anchored, the pattern fires only where that clause already fired and stranded a day, so no title that used to stay apart is merged; the ABBREVIATED spelling ("by Oct 1") is deliberately left behind the clause and still splits, unchanged. `tests/test_scanner.py::TestNormalizeTitle` is the gate CLAUDE.md names for any `_DATE_PATTERNS` change, and it now pins both directions ("by June 30"/"by July 31" merge; "on June 30"/"on July 1" do not). (3) **Non-string subtitles read as absent, never raise** (a `MagicMock` auto-attribute, `None` from an old cache record) — the same fail-safe-by-type rule `leg_sides` and `strategy._depth_levels` follow. **Cache caveat:** backtest day slices written before the 2026-08 subtitle fix carry `subtitle=None`, so a backtest over them still groups time-series candidates by title alone and stays strike-blind; refreshing them is the deletion procedure in the subtitle-drift gotcha below. **And the guard is only as good as the field.** `subtitle` is normalized in at ingest from `subtitle`/`yes_sub_title` (see that same gotcha, which records that the field comes and goes): if BOTH ever go missing again, every market keys with an empty outcome label and the time-series key silently reverts to the pre-fix, strike-blind `normalize_title(pair_key(m))` — with real money on it and no warning of any kind; and when only ONE leg of a genuine pair carries the label, the two legs key apart and the pair is silently dropped (a missed trade, also unlogged). **The live and backtest paths have DIFFERENT symptoms, and the long-standing counter covers only one of them.** `scanner.find_time_series_pairs` — the LIVE finder, and the counter's only home — logs `Distinct normalized title+outcome keys with >= 1 market`; a count collapsing toward the market count, or a time-series pair count dropping to zero, is the symptom to check first on the live path. That is the ONE-leg-labelled case, where the two legs key APART and keys SPLIT. It says nothing about a backtest, for two independent reasons: the backtester never calls that function (it calls `_group_by_normalized_title` directly), and when BOTH legs are unlabelled the keys MERGE instead, so the count moves the other way entirely. `backtester._log_outcome_label_coverage` is the backtest-path signal (DR-66; since SS-1 `_prepare_candidates` runs its two halves, `_OutcomeLabelTally` and `_report_outcome_label_coverage`, directly — see below): an INFO census of `subtitle` and `event_title` coverage over the eligible markets on every run, escalating to a WARNING naming the consequence and the cache-refresh remedy when subtitle coverage falls below `config.BACKTEST_OUTCOME_LABEL_WARN_FRACTION`. It exists because a backtest over a pre-2026-08-14 cache reported pair counts, trades, a return figure and an empirical `k̂` recommendation for `TIME_SERIES_INTERVAL_PROB_DISCOUNT` that all described the strike-blind strategy, while being indistinguishable in its own output from a run on a good cache — measured on the assembled 2026-05-01 cache: 2,344,886 records, 98.14% with a blank subtitle and 87.89% with a blank event title, against ZERO blank subtitles on either post-fix assembled cache. **The DASHBOARD says so too, and that half is DR-66b.** The log alone was not enough: `backtest.py`'s own closing line points the operator at the HTML, and a dashboard generated from a run whose census had logged 0.00% coverage contained none of the strings "subtitle", "coverage", "strike-blind" or "cache" anywhere in its 140 KB, rendering a bare `Pooled empirical k̂` card — a recommendation for the real-money `TIME_SERIES_INTERVAL_PROB_DISCOUNT` — with no caveat of any kind. (A reviewer was fooled by exactly this and reported a pooled `k̂` of 1.114 upstream as a finding about the strategy. "The number is arithmetically correct for the corpus it was handed" is the same defence that would have excused the log silence, and it is not enough.) `_log_outcome_label_coverage` therefore RETURNS the frozen `OutcomeLabelCoverage(total, with_subtitle, with_event_title, subtitle_fraction, event_title_fraction, below_floor, cumulative_markets, snapshot_markets, unknown_deadline_markets)` it just logged — same single pass, same position in `_prepare_candidates` (the first half of `_prepare_entries`), same log wording byte-for-byte (since SS-1 `_prepare_candidates` uses the census's two halves directly: it feeds an `_OutcomeLabelTally` inside its first walk over the corpus and logs through `_report_outcome_label_coverage` at that same position; `_log_outcome_label_coverage` is their one-shot composition and still accepts any iterable, walked exactly once) — which rides out on `_Candidates.label_coverage` onto `BacktestSweep.label_coverage` and into `_section_interval_discount` (`_prepare_entries` also returns it as element 1 of its pair, which `run_backtest` discards). Four things are load-bearing. (1) **A RETURN VALUE, not an optional sink.** An `emit`-style callback (the idiom `_fetch_archive_day` already uses) would have cost zero test edits, but a caller can FORGET it and silently lose the caveat — reproducing DR-66's own failure mode inside the mechanism built to close it. The nine constructions that pass all three explicitly (counted 2026-09-23 by grepping `OutcomeLabelCoverage(` over `kalshi_betting/` and `tests/`): two in `backtester.py` (the empty-corpus branch passes `0, 0, 0` because that IS a measurement, and the main branch reads them off the census); one in `tests/test_backtester.py` (`TestOutcomeLabelCoverageIsCarried::test_the_sweep_carries_the_census`); five in `tests/test_dashboard.py` (the module-level `_coverage` and `_scn_coverage` helpers, `TestOutcomeLabelCoverageIsRendered::test_the_verdict_is_carried_not_recomputed` and `::test_an_empty_corpus_is_not_reported_as_zero_percent`, and `TestDeadlinePhrasingIsRendered._coverage`, whose `**base` dict carries all three); and one in `tests/dashboard_golden.py` (`_coverage`). The banner's consequence sentence is the one claim that legitimately spans both. (4) **`subtitle_fraction`/`event_title_fraction` are `None`, not `0.0`, on an empty corpus** (undefined rather than zero), and the carrier holds scalars only (counts, fractions and one verdict) and no reference to any market dict — enriching it with sample tickers or a per-category breakdown would pin every record alive past `_prepare_candidates`' release of the corpus and the groupable subset and undo TS-07's residency work. Every number rendered is this run's own count or the configured floor; the historical figures above stay in `config.py` and this file, never in an emitted string (TS-07). **Concentration moved too:** the one-best-pair-per-group rule used to bound a whole daily family to ONE pair, and now bounds one STRIKE to one pair, so an N-strike family can contribute up to N pairs — all on the same underlying over the same window, and `strategy.select_portfolio` dedups tickers only, with no per-event or per-family cap. **Sibling (DR-17): the outcome label is now visible.** `scanner.display_title` appends " — <subtitle>" unless the subtitle IS the label already (`market_title` falls back to it when the title is empty), which is what the prod Excel "Market A"/"Market B" cells render; and `main.print_pairs_table` gained its own "Outcome A"/"Outcome B" columns, because `main._truncate` cuts the two title cells at 40 characters and a real `display_title` is well past that — so appending alone would have left the four cross-strike rows of that dry run looking identical, which is exactly why nobody caught them in review. `main._print_portfolio` — the log of the trades actually SELECTED — names both tickers for the same reason: it prints `canonical_title[:55]`, and a time-series canonical title now ends with the outcome label, which that cut drops. **A strike spelled inside the TITLE is a different case and is NOT addressed here** (DR-26, deliberately out of this plan): a `$80k`-shaped strike survives `normalize_title`, so two such markets already key apart, but a bare 4-digit one is eaten by the standalone-year pattern and nothing added here guards that.

**Identical wording across two events of ONE series is two fixtures, not one question (DR-02, DR-54, fixed 2026-09).** A Kalshi event ticker is a series prefix followed by an instance stamp (`KXNPBRFI-26SEP160500FUKORI`, `KXTTELITEMATCH-26SEP101835KKAMOL`, `KXMVECROSSCATEGORY-SHARD1-S6471E4699E9`), so two events of ONE series are two instances of one recurring fixture — two ball games, two 15-minute price windows, two combos of different games. The date lives only in the event ticker, the event sub-title, the close time and the rules text — none of which any grouping key reads — so the `event_ticker` inequality guard both finders already had *passes* on exactly this shape. Identical wording across them is the same question asked about two DIFFERENT events, and neither strategy's premise survives it: the 95% co-resolution prior is simply false (the 2026-09-15 dry run's NPB pair — `KXNPBRFI-26SEP160500FUKORI-Y` and `…150500FUKORI-Y`, identical title, subtitle and event title, closes 24 h apart — was quoted 0.97 and 0.01, and `strategy._kelly_p` priced it at the flat `SAME_TITLE_CO_RESOLVE_PROB` 0.95, sizing 16 contracts a side for $12.39 against a reported "$3.61 profit floor" whose true expected value, on the two markets' own prices with independent games, is negative), and there is no cumulative-deadline premise either, because the deadline lives entirely outside the wording. 71 of that run's 75 same-title rows were this shape. **The rule is fixture identity, not close time.** The sweep's adversary critic measured 117,801 identical-wording NON-combo pairs off the settled cache: they co-resolved 96.3–98.2% of the time in EVERY close-gap band, so no threshold isolates the bad ones (that figure pools both sides of this rule — the same-series pairs it now rejects and the different-series ones it keeps — and it is an UNCONDITIONAL rate, whereas the finder only ever prices a pair the market has already diverged 5% on; treat it as the reason a close-gap gate was rejected, never as a co-resolution estimate for what survives) — while identical-wording COMBO pairs closing within one hour of each other still settled differently 13.8% of the time (an admitted example closed 96 seconds apart and settled yes vs no). A one-hour gate was therefore rejected: it would drop pairs that co-resolve almost always and still admit two matches of one table-tennis player (`KXTTELITEMATCH-26SEP101835KKAMOL` vs `…101810MOLJMI`, about half an hour apart, settled yes and no) and two consecutive 15-minute gas windows. **Both finders carry it, and that is the whole point.** `scanner.find_same_title_pairs` skips a candidate when `_same_series(m_outer, m_inner)` (its group key already guarantees identical wording), counting the skips and reporting them once as `Same-title candidates skipped as two instances of one event series (identical wording, different fixture): N`; `scanner.find_time_series_pairs` skips when `_identical_wording(mA, mB) and _same_series(mA, mB)`. Gating only the same-title finder would have RELABELLED the trade rather than removed it: the same two NPB tickers clear the time-series filter too (`pB − pA` = 0.96, gap 1 day), and `main._dedup_pairs` only ever dropped that copy because a same-title copy existed — 39 of that run's 75 same-title rows would have come back as time-series pairs. `backtester._extract_pairs` mirrors both branches through `_same_series_dicts` / `_identical_wording_dicts`, which derive the prefix from the same `scanner.event_series`, so live and backtest can never disagree about what a series is; all of it is pinned by AST in `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_apply_the_one_series_rule` and `::test_ast_the_series_prefix_has_one_definition`. **`event_series` fails CLOSED.** An empty, hyphen-leading or non-string event ticker yields `""`, and `_same_series` reads an unknown prefix on either side as the SAME series — a pair whose fixture identity cannot be read must not be priced on the co-resolution prior. **What still pairs under THIS rule:** two DIFFERENT series asking one question (the shape the same-title strategy was built for); and any pair of ONE series whose deadline is IN the wording — `KXSOLD-26SEP14` / `KXSOLD-26SEP18` titled "Solana price on Sep 14/18, 2026?", or the FIDE Oct/Nov markets from the same run, make `_identical_wording` false. Note both of those named examples are nonetheless refused as TIME-SERIES pairs by DR-67, on the separate ground that "price on \<date\>" and "top-10 in \<month\>" are snapshot wordings; `tests/test_scanner.py::TestOneEventSeriesIsTwoFixtures` pins both verdicts on the same fixture, so a reader can see which rule decides what. **This rule decides fixture identity only, in both directions.** It does not certify that a dated one-series pair is genuinely CUMULATIVE — "price on <date>" is exactly the SNAPSHOT shape the time-series paragraph above names (SOL ≥ $180 on Sep 14 does not imply SOL ≥ $180 on Sep 18; top-10 in October does not imply top-10 in November). **DR-67 now answers that separately**: the cumulative-deadline rule refuses both of those examples on their wording, so the `KXSOLD` Sep 14/18 pair and the FIDE Oct/Nov pair named above as "what still pairs" are eligible under THIS rule and refused by that one. And different series is a NECESSARY condition for a same-title pair, never a sufficient one: the same prop listed for two different games in two different leagues shares its wording too (`KXBRASILEIROB1HTOTAL-26SEP10VINGGO-1` and `KXUCL1HTOTAL-26SEP10MUNSBH-1`, both "Over 0.5 1H goals scored", settled no and yes), and only the `event_title` component of the same-title key separates them — which live ingest populates but pre-`event_title` cache records leave `""`, so the backtest path pairs them and the live path usually does not. **The accepted cost:** a genuine cumulative-deadline pair of ONE series whose deadline appears *only* in the event ticker — never in the title, subtitle or event title — is dropped along with the recurring fixtures, because at that point nothing in the data the finders read separates the two. That is deliberate, not an oversight: the same-title finder had exactly this ambiguity before and resolved it the other way, with real money on it. **What stops entirely:** every same-title pair between two MVE combo EVENTS. Kalshi lists combos under several series prefixes, all beginning `KXMVE` — a census of `backtest_cache/event_titles.json` (3,996,906 keys, 2,444 distinct prefixes, measured 2026-09-16) found exactly four: `KXMVECROSSCATEGORY` (2,960,840), `KXMVESPORTSMULTIGAMEEXTENDED` (906,157), `KXMVECROSSCATEGORY0` (94,230) and `KXMVENBASINGLEGAME` (61), with no `KXMV*` prefix that is not also `KXMVE*` — so `scanner.event_series` collapses the whole family onto one series (`config.MVE_SERIES_FAMILY_PREFIX = "KXMVE"`, DR-55) and the one-series rule treats any two combo tickets as two instances of one recurring fixture. Reading the literal prefix DID refuse two combos listed under ONE of those prefixes; what it could not see was a pair spanning TWO of them, which read as two different series and was priced on the 0.95 co-resolution prior. That exposure is measured, not assumed: in `backtest_cache/live_days/2026-09-14.json.gz` (9,009,087 records, 8,939,229 of them `KXMVE*`), 10,643 distinct `(event_title, title, subtitle)` wordings appear under TWO literal `KXMVE` prefixes — every one of them `KXMVECROSSCATEGORY` x `KXMVECROSSCATEGORY0` — forming 26,072 cross-prefix market pairs of which 17,829 co-resolved and **8,243 settled DIFFERENTLY, a 68.4% co-resolution rate against the 0.95 prior**. That 68.4% carries the SAME caveat as the 96.3–98.2% above and for the same reason: it is an UNCONDITIONAL rate over every record in each cross-prefix wording class, with no price, liquidity or activity filter, whereas the finder only ever prices a pair the market has already diverged 5% on — treat it as the measured reason the family rule exists, never as a co-resolution estimate for the pairs that would actually have been traded. A FAMILY PREFIX rather than an enumerated allowlist, because enumerating the combo series would BE an allowlist and the codebase's own prior belief ("every combo sits under `KXMVECROSSCATEGORY`") was already such an allowlist with one of the four entries — the artefact that was measurably wrong here — and it rots every time Kalshi adds a combo series (`KXMVENBASINGLEGAME`, 61 keys, appears in no day slice at all yet). Over-collapsing is the safe direction since `_same_series` only ever REFUSES pairs, so its worst case is a missed trade between two genuinely independent `KXMVE*` series, or a still-eligible runner-up promoted where the refused pair was a group's best candidate, never a trade priced on a false premise. The family literal is deliberately narrow — prefix containment among ordinary series is common (`KXART` vs `KXARTISTSTREAMS` are unrelated), so it must never be widened to `KXMV` or to a generic containment rule. That is a pairing rule, not an ingest exclusion, and it is the intended reading of DR-54; if combo duplicates are ever wanted the discriminator is `mve_selected_legs`, which ingest does not carry today. **Backtest impact:** the `Potential pairs` count drops (fewer, correct pairs), `_can_ever_enter` is untouched so there is no `SETTLED_PREFILTER_CACHE_TAG` bump, and any later profiling baseline must be taken after this change. **Skipping is not only subtractive.** Both finders keep ONE best pair per group, so removing a group's top candidate PROMOTES the runner-up: a group whose widest gap was a one-series look-alike can now yield a time-series pair on tickers the previous code never proposed at all (pinned by `tests/test_scanner.py::TestOneEventSeriesIsTwoFixtures::test_skipping_the_widest_candidate_promotes_the_next_one`). That is intended — the promoted pair is the one the group actually supports — but it means this rule can ADD a trade as well as remove one, so a diff of two runs' pairs tables will not be purely a deletion. **Test fixtures moved with the rule:** every synthetic same-title pair a FINDER actually forms was re-pinned onto distinct series — the one-prefix `EVT-A`/`EVT-B` and `EV-A`/`EV-B` fixtures in `tests/test_scanner.py` and `tests/test_backtester.py` became `EVA-1`/`EVB-1` or `EA-1`/`EB-1`, and the eight event tickers in `tests/test_main.py`'s `_build_events` became eight distinct series. Fixtures that only exercise GROUPING, or that build a `CandidatePair` directly without going through a finder (`_st_candidate`, the enrichment and reachability pairs), keep their one-prefix tickers because no finder ever reads them. The synthetic TIME-SERIES fixtures also kept their one-series tickers and had their titles dated instead (`_ts_pair_markets`, both `TestTimeSeriesBestPairPerGroup` groups and `TestTimeSeriesGrouping::test_pricier_earlier_contract_is_not_a_candidate` now spell each market's own close date, the shape a real two-deadline family has) — that last one matters because without the dated titles the one-series rule, not the directional price filter, was what made its assertion pass. No assertion changed in either group.

**`subtitle` is not dependable on a market payload — ingest normalizes `yes_sub_title` into it (2026-08 drift).** Live-verified 2026-08-14: the live `/markets` endpoint, `/events?with_nested_markets=true`, and the signed `/historical/markets` archive ALL served payloads with no `subtitle` key; on 2026-09-15 a verification read observed payloads carrying `subtitle` AND `yes_sub_title`, so the fallback is defence against a field that comes and goes, not the only source. The distinguishing outcome label arrives as `yes_sub_title` (e.g. the candidate names under one shared `title` of "Who will the next Pope be?"), with `no_sub_title` carrying the negated phrasing. This is not cosmetic: `subtitle` is the only intra-title discriminator in BOTH grouping keys — the same-title key `(event_title, title, subtitle)` used by `scanner.find_same_title_pairs()` and `backtester._group_by_exact_title()`, and (since DR-01) the time-series key built by `scanner.time_series_group_key()` for `scanner.find_time_series_pairs()` and `backtester._group_by_normalized_title()`. With every market parsing to `subtitle=""` the key collapsed to `(event_title, title)`, so two **different** outcomes sharing one question title on different event tickers grouped as the *same* contract and were traded under the 95% co-resolution assumption — a real-money false positive (reproduced offline: two distinct papal candidates paired with `tradeable=True`). The fix is at ingest only: `scanner._market_from_dict()` and `historical._market_to_dict()` read `subtitle` with a fallback to `yes_sub_title`, so the `ApiMarket.subtitle` attribute and the `"subtitle"` cache key keep their existing names and shape and no downstream code changed. Use `yes_sub_title`, never `no_sub_title` — the negated phrasing would make the grouping key asymmetric between the YES and NO framings of one outcome. Display fallbacks (`scanner.market_title`, `backtester._pair_key`, the backtester's trade labels) read the now-populated subtitle and silently improve: a title-less market falls back to its outcome label instead of the opaque ticker. **Cache caveat:** backtest day slices written before this fix carry `subtitle=None` and therefore reproduce the pre-fix weakened grouping — this is backtest fidelity only, with no live-money exposure — and `--no-cache` does NOT refresh them (day slices are deliberately reused unconditionally, see the sharded-fetch gotcha). A genuine refresh requires deleting `backtest_cache/archive_days/` and `backtest_cache/live_days/` **and** re-running with `--no-cache` (equivalently, also deleting the assembled `backtest_cache/settled_markets_*.json`) — on a default run the assembled per-`start_date` cache is loaded first and returns before the day slices are ever consulted, so deleting the slices alone changes nothing.

**Backtest fetch uses direct signed GETs — the pinned SDK has NO historical_api module.** `historical.build_historical_client()` returns a plain prod `KalshiClient`; `/historical/cutoff`, `/historical/markets`, `/historical/markets/{ticker}/candlesticks`, and `/events/{ticker}` are reached via `historical._signed_raw_get()` (KalshiAuth signs timestamp+method+path, the SDK's rest client executes) composed with `_http.fetch_json_page()` for status checks and `api_call_with_retry` for backoff. Hard-won facts about the archive endpoint (all live-verified 2026-07-13): (1) it IGNORES every server-side time filter (`min_settled_ts`, `max_settled_ts`, etc. all return the identical page); (2) its page size is hard-capped at 1000 (larger → HTTP 400); (3) it is ordered by **`created_time` DESC, ticker DESC — NOT by settlement time** (settlements interleave hours out of order, and long-lived markets created before a date can settle long after it); (4) its pagination cursor is a urlsafe-base64 **protobuf of the keyset position** (field 1 = Timestamp of `created_time`, field 2 = ticker), which `historical._encode_archive_cursor()` reproduces byte-for-byte — this is what makes sharded parallel fetching possible. The live `/markets` endpoint honors `min_settled_ts` AND `max_settled_ts` server-side (page size also capped at 1000), but does NOT serve pre-cutoff settlements — once markets migrate into the archive they disappear from `/markets` entirely. Candlestick candles now arrive with the dollar string in `yes_ask.close` (the old `close_dollars` field is gone); the parser prefers `close_dollars` when present so both formats read as dollars, never cents.

**`fetch_all_settled_markets()` is sharded, parallel, and incrementally cached — don't serialize it again.** A sequential walk of the settled-market history is tens of millions of records at 1000/page (live-measured 2026-07-13: 95+ minutes for 8,300 pages without finishing). The fetch therefore: (a) runtime-verifies archive cursor synthesis (`_archive_cursor_synthesis_ok` re-encodes page 1's last record and byte-compares against the server cursor); (b) fetches one slice per UTC **created-day** via synthesized cursors across `SETTLED_FETCH_MAX_WORKERS` (config.py, 8) threads, persisting each completed slice to `backtest_cache/archive_days/<day>.json.gz`; (c) walks a sequential **tail** below `created_time == start_date` — the archive is created-ordered, so markets created before start_date can still settle in-window; the old single walk dropped ~28k such markets (verified live) as a page-alignment artifact, and the tail catches them deterministically (its output is a verified strict superset of the old: zero markets lost, extras are all genuinely in-window settlements); (d) sweeps the post-cutoff range as parallel per-**settled-day** windows via `min/max_settled_ts`, persisting fully-elapsed days to `backtest_cache/live_days/`. Any runtime-assumption failure raises `_ShardedFetchUnsupported` and falls back to the original sequential walks (which rely only on documented behavior) — never delete the fallbacks or the runtime checks. **The whole phase is skipped when `start_ts >= cutoff_ts`** (an INFO line says so): the archive holds only pre-cutoff settlements, so no record can satisfy such a window, and proving that by running the cursor-synthesis probe and the tail walk cost ~18 seconds and ~50,000 parsed records on every post-cutoff run. Note the skip also silences the synthesis probe on that path, so such a run reports on cursor synthesis at all (TS-25). **Both archive walks (`_fetch_archive_tail` and the `_fetch_archive_sequential` fallback) stop on a barren-page counter, not on a settlement comparison.** No exact stop rule exists on a created-ordered walk: a market created arbitrarily early can settle in-window, so no page proves deeper pages are unproductive. Both walks used to stop at the first page whose `page[0]` (the newest-*created* record on it, whose settlement time says nothing about the rest of the page) settled before `start_ts` — since most Kalshi markets are short-lived, that fired after one or two pages and silently dropped exactly the long-lived in-window settlers the tail exists to collect (BS-02). They now stop after `ARCHIVE_MAX_BARREN_PAGES` (config.py, 50) **consecutive** pages containing zero in-window settlements — the same productivity bail-out idiom as `EVENT_TITLE_LISTING_MAX_BARREN_PAGES` / `MVE_MAX_EMPTY_PAGES`, ~50k records of created-time depth past the last productive page. The tail walk also has no chunked `emit` sink — the day workers stream into slice files and the live frontier streams through a prefilter-applying in-memory sink (below) — and, unlike the two sequential fallbacks, it applies no prefilter either, so it holds its whole unfiltered result in memory; that is why it carries `ARCHIVE_TAIL_MAX_RECORDS` (config.py, 500k ≈ 1.3 GB) as well. The two caps COMPOSE, whichever binds first: the page cap alone allows 2000 × 1000 × ~`BACKTEST_RECORD_BYTES_ESTIMATE` ≈ 5 GB, the same OOM shape the sharded fetch was rewritten to avoid (BS-15, TS-15). The tail walk (`_fetch_archive_tail`) additionally has a hard backstop, `ARCHIVE_TAIL_MAX_PAGES` (config.py, 2000): a single long-dated in-window settlement resets the barren counter, so without a ceiling the tail could crawl most of created-time history one serial request at a time on every run; hitting it logs a WARNING naming how many pages were walked. Productivity is judged on ANY in-window settlement on the page, deliberately **independent** of the binary-result and created-time keep filters, so a run of all-voided (or, in the tail, day-slice-skipped) pages can't spuriously trip the counter. Don't reintroduce a `page[0]`-based stop, and don't judge productivity on "records kept". The test oracle used to replay the same flawed rule, so the parity tests structurally could not catch this; it is now `_expected_in_window`, a direct predicate over the fixture records (see `tests/test_historical.py`). The cursor-synthesis probe issues a real request, so **any** unexpected exception from it (auth, outage, unparseable body) is wrapped into `_ShardedFetchUnsupported` too — it used to escape the phase and kill the run with no warning logged. Both pool loops call `pool.shutdown(wait=False, cancel_futures=True)` when a worker raises: the executor's `__exit__` would otherwise drain every still-queued day (hundreds of them — hours) before the fallback is even reached. **Progress-line labels are load-bearing for diagnosis:** the sharded and sequential paths emit the same line shape, so they are suffixed `[sharded]`/`[windowed]` vs `[sequential]` — with identical labels (the pre-2026-08-03 state) a log cannot tell you which path a run actually took, and a live run was misdiagnosed exactly that way. Each completed slice also logs `N/M complete` with a rate and ETA; don't drop it, it's the only signal of how far a multi-hour fetch has actually got. Slice-reuse rules are load-bearing: archive day files are stamped with the `cutoff_ts` they were fetched under and are ONLY reused while it matches the current cutoff (a cutoff advance migrates markets archive-ward and OFF the live endpoint, so stale slices would silently miss them); live day files cover immutable fully-elapsed UTC days and are reused unconditionally; the frontier (current) day is always refetched and never persisted. Day slices are deliberately reused even under `--no-cache` (they cannot go stale by construction) — that's what makes refresh runs cheap, and an interrupted fetch resumes at day granularity. **Slice records are never accumulated in memory — not across days, and not within one day.** Each pool worker (`_fetch_and_store_archive_day` / `_fetch_and_store_live_window`) persists its own slice and returns only a count, and each phase then rebuilds its record list by streaming the slices back off disk via `_assemble_day_slices()` — newest day first, which is the ordering the caller's first-wins ticker dedup depends on. Don't "simplify" by having workers return their records and flattening them: that is exactly what OOM'd a full-history run (2.7 GB RSS only 17% through, growing superlinearly with GC pressure), and it also drags gzip/JSON serialization back onto the main thread where it can't overlap. A worker no longer holds a whole day either (BS-15): at 2026-08 volumes one UTC day is ~4.4–4.8M markets, and buffering a day per worker sawtoothed RSS 3.4 → 4.3 → 7.89 GB on a 16 GB host. `_fetch_archive_day` / `_fetch_live_window` therefore take an optional `emit` callback; with it set they flush and drop their buffer every `SETTLED_FETCH_CHUNK_RECORDS` (config.py, 50k — the real bound is that plus the page in flight, since flushes land on page boundaries) and return a COUNT instead of a list. No production caller passes `emit=None` any more (SS-1, fixed 2026-09-24): past-day workers stream into their slice file, and the frontier (never-persisted, partial) day streams through `historical._extend_kept`, a sink that applies the caller's `keep` predicate (the backtester's `_can_ever_enter` prefilter) to each batch as its pages arrive, so only the keep-passing subset of the partial day is ever retained, plus one batch in flight. The frontier used to be accumulated UNFILTERED and filtered only after the whole pool drained — the same records in the same order, but at a peak that grows through the UTC day (1.9M records at 07:30 UTC on 2026-09-24; a full day is up to 9.2M) whatever the window length, and that alone peaked a 7-day backtest at ~5.5 GiB RSS. Don't restore the post-hoc filter. The sink runs on the frontier's worker thread (so `keep` must be thread-safe — `_can_ever_enter` is pure) and the main thread reads the list only after the frontier future's `result()`. `frontier_future.result()` is LOAD-BEARING even though its return value is discarded: it is the only place a frontier-window failure (an exhausted retry, a non-transient error, `keep` raising on the worker) surfaces, and the pool's exit waits for the worker either way, so deleting it returns a silently SHORT frontier instead of raising — pinned by `TestFrontierStreamsThroughKeep`'s failure tests. **What this does NOT bound:** the keep-passing frontier is still held whole, as a list, and its size depends on the WEEKDAY, not on the window's length — `_can_ever_enter` admits every market open over a Monday checkpoint on/after `start_date` that closes at least a day later, so a frontier captured the day after a Monday can be mostly eligible (7,190,452 of the 9,176,306 records settled on Tuesday 2026-09-22 passed `_can_ever_enter(m, 2026-09-17)`). Bounding that means not holding the frontier as a list at all, which the phase cannot do while it returns one materialized list. The list-returning `emit=None` form is retained for direct callers; the sequential fallbacks (`_fetch_archive_sequential`/`_fetch_live_sequential`) are separate walks with no sink that apply the same `keep` per record as each page arrives — exact, because the merge re-applies the prefilter before its first-wins dedup, and their progress lines still count records before `keep` — but still hold their whole keep-passing result; a live-phase fallback first clears the partial frontier, since the sequential sweep refetches today anyway. **Two slice formats exist on disk and both must stay readable:** the legacy single gzipped JSON document `{"meta":…, "markets":[…]}` written by `_day_store_save` (hundreds of MB already cached; refetching them costs hours), and the streamed `"jsonl-v1"` format written by `_DayStreamWriter` — meta line first, then one compact market dict per line, in fetch order (server newest-settled-first, which is what preserves the newest-first assembly / first-wins dedup contract). Both writers are kept: the streaming one for the workers, `_day_store_save` for callers already holding a full list, so neither format rots. `_DayStreamWriter` writes to `<path>.tmp` and only `commit()` renames it into place, same atomicity contract as `_day_store_save` — a killed worker leaves no visible slice. `_day_store_load` routes on file CONTENT (a first line that parses to a dict *without* a `"markets"` key is JSONL), **never on whether a whole-file parse succeeds**: an empty JSONL day is a lone meta line that parses fine as a document, so a parse-success test would misclassify every empty day. It parses JSONL one line at a time and applies the optional `keep` predicate per record (threaded down from `_assemble_day_slices`, and result-identical to filtering afterwards — pinned by the prefilter-equality test), so a multi-million-record day is never materialized unfiltered; any malformed line or meta mismatch fails the WHOLE slice (`None` → refetch). The prescan deliberately loads-and-discards to test slice validity (it passes `_discard_all`, so a streamed slice is fully parsed but nothing is retained), so reused days are decoded twice — minutes against a multi-hour fetch, and the alternative (partial-JSON meta peeking) is far more fragile. **The backtester's candlestick fetch (`backtester._fetch_candles_parallel`) is parallel for the same reasons**, across `CANDLESTICK_FETCH_MAX_WORKERS` (config.py, 8) threads, and uses the identical `pool.shutdown(wait=False, cancel_futures=True)` tear-down. It is safe because candle cache paths are strictly **per ticker**, so two workers can never target one path — `_save_json_cache` writes atomically (tmp+replace, so a truncated file can never become visible), but its tmp name is derived from the destination, so a shared cache path would still collide between workers; never introduce a fetch whose cache path is shared across workers. Reads go through `_load_json_cache`, which treats a corrupt/truncated file as a cache MISS (WARNING + refetch) rather than raising out of a worker. Worker exceptions must **propagate** out of `run_backtest`: `fetch_candlesticks` already fail-softs network errors to `[]` internally, so anything that still raises is a real defect (e.g. a market that should have been prefiltered out — the run_backtest tests rely on exactly that KeyError surfacing) and must not be degraded into "this ticker has no prices".

**The old fetch's multi-minute stalls were client-side memory/GC, not API throttling.** The 2026-07-13 live run showed growing pauses (up to ~14 minutes between page-100 log lines, growing roughly linearly with markets held) with ZERO retry warnings logged and consistent ~0.1–0.3s server latency — the cause was accumulating millions of RAW market payloads (30+ fields plus nested `mve_selected_legs` lists) in one Python list. The rewritten fetch normalizes every record to the compact `_market_to_dict()` form at keep-time and streams day slices to disk. Don't "optimize" by deferring normalization or accumulating raw pages again. The same failure recurred on 2026-08-03 in compact form — the phase functions still held every completed slice in a `results` dict *and* flattened it into a second list — so slices are now dropped as soon as they're persisted and re-read at assembly (see the sharded-fetch gotcha above). If a future run stalls again, check RSS before suspecting the API. **The failure class then moved one phase later, into the grouping/pairing step (TS-07).** `_prepare_candidates` (the first half of both `_prepare_entries` and `run_backtest_sweep`) held the whole eligible window as ONE list and built two group maps and two candidate-pair lists over it — until SS-1 (below), which stopped materializing the records that cannot group. Two measurements exist, both on a 16 GB host and both of the same 1,089,165-record FIVE-DAY window (the cheapest run the tool supports) — and they attribute the cost to two DIFFERENT places, so never quote one as if it explained the other. (1) **2026-09-12, cache MISS:** the fetch assembled the streamed day slices into that list and the recorded peak for the run is **6.05 GiB RSS**; that run predates the `_log_rss()` lines, so its own log carries no RSS line to confirm it — the figure was observed outside the log. (2) **2026-09-13, cache HIT:** `fetch_all_settled_markets` returned at its `use_cache` early return (`Loaded 1089165 settled markets from cache`) and assembled NOTHING; the memory went into `historical._load_json_cache`, which does `json.loads(path.read_text())` over the 1.43 GB assembled `settled_markets_*.json` — logged `Peak RSS before grouping: 3816 MiB` and `Peak RSS after pair extraction: 3977 MiB`, i.e. grouping and pair extraction added only 161 MiB to the high-water mark on that path. **That cache-load cost is a real, separate finding and is deliberately NOT fixed here** (`_load_json_cache` materializes the whole file as one `str` and then every record from it; the fix is a streaming reader). The window is instrumented rather than invisible: `backtester._log_rss()` logs peak RSS in MiB (normalizing `ru_maxrss`, which is BYTES on macOS and KILOBYTES on Linux) at `before grouping` and `after pair extraction`. The `before grouping` line is logged **before** the RAM-budget warning so the two read in causal order: the RSS line is what the fetch or cache load — and, since SS-1, the two passes over the corpus — has ALREADY cost, and the warning (fired when the GROUPABLE subset exceeds `BACKTEST_MARKETS_RAM_WARN`; it counted every eligible market before SS-1) names that subset's share of it and what grouping adds on top. Two rules on that warning: it must not claim to precede the spend — by the time it fires every record it counts is already resident, which is why it counts the groupable records (what stays resident from the warning onward: the corpus is released just before it) and not the eligible ones — and it must print **only the running process's own numbers**, never a figure from another run, because nothing will ever prompt a reader to refresh a measurement baked into a string emitted on every run; the historical figures above belong in `config.py`'s comment and in this file, and nowhere else. `BACKTEST_RECORD_BYTES_ESTIMATE` (2,700) is the PARSED footprint of one cached record — what the list of dicts costs in memory — not its size on disk and not a peak-RSS predictor, since peak also covers whatever transients are live alongside it (the decoded JSON string on the cache-hit path; the group maps and pair lists during pairing). Two measurements on the real 2026-09-07 assembled cache bracket it: ~3.0 KB/record allocated when 195,038 sampled records are decoded under `tracemalloc`, and no more than ~2.4 KB/record resident once that 1.43 GB decoded string is subtracted from the 3,816 MiB pre-grouping peak — so it stays a round estimate between the two. The corpus (`markets`) and the first pass's key index are `del`'d right after the second pass, before any group map exists, and `ts_groups`, `same_groups` and `groupable` in ONE statement as soon as the pair lists are built, before the candlestick pool spawns its threads: nothing below reads any of them, and dropping the group maps ALONE frees no record dicts at all, because `groupable` still references every one of them. That release lowers RESIDENCY across grouping, the candlestick fetch and the `_find_entry` sweep; it does **not** lower peak RSS, which is a high-water mark already reached by that point. All of it is advisory — nothing is capped or dropped. **Known residual of that re-pointing:** while the corpus is a list (always, until it streams), every eligible record WAS resident up to its release and the `before grouping` RSS line includes all of them, yet the warning does not count them — so a run whose eligible count is far above the threshold but whose groupable count is not (the 7-day window below: 7,260,952 eligible, 184,255 groupable) gets no warning for the list that set its peak; the eligible count is still on the `Eligibility prefilter` and `Groupable subset` lines, and the cost on the RSS line. **SS-1 (2026-09-24): only the groupable eligible records are grouped, and `_prepare_candidates` builds no eligible list of its own.** A 7-day window (`--start-date 2026-09-17`) found 7,260,952 of 18,061,549 fetched past-day records eligible (99.75% of them MVE combos) at a measured 3,926 B/record under `tracemalloc` — ~28 GB for the eligible list alone — yet both grouping functions drop every single-member group, and only 184,255 of those records share a time-series OR same-title key with another eligible record; the rest can never appear in any pair of either type. `_prepare_candidates` therefore walks the corpus TWICE, treating it as any re-iterable of market dicts. **What SS-1 does NOT remove is the corpus itself:** `fetch_all_settled_markets` still returns ONE list, and because the prefilter is applied during its assembly that list IS the eligible set — resident through both walks until `del markets`, and on that window alone ~28 GB, so the window still cannot fit while the corpus is a list. What SS-1 removes is the second, filtered copy the old code built and the grouping over every eligible record; the passes are written for any corpus that re-iterates identically, fresh dicts per walk included, so a streaming corpus can replace the list without touching `_prepare_candidates`. Pass 1, `_index_eligible_keys`, counts every record (the `Total settled markets to analyze` figure), applies `_can_ever_enter`, feeds the outcome-label census (an `_OutcomeLabelTally`, so the census costs no pass of its own), and appends `hash()` of each eligible record's two keys to `array('q')` buffers with validity flags — about 27 B per eligible record while the walk runs (187 MiB at 7,260,952 eligible records, measured on synthetic keys, 2026-09-24), plus a transient of about 74 B per record (515 MiB at that count) while `_shared_key_mask`'s `np.unique` computes the keep flags: small beside the records it stands in for, but not "a few bytes" — through `_ts_group_key`/`_st_group_key`, the SAME single definitions `_group_by_normalized_title`/`_group_by_exact_title` now group on (AST-pinned in `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_group_through_the_shared_key_helper`, which is a two-link chain since this change). `_shared_key_mask` (numpy) flags a hash that occurs at least twice among VALID keys of its kind. **Hashing is safe in exactly the direction that matters:** equal keys always hash equal, so a shared key is always kept, and a 64-bit collision can only keep an EXTRA record, which the exact grouping then drops as the singleton it is — results never move (pinned by forcing every hash to collide). Pass 2, `_materialize_groupable`, re-applies `_can_ever_enter` and keeps the flagged records BY POSITION among eligible records — the normalize_title-dominated keys are never recomputed for the records it drops — and **raises `RuntimeError`** if the corpus did not re-iterate identically in anything the mask was chosen from: a different eligible count, or at any eligible position a different `_corpus_identity` — one hash over the ticker and every field either grouping key reads (`event_title`, `title`, `subtitle`) — so a same-count reorder, or a grouping field changed between walks under unchanged tickers, is refused rather than silently misaligning the mask. No other field is compared, because none can change which records are grouped; eligibility is re-applied by pass 2 itself. Every member of every group of two or more is kept, in its original relative order, so the group maps (keys, members, member order, insertion order), both pair lists, the census and every reported number are exactly those of grouping the whole eligible list; the census still logs from its old position through `_report_outcome_label_coverage`, after the RAM warning. Log lines are unchanged in text and relative order except one new INFO line after pass 2 (`Groupable subset: materializing %d of %d eligible markets — ...`) and the reworded RAM warning (`%d groupable markets (of %d eligible) are materialized for grouping: ...`). Not changed: `_can_ever_enter`, both grouping keys, pairing, Kelly, fees and `SETTLED_PREFILTER_CACHE_TAG`. The per-eligible-record cost is unchanged too — pass 1 computes each key once, exactly as the old full-list grouping did — so a long window's pass 1 is as silent as its old grouping step was. **Pruning each market dict to the keys the backtester actually reads is a specified but UNLANDED follow-up**, deliberately gated on a profiling measurement (accept only if peak RSS ≤ 3 GB and the `Potential pairs` counts are byte-identical on the same assembled cache); don't land a pruning diff without it.

**The live-sweep `min_settled_ts` must track `start_date`, not just `cutoff_ts` (fixed 2026-07-13).** `fetch_all_settled_markets()`'s live phase used to always pass `min_settled_ts=cutoff_ts` — correct for the common case (`start_date` far in the past, e.g. the default `2024-01-01`, where the archive already covers everything before `cutoff_ts` anyway), but catastrophic for a narrow recent `start_date`: live-verified 2026-07-13, requesting the last 7 days scanned 20k+ pages (20M+ records) over ~5 hours because the server was asked for everything since `cutoff_ts` (which can trail `now` by a long way) and the existing client-side `settle_epoch < start_ts` check just silently discarded almost every page. Since the live endpoint DOES honor `min_settled_ts` server-side, the fix is `min_settled_ts=max(cutoff_ts, start_ts)` — strictly narrows the server-side window (never widens it, so it can't skip markets the client-side filter wasn't already going to drop) and collapses a multi-hour scan to a bounded one for recent windows. Don't revert to a bare `cutoff_ts` — that reintroduces the unbounded scan for any caller that passes a recent `start_date` (e.g. a quick verification run or a future `--recent-only` mode). In the windowed live sweep this bound survives as the floor of the settled-day windows at the **phase** level: `live_min_ts = max(cutoff_ts, start_ts)` is computed once and never goes below that bound. The *per-window* `min_settled_ts` the server actually sees can be up to 86,399s below it, though — the first window rounds `live_min_ts` down to UTC midnight (`first_lo = live_min_ts - (live_min_ts % _DAY_SECONDS)`) so windows align on day boundaries. This is harmless: the live endpoint serves nothing before the archive cutoff regardless of what `min_settled_ts` asks for, and the client-side `_merge` step still drops any record with `settle < start_ts`. The existing tests use a midnight cutoff, so they cannot observe the rounding; don't read "tests assert the minimum" as proof the per-window value never dips below `max(cutoff_ts, start_ts)`.

**`KalshiClient` monkey-patch pattern:** The SDK does NOT accept `api_key_id` or `private_key_pem` as constructor parameters. They must be set as attributes on the `Configuration` object:
```python
cfg = Configuration(host=url)
cfg.api_key_id = key_id        # detected by hasattr() inside SDK
cfg.private_key_pem = pem_text
client = KalshiClient(configuration=cfg)
```
Do not "fix" this by moving them to the constructor — it will break silently.

**Fee ceiling rounding at small `n`:** `fee_leg_exact(1, 0.5)` = `ceil(0.07 * 1 * 0.5 * 0.5 * 100) / 100` = `ceil(1.75) / 100` = `$0.02`. At `n=1`, fees round up aggressively. The exact payoff check `min_payoff > 0` in `compute_trade()` (`min_payoff` is the profit floor for a same-title pair and the profit in either WIN cell for a time-series pair — the in-between cell loses `total_cost_with_fees`) catches this and returns `None` — this is intentional, not a bug. Also: `fee_leg_exact()` rounds to 6 decimals *before* the ceiling so binary float noise (e.g. `175.00000000000003`) can't bump an exact-cent fee up an extra cent — don't remove the `round()`.

**Ambiguity is resolved by position DELTA, never by absolute holdings.** An exception from `create_order` doesn't prove rejection (a timeout can land after the fill), so `_execute_one` consults the account — but the account's *absolute* position in a ticker is not evidence about a specific order: it may already hold contracts from an earlier run or a manual trade. `_execute_one` therefore reads `_position_count()` immediately **before** each submission (the NO leg's ticker first, then the YES leg's) and again after an ambiguous one, and attributes only `_fill_delta(before, after)` — expected `−no_leg.count` for the NO leg and `+yes_leg.count` for the YES leg. The old absolute checks were wrong in both directions: a stale external YES holding made an unfilled YES leg report `"executed"` (leaving the NO leg unhedged while the log claimed a complete pair), and a stale external NO holding made an unfilled NO leg trigger a `reduce_only` sell that liquidated an unrelated position. Compare deltas with `trader._DELTA_EPS` (`1e-6`) — fills are whole contracts, but `position_fp` arrives as a string and is float-parsed. Never reintroduce a bare `held == 0` / `if held:` test. **A delta of ZERO is not, by itself, a confirmed non-fill (DR-63/DR-64).** That rule is about which QUANTITY is evidence — the delta, never the absolute holding — and it is unchanged; what one un-refreshed read cannot establish is that the quantity has stopped moving. A transport error (the `urllib3.ProtocolError`/`ConnectionError`/`ReadTimeoutError` classes `_http._TRANSIENT_NETWORK_ERRORS` lists) can be raised milliseconds after the exchange FILLED the order, and the positions ledger is read-after-write lagged, so the first post-failure read returns the pre-fill value and `delta == 0`. On the YES leg that sent the reduce-only unwind of a NO leg that was really hedging a live YES fill — selling the hedge, leaving a naked YES position, and reporting `"rolled_back"`, which means flat; on the NO leg it returned `"failed"` ("nothing to unwind") with a full-size UNHEDGED NO position open and no status in `EXIT_TRADES_NEED_ATTENTION` to escalate it, so the run exited 0. Each ambiguous branch therefore re-reads its own ticker ONCE after `trader._V2_MAPPING_RECHECK_DELAY_SECONDS` and judges the RE-READ — the same reasoning `_confirm_v2_no_mapping` already applies (DR-21) and `v2_probe` applies twice over (DR-60, DR-20). An unreadable re-read is the existing unattributable case, i.e. `manual_review` with no order submitted. The NO leg's re-read is SINGLE-SHOT (`_position_count_once`) because it sits in the unhedged window; the YES leg's is the ordinary retried `_position_count`, matching the first read beside it. Both re-reads, like both first reads, stay OUTSIDE the `except` clause for the `__context__` reason above.

**`TradeResult.status` vocabulary** (the legs below are the SUBMISSION legs from `trader._ordered_legs(spec)` — the NO leg first, then the YES leg; which market each sits on depends on the pair type): `"executed"` (both legs filled, or the YES leg errored but the position delta was exactly `+yes_leg.count`), `"simulated"` (dry run), `"failed"` (the NO leg confirmed unfilled — a clean FoK rejection, or an error with a delta of 0 **on both the first read and the lag re-read**, DR-64; nothing to unwind), `"rolled_back"` (the YES leg confirmed unfilled — FoK rejection, or an error with a delta of 0 **on both readings**, DR-63 — and the NO leg's unwind FoK filled), `"rollback_failed"` (unwind did not fill — orphaned position), `"manual_review"` (a leg errored and its outcome could NOT be attributed to this order — either position lookup failed, or the position moved by an amount the order can't explain — or, on the V2 path, the NO-leg mapping was disproven by `_confirm_v2_no_mapping` after a confirmed NO-leg fill). `manual_review` submits no order at all — on the YES leg because unwinding could reverse a real fill, on the NO leg because a `reduce_only` sell against a position this order may not own would liquidate an unrelated holding, and on a disproven V2 mapping because the unwind rests on the very hypothesis just disproven (the YES leg is left unsubmitted and the NO leg deliberately left in place). The error strings say "NO leg"/"YES leg" (the ambiguous-but-confirmed YES-leg case keeps the word "ambiguous"), and the prod Excel row's Notes cell is prefixed `[<pair_type>: <SIDE_A> A / <SIDE_B> B[ nB=…]] ` so a row can be read without knowing which pair type it came from. Don't "simplify" `manual_review` into an automatic rollback in either leg.

**FoK price protection:** Every buy leg must be capped so it fills at or below the scanned price plus a small allowance, or not at all. On the **V2 path (default)** there is no "market" order type: a taker order is a marketable fill-or-kill LIMIT, and **the limit price IS the price protection** — `trader._v2_limit_price(leg_kind, scanned_price_dollars, market)` (`leg_kind` is `"buy_yes"`/`"buy_no"`; the scanned price is the leg's `_Leg.price_dollars` — `nA`/`pB` for same-title, `pA`/`nB` for time-series) computes it as the scanned price ceiled onto the market's own tick grid (`scanner.tick_size_for_price()`) plus `BUY_SLIPPAGE_TICKS` ticks, and the buy-NO leg sends the complement `1 − cap` as an ask. The scanned price is **quantized to 6 decimals (`trader._SCANNED_PRICE_QUANTUM`) before that ceiling**, the same round-before-ceil guard the legacy cap and `fee_leg_exact()` apply: every scanned ask level is `1.0 − float(bid)` and 20 of the 99 whole-cent complements land one ULP *above* the exact cent (`1.0 - 0.43 = 0.5700000000000001`), which un-quantized ceils a whole extra tick and hands the FoK limit two ticks of tolerance where one was configured. No Kalshi grid point has a 7th decimal, so the quantize can only remove float noise — it tightens or keeps the cap, never loosens it (TS-03). The final price is then **re-quantized (ceiling) onto the grid of the band that actually contains it** — the cap can step up into a coarser band, or be mirrored across the book by the complement, where the scanned band's grid is no longer valid — and clamped one tick inside the open unit interval on this market's own grid (0.99/0.01 on a cent market, not the finest-grid 0.9999/0.0001). Ceiling is chosen because a floor could round a YES cap BELOW the scanned price and make the order structurally unfillable. It is **not** purely protective, and this file used to claim it was: when the final price lands in a COARSER band than the one it was computed on, ceiling moves it AWAY from the scanned price and LOOSENS the cap by up to one destination-band tick (reachable: scanned 0.10 on `tapered_deci_cent` submits 0.11 where 0.101 was intended). That residual is bounded by one tick, is the accepted cost of keeping the order fillable, and is recorded as its own open finding — distinct from TS-10, which fixed the other half by making `tick_size_for_price` resolve a boundary price to the FINEST containing band instead of the first one. On the **legacy path** (`ORDER_API_VERSION="legacy"`) the cap is `buy_max_cost` = `count × (scanned price + BUY_MAX_COST_SLIPPAGE_CENTS)` (`trader._buy_max_cost_cents(leg.count, leg.price_dollars)`); that constant applies to the legacy path only, and `_buy_max_cost_cents()` rounds the price product to 6 decimals *before* the ceiling (the `fee_leg_exact()` idiom) so binary float noise — `7 * 0.07 * 100 = 49.000000000000006` — can't ceil the cap a cent looser; this only ever tightens it. Any new order-building code must carry the cap appropriate to its path.


**Order-book LEVELS and MARKET eligibility use different price bounds, and must keep doing so (TS-14).** `scanner._bids_to_ask_levels` drops a level whose complement falls outside `config.MIN_ACTIVE_PRICE_DOLLARS`/`MAX_ACTIVE_PRICE_DOLLARS` (`0.0001`/`0.9999`) — the extreme tradeable levels on Kalshi's FINEST grid. It used to use the 0.01/0.99 MARKET-eligibility bound instead, which silently discarded genuine depth on exactly the regimes whose point is sub-cent ticks: on a `deci_cent` or `center_deci_edge_centi_cent` book, every level under a cent or over 99c vanished before pairing, so a full book reached the sizer as a thin one. The drops are now counted and reported as one summary WARNING per book naming the ticker and the count (silent at zero) — the same idiom as the trading-inactive shard skip count — because invisible drops read downstream as genuinely thin depth. **`scanner._MIN_ACTIVE_PRICE`/`_MAX_ACTIVE_PRICE` (0.01/0.99) did NOT move and must not be unified with the level bound**: they answer a different question — "is this MARKET worth trading at all" — where a sub-cent YES ask means a near-settled market, and widening them would turn a 0.9999 quote into a $0.0001 hedge leg. `backtester.py`'s two mirrors of that market bound stay in step with it for the same reason. Widening the market half is a recorded, deliberately-held operator decision, not an oversight.
**The rollback carries the same kind of protection on the unwind side, on BOTH paths.** Neither unwind may ever be an unpriced order: the legacy `CreateOrderRequest` has no proceeds floor for `type="market"`, and V2 has no market type at all, so a book that collapsed between the NO leg's fill and the unwind would realize an unbounded loss. One bound, two expressions — `trader._rollback_floor_cents(no_leg)` is the NO leg's scanned entry (`no_leg.price_dollars`: `nA` for same-title, `nB` for time-series — the depth-weighted fill after enrichment) less `ROLLBACK_MAX_LOSS_CENTS_PER_CONTRACT` (12), clamped into the API's valid `1..99` cent range, with `round()` applied *before* `int()` because that price is a cent-quantized book price carried as a float (`0.57 → 56.99999999999999`, which `int()` would truncate to 56):
- **legacy** — a *floored* FoK **limit** sell (`type="limit"`, `no_price=_rollback_floor_cents(no_leg)`, `reduce_only`, on `no_leg.market.ticker` for `no_leg.count` contracts — the body is built inline in `_build_rollback_order_any`), never `type="market"`.
- **V2** — a reduce-only YES **bid** (a held NO is a short YES, so closing it is a buy-back), so the same bound is a bid **CEILING** of `1 − floor/100`. `trader._v2_rollback_price(no_leg)` **ceiling**-quantizes that cap onto the grid of the band containing it and then clamps it by `_v2_top_of_grid_price(no_leg.market)` (`V2_ROLLBACK_BID_PRICE_DOLLARS` floored onto its own band — 0.99 / 0.999 / 0.9999 by regime; `v2_probe`'s unfillable-ask step submits at exactly that level, and so does its no-mapping step's closing bid — the probe overrides the loss-floored price precisely because it is verifying a side, not a price). The ceiling direction here is deliberate and is the OPPOSITE trade-off from the buy legs: it loosens the loss bound by strictly under one destination-band tick, because a floor-quantized off-grid cap would sit below every valid level in its band and structurally kill every off-grid unwind — the orphaned-position failure this path exists to prevent.

A book past the bound kills the unwind on either path, leaving the NO-leg position open — reported as `status="rollback_failed"` for manual review (`_rollback_no_leg(client, spec, no_leg, reason)`'s ORPHANED POSITION alerts name `no_leg.market.ticker` and `no_leg.count`, so a time-series rollback failure names `market_b`, not `market_a`), exactly the path an unfilled market unwind already took, so the caller's contract is unchanged and only the loss is now bounded. Don't "simplify" either unwind back to an unpriced (or flat top-of-grid) order.

**Backtest cache semantics:** `fetch_all_settled_markets()` and `fetch_candlesticks()` always persist a fresh fetch to disk even when `use_cache=False`, so `--no-cache` refreshes what the next default run loads. `use_cache` gates only the assembled per-start_date `settled_markets_*.json` file; the per-day slice stores under `backtest_cache/archive_days/` and `backtest_cache/live_days/` are consulted regardless (see the sharded-fetch gotcha for why they can't go stale). The assembled file is named `settled_markets_<start_date>[_<prefilter_tag>][_nomve].json`, and every component of that name is part of the RESULT's identity. When a `prefilter` is passed, the tag is appended — a prefiltered result is a strict subset, so it must never be served to an unfiltered caller or to one using different filter semantics. **`INCLUDE_MVE_MARKETS=False` appends `_nomve` (DR-57).** The flag changes WHAT IS FETCHED, not just how markets are grouped: it adds `mve_filter="exclude"` to the archive query and to every live page (three sites in `historical.py`), so an unkeyed cache served an MVE-INCLUSIVE assembly to a run configured to exclude MVE, and vice versa — severe in practice because ~99.7% of the assembled cache is MVE combo markets, so an `INCLUDE_MVE_MARKETS=False` run analysed an almost entirely MVE corpus while believing it had excluded them, with nothing abnormal in the output. **Only the False case is marked, deliberately:** every assembled cache currently on disk was built with MVE included (there is a 3.27 GB one), so the default `True` filename stays byte-identical to the pre-DR-57 name and no existing cache is orphaned into a multi-hour refetch — don't "tidy" this into a symmetric `_mve`/`_nomve` pair. The per-day slice stores need no such marker: their meta already carries `include_mve`, so a flag flip invalidates them on the existing meta check — at the cost of refetching and OVERWRITING every slice on each flip, since the slice PATHS themselves are not flag-keyed (before DR-57 the assembled-cache hit masked this, so a flip never reached the slices at all; now a flipped run re-pays the day fetch, and so does the next run that flips back and misses its assembled cache). `_prepare_candidates()` (the band- and k-independent prologue shared by `run_backtest()`, through `_prepare_entries()`, and `run_backtest_sweep()`) passes `config.SETTLED_PREFILTER_CACHE_TAG`, which names `backtester._can_ever_enter`'s semantics: **bump the tag whenever that predicate changes**, or a stale prefiltered cache is silently reused. `prefilter` and `prefilter_tag` must be passed together (`ValueError` otherwise) precisely so an untagged filtered cache can't exist. Candlestick cache files are tagged with the `[open_ts, close_ts]` window AND the `period_interval` they cover — a cache whose window starts later than the request (one built for a later `--start-date`) is not reused for an earlier one, while a market that opened after both start dates is requested from its own open (`backtester._candle_window_open`) under either and reuses its cache, and a cache built under a different granularity (e.g. an old pre-hourly daily cache) is not silently reused as if it matched the current `CANDLESTICK_PERIOD_INTERVAL_MINUTES`. Old caches from before this tag existed migrate automatically on the next fetch, same as the legacy bare-list format. **`event_titles.json` is a cross-run accumulator, is written as a MERGE, and is RETURNED as one, so `--no-cache` no longer wipes it OR discards it:** `_load_or_build_event_titles` always reads the disk map (even when `use_cache=False`, which still starts resolution empty so this run's tickers are genuinely re-fetched), then at save time preserves disk entries, lets a fresh non-empty title win, and never lets a fresh `""` (the poison pill from a failed lookup or the fallback cap) clobber a non-empty disk title — while a fresh `""` for a ticker disk has never seen is still stored, keeping poison-pill semantics. **The RETURN is that merged view restricted to the caller's tickers** (`{tkr: merged.get(tkr, "") for tkr in event_tickers}`), not this run's resolution alone. Returning `cached` discarded the accumulator at the last step: under `--no-cache` every ticker the listings missed and the `EVENT_TITLE_FALLBACK_MAX_LOOKUPS` cap skipped came back as the `""` pill even though disk held a real title — 771,601 unresolved against a 5,000 cap, so ~99% of stragglers. Those markets then group by market title alone, collapsing `(event_title, title, subtitle)` toward the bare title (measured: 52 groups with titles vs 133, largest 112, without), which is the direction that manufactures cross-event false positives under the 95% co-resolution prior (TS-11). Restricted to the requested tickers because the accumulator holds every ticker every past run ever resolved; a caller asking about forty must not receive eight hundred thousand.

**The Monday-feasibility pre-check measures its window in UTC.** `_prepare_candidates` decides whether any 09:00 **UTC** entry checkpoint exists in `[start_date, today]`, and `today` is `datetime.now(UTC).date()` — never `date.today()`, which is LOCAL. West of UTC the local date lags for the first hours of each UTC day (7 of every 24 on a PDT host), so a window whose only Monday IS the current UTC day short-circuited to zero trades and reported the run as structurally impossible when it was not (TS-13). `_build_equity_curve` already used UTC for the same reason; `backtest.py`'s "Period:" line and `dashboard.py`'s rendered period follow, or they print a span the run did not simulate. Tests freeze `backtester.datetime.now(tz)`, not `backtester.date.today()` — the seam moved with the fix.

**Backtest windows must start BEFORE the archive cutoff or they find zero trades by construction.** Live-era (post-cutoff) markets 404 on `/historical/markets/{ticker}/candlesticks` — verified live 2026-08-03: a `--start-date` after the cutoff (then 2026-06-04) produced 404s for every one of its pair tickers, so `_find_entry()` saw no candles for either leg and the run could never have entered a trade, no matter how many pairs were extracted. A near-zero trade count on a recent window is this, not a strategy result. The window always runs from `--start-date` to today, so even a correctly-chosen pre-cutoff start still has a post-cutoff tail whose 404s are unavoidable; those failures are deliberately NOT cached (a poisoned cache would silence a ticker forever, including after its data migrates into the archive), so they are re-paid on every run — just in parallel now. **Because they are re-paid every run, each one must be cheap to log (TS-02).** `historical.fetch_candlesticks` logs a failure as ONE line — `HTTP <status> <reason>` via `historical._exception_summary()`, never the SDK's `ApiException.__str__`, which emits the status, the reason, the ENTIRE HTTP header dict and the body across five lines (~900 bytes) and whose own first line is only `(404)`. `backtester._fetch_candles_parallel` then reports the per-run count once, just before it returns: `N of M tickers returned no candles`, counted off the RESULT dict (there is no exception to count — `fetch_candlesticks` already fail-softs to `[]`) and deliberately outside its `if work:` block so tickers resolved to `[]` for a missing/unparseable `close_time` are included, silent at zero. `historical._lookup_one`'s event-title failure takes the identical one-line treatment, for the same reason: it fires once per unresolved ticker, up to `EVENT_TITLE_FALLBACK_MAX_LOOKUPS` of them. Don't log an SDK exception whole on any per-ticker path — one ordinary backtest emitted hundreds of MB into `kalshi_backtest.log`'s 20 MB × 3 rotation, 99.5% of the file was that single warning, and the rotation evicted ~419 MB of history including the shard census, prefilter counts and calibration table the same runs had written.

**Daily candlesticks silently produced zero data for most markets — use hourly.** `historical.fetch_candlesticks()` requests `period_interval=CANDLESTICK_PERIOD_INTERVAL_MINUTES` (60, hourly), not daily (1440). Confirmed 2026-07 by direct API testing: `/historical/markets/{ticker}/candlesticks` with `period_interval=1440` only emits a bar for a market whose lifespan crosses a UTC midnight boundary — a market open for 2 hours entirely within one day returned 0 daily candles but 2 hourly candles for the same window. Most Kalshi markets are single-game/few-hour windows within one calendar day, so daily granularity structurally produced zero price data for most markets regardless of liquidity or age, which is why backtest runs kept finding 0 trades even after the pair-extraction logic itself was verified correct. `period_interval=1` (minute) returns HTTP 400 — hourly is the finest granularity actually available. `_candle_at_or_before()` and `_monday_timestamps()` in `backtester.py` are granularity-agnostic (they just scan sorted candles for the latest one at-or-before a timestamp), so switching interval required no change to the entry-detection logic — only the fetch call and the cache tag. Candles are fetched in parallel across tickers (`backtester._fetch_candles_parallel`, `CANDLESTICK_FETCH_MAX_WORKERS`); each worker still paces its own pages with `fetch_candlesticks`'s unchanged `rate_limit_sleep` default (0.15s), so the per-connection rate is the same as before — only the number of connections changed.

**Backtester pair-extraction eligibility prefilter — don't remove it.** At current Kalshi volumes, normalized-title groups can collapse tens of thousands of hourly/intraday markets into one group (a live measurement found a 53k-member hourly-crypto group in a 3-month window), making the naive O(n²) pairing in `_extract_pairs()` infeasible (500B+ iterations observed, hung for over an hour). `_prepare_candidates()` (shared by `run_backtest()`, through `_prepare_entries()`, and `run_backtest_sweep()`) filters `markets` through `backtester._can_ever_enter(m, start_date)` before either grouping call: `_find_entry()` can only open a trade at a Monday-09:00-UTC checkpoint in `[start_date, min(close_a, close_b) − 1 day]` and needs an hourly candle at-or-before that Monday for both legs (i.e. each market must have opened by then) — so a market whose own `[open_time, close_time − 1 day]` window contains no Monday on/after `start_date` can never appear in any entered pair, as either leg, in either pair type, and can be safely dropped before grouping. `open_time` is carried through `historical._market_to_dict()`; **cache files written before this field existed have no `open_time` and read back as `None`**, and `_can_ever_enter()` treats a missing/unparseable `open_time` or `close_time` as "can't prove ineligibility" (keeps the market, no speedup) rather than risking an incorrect drop — re-run with `--no-cache` to unlock the speedup on old caches. The same predicate is ALSO handed to `fetch_all_settled_markets(prefilter=...)` so ineligible records are dropped during assembly instead of being materialized and cached first — at full-MVE volumes the unfiltered list is the difference between a working run and an OOM, and it also shrinks the `_load_or_build_event_titles` ticker set from runaway to bounded. This is result-neutral by construction (filtering during an order-preserving merge yields the same subsequence as filtering afterwards; `test_prefilter_assembly_equals_postfilter` asserts exact list equality), and the day-slice FILES stay complete and unfiltered because they're shared across start dates. **Keep `_prepare_candidates()`'s own post-fetch filter anyway** — it's idempotent, is applied inside both of its walks over the corpus at no extra pass (SS-1), and keeps the guarantee local to the O(n²) pairing that depends on it. (A market that passes it but shares neither grouping key with another eligible market is not grouped either — since SS-1 `_prepare_candidates` never copies it into the list it groups, although while the fetch returns a list it is still resident in that corpus until the second walk ends; see TS-07.)

**Time-series pair extraction is close-time-windowed, not naive O(n²).** For string-keyed (time-series) groups, `_extract_pairs()` sorts members by `close_time` and sweeps a nested loop with an early `break` once the window closes, bounded by `MAX_DEADLINE_GAP_DAYS + 1` days of margin — the outcome is O(n·window), not the naive O(n²), but it isn't a classic two-pointer sweep since the inner loop restarts from each outer index rather than advancing a shared second pointer. The window exists because `_find_entry()` unconditionally rejects any time-series pair whose close dates differ by more than `MAX_DEADLINE_GAP_DAYS`, so pairs outside it are skipped without ever being materialized as a candidate. The `+1` day is slack only (it can only add harmless boundary candidates that `_find_entry`'s exact cutoff then rejects, never drop a legitimate one). Same-title (3-tuple-keyed) groups have no deadline-gap concept and stay naive — the eligibility prefilter above is what keeps those groups small. Both branches also drop two events of one series (`_same_series_dicts`, plus `_identical_wording_dicts` on the time-series branch — see the one-series gotcha); grouping is deliberately left alone, so the rule lives in exactly one place on this path, as it does on the live one. `config.LARGE_GROUP_WARN_THRESHOLD` (1000) logs a warning (not a cap) whenever a post-filter group is still large, as a canary that the prefilter/windowing are working as expected.

**`secrets.json` may be missing outer braces.** `auth.py` wraps it if needed. New code must call `auth.build_client()` rather than reading `secrets.json` directly.

**`CandidatePair.max_contracts = 0` means NOT ENRICHED, and nothing else.** Before `enrich_with_orderbook_prices()` it is the dataclass default (`depth_levels` is `()` alongside it) and `strategy.compute_trade` reads it as "no depth cap", taking the single-shot sizing path. After enrichment it is the affordability-bounded qualifying depth — **how many contracts the pair's written leg prices are valid for** — and enrichment never writes 0: a pair whose book holds under one contract at the gap, or whose budget cannot afford one contract pair, is dropped with `tradeable=False` and its own INFO line. That closes the older trap, where `max_contracts` came from `int(total_qty)` over a `float` quantity sum and a qualifying book with `0 < total_qty < 1` enriched to `max_contracts=0` with `tradeable=True`, which `compute_trade` then read as *uncapped*. A pair marked `tradeable=False` may still carry `max_contracts=0` from never having reached the writeback (unavailable orderbook, no qualifying depth, unaffordable) — check `pair.tradeable` first, as before.

**Backtest uses prod credentials**, not sandbox. The Kalshi historical API endpoint doesn't exist on the sandbox. `historical.py` always calls `build_prod_live_client()`.

**Dev mode skips `get_held_tickers()`** because the sandbox account is separate and has no positions from production. Don't add held-ticker filtering to `_run_dev()`.

**`normalize_title()` pattern order matters.** `_DATE_PATTERNS` in `scanner.py` applies patterns sequentially. Longer/more specific patterns must come before shorter ones to avoid partial matches leaving date fragments. If adding new patterns, prepend them before similar shorter ones.

**Event-title resolution is bounded, parallel, and must stay loud.** `_load_or_build_event_titles` resolves `event_ticker` → title in three phases: bulk `get_events` listings (settled/closed/open), the MVE listing (capped at `MVE_TITLE_LOOKUP_MAX_PAGES`), then a per-ticker `/events/{ticker}` fallback. That fallback costs **one HTTP round trip per ticker** and was written for a handful of stragglers — but a 21-day window measured **289,235 unresolved tickers** live (2026-08-03), where the original sequential, uncapped loop ground for hours emitting nothing, which is indistinguishable from a hang. It is now capped at `EVENT_TITLE_FALLBACK_MAX_LOOKUPS` (5000), run across `EVENT_TITLE_FALLBACK_MAX_WORKERS` (8) threads, and selected from a **sorted** miss list so the cap keeps a deterministic subset across runs. Tickers past the cap are stored as `""` — the exact poison pill a failed lookup already produced, so the caller's behaviour is unchanged (those markets group by market title alone). Every phase logs progress and the cap logs a WARNING naming how many were skipped: **never make this phase silent again, and never remove the cap** without replacing it with something else bounded. The bulk listings are bounded too, by a productivity bail-out (`EVENT_TITLE_LISTING_MAX_BARREN_PAGES`, 50 consecutive pages resolving nothing → move on), the same idiom as `MVE_MAX_EMPTY_PAGES`. That matters because a listing is an O(all events) scan for a specific ticker set, and `get_events` **excludes MVE events by API design** — so for an MVE-heavy miss set it can never resolve them no matter how long it pages. Live-measured 2026-08-03: the `settled` listing resolved 8,696 of 289,235 tickers in its first ~500 pages, then 9 more across the next 400.

**MVE event-title plumbing.** The live scanner attaches an `_event_title` attribute to each `Market` object inside `fetch_open_events_with_markets()`. The backtest stores it as the `event_title` key in cached market dicts. Both pair-finder paths (`find_time_series_pairs`, `find_same_title_pairs`) and their backtester counterparts (`_group_by_normalized_title`, `_group_by_exact_title`) require this to be set for MVE markets — without it they fall back to grouping by market title (plus, on the time-series side, the outcome label) alone, which would let cross-event option-label collisions through. If you add a new entry point that produces markets, attach `_event_title` (or `event_title` in dict form) before passing into the grouping functions. Old backtest caches written before this change have no `event_title` field; re-run with `--no-cache` to refresh.

**Tick structure drives the V2 order price cap (2026-08).** Live market payloads now carry `price_level_structure` (a string naming the tick regime — observed: `"linear_cent"` = 1c ticks, `"tapered_deci_cent"`, `"deci_cent"` = $0.001 ticks, and `"center_deci_edge_centi_cent"` = the regime all MVE/combo markets migrated to on 2026-08-17, with $0.0001 ticks below $0.01 and above $0.99 and $0.001 ticks in between) and `price_ranges` (an array of dollar-string bands `{"start", "end", "step"}` — a tapered market has multiple bands, e.g. finer ticks near 0/1 and coarser in the middle). `scanner.ApiMarket` now carries both (`price_level_structure: str = ""`, `price_ranges: list[PriceRange] | None = None`, parsed by `scanner._parse_price_ranges`, fail-soft to `None` on anything malformed), and `historical._market_to_dict` passes both through **raw** (not parsed) into the backtest cache, since that dict is JSON-serialized directly. **`scanner.tick_size_for_price(market, price_dollars)` now reads both** to derive the tick grid a V2 order price cap must land on: it returns the **FINEST** `step` among the `price_ranges` bands containing the price, as a `Decimal`, short-circuiting to `Decimal(config.DEFAULT_TICK_SIZE_DOLLARS)` (`"0.01"`) when `price_level_structure` is `""`/`"linear_cent"` or the bands are absent, and falling back to that same default with a `logging.warning` when no band contains the price or every containing band's step is nonpositive. **Finest, not first (TS-10).** A price sitting exactly on a band boundary belongs to two bands, and first-match is only "finer" at a band's LOWER edge — at an UPPER edge the earlier band is 10x COARSER, so `BUY_SLIPPAGE_TICKS` was multiplied by a 10x tick exactly there and the buy cap, which is a bid, was LOOSENED (`tick_size_for_price(m, 0.99)` returned 0.001 where the finest containing band is 0.0001). Scanning every band also means one malformed band no longer discards the valid ones after it, which the old `break` did. The fallback is always safe because the grids are nested ($0.01 ⊂ $0.001 ⊂ $0.0001) — a coarse-grid price is valid on any finer grid. The reverse is NOT true: a fine-grid cap that steps up into a coarser band (or is complemented across the book) can land off that band's grid, which is why `_v2_limit_price` re-quantizes the final price onto the grid of the band containing it. Old backtest cache records (written before this change) lack both keys entirely and read back as `None`; every reader goes through `.get()`, so this is not a crash risk. **On 2026-08-17, all MVE/combo markets migrated from $0.001 to the center_deci_edge_centi_cent regime described above.** That is what made the legacy cap untenable: `trader._buy_max_cost_cents`'s FoK price protection (`BUY_MAX_COST_SLIPPAGE_CENTS`, config.py) is denominated in whole cents — 1c of tolerance, roughly "one tick" back on a $0.001 grid, now means roughly 10-100 ticks of permitted drift depending on where in the band the price sits. **Resolved by the V2 migration:** order submission now defaults to the V2 endpoint `/portfolio/events/orders` (`config.V2_ORDER_PATH`, `ORDER_API_VERSION="v2"`) — dollar-string fill-or-kill LIMIT prices, fixed-point counts, bid/ask sides on the single YES book, and an explicit `exchange_index` — where the tick-aware cap `_v2_limit_price()` (scanned price ceiled to `tick_size_for_price()` plus `BUY_SLIPPAGE_TICKS` ticks) is finally expressible. The legacy `/portfolio/orders` path (deprecated June 2026, 5x rate-limit tokens, integer-cent `buy_max_cost`) is retained **unmodified** behind `ORDER_API_VERSION="legacy"` as the instant rollback; the side/price mapping lives in `trader._V2_LEG_SIDE`. Do not attempt a cents-based tick-aware cap on the legacy endpoint — it cannot express one. Fractional-contract sizing remains a deferred follow-up (`_format_count` always emits `.00`).

**V2 order semantics — assumptions to verify at the first live submission.** The V2 mapping was built from the docs, not from an observed live order, and every piece of it is deliberately arranged so a correction is a one-line change:
- **Side mapping** (`trader._V2_LEG_SIDE`, the single point of correction): buy YES = `bid` at the capped YES price; buy NO = `ask` at `1 − cap` (selling YES you don't hold IS a long NO); the rollback closes a held NO by buying the YES short back, i.e. a **reduce-only `bid`** at the highest tradeable level of the market's own grid (`trader._v2_rollback_price()`: the finest-grid target `V2_ROLLBACK_BID_PRICE_DOLLARS` = "0.9999" floored onto the market's grid — 0.99 on linear-cent, 0.999 on deci-cent, 0.9999 on a centi-cent edge band — emulating the legacy capless `type="market"` unwind; a flat 0.99 would fail to cross asks resting in (0.99, 1) on sub-cent regimes, and $1.00 is not a tradeable level). If the exchange reads a leg the other way round, flip the value in that dict — no builder logic moves.
- **Runtime backstop on the NO-leg mapping** (`trader._confirm_v2_no_mapping(client, spec, no_leg, before_no)`): the side mapping above cannot be proven offline, so the **first V2 NO-leg fill of each process** is checked against the account's own signed positions ledger before the YES leg is submitted. It is judged by the **position DELTA across the fill, never by the absolute sign** — the module's standing rule (see the delta gotcha above). `_execute_one` hands in the NO-leg baseline it already took before submitting, and the backstop compares `_fill_delta(before_no, after)` against `-no_leg.count`. Absolute sign was wrong in both directions: an account already long +100 YES on the NO leg's market that buys 10 NO nets +90, a *positive* reading that would have declared the mapping disproven and stopped the pair at `manual_review` with a real unhedged NO leg, while an account already short −100 masks a genuinely wrong mapping and latches a false confirmation for the rest of the process. A delta of **−`no_leg.count`** confirms the hypothesis (an `ask` really did open a NO position) and latches the module-level `_V2_NO_MAPPING_CONFIRMED`, so the check costs one extra positions read per **process**, not per trade — the mapping is a property of the exchange, and one confirmation proves it for every later trade in the run; the latch is deliberately not persisted, so a fresh process re-verifies. For a time-series pair the NO leg is `market_b`, so the read is of `market_b`'s ticker; the latch is **shared across pair types** because it verifies the exchange's side mapping, not a market — a same-title confirmation covers later time-series trades and vice versa. **Any other delta** means the mapping is DISPROVEN live; a delta of **zero** is re-read once after `_V2_MAPPING_RECHECK_DELAY_SECONDS` (1s) before that verdict, because an unmoved ledger immediately after a confirmed fill is usually read-after-write lag, not disproof (a persistent zero — fill reported, ledger flat — is still contradictory and goes to manual review). On disproof: the pair stops at `status="manual_review"` with **the YES leg unsubmitted** (it would hedge a position we don't hold) and **the NO leg deliberately left in place** — the unwind is a `bid` resting on the same disproven hypothesis, so an automated unwind could double the error rather than reverse it (`reduce_only` would make a wrong unwind fail safe into `rollback_failed`, but a human must decide); a `logging.critical` names the remedy, `ORDER_API_VERSION="legacy"`. An **unknown delta** (either snapshot missing) is not disproof: it warns, proceeds to the YES leg, and does NOT latch, so the check re-arms on the next NO fill — one flaky positions read must never stall trading. **This read is ONE OF THE TWO SINGLE-SHOT position reads in that window** (`trader._position_count_once`, sharing `_read_position`'s parse with the retried `_position_count`; the other is `_execute_one`'s NO-leg ledger-lag re-read, DR-64, which also pays a 1s pause): it is a blocking call inside the window where the NO leg is filled and unhedged, `api_call_with_retry` can hold a call for ~62s of sleeps, and because a failing endpoint never latches, **every** V2 trade in a 429 storm would pay that stall with a naked NO leg — the same bounded-wait reasoning `_await_transfer_settlement` uses for its unretried balance reads. Don't retry-wrap it, don't make this check unconditional per-trade (it is a per-process property), and don't turn the disproven branch into an automatic rollback.
- **Fill classification:** a full FoK fill is assumed to report `fill_count == count` and a kill to report **2xx with `fill_count == 0`**. `_v2_fill_status()` maps only those two to the legacy `"executed"`/`"canceled"` vocabulary; a partial fill (a FoK invariant violation), a missing `fill_count`, or anything else logs `logging.critical` and **raises**. That is the design, not an oversight: raising routes into `_execute_one`'s existing ambiguous-exception path, which consults `_position_count` (the account's ground truth), so a mispredicted response shape degrades safely into `failed`/`rolled_back`/`manual_review` instead of being misread as a clean fill or a clean kill. Never "simplify" it into returning a guessed status.
- **Response shape:** the order object may arrive wrapped under an `"order"` key or flat, and counts as either `fill_count` or the fixed-point string `fill_count_fp` — all four combinations are accepted (`_parse_fixed_point` prefers the `_fp` variant).
- **Sandbox V2 support is unknown.** Dev mode never submits orders, so it cannot verify this; the smallest possible prod run is the real check — and `python3 -m kalshi_betting.v2_probe` is the ~1-cent way to verify the NO-leg mapping, FoK kill semantics, and the transfer centicent unit before real size flows. If anything misbehaves, set `ORDER_API_VERSION="legacy"` — that is the whole reason the legacy path is retained intact. **The probe verifies a SIDE mapping, not a price, so two of its own prices are deliberately NOT the builders' (DR-04).** `v2_probe._no_close_body` overrides the rollback builder's price with `trader._format_price(trader._v2_top_of_grid_price(market))` — the same level `_step_unfillable_ask` submits at. Exactly TWO keys are overridden, the price and the count (the V2 fractional minimum, `PROBE_COUNT_STR`); every other key — side, `reduce_only`, time-in-force, ticker and shard — stays the builder's. The builder's price is a loss floor derived from the leg's scanned entry, and the probe's placeholder entry of 0.5 puts that floor at **$0.62 on every market and every tick regime**, so the close was structurally killed on any market whose YES ask is above 62c: the one gate deciding whether the bot stays on V2 FAILed for a reason unrelated to the mapping, told the operator to downgrade to legacy, and left a real 0.01 NO position open. `reduce_only=True` is what bounds the top-of-grid bid — it can only close the 0.01 contracts just opened. Same commit, same reasoning one step earlier: a position of exactly 0 after a reported full fill is **re-read once** after `trader._V2_MAPPING_RECHECK_DELAY_SECONDS`, BEFORE any sign branch, so a re-read that comes back positive (disproven) or `None` (lookup failed) still takes its own branch (DR-21); a still-zero ledger keeps its FAIL, now worded "still 0 after a re-read". That re-read uses the RETRIED `trader._position_count` — acceptable at 0.01 contracts in a human-supervised tool, and never to be copied into `trader._confirm_v2_no_mapping`, whose read must stay single-shot. **A 2xx order body that is not a JSON object is handled the same way, one step earlier again (DR-58):** `_fill_counts` and `_report_fee` both `.get()` the body, so `"accepted"`, `[]`, `123`, `true` or `null` raised an uncaught `AttributeError` straight after a real ask, skipping the position read, every flatten warning, and the reduce-only close. `v2_probe._non_object_body_fail` now guards both submission-response READERS — the probe submits three orders but only the NO buy and the unfillable ask read their body, since the NO close's response is only `_emit`'d and its verdict comes from `trader._position_count` — restoring the position read (with its own re-read, on a flat OR unreadable first result) and the warning but NOT the close — see the DR-05 paragraph for why the probe is carved out of the rule that keeps the `trader.py` order readers loud, and why the close stays unsubmitted. **A body that IS a JSON object but whose `fill_count`/`remaining_count` cannot be read is the same epistemic state one step later, and in `_step_no_mapping`'s NO buy it now takes the same remedy (DR-60).** That branch used to decide from a SINGLE un-refreshed position read — DR-21's re-read is gated on `filled`, which is `None` and therefore falsy exactly there — and printed a warning only when that read was truthy, so a lagging ledger and a FAILED lookup both came out as silence while a real 0.01 NO position could be open. The re-read-and-report tail is extracted as `v2_probe._recheck_and_report_position(client, ticker, observed)`, ONE definition — since DR-20 below, called from three branches, and the helper's own docstring is the authority on which: it re-reads once after `trader._V2_MAPPING_RECHECK_DELAY_SECONDS` when the caller's first read is `None` or `0` (a read that already moved is evidence and is not re-polled), then prints lookup-failed / position-open / genuinely-flat as three distinct outcomes. The verdict and the exit code are unchanged (`_FAIL`, 1), and the `filled is True` / `filled is False` branches — including DR-21's own re-read and the kill NEUTRAL — are untouched. **Scope, recorded rather than implied: DR-58's guard covers BOTH submission-response readers, DR-60's covers only the NO buy.** `_step_unfillable_ask` has a structurally identical unreadable-fill-counts branch that returns `_FAIL` above its only post-submission position read, so a 2xx object body with no readable fill counts there still prints one FAIL line and never looks at the account. That is a real residual, not a stated trade-off — the step's own DR-58 comment already argues that "an unreadable 2xx body is not proof that it was killed", the same reasoning that would apply here — and it was left alone only because that step was explicitly out of DR-60's scope. Three further branches sit in the same state and also do not call the helper: `_step_unfillable_ask`'s `not killed` branch — the direct sibling of DR-20's new one below, which names the counts and FAILs but reports the account from a single un-refreshed read and never says FLATTEN — and both steps' post-submission EXCEPTION handlers, where `_step_no_mapping`'s bare `if after_err:` collapses a failed lookup into "flat". Do not read the helper's "single definition" wording as coverage of any of these four. **A READABLE response can be impossible too, and `_step_no_mapping` used to call it a clean kill (DR-20).** `filled = remaining == 0 and fill == PROBE_COUNT` collapsed every non-full outcome into one boolean, so a PARTIAL fill (0.005 filled, 0.005 remaining against a count of 0.01) took the `not filled` branch — where DR-21's re-read does not run, because that re-read is gated on `filled` — and, with a ledger that had not caught up, printed "the fill-or-kill was killed unfilled and the account is still flat", exited NEUTRAL (code 2) and gave no flatten warning while a real 0.005 position was open on the production account; `_report_fee`'s absent-`average_fee_paid` line added a second, independent "(nothing filled)" claim just above it. The step now carries a separate `conforming` flag — `filled or (fill == 0 and remaining == PROBE_COUNT)` — and anything else (partial, over-fill, stale remainder) is the fill-or-kill INVARIANT VIOLATION this probe exists to catch: it FAILs, names the actual `fill_count`/`remaining_count`, points at `ORDER_API_VERSION = "legacy"`, and reports the account through the same shared `_recheck_and_report_position` tail. This is the ONE `filled is False` change DR-60 left untouched; the TRUE-kill NEUTRAL (verdict pinned by `tests/test_v2_probe.py::TestNoMappingVerdict::test_no_fill_is_neutral_and_submits_no_unwind`, wording by `::TestNonConformingFillOrKill::test_a_true_kill_with_a_flat_account_is_still_neutral`), the `filled is True` branches and DR-21's own re-read are all unchanged. `_report_fee` no longer asserts "nothing filled" — it reads no fill counts and so cannot say. The sibling `_step_unfillable_ask` already classified this way (`killed = fill == 0 and remaining == PROBE_COUNT`, FAILing a partial and printing the counts), so the two steps now apply the SAME kill test — their remedies still differ, since that step's ask is meant to be unfillable, so it folds a complete fill into the same FAIL and reports the account from one un-refreshed read. **The probe deliberately holds a STRICTER kill contract than `trader._v2_fill_status`, and the FAIL text says so rather than claim the live path would have caught the same body.** That reader consults ONLY `fill_count` (it never reads `remaining_count` anywhere in `trader.py`), so it genuinely raises on a partial or an over-fill — `fill_count` neither the requested count nor zero — but a STALE REMAINDER (`fill_count == count` with a non-zero `remaining_count`) books as `"executed"` there and a kill whose `remaining_count` is not the full count books as `"canceled"`. The probe reads both counts because an unexpected `remaining_count` is itself a finding on the one gate that decides whether the bot stays on V2, and because matching `_step_unfillable_ask`'s long-standing test is what makes the two steps agree. The practical consequence to expect on a first live run: a genuine kill reporting `fill_count=0` with a zeroed rather than full `remaining_count` is now a FAIL naming both counts, where it used to be a NEUTRAL with a retry hint — and it would have FAILed the kill-semantics step regardless, since `_step_unfillable_ask` has required the full remainder since it was written. **And `--dest-shard` may not name the source shard (DR-22).** It is declared `type=int` with no `choices`, and `_step_transfer`'s two guards — is the shard advertised, are its transfers active — are both satisfied by shard 0 BY CONSTRUCTION, since it IS `_TRANSFER_SOURCE_SHARD`; so `--dest-shard 0` POSTed a real, non-idempotent, never-retried transfer with `source_exchange_shard == destination_exchange_shard`. **Derived from source, not observed** (the probe was never run this way): the POST is what the bug is, and IF the exchange accepts it, a net-zero move cannot raise that shard's balance by the probe cent `_await_transfer_settlement`'s target demands, so the poll burns the full `TRANSFER_SETTLE_TIMEOUT_SECONDS` and reports a FALSE `MONEY MAY BE IN FLIGHT`; if the exchange 400s it instead, the step FAILs on the POST with a different message. The refusal is a NEUTRAL at the TOP of `_step_transfer`, before any transfer I/O (`main()` still builds the client and reads the balance before dispatching to any step) — not in argparse — because `_step_transfer` is what spends the money and is reachable from `main()`'s step dispatch and from any future caller, not only from the CLI. Negative and unknown destinations need no separate check: they are not advertised, so the existing advertised-shard guard already short-circuits them to NEUTRAL.
- **Omitted optional fields rely on server defaults:** `self_trade_prevention_type`, `subaccount`, and `cancel_order_on_pause` are deliberately not sent.
- Other fixed choices: prices are 4-decimal dollar strings (`_format_price`, exactly representing every grid point of every regime); counts are fixed-point strings (`_format_count`); each order body's `exchange_index` is that leg's OWN market's `exchange_index` (the NO leg and its rollback from the NO leg's market — `market_a` for same-title, `market_b` for time-series — and the YES leg from the YES leg's market; a pair's legs can sit on different shards) and never `-1` auto-route, so a wrong shard model is rejected loudly by the exchange instead of silently routed, and an explicit-shard write bills only that shard's rate-limit bucket where auto-route bills every nonzero shard's. The legacy endpoint has no shard-routing parameter at all, so while `ORDER_API_VERSION` is not `"v2"`, `trader._legacy_routable()` refuses any spec with a leg off `DEFAULT_EXCHANGE_INDEX` at the top of `_execute_one()` — `status="failed"`, since nothing was submitted and there is nothing to unwind; `post_only` is always `False` (we are deliberate takers) and `reduce_only` is `True` only on the rollback.

def my_function(arg: type) -> ReturnType:
    """

## What NOT To Do

- **Do not bypass the rollback logic in `trader._execute_one()`**. If the YES leg is *confirmed* unfilled after the NO leg fills — a clean FoK rejection, or an error whose position delta is 0 on the first read AND on the lag re-read (DR-63) — an unwind must be attempted immediately: an orphaned NO-leg position (`market_a` for same-title, `market_b` for time-series) is an unhedged one-sided position. But an unwind requires *confirmation*, not a guess. When a leg errors and the delta is unattributable (the lookup failed, or the position moved by an amount the order can't explain), the correct behavior is `status="manual_review"` with no order submitted — on the YES leg because an unwind could reverse a real fill, and on the NO leg because a `reduce_only` sell could liquidate an unrelated holding. Do not "restore" the NO leg's old unconditional unwind-on-unknown.
- **Do not add retry logic to order submission** — this covers `trader._submit_order` (legacy, via `fetch_json_page`), `trader._submit_order_v2` (V2, via `_http.signed_request_json`) and `trader._execute_transfer` (the non-idempotent collateral POST) equally. One retry after a fill-or-kill rejection could submit the NO leg twice at different prices, creating an unhedged position, and a retried transfer moves the money twice. **The read-only position lookups in `trader._position_count` ARE retried and must stay that way** — a GET cannot duplicate a trade, but an unretried transient 429 there turns a resolvable ambiguity into a rollback or `manual_review`. Assert the rule per-function on the submission/transfer sources, never as a module-wide "trader.py must not import `api_call_with_retry`" ban.
- **Do not unwind the NO leg with an unpriced order on either path.** The legacy unwind is a floored FoK LIMIT sell and the V2 unwind is a floored (bid-capped) FoK limit bid; both express the same `ROLLBACK_MAX_LOSS_CENTS_PER_CONTRACT` bound. A market-type (or top-of-grid-flat) unwind has no loss floor at all. (This rule is about the TRADE unwind in `trader.py` and is absolute there. `v2_probe._no_close_body`'s closing bid is deliberately top-of-grid-flat and is not a trade unwind — it is a 0.01-contract `reduce_only` probe order whose whole point is to fill; see the V2-semantics bullet above before "restoring" the builder's price to it.)
- **Do not hardcode `spec.pair.market_a` as the NO leg, or `market_a`'s side as NO, anywhere.** `config.SAME_TITLE_LEG_SIDES`/`TIME_SERIES_LEG_SIDES` via `scanner.leg_sides()`, `scanner.leg_prices()` and `trader._ordered_legs()` are the only source of truth for which side a leg buys, which price it pays, and which leg is submitted first and unwound; for a time-series pair the NO leg is `market_b`.
- **Do not describe, price or pay a fourth time-series settlement cell.** A=YES/B=NO is impossible for a cumulative-deadline pair; the backtester excludes and counts it as a premise violation. No table, docstring, log string or README/CLAUDE.md sentence may assign that cell a payout of any kind; the only double-payout cell anywhere is the SAME-TITLE table's NY cell in `_settlement_receipt`.
- **Do not apply the one-series rule to only one finder, and do not replace it with a close-time gate.** `scanner._same_series` must gate BOTH `find_same_title_pairs` and (conjoined with `_identical_wording`) `find_time_series_pairs`, and `backtester._extract_pairs` must mirror it on both of its branches — the same two tickers qualify for both pair types, so a one-sided gate relabels the trade instead of stopping it (pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_apply_the_one_series_rule`). A close-gap threshold is not a substitute: identical-wording non-combo pairs co-resolved 96.3–98.2% of the time in every close-gap band, while combo pairs closing 96 seconds apart still disagreed 13.8% of the time. Fixture identity separates them; proximity does not.
- **Do not apply the cumulative-deadline rule to only one path, and do not let a snapshot pair through.** `scanner.cumulative_deadline_pair` (over `scanner.deadline_phrasing`) must gate BOTH `scanner.find_time_series_pairs` and `backtester._extract_pairs`' time-series branch — one shared helper, only the field extraction differing (pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_apply_the_cumulative_deadline_rule` and `::test_ast_the_deadline_classifier_has_one_definition`). Gating only the live path would leave the backtester replaying the defect instead of detecting it, exactly as it reproduced DR-01 before the grouping key was shared. The rule belongs on the time-series branch ONLY — a same-title pair has no deadline concept — and it must keep failing CLOSED: wording that names no deadline is refused, because the YES-on-earlier/NO-on-later trade has no premise without the nesting a cumulative deadline provides. Do not move it into `_can_ever_enter` for speed: that is a MARKET-eligibility predicate named by `config.SETTLED_PREFILTER_CACHE_TAG`, and putting it there silently corrupts every assembled cache. Do not merge the phrasing tables into `_DATE_PATTERNS` — one erases dates, the other reads the preposition around them.
- **Do not order or tier a same-event ladder on `close_time`, and do not apply the ladder rule to only one path (DR-73).** A ladder's legs are ordered by `scanner.stated_deadline` and gapped by `scanner.same_event_ladder`, and that stated gap is what chooses the tier, is checked against `MAX_DEADLINE_GAP_DAYS`, travels on `CandidatePair.stated_gap_days` and is read downstream only through `scanner.pair_gap_days` — because a settled or single-instant event closes every rung together (681 of 1,821 archive same-event pairs have a close gap of ZERO days and 13 are ordered the wrong way round by realized close), so `close_time` silently re-tiers such a pair from the 0.70 ceiling to 0.85 or inverts its legs. The rule must gate BOTH `scanner.find_time_series_pairs` and `backtester._extract_pairs`/`_find_entry`, on the SAME `TIME_SERIES_SAME_EVENT_LADDERS` resolved at call time — each module's own by-value binding of the config constant, so a test or harness patches `scanner.` / `backtester.` / `backtest.` and never `config.`, which none of them reads — never on `event_ticker` equality alone, which would hand ladder semantics to any caller regardless of the switch — and it is pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_apply_the_same_event_ladder_rule` and `::test_ast_pair_ceiling_reads_the_pair_gap`. A one-sided rule would let a ladder-enabled live run be measured by a backtest that refuses every same-event pair, the same relabelling trap the one-series rule records. It must keep failing CLOSED at every step: an empty shared event ticker, identical wording, a non-cumulative verdict, a deadline stating no placeable calendar day, fields naming irreconcilable days, both rungs naming ONE day, or a stated gap over the cap all refuse the pair. Branch on `is None` / `is SAME_DAY`, never truthiness — `SAME_DAY` is a non-empty string.
- **Do not import `trader.py` from `scanner.py` or `strategy.py`** — circular dependency.
- **Do not write output files outside `PROJECT_ROOT`**. All logs, Excel files, and HTML dashboards write relative to `PROJECT_ROOT`.
- **Do not modify `_DATE_PATTERNS` without running `test_normalize_title`** — a regression silently causes missed pairs or false positives with no error.
- **Do not import `v2_probe` from any pipeline module** — it is a human-run tool that submits real-money orders; a single import would put probe submissions one code path away from the weekly scheduler (a test asserts this).
- **Do not add tests that call the real Kalshi API**. Use `unittest.mock.MagicMock` for `KalshiClient`. Tests should be runnable offline.
- **Do not change the fee formula without updating both** `fee_per_pair_approx()` and `fee_leg_exact()` in `config.py`. The backtester also uses both.
- **Do not take the fee out of Kelly's denominator, and do not merge Kelly's `b` with the reported `profit_ratio` (DR-62).** `b` divides by `price_a + price_b + fee_per_pair_approx(...)` — the dollars a losing pair actually forfeits — in all three sizers (`strategy._evaluate_size`'s `kelly_b`, `backtester._simulate_at_discount`'s `kelly_b_entry`, `dashboard._kelly_fraction`'s `b`); dropping the fee there overstates modelled EV by exactly `q·fee`, so `f* > 0` stops meaning positive expected value even under the continuous fee approximation the gate prices with. (With the fee in place it means positive EV under that approximation and nothing more — at single-digit `n` the ceiling-rounded exact fee can still leave an accepted spec marginally EV-negative on its own fields; never restate the guarantee without that qualifier.) The fee-less ratio beside it is the REPORTED return on contract cost and feeds `select_portfolio`'s ranking key — two names, two quantities, on purpose.
