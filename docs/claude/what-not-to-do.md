# What NOT To Do — the full rules

Moved word for word from the "What NOT To Do" section of the project's `CLAUDE.md` on 2026-10-26, when that file was cut down to a short root that indexes these notes. Where the text below says "this file", it means the project's notes as a whole: `CLAUDE.md` and the files in `docs/claude/`. Section names the code and README use ("Key Patterns", "Known Gotchas", "Module Map") name the folders of `docs/claude/`. Each paragraph is one line, some of them long: find one with `grep -n`, then read that line by number.

- **Do not bypass the rollback logic in `trader._execute_one()`**. If the YES leg is *confirmed* unfilled after the NO leg fills — a clean FoK rejection, or an error whose position delta is 0 on the first read AND on the lag re-read (DR-63) — an unwind must be attempted immediately: an orphaned NO-leg position (`market_a` for same-title, `market_b` for time-series) is an unhedged one-sided position. But an unwind requires *confirmation*, not a guess. When a leg errors and the delta is unattributable (the lookup failed, or the position moved by an amount the order can't explain), the correct behavior is `status="manual_review"` with no order submitted — on the YES leg because an unwind could reverse a real fill, and on the NO leg because a reduce-only unwind of a position this order may not own could close an unrelated holding. Do not "restore" the NO leg's old unconditional unwind-on-unknown. The unwind's count is always `no_leg.count`, never a position read, and on a market the account held before the pair (an add-on) that confirmation is what keeps it off the older contracts; nor drop `trader._add_on_mismatch`, which sends an add-on only while both markets still hold exactly the pair it adds to.
- **Do not add retry logic to order submission** — this covers `trader._submit_order_v2` and `trader._submit_sale_v2` (both via `_http.signed_request_json`) and `trader._execute_transfer` (the non-idempotent collateral POST) equally; a resent sale could sell twice. One retry after a fill-or-kill rejection could submit the NO leg twice at different prices, creating an unhedged position, and a retried transfer moves the money twice. **The read-only position lookups in `trader._position_count` ARE retried and must stay that way** — a GET cannot duplicate a trade, but an unretried transient 429 there turns a resolvable ambiguity into a rollback or `manual_review`. Assert the rule per-function on the submission/transfer sources and at `_submit_order_v2`'s two call sites (`_execute_one`, `_rollback_no_leg`), never as a module-wide "trader.py must not import `api_call_with_retry`" ban. The write pacer (`trader._ORDER_WRITE_PACER`) is not a retry and must stay exactly one place before the one POST — `acquire`, `acquire_hedge`, or a held write's `send` through `_PairWrites` — never a loop around it, and never a reason to re-send after a 429. Nor may a held write stop counting against the bucket before it is sent or released (the refill cap of `burst` minus the held writes): that cap is the only thing keeping a YES leg sent late inside the write limit.
- **Do not unwind the NO leg with an unpriced order.** The unwind is a floored (bid-capped) immediate-or-cancel limit bid (IOC is mandatory with `reduce_only`) that expresses the `ROLLBACK_MAX_LOSS_CENTS_PER_CONTRACT` bound. A market-type (or top-of-grid-flat) unwind has no loss floor at all. (This rule is about the TRADE unwind in `trader.py` and is absolute there. `v2_probe._no_close_body`'s closing bid is deliberately top-of-grid-flat and is not a trade unwind — it is a 0.01-contract `reduce_only` probe order whose whole point is to fill; see the V2-semantics bullet above before "restoring" the builder's price to it.)
- **Do not hardcode `spec.pair.market_a` as the NO leg, or `market_a`'s side as NO, anywhere.** `config.SAME_TITLE_LEG_SIDES`/`TIME_SERIES_LEG_SIDES` via `scanner.leg_sides()`, `scanner.leg_prices()` and `trader._ordered_legs()` are the only source of truth for which side a leg buys, which price it pays, and which leg is submitted first and unwound; for a time-series pair the NO leg is `market_b`.
- **Do not describe, price or pay a fourth time-series settlement cell.** A=YES/B=NO is impossible for a cumulative-deadline pair; the backtester excludes and counts it as a premise violation. No table, docstring, log string or README/CLAUDE.md sentence may assign that cell a payout of any kind; the only double-payout cell anywhere is the SAME-TITLE table's NY cell in `_settlement_receipt`.
- **Do not apply the one-series rule to only one finder, and do not replace it with a close-time gate.** `scanner._same_series` must gate BOTH `find_same_title_pairs` and (conjoined with `_identical_wording`) `find_time_series_pairs`, and `backtester._extract_pairs` must mirror it on both of its branches — the same two tickers qualify for both pair types, so a one-sided gate relabels the trade instead of stopping it (pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_apply_the_one_series_rule`). A close-gap threshold is not a SUBSTITUTE for it: on the corpus that rejection was measured on, identical-wording non-combo pairs (same-series and cross-series pooled) co-resolved 96.3–98.2% of the time in every close-gap band, while combo pairs closing 96 seconds apart still disagreed 13.8% of the time — so for the ONE-SERIES case, fixture identity separates them and proximity does not. That verdict is about the same-series case only: on DR-74's 365-day corpus, CROSS-series identical-wording pairs settled the same way 99.2% of the time at a 0 s close gap against 60.7% beyond 1 minute, so there proximity DOES separate them (see the DR-02 gotcha's annotation and the close-gate gotcha). DR-74's close gate is not a replacement either — it is an ADDITIONAL condition on the cross-series same-title pairs the series rule already admits (see the next bullet), and the one-series rule stays in front of it on both paths.
- **Do not apply the same-title close gate on only one PATH, and do not add it to `find_time_series_pairs` (DR-74).** `scanner.closes_apart` must gate BOTH `scanner.find_same_title_pairs` (through `_closes_apart`) and `backtester._extract_pairs`' same-title branch (through `_comparable_closes_dicts`) — one definition, pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_paths_apply_the_same_title_close_gap` and `::test_ast_the_close_gap_has_one_definition` — or the backtest replays the men's/women's trades the live path refuses, exactly as it reproduced DR-01 before the group key was shared. It belongs on the same-title finder ONLY: identical wording can never form a time-series pair (DR-67), so a same-title-only gate cannot relabel the trade, and a close gate on the time-series finder would refuse every genuine cross-event deadline pair, whose closes differ by design (the same AST pin asserts its absence there). Keep it failing CLOSED on a close it cannot compare, keep it AFTER the series test so the older counts do not move, and keep the backtest's unreadable-close count on its own line so the close-gap line stays the live one's verbatim twin.
- **Do not drop the same-title sport and competition check from either path or from `held_pair_kind`, and do not add it to `find_time_series_pairs` (DR-79).** `scanner._labels_differ` and `scanner._competitions_differ` (over the one definitions `labels_differ` and `competitions_differ`) must gate BOTH `scanner.find_same_title_pairs` and `scanner.held_pair_kind`'s same-title branch — leaving `held_pair_kind` out lets live trimming price a held football/volleyball pair on the 95% prior. The backtest applies the same two definitions — `labels_differ` in `backtester._extract_pairs`' same-title branch, right after the close gate, and `competitions_differ` in `backtester._refuse_other_competitions` over the labels `historical.load_event_competitions` reads — or a backtest replays the pairs the live path refuses (pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_the_backtest_applies_the_sport_check`); there, keep an event whose competition could not be read a refusal (its own backtest-only line), and keep `event_competitions.json` holding only answers Kalshi gave, so an unread label is asked again rather than cached as "names none". It belongs on the same-title readers ONLY: identical wording is never a time-series pair (DR-67). Keep both checks failing CLOSED (a market with no `_series_labels`, labels that are not a (category, tag) pair of strings, a competition that is not a string, which `event_competition` gives as `None` for a label in the payload that is not text), keep a one-sided competition a refusal, keep them AFTER the close gate so the older counts do not move, and keep `main._attach_series_labels` running on every market before the sale block and both finders, from the one listing the run reads (pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_same_title_readers_apply_the_sport_check` and `::test_ast_both_run_modes_file_every_market_before_they_pair`).
- **Do not apply the cumulative-deadline rule to only one path, and do not let a snapshot pair through.** `scanner.cumulative_deadline_pair` (over `scanner.deadline_phrasing`) must gate BOTH `scanner.find_time_series_pairs` and `backtester._extract_pairs`' time-series branch — one shared helper, only the field extraction differing (pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_apply_the_cumulative_deadline_rule` and `::test_ast_the_deadline_classifier_has_one_definition`). Gating only the live path would leave the backtester replaying the defect instead of detecting it, exactly as it reproduced DR-01 before the grouping key was shared. The rule belongs on the time-series branch ONLY — a same-title pair has no deadline concept — and it must keep failing CLOSED: wording that names no deadline is refused, because the YES-on-earlier/NO-on-later trade has no premise without the nesting a cumulative deadline provides. Do not move it into `_can_ever_enter` for speed: that is a MARKET-eligibility predicate named by `config.SETTLED_PREFILTER_CACHE_TAG`, and putting it there silently corrupts every assembled cache. Do not merge the phrasing tables into `_DATE_PATTERNS` — one erases dates, the other reads the preposition around them.
- **Do not order or tier a same-event ladder on `close_time`, and do not apply the ladder rule to only one path (DR-73).** A ladder's legs are ordered by `scanner.stated_deadline` and gapped by `scanner.same_event_ladder`, and that stated gap is what chooses the tier, is checked against `MAX_DEADLINE_GAP_DAYS`, travels on `CandidatePair.stated_gap_days` and is read downstream only through `scanner.pair_gap_days` — because a settled or single-instant event closes every rung together (681 of 1,821 archive same-event pairs have a close gap of ZERO days and 13 are ordered the wrong way round by realized close), so `close_time` silently re-tiers such a pair from the 0.70 ceiling to 0.85 or inverts its legs. The rule must gate BOTH `scanner.find_time_series_pairs` and `backtester._extract_pairs`/`_find_entry`, on the SAME `TIME_SERIES_SAME_EVENT_LADDERS` resolved at call time — each module's own by-value binding of the config constant, so a test or harness patches `scanner.` / `backtester.` / `backtest.` and never `config.`, which none of them reads — never on `event_ticker` equality alone, which would hand ladder semantics to any caller regardless of the switch — and it is pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_apply_the_same_event_ladder_rule` and `::test_ast_pair_ceiling_reads_the_pair_gap`. A one-sided rule would let a ladder-enabled live run be measured by a backtest that refuses every same-event pair, the same relabelling trap the one-series rule records. It must keep failing CLOSED at every step: an empty shared event ticker, identical wording, a non-cumulative verdict, a deadline stating no placeable calendar day, fields naming irreconcilable days, both rungs naming ONE day, or a stated gap over the cap all refuse the pair. Branch on `is None` / `is SAME_DAY`, never truthiness — `SAME_DAY` is a non-empty string.
- **Do not let the one-open-trade-per-ladder rule fail open (DR-76).** A held market `scanner.resolve_held_ladders` cannot identify must keep meaning NO time-series pair that run — never "treat it as on no ladder", and never a question key built without its event title, which matches none of its siblings. Both `find_time_series_pairs` and `select_portfolio` must be handed the run's held ladders (both default to an empty set, so a dropped keyword refuses nothing silently — pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_the_live_run_refuses_pairs_on_held_ladders`), the resolver must read the market list BEFORE held markets are removed from it, and the labels must come from `scanner.ladder_keys`, the one definition. Keep the finder's refusal FIRST and before the one-best-pair contest, so a runner-up off every held ladder can still trade. Nor apply the rule on only one path: the backtest mirror labels markets through the same definition (`backtester._ladder_keys_dict` → `scanner.ladder_keys`, pinned by `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_the_backtest_reads_ladders_through_the_one_definition`), and `SweepPoint.peak_kelly_fraction` must keep covering every Monday a pair may be traded on (every passing Monday of a time-series pair, a same-title pair's first and, with `add_to_held`, a same-title pair's later same-legs Mondays) — a peak read off the traded, first or last Monday only makes `CapSweep`'s shared copies silently wrong.
- **Do not let adding to held pairs fail open (DR-77).** A `HeldPair` comes only from `scanner.held_pairs`, which returns one only when its markets (two for an exact pair, one for a lone leg) are alone on their ladder and every held market's ladder is known — that isolation is the whole safety of the finders' and `select_portfolio`'s exemptions — so never build one anywhere else, and never hand the finders `add_on_pairs` from a positions listing that stopped early, from a run that could not identify every held market, or, when anything is held, from a run whose portfolio value counts only the cash because Kalshi's value of the open positions was unread or refused (`main._run_prod` hands `{}` and WARNs). Nor hand them a pair that did not pass `seller.plan_add_ons`: `add_on_tickers` is built from its result alone, and the wait and the minimum price movement fail closed, so a fills list that cannot be read, or (with a wait) one that is empty or does not reach back far enough, keeps no pair, and a pair whose last fill, price then or price now cannot be read is left out and its markets stay blocked — never read as rested or as "no minimum". Keep `pair_held` reading by type, the sides checked with `HeldPair.matches` after a ladder's legs are ordered, and the trader's check just before the NO leg (`trader._add_on_mismatch`). Keep the fees paid in a held pair's stake (`HeldPair.stake_dollars` live, what each of `held["trades"]` spent in the backtest): the portfolio value leaves them out, and a stake without them tops a held pair up by about a contract pair on every run it passes, each top-up paying a fee of its own. Keep the setting read only through `LiveSettings.rebalance` (the AST pin forbids `REBALANCE` on the live path), and keep a saved file that leaves the toggle out reading it as off (`config._OPTIONAL_TOGGLES`): nobody confirmed a value for that file. Nor read a file an older version saved (one holding `config._RETIRED_TOGGLES`) as its proposal anywhere a run starts: it stays `LiveDefaultsOutdated`, refused, and only a Confirm and save on the defaults server's page turns its values into settings a run trades.
- **Do not size on a positions value the contracts held cannot back.** `main._checked_positions_value` is the one check: Kalshi's value of the open positions, when above 0, counts only when it is at most `config.CONTRACT_PAYOUT_DOLLARS` × the contracts held, over a positions listing read to its end whose every count can be read; a value of 0 is always kept, since it adds nothing. A refused value sizes the run on the cash alone, applies the $50 minimum to the cash again and adds to no held pair. Keep its WARNING in that check, which `_run_prod` calls once it has read the positions, never in `_bankroll_cents` (a test pins that function's WARNINGs exactly), and keep the low-cash WARNING after the check, so it describes the value the run sizes on.
- **Do not decide the category/tag filter anywhere but `config.trade_filter_for`, and do not read a tied tag as a plain one.** `config.trade_filter(settings)` (which `main._filter_by_category` keeps every pair by) delegates to it, and `dashboard._live_filter_ticks` asks it too; the dashboard script's `atomsOf` is its one twin, held to it by `tests/test_dashboard.py::TestMixedSelection::test_the_page_shows_exactly_what_the_live_filter_keeps`. An excluded tag written "Category · Tag" must keep excluding only in its own category, `LiveSettings` must keep refusing an excluded category written as a tied tag, a category or tag not excluded must keep trading whether or not any backtest saw it, and an excluded plain tag must keep excluding under every category, since every saved file, flag and scheduled run relies on it. Nor may the filter guess the category or tag of a pair whose series Kalshi's listing lacks while any category or tag is excluded: `main._filter_by_category` leaves such a pair out (with its WARNING), since a ticker-prefix guess could trade it through the exclusion of its real category or tag. Nor read an old saved `categories` or `tags` (a list to trade) as anything but outdated: both stay in `config._RETIRED_TOGGLES`, and a proposal that trades every category, or every tag, because the old list named some is offered only with the defaults server's red warning.
- **Do not let live selling fail open, read a sale's reply as a buy leg's, or move its rule out of the shared functions.** A held market is sold only from a plan whose ladder is known, whose partner (if any) is the one paid-out market that fits, and whose count the account still holds (`trader._holding_problem`, read just before the first order of the position): an unknown ladder, an incomplete positions listing, a missing book or candle and an ambiguous partner each mean no sale and a log line. A sale's count is the plan's, never a position read; its reply is read by `_sale_fill_count`, never `_v2_fill_status` (a part fill is normal, and `_v2_fill_status` raises on one); it goes through `_submit_sale_v2` once, after one pacer place, and is never retried; the reads after a POST that raised stay outside the `except`. The YES ask rounds up and the NO's YES bid rounds down (`_sale_limit`): swapping either sells below the walk. The rule's arithmetic stays in `config.take_profit_reached`/`reached_every_check`/`days_to_maturity`, `scanner.walk_bids` and `historical.usable_candle_ask`/`candle_sale_bids`/`bid_before`; `seller.py` imports `config`, `scanner` and `historical` only and keeps no copy of the fee, the float tolerance or the candle bid rule (`tests/test_seller.py::TestIsolation`); `historical.recent_candles` never reads or writes the candle cache, so a live sale's candle reads touch nothing under `backtest_cache/`. Sales stay before every purchase, and the markets sold stay blocked from both finders and from add-ons (`test_ast_the_live_run_sells_before_it_buys`).
- **Do not let live trimming fail open, size a trim on a value that leaves positions out, or read a trim's count off the account.** A pair is trimmed only from a plan (`seller.plan_trims`) made while every held market's ladder is known and the positions listing was read to its end, the cash on every shard was counted (`AccountBalance.cash_complete`), Kalshi's value of the open positions was read, kept and above $0, and no order rests on the account (`scanner.get_resting_orders`, read last and only then: Kalshi holds a resting order's cash in neither its balance nor its value of the open positions, so an unreadable list counts as one resting) — `main._run_prod` hands `plan_trims` `checked_value_cents`, never the raw `positions_value_cents`: a trim grows as the value it is sized on shrinks, where a purchase is only made smaller by one, so a value that leaves cash or positions out would sell too much. The value is the cash plus the larger of Kalshi's value and what the held markets fetch at this run's bids (`scanner.held_positions_bid_value`), and a pair that alone would fetch more at its best bids than all open positions are valued at stops every trim of the run, as do the pairs whose books were read when together they would. Anything unreadable (the fills list, a book, a best bid a candle could not show, a price then, a pair's kind) means no trim and a log line, never a guess. A trim's count is the plan's, never a position read: it goes out through the sale orders (`_sale_limit` from the lowest bid the walk reached, one pacer place, one POST, never retried, a reply read by `_sale_fill_count`), and `trader._holding_problem` still requires the account to hold exactly what the plan was made on (`SaleLeg.held`) before the first order is sent. Trims are planned in the one sale block, right after the take-profit plans and before any sale is sent, and never for a pair the take-profit rule picked; a pair trimmed in part stays held (a dry run takes out only what its sales would empty, `main._emptied_tickers`), so its ladder stays blocked and it is neither bought nor added to that run. The two settings are read only through `LiveSettings.rebalance` and `.min_price_move`; the AST pin forbids `REBALANCE` and `MIN_PRICE_MOVE` on the live path.
- **Do not count the rebalance wait (a Kelly trim's or an add-on's) any way but `config.rebalance_rested`, or from more than one last-trade day per path.** The wait is whole calendar days between two plain dates, `config.trade_day` of a moment on the bot's own clock (the zone of `config.SCHEDULED_RUN`) and today, and it reads no schedule, so it holds however often a run happens. The backtest asks it in `planned_trims`, of `_last_trade_day` (the latest purchase or add-on, or a later trim), and in the walk's add-on gate, of the day `_held_pair_move` (the same `_last_trade_day`) or `_lone_leg_move` gives; the live trim asks it in `_trim_one`, of the latest fill on either market from `scanner.get_fill_times`, and in `plan_trims`, of the fills list's oldest fill (the list must reach back the whole wait); a live add-on asks it the same two ways, in `seller._add_on_one` (of the same latest fill; for a lone leg, of the latest fill on any market of its ladder in the run's list too, since the finders pair a lone leg only with one of those) and `plan_add_ons`. No `None`, datetime or missing fill ever reaches it, so an absence never reads as rested: a pair with no fill listed last traded no later than the list's oldest fill, an empty or too-short list trims or adds to nothing, and with a minimum price movement set a price that cannot be read means no trim and no add-on, never "no minimum". Each module binds `REBALANCE_MIN_DAYS_SINCE_TRADE` by value and checks its own binding when it applies it (`backtester._resolve_rebalance_min_days`, `seller._rebalance_min_days`), so a test patches that module's binding, never `config`'s; the price move measures from the same last-trade day as the wait on each path, and counts a fall as it counts a rise (`config.price_move_reached`, never a signed comparison of a move).
- **Do not import `trader.py` from `scanner.py` or `strategy.py`** — circular dependency.
- **Do not write output files outside `PROJECT_ROOT`**. All logs, Excel files, and HTML dashboards write relative to `PROJECT_ROOT`. The one exception is the live-run lock, `config.LIVE_RUN_LOCK_FILE` (`~/.kalshi_betting/live_run.lock`, whose folder and holder record `run_lock.acquire()` writes): it is machine-wide state rather than an output file, and it sits in the home folder so every checkout and worktree trading the account shares one lock. Never move it under `PROJECT_ROOT`, or each checkout gets a lock of its own and two real-money runs can trade at once. The run result `main.py --result-file PATH` writes is not written by the bot on its own: it goes to the path its caller names (and to a hidden staging file beside it), and any file already at that path is removed when the run starts.
- **Do not modify `_DATE_PATTERNS` without running `tests/test_scanner.py::TestNormalizeTitle`** — a regression silently causes missed pairs or false positives with no error.
- **Do not import `defaults_server` from any pipeline module, and do not give it a route that serves the dashboard.** It is a human-run tool whose pages write the live defaults every live run trades and start live runs with real orders (pinned by `tests/test_defaults_server.py::TestIsolation`), and any script on a page served from its own address could press its buttons — the dashboard carries scripts. Keep every check in front of a save or a run (Host, Origin, the token over the page's purpose, the fingerprint, the nonce and the raw fields, the used-nonce check right after it, the stale-page re-render, the run's blockers and the attention acknowledgement before any save, the CSP-hashed arming script), and never send `Referrer-Policy: no-referrer`, under which a browser posts `Origin: null` and every honest save is refused.
- **Do not let the defaults server import `main`, `trader` or any other pipeline module, start a process anywhere but `_App._start_run`, or stop a run.** Its one process start is `self._start_process(...)` in `_App._start_run`, in a new session (`start_new_session=True`), so Ctrl-C on the server never reaches a run placing orders; `start_process` defaults to `None`, which refuses every run, and only `main()` passes `subprocess.Popen`, so no `_App` a test (or `_Handler._app()`'s fallback) builds can start `main.py`. A dry run never saves. Confirm and trade saves only after every blocker and the attention acknowledgement have passed, and starts nothing when the save fails. Never kill a run the server started, from the server or its pages: killing a run mid-trade can leave half of a pair open (pinned by `tests/test_defaults_server.py::TestIsolation`, `::TestActions` and `::TestBlockers`). A start that finds its port taken must bind nothing and start nothing: it may only open a page, and only when the listener's `/checkout` names this checkout's resolved root and its current code fingerprint; anything else exits 2 (pinned by `::TestMain` and `::TestBusyPortOverASocket`, whose guard fails any bind that succeeds).
- **Do not write `live_defaults.json` except through `config.save_live_defaults`, and do not add a config.py fallback to `main._resolve_live_settings`.** The writer parses the text exactly as a live run will before replacing the file atomically, then reads it back; `defaults_server._App._post_confirm` is its one caller (the AST pin's `_DEFAULTS_WRITERS`). With no saved file a live run must exit 2 — falling back to config.py's toggle constants would trade values nobody confirmed.
- **Do not let a run that sends no orders take the live-run lock, and do not release it before the run ends.** Only `--mode prod` without `--dry-run` takes it in `main()`, before `build_client`, and the descriptor is closed in the `finally` after the run mode returns or raises; a dry run or a dev run that took it would block the Monday run, and one released early would let a second real-money run trade the same balance. Keep `run_lock.held()` a momentary shared lock and `acquire()`'s retry longer than one such check, or a check could stop a starting run. Keep an error making or opening the lock file an error (exit 1), never `EXIT_RUN_IN_PROGRESS`, which the scheduler counts as a done slot.
- **Do not start the dashboard's Sell workers from a module without a `__main__` guard, and do not move them to the fork start method.** `generate_dashboard(..., sell_workers=N)` with N > 1 spawns its worker processes, and a spawned worker re-imports the caller's main module, so a script that builds a page at import time builds it again in every worker (`backtest.py` runs `main()` only under its guard); fork is unsafe on macOS. Nor publish a page apart from its sidecar folder: `_publish_page` renames the page and deletes the older build folders together, under the lock, so the page in place always has the chunks it names.
- **Do not import `v2_probe` from any pipeline module** — it is a human-run tool that submits real-money orders; a single import would put probe submissions one code path away from the weekly scheduler (a test asserts this).
- **Do not add tests that call the real Kalshi API**. Use `unittest.mock.MagicMock` for `KalshiClient`. Tests should be runnable offline.
- **Do not change the fee formula without updating both** `fee_per_pair_approx()` and `fee_leg_exact()` in `config.py`. The backtester also uses both.
- **Never charge a leg the other leg's fee multiplier, and never leave a fee call to the multiplier's default.** `fee_per_pair_approx`'s `multiplier_a` goes with its `price_a` (market A's in market order, `scanner.leg_fee_multipliers`); code in submission order (the NO leg first, which is market B for a time-series pair) or side order maps each leg to its own market. Do not add a multiplier to `config.CONFIRMED_FEE_MULTIPLIERS` without fills Kalshi charged that match it to the cent.
