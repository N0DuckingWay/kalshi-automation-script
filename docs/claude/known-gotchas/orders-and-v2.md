**Fee ceiling rounding at small `n`:** `fee_leg_exact(1, 0.5)` = `ceil(0.07 * 1 * 0.5 * 0.5 * 100) / 100` = `ceil(1.75) / 100` = `$0.02`. At `n=1`, fees round up aggressively. The exact payoff check `min_payoff > 0` in `compute_trade()` (`min_payoff` is the profit floor for a same-title pair and the profit in either WIN cell for a time-series pair — the in-between cell loses `total_cost_with_fees`) catches this and returns `None` — this is intentional, not a bug. Also: `fee_leg_exact()` rounds to 6 decimals *before* the ceiling so binary float noise (e.g. `175.00000000000003`) can't bump an exact-cent fee up an extra cent — don't remove the `round()`.

**Ambiguity is resolved by position DELTA, never by absolute holdings.** An exception from `create_order` doesn't prove rejection (a timeout can land after the fill), so `_execute_one` consults the account — but the account's *absolute* position in a ticker is not evidence about a specific order: it may already hold contracts from an earlier run or a manual trade. `_execute_one` therefore reads `_position_count()` immediately **before** each submission (the NO leg's ticker first, then the YES leg's) and again after an ambiguous one, and attributes only `_fill_delta(before, after)` — expected `−no_leg.count` for the NO leg and `+yes_leg.count` for the YES leg. The old absolute checks were wrong in both directions: a stale external YES holding made an unfilled YES leg report `"executed"` (leaving the NO leg unhedged while the log claimed a complete pair), and a stale external NO holding made an unfilled NO leg trigger a `reduce_only` sell that liquidated an unrelated position. Compare deltas with `trader._DELTA_EPS` (`1e-6`) — fills are whole contracts, but `position_fp` arrives as a string and is float-parsed. Never reintroduce a bare `held == 0` / `if held:` test. **A delta of ZERO is not, by itself, a confirmed non-fill (DR-63/DR-64).** That rule is about which QUANTITY is evidence — the delta, never the absolute holding — and it is unchanged; what one un-refreshed read cannot establish is that the quantity has stopped moving. A transport error (the `urllib3.ProtocolError`/`ConnectionError`/`ReadTimeoutError` classes `_http._TRANSIENT_NETWORK_ERRORS` lists) can be raised milliseconds after the exchange FILLED the order, and the positions ledger is read-after-write lagged, so the first post-failure read returns the pre-fill value and `delta == 0`. On the YES leg that sent the reduce-only unwind of a NO leg that was really hedging a live YES fill — selling the hedge, leaving a naked YES position, and reporting `"rolled_back"`, which means nothing of the pair is open; on the NO leg it returned `"failed"` ("nothing to unwind") with a full-size UNHEDGED NO position open and no status in `EXIT_TRADES_NEED_ATTENTION` to escalate it, so the run exited 0. Each ambiguous branch therefore re-reads its own ticker ONCE after `trader._V2_MAPPING_RECHECK_DELAY_SECONDS` and judges the RE-READ — the same reasoning `_confirm_v2_no_mapping` already applies (DR-21) and `v2_probe` applies twice over (DR-60, DR-20). An unreadable re-read is the existing unattributable case, i.e. `manual_review` with no order submitted. The NO leg's re-read is SINGLE-SHOT (`_position_count_once`) because it sits in the unhedged window; the YES leg's is the ordinary retried `_position_count`, matching the first read beside it. Both re-reads, like both first reads, stay OUTSIDE the `except` clause for the `__context__` reason above.

**`TradeResult.status` vocabulary** (the legs below are the SUBMISSION legs from `trader._ordered_legs(spec)` — the NO leg first, then the YES leg; which market each sits on depends on the pair type): `"executed"` (both legs filled, or the YES leg errored but the position delta was exactly `+yes_leg.count`), `"simulated"` (dry run), `"failed"` (the NO leg confirmed unfilled — a clean FoK rejection, which includes the exchange's HTTP 409 kill response, or an error with a delta of 0 **on both the first read and the lag re-read**, DR-64; nothing to unwind — and, with nothing sent at all, a pair stopped because the V2 NO-leg mapping was disproven earlier in the process, whose error reads `NO leg not sent: V2 NO-leg mapping disproven earlier in this run; nothing submitted`, and an add-on whose held pair no longer matched it just before its NO leg, whose error reads `not sent: this does not match the held pair it adds to (<reason>); nothing submitted` — see the paragraph after DR-77's), `"rolled_back"` (the YES leg confirmed unfilled — FoK rejection, or an error with a delta of 0 **on both readings**, DR-63 — and the NO leg's immediate-or-cancel unwind of this pair's NO contracts filled in full; anything the account held on that market before the pair is left as it was), `"rollback_failed"` (the unwind did not fill, or — because the immediate-or-cancel unwind can stop part-way — closed only part of this pair's NO contracts; what is left open is an orphaned position. When the unwind's own 2xx response reports a fill count strictly between zero and the NO leg's count N, the CRITICAL and the error text name exactly how many of this pair's NO contracts are still open, N − fill_count — the error ends `; <N − fill_count> of <N> NO contracts still open`, and the CRITICAL still says to check the account; when that count cannot be known — an error response, a transport error, a body that is not JSON or not a JSON object, or a fill count that is missing, not a finite number, below zero, above N, or too long to subtract exactly at decimal's default 28 digits — the CRITICAL says "up to N". A 2xx fill count of exactly zero is a clean `"canceled"`, whose CRITICAL names all N as open), `"manual_review"` (a leg errored and its outcome could NOT be attributed to this order — either position lookup failed, or the position moved by an amount the order can't explain — or the NO-leg mapping was disproven by `_confirm_v2_no_mapping` after a confirmed NO-leg fill, or a pair's NO leg filled after an earlier disproof). `manual_review` submits no order at all — on the YES leg because unwinding could reverse a real fill, on the NO leg because a reduce-only unwind of a position this order may not own would close an unrelated holding, and on a disproven V2 mapping because the unwind rests on the very hypothesis just disproven (the YES leg is left unsubmitted and the NO leg deliberately left in place). The error strings say "NO leg"/"YES leg" (the ambiguous-but-confirmed YES-leg case keeps the word "ambiguous"), and the prod Excel row's Notes cell is prefixed `[<pair_type>: <SIDE_A> A / <SIDE_B> B[ nB=…] fees=$x.xx[ adds to N held]] ` so a row can be read without knowing which pair type it came from (the last part only on a trade that adds to a held pair). Don't "simplify" `manual_review` into an automatic rollback in either leg. A held position's sale has a vocabulary of its own (`reporter.SaleResult.status`: `sold`, `partly_sold`, `not_sold`, `unbalanced`, `manual_review`, `simulated`; see the live-selling paragraph under Key Patterns), kept apart from these: a sale's status lives on `SaleResult` and is never put on a `TradeResult` (the two vocabularies share only `manual_review` and `simulated`, with the same meaning: a person must check, and nothing was sent), and the trade log words a sale's in its Status column as `sold`, `partly sold`, `not sold`, `unbalanced`, `check` and `simulated`.

**FoK price protection:** Every buy leg must be capped so it fills at or below the scanned price plus a small allowance, or not at all. The V2 endpoint, the only order path, has no "market" order type: a taker order is a marketable fill-or-kill LIMIT, and **the limit price IS the price protection** — `trader._v2_limit_price(leg_kind, scanned_price_dollars, market)` (`leg_kind` is `"buy_yes"`/`"buy_no"`; the scanned price is the leg's `_Leg.price_dollars` — `nA`/`pB` for same-title, `pA`/`nB` for time-series) computes it as the scanned price ceiled onto the market's own tick grid (`scanner.tick_size_for_price()`) plus `BUY_SLIPPAGE_TICKS` ticks, and the buy-NO leg sends the complement `1 − cap` as an ask. The scanned price is **quantized to 6 decimals (`scanner._SCANNED_PRICE_QUANTUM`) before that ceiling**, the same round-before-ceil guard `fee_leg_exact()` applies: every scanned ask level is `1.0 − float(bid)` and 20 of the 99 whole-cent complements land one ULP *above* the exact cent (`1.0 - 0.43 = 0.5700000000000001`), which un-quantized ceils a whole extra tick and hands the FoK limit two ticks of tolerance where one was configured. No Kalshi grid point has a 7th decimal, so the quantize can only remove float noise — it tightens or keeps the cap, never loosens it (TS-03). The final price is then **re-quantized (ceiling) onto the grid of the band that actually contains it** — the cap can step up into a coarser band, or be mirrored across the book by the complement, where the scanned band's grid is no longer valid — and clamped one tick inside the open unit interval on this market's own grid (0.99/0.01 on a cent market, not the finest-grid 0.9999/0.0001). Ceiling is chosen because a floor could round a YES cap BELOW the scanned price and make the order structurally unfillable. It is **not** purely protective, and this file used to claim it was: when the final price lands in a COARSER band than the one it was computed on, ceiling moves it AWAY from the scanned price and LOOSENS the cap by up to one destination-band tick (reachable: scanned 0.10 on `tapered_deci_cent` submits 0.11 where 0.101 was intended). That residual is bounded by one tick, is the accepted cost of keeping the order fillable, and is recorded as its own open finding — distinct from TS-10, which fixed the other half by making `tick_size_for_price` resolve a boundary price to the FINEST containing band instead of the first one. Any new order-building code must carry this cap.


**Order-book LEVELS and MARKET eligibility use different price bounds, and must keep doing so (TS-14).** `scanner._bids_to_ask_levels` drops a level whose complement falls outside `config.MIN_ACTIVE_PRICE_DOLLARS`/`MAX_ACTIVE_PRICE_DOLLARS` (`0.0001`/`0.9999`) — the extreme tradeable levels on Kalshi's FINEST grid. It used to use the 0.01/0.99 MARKET-eligibility bound instead, which silently discarded genuine depth on exactly the regimes whose point is sub-cent ticks: on a `deci_cent` or `center_deci_edge_centi_cent` book, every level under a cent or over 99c vanished before pairing, so a full book reached the sizer as a thin one. The drops are now counted and reported as one summary WARNING per book naming the ticker and the count (silent at zero) — the same idiom as the trading-inactive shard skip count — because invisible drops read downstream as genuinely thin depth. **`scanner._MIN_ACTIVE_PRICE`/`_MAX_ACTIVE_PRICE` (0.01/0.99) did NOT move and must not be unified with the level bound**: they answer a different question — "is this MARKET worth trading at all" — where a sub-cent YES ask means a near-settled market, and widening them would turn a 0.9999 quote into a $0.0001 hedge leg. `backtester.py`'s two mirrors of that market bound stay in step with it for the same reason. Widening the market half is a recorded, deliberately-held operator decision, not an oversight.
**The rollback carries the same kind of protection on the unwind side.** The unwind may never be an unpriced order: V2 has no market type at all, and an unwind with no price bound would let a book that collapsed between the NO leg's fill and the unwind realize an unbounded loss. The bound — `trader._rollback_floor_cents(no_leg)` — is the NO leg's scanned entry (`no_leg.price_dollars`: `nA` for same-title, `nB` for time-series — the depth-weighted fill after enrichment) less `ROLLBACK_MAX_LOSS_CENTS_PER_CONTRACT` (12), clamped into the API's valid `1..99` cent range, with `round()` applied *before* `int()` because that price is a cent-quantized book price carried as a float (`0.57 → 56.99999999999999`, which `int()` would truncate to 56):
- **The unwind** — a reduce-only YES **bid** (a held NO is a short YES, so closing it is a buy-back), so that bound is a bid **CEILING** of `1 − floor/100`. `trader._v2_rollback_price(no_leg)` **ceiling**-quantizes that cap onto the grid of the band containing it and then clamps it by `_v2_top_of_grid_price(no_leg.market)` (`V2_ROLLBACK_BID_PRICE_DOLLARS` floored onto its own band — 0.99 / 0.999 / 0.9999 by regime; `v2_probe`'s unfillable-ask step submits at exactly that level, and so does its no-mapping step's closing bid — the probe overrides the loss-floored price precisely because it is verifying a side, not a price). The ceiling direction here is deliberate and is the OPPOSITE trade-off from the buy legs: it loosens the loss bound by strictly under one destination-band tick, because a floor-quantized off-grid cap would sit below every valid level in its band and structurally kill every off-grid unwind — the orphaned-position failure this path exists to prevent. **The V2 unwind is `immediate_or_cancel`, not fill-or-kill**, because the endpoint rejects a `reduce_only` order with any other time in force (its docs, verbatim: "Orders with reduce_only set to true will be rejected unless time_in_force is immediate_or_cancel."): it buys back what rests at or under the cap and cancels the rest, never resting on the book, so it can close PART of this pair's NO contracts (its count is always `no_leg.count`, never a position read, so on a market the account held before the pair it never reaches the older contracts). A partial close reports a fill count that is neither the full count nor zero, so `_v2_fill_status` raises; `_rollback_no_leg`'s `except` catches it and returns `rollback_failed`, and no second order is sent — a partial close is never reported as closed. Its CRITICAL names the exact count still open, N − fill_count, read from the unwind's own response (see the Fill classification bullet), and says "up to N NO contracts" only when that count cannot be known. Pinned by `tests/test_trader.py::TestV2ExecuteOne::test_v2_partial_unwind_is_rollback_failed` and `::TestPartialUnwindCount`.

A book past the bound kills the unwind, or the part of it past the bound (the IOC bid closes only what rests at or under its cap), leaving the NO-leg position, or what is left of it, open — reported as `status="rollback_failed"` for manual review (`_rollback_no_leg(client, spec, no_leg, reason, *, before=)`'s ORPHANED POSITION alerts name `no_leg.market.ticker` and `no_leg.count`, so a time-series rollback failure names `market_b`, not `market_a`, and, when `before` — the NO market's position read before the pair — is not zero, that earlier holding, which must stay open), exactly the path an unfilled market unwind already took, so the caller's contract is unchanged and only the loss is now bounded. Don't "simplify" the unwind back to an unpriced (or flat top-of-grid) order.

**`CandidatePair.max_contracts = 0` means NOT ENRICHED, and nothing else.** Before `enrich_with_orderbook_prices()` it is the dataclass default (`depth_levels` is `()` alongside it) and `strategy.compute_trade` reads it as "no depth cap", taking the single-shot sizing path. After enrichment it is the affordability-bounded qualifying depth — **how many contracts the pair's written leg prices are valid for** — and enrichment never writes 0: a pair whose book holds under one contract at the gap, or whose budget cannot afford one contract pair, is dropped with `tradeable=False` and its own INFO line. That closes the older trap, where `max_contracts` came from `int(total_qty)` over a `float` quantity sum and a qualifying book with `0 < total_qty < 1` enriched to `max_contracts=0` with `tradeable=True`, which `compute_trade` then read as *uncapped*. A pair marked `tradeable=False` may still carry `max_contracts=0` from never having reached the writeback (unavailable orderbook, no qualifying depth, unaffordable) — check `pair.tradeable` first, as before.

**Tick structure drives the V2 order price cap (2026-08).** Live market payloads now carry `price_level_structure` (a string naming the tick regime — observed: `"linear_cent"` = 1c ticks, `"tapered_deci_cent"`, `"deci_cent"` = $0.001 ticks, and `"center_deci_edge_centi_cent"` = the regime all MVE/combo markets migrated to on 2026-08-17, with $0.0001 ticks below $0.01 and above $0.99 and $0.001 ticks in between) and `price_ranges` (an array of dollar-string bands `{"start", "end", "step"}` — a tapered market has multiple bands, e.g. finer ticks near 0/1 and coarser in the middle). `scanner.ApiMarket` now carries both (`price_level_structure: str = ""`, `price_ranges: list[PriceRange] | None = None`, parsed by `scanner._parse_price_ranges`, fail-soft to `None` on anything malformed), and `historical._market_to_dict` passes both through **raw** (not parsed) into the backtest cache, since that dict is JSON-serialized directly. **`scanner.tick_size_for_price(market, price_dollars)` now reads both** to derive the tick grid a V2 order price cap must land on: it returns the **FINEST** `step` among the `price_ranges` bands containing the price, as a `Decimal`, short-circuiting to `Decimal(config.DEFAULT_TICK_SIZE_DOLLARS)` (`"0.01"`) when `price_level_structure` is `""`/`"linear_cent"` or the bands are absent, and falling back to that same default with a `logging.warning` when no band contains the price or every containing band's step is nonpositive. **Finest, not first (TS-10).** A price sitting exactly on a band boundary belongs to two bands, and first-match is only "finer" at a band's LOWER edge — at an UPPER edge the earlier band is 10x COARSER, so `BUY_SLIPPAGE_TICKS` was multiplied by a 10x tick exactly there and the buy cap, which is a bid, was LOOSENED (`tick_size_for_price(m, 0.99)` returned 0.001 where the finest containing band is 0.0001). Scanning every band also means one malformed band no longer discards the valid ones after it, which the old `break` did. The fallback is always safe because the grids are nested ($0.01 ⊂ $0.001 ⊂ $0.0001) — a coarse-grid price is valid on any finer grid. The reverse is NOT true: a fine-grid cap that steps up into a coarser band (or is complemented across the book) can land off that band's grid, which is why `_v2_limit_price` re-quantizes the final price onto the grid of the band containing it. Old backtest cache records (written before this change) lack both keys entirely and read back as `None`; every reader goes through `.get()`, so this is not a crash risk. **On 2026-08-17, all MVE/combo markets migrated from $0.001 to the center_deci_edge_centi_cent regime described above.** That is what made the legacy order path's price protection untenable: its `buy_max_cost` cap was denominated in whole cents: 1c of tolerance — one tick on a whole-cent grid, but 10 ticks on a $0.001 grid and 100 on the $0.0001 edge bands. **Resolved by the V2 migration:** order submission goes to the V2 endpoint `/portfolio/events/orders` (`config.V2_ORDER_PATH`, `ORDER_API_VERSION="v2"`) — dollar-string fill-or-kill LIMIT prices, fixed-point counts, bid/ask sides on the single YES book, and an explicit `exchange_index` — where the tick-aware cap `_v2_limit_price()` (scanned price ceiled to `tick_size_for_price()` plus `BUY_SLIPPAGE_TICKS` ticks) is finally expressible. The legacy `/portfolio/orders` path (integer-cent `buy_max_cost`) is not an alternative: Kalshi deprecated those endpoints in June 2026 and no longer accepts orders on them, and its code was deleted on 2026-09-28 (see the V2-semantics bullets below); `main.py` and `v2_probe` refuse to start on any `ORDER_API_VERSION` but `"v2"`, and the side/price mapping lives in `trader._V2_LEG_SIDE`. Fractional-contract sizing remains a deferred follow-up (`_format_count` always emits `.00`).

**V2 order semantics — built from the docs, confirmed live on 2026-09-28 (see the order-path bullet below).** Every piece of the mapping is deliberately arranged so a correction is a one-line change:
- **Side mapping** (`trader._V2_LEG_SIDE`, the single point of correction): buy YES = `bid` at the capped YES price; buy NO = `ask` at `1 − cap` (selling YES you don't hold IS a long NO); the rollback closes a held NO by buying the YES short back, i.e. a **reduce-only `bid`** capped at the loss floor mirrored onto the YES book and never above the highest tradeable level of the market's own grid (`trader._v2_rollback_price()`; that top level is the finest-grid target `V2_ROLLBACK_BID_PRICE_DOLLARS` = "0.9999" floored onto the market's grid — 0.99 on linear-cent, 0.999 on deci-cent, 0.9999 on a centi-cent edge band — since a flat 0.99 would fail to cross asks resting in (0.99, 1) on sub-cent regimes, and $1.00 is not a tradeable level; see the rollback paragraph above). A held YES is sold by the mirror image, a **reduce-only `ask`** on the YES book (`close_yes`, built by `trader._build_sale_order_v2` for live selling), and a held NO by the same `close_no` bid as the unwind. `close_no` was confirmed live on 2026-09-28; a reduce-only ask that sells a held YES has never been sent live by anything else, which is why `v2_probe --step yes-close` exists: you run it, and it has to PASS before live selling or rebalancing is turned on (a rebalance's Kelly trim sends the same two order shapes). If the exchange reads a leg the other way round, flip the value in that dict — no builder logic moves.
- **Runtime backstop on the NO-leg mapping** (`trader._confirm_v2_no_mapping(client, spec, no_leg, before_no)`): the side mapping above cannot be proven offline, so the **first V2 NO-leg fill of each process** is checked against the account's own signed positions ledger before the YES leg is submitted. It is judged by the **position DELTA across the fill, never by the absolute sign** — the module's standing rule (see the delta gotcha above). `_execute_one` hands in the NO-leg baseline it already took before submitting, and the backstop compares `_fill_delta(before_no, after)` against `-no_leg.count`. Absolute sign was wrong in both directions: an account already long +100 YES on the NO leg's market that buys 10 NO nets +90, a *positive* reading that would have declared the mapping disproven and stopped the pair at `manual_review` with a real unhedged NO leg, while an account already short −100 masks a genuinely wrong mapping and latches a false confirmation for the rest of the process. A delta of **−`no_leg.count`** confirms the hypothesis (an `ask` really did open a NO position) and latches the module-level `_V2_NO_MAPPING_CONFIRMED`, so the check costs one extra positions read per **process**, not per trade — the mapping is a property of the exchange, and one confirmation proves it for every later trade in the run; the latch is deliberately not persisted, so a fresh process re-verifies. For a time-series pair the NO leg is `market_b`, so the read is of `market_b`'s ticker; the latch is **shared across pair types** because it verifies the exchange's side mapping, not a market — a same-title confirmation covers later time-series trades and vice versa. **Any other delta** means the mapping is DISPROVEN live; a delta of **zero** is re-read after each pause in `config.V2_MAPPING_ZERO_RECHECK_DELAYS_SECONDS` (1, 2 and 4 s, so up to 7 s; the first re-read that moved is judged) before that verdict, because an unmoved ledger immediately after a confirmed fill is usually read-after-write lag, not disproof — a lag of about 1 s was seen live on 2026-09-28, so the single 1 s re-read this check used before could read a healthy fill as disproof, and a wrong mapping moves the position the wrong way rather than not at all (a zero that survives every re-read — fill reported, ledger flat — is still contradictory and goes to manual review; the price is that a filled NO leg checked while the mapping is unverified — usually only the process's first — can wait up to 7 s unhedged, and only when the ledger lags). `v2_probe` still judges a zero on one re-read after `_V2_MAPPING_RECHECK_DELAY_SECONDS` (1 s), as do `_execute_one`'s DR-63/DR-64 ambiguous-leg re-reads, so a ledger lagging past 1 s can FAIL a probe step that the trader's check would accept. On disproof: the pair stops at `status="manual_review"` with **the YES leg unsubmitted** (it would hedge a position we don't hold) and **the NO leg deliberately left in place** — the unwind is a `bid` resting on the same disproven hypothesis, so an automated unwind could double the error rather than reverse it (`reduce_only` would make a wrong unwind fail safe into `rollback_failed`, but a human must decide); a `logging.critical` names the remedy: stop trading until the disproof is understood (stop the scheduler daemon, do not run `main.py --mode prod`, and, if the defaults server is running, stop it with Ctrl-C in the terminal running `./start_dashboard.sh` or `python3 -m kalshi_betting.defaults_server` and do not press Confirm and trade) and flatten the position by hand in the Kalshi UI — there is no other order path to fall back on — and says the rest of the run is stopped. When the NO leg's market was not flat before the pair (an add-on to a held pair, or any earlier holding), flattening would close those older contracts too, so the remedy reads instead, e.g., "put the position on T back to 30 NO contracts (-30) by hand in the Kalshi UI (that is what the account held there before this pair; do not close it to 0)" (`trader._restore_remedy`, which says the holding in the words the Kalshi UI uses through `trader._held_words` and writes the number exactly through `config.count_text`; the ambiguous NO leg's run-stopping CRITICAL and the already-disproven branch say the same). A disproof needs a baseline that was read, since an unknown delta is not a disproof; a baseline that was read but is not a finite number (the listing sent something like "nan") gives the flatten text, as a flat one does (`trader._flat_before`). **A disproof stops the rest of the process, and until the mapping is settled pairs run one at a time.** The disproof branch sets a second process-lifetime latch, `_V2_NO_MAPPING_DISPROVEN` (every disproof sets it, a zero delta that survives every re-read included, since the ledger then contradicts the fill report), and `_execute_one` checks it first of all — before any position read, order build or pacer place — returning `status="failed"` with the error `NO leg not sent: V2 NO-leg mapping disproven earlier in this run; nothing submitted`: nothing was sent, so there is nothing to unwind, the run still exits `EXIT_TRADES_NEED_ATTENTION` through the disproving pair's `manual_review`, and `main`'s undetermined-fill count names only that pair. An **ambiguous NO leg** can disprove the mapping too: when the NO POST raises (or answers a 2xx body `_v2_fill_status` cannot classify) the check never runs, so `_execute_legs` treats a KNOWN position move of anything but 0 or −`no_leg.count` as a disproof while the mapping is unconfirmed (a wrong mapping moves it by +count) — it sets the latch and says so in its CRITICAL, and the result's error ends `; V2 NO-leg mapping treated as disproven, rest of run stopped`. Without that, a mapping flip that also changed the response shape would send every pair down the ambiguous path, one wrong-side position each, with the latch never set. An unknown move (the read failed), or any unexplained move once the mapping is confirmed (an unrelated trade), stops only that pair, as before. A latch alone does not bound the damage, because `execute_trades` runs pairs concurrently and every pair already running sends its NO leg before the first check can finish: on the first live run (2026-09-28 02:26 PDT) all 7 NO legs were POSTed before the first mapping confirmation was logged, and without the latch an offline reproduction of 12 pairs whose NO fills all moved the position the wrong way gave 12 NO-leg POSTs, 12 `manual_review` results and 12 CRITICALs. So while neither latch is set (`trader._v2_mapping_unverified()`), `execute_trades` holds each pair back until the one before it has settled the mapping or finished, checking every `config.V2_MAPPING_VERDICT_POLL_SECONDS` (0.05 s); the next pair starts the moment the mapping is settled, even while the pair that settled it is still sending its YES leg or an unwind, and once it is confirmed the rest start together, as before. **The phase is bounded in time.** A pair can finish without a verdict — its NO leg killed, its NO POST raising without a disproving move, its worker raising, or the check unable to read the account — and the next pair then runs alone in turn; when position reads keep failing every pair finishes that way behind two retried baseline reads (~62 s each), which one at a time stretched 7 pairs from about 2 minutes to about 15 and would pass the scheduler's `SCHEDULER_JOB_TIMEOUT_SECONDS` at about 30 pairs. So once the phase has lasted `config.V2_MAPPING_CHECK_SERIAL_BUDGET_SECONDS` (300, operator decision 2026-09-28), `execute_trades` stops waiting for the pair still running (the wait is cut at the deadline), logs one WARNING (`V2 NO-leg mapping still unverified after 300s of running pairs one at a time — …`) and starts the rest together, each still checking its own NO fill. The bound is time, not a count of pairs without a verdict: a first cut capped the phase at three such pairs, and a killed NO leg — one round trip — used up a slot, so three kills in a row started the rest together and a wrong mapping then opened a wrong-side position on every pair in flight (measured by the review: 12 pairs, first three killed, 8 wrong-side positions). The clock starts with the run, so slow position reads spend it before any NO leg is checked: a first budget of 60 s ran out during the first pair's two baseline reads when each read succeeded only after ~35 s, and a wrong mapping then opened 7 wrong-side positions instead of 1 (review measurement) — hence 300 s, which covers a first pair behind such reads (~105 s to a verdict) plus two or three killed legs at that speed. When every position read fails, about three pairs run alone before the rest start (7 pairs ~10–13 min, 30 pairs ~15 min, inside the scheduler's one-hour timeout). The budget also bounds how long a stuck order POST holds the OTHER pairs back; `execute_trades` still returns only when that POST does, since order POSTs carry no request timeout (a pre-existing residual). A disproof inside the budget costs one wrong-side position, plus any earlier pair that went ahead because its check could not read the account (see below); after the budget it stops only the pairs that start after it, so up to `TRADER_MAX_WORKERS` pairs in flight can still send their NO legs. The cost is paid once per process: usually just the first pair's NO POST and check (a few round trips, up to 7 s more when the ledger lags), and never more than the budget. A dry run never reaches `_execute_one`. **Pairs that went ahead unchecked are named.** A pair whose check could not read the account sends its YES leg and reports `executed`, so if a later pair disproves the mapping that position rests on the same wrong mapping. The check's unknown outcome records the NO leg's ticker in `_V2_UNCHECKED_NO_LEGS` (and, when the position read before that pair was a finite number other than zero, that reading in `_V2_UNCHECKED_BASELINES`, rendered after the ticker as, e.g., `(held 30 NO contracts before that pair)`), and every disproof CRITICAL (the check's and the ambiguous leg's) ends by naming them: `Earlier pairs of this run went ahead after their NO-leg fill could not be checked, so they rest on the same mapping: check the positions on … too.` `_confirm_v2_no_mapping` checks the disproven latch before the confirmed one and reads nothing when it is set: a pair whose NO leg filled after another pair's disproof stops at `manual_review` before its YES leg, with no unwind. While pairs run one at a time that cannot happen, since no pair is between its start and its check when the latch is set; it can after the budget, or for a caller that runs `_execute_one` concurrently some other way. **Only a new process clears either latch, so each scheduled Monday run starts clear.** After a genuine disproof, every weekly run therefore opens one more wrong-side position (its first NO fill), and exits 20, until someone stops the scheduler or corrects `trader._V2_LEG_SIDE` — the latch bounds a run, not the weeks. Each run the defaults server's Confirm and trade starts is a new process too, so each press after a disproof would open another; that is why both disproof CRITICALs (the check's and the ambiguous NO leg's) and `v2_probe._STOP_TRADING` name every way a real-money run starts: stop the scheduler daemon, do not run `main.py --mode prod`, and stop that server and do not press the button. `tests/conftest.py` clears the disproven latch, `_V2_UNCHECKED_NO_LEGS` and `_V2_UNCHECKED_BASELINES` before every test. An **unknown delta** (either snapshot missing) is not disproof: it warns, proceeds to the YES leg, and does NOT latch, so the check re-arms on the next NO fill — one flaky positions read must never stall trading. **This read is ONE OF THE TWO SINGLE-SHOT position reads in that window** (`trader._position_count_once`, sharing `_read_position`'s parse with the retried `_position_count`; the other is `_execute_one`'s NO-leg ledger-lag re-read, DR-64, which also pays a 1s pause): it is a blocking call inside the window where the NO leg is filled and unhedged, `api_call_with_retry` can hold a call for ~62s of sleeps, and because a failing endpoint never latches, **every** V2 trade in a 429 storm would pay that stall with a naked NO leg — the same bounded-wait reasoning `_await_transfer_settlement` uses for its unretried balance reads. Don't retry-wrap it, don't make this check unconditional per-trade (it is a per-process property), don't turn the disproven branch into an automatic rollback, and don't drop the disproven latch or `execute_trades`' one-at-a-time phase — without the phase the latch stops only pairs that start after the disproof, which on a portfolio no larger than `TRADER_MAX_WORKERS` (8) is none of them — and don't remove the phase's time budget, or turn it back into a count of pairs, which killed NO legs use up: the budget is what keeps a positions outage, or a stuck order, from holding the whole portfolio one pair at a time.
- **Fill classification:** a full FoK fill reports `fill_count == count`. **A kill arrives as an error, not a 2xx:** the first live probe (2026-09-28) got HTTP 409 `{"error":{"code":"fill_or_kill_insufficient_resting_volume",…}}` for a fill-or-kill ask that could not fill, with the position unchanged. `_submit_order_v2` maps exactly that — status `config.V2_FOK_KILL_HTTP_STATUS` AND code `config.V2_FOK_KILL_ERROR_CODE`, on a `fill_or_kill` body only, recognised by `trader._is_fok_kill` (the probe reads the same helper) — to `"canceled"`, so a killed NO leg ends `failed` and a killed YES leg rolls back at once, with no position read and no pause; any other error response still raises into the ambiguous path, and an error on the IOC unwind stays `rollback_failed`. A 2xx with `fill_count == 0` is still read as a kill. Two residuals: "409 means nothing filled" rests on that one observation, an order with no crossing depth at all — no 409 has been seen for a fill-or-kill that crosses some depth but not enough; and a killed YES leg is now unwound within about one round trip of the NO fill (the ambiguous path it took before waited at least a second), while no live run has shown a `reduce_only` order accepted that soon after the position opens — the probe's close came after DR-21's re-read. If the exchange checks `reduce_only` against a lagging position, that unwind fills nothing and ends `rollback_failed` (a CRITICAL, exit 20). `_v2_fill_status()` maps only the two 2xx shapes to the `"executed"`/`"canceled"` statuses `_execute_one` and `_rollback_no_leg` branch on; a partial fill (a FoK invariant violation on a buy leg), a missing `fill_count`, or anything else logs `logging.critical` and **raises**. That is the design, not an oversight: raising routes into `_execute_one`'s existing ambiguous-exception path, which consults `_position_count` (the account's ground truth), so a mispredicted response shape degrades safely into `failed`/`rolled_back`/`manual_review` instead of being misread as a clean fill or a clean kill. Never "simplify" it into returning a guessed status. **On the unwind a partial fill is a real outcome**, not an invariant violation: the reduce-only unwind is `immediate_or_cancel` (see the rollback paragraph), so it can close part of the position. The same `ValueError` is raised for it, but it never reaches `_execute_one`'s ambiguous path — `_rollback_no_leg`'s `except` catches it and returns `rollback_failed`, sending no further order. It also reads the fill count itself, so its CRITICAL and the error text can name exactly how many NO contracts are still open (N − fill_count): `_submit_order_v2` re-raises the classifier's `ValueError` as `trader._UnclassifiableV2Response` — still a `ValueError`, with the same message, so a buy leg's caller sees what it always did — carrying the parsed body, and `_rollback_no_leg` reads it through `_partial_unwind_counts`, which unwraps it exactly as `_v2_fill_status` does and reads it with the same `_parse_fixed_point`, trusting only a finite count strictly between 0 and N whose remainder it can compute exactly (a local decimal context traps `Inexact`, so a count too long for decimal's default 28 digits is unknown rather than printed wrong); anything else, and every error response or transport error, keeps "up to N", and reading the count sits in its own `try` so it can never cost the orphan alert. The count covers this pair's NO contracts as the response reports them; the account may hold others on the market, so the CRITICAL still says to check the account. `_v2_fill_status` stays one reader for all three orders on purpose: a "partial" status returned there would read a partial NO leg as `failed` and a partial YES leg as a confirmed non-fill, which unwinds the NO leg while a naked YES position is open.
- **Response shape:** the order object may arrive wrapped under an `"order"` key or flat (the probe's NO-buy fill on 2026-09-28 came back flat), and counts as either `fill_count` or the fixed-point string `fill_count_fp` — all four combinations are accepted (`_parse_fixed_point` prefers the `_fp` variant).

- **Required fields, and the optional ones left out.** The endpoint requires `ticker`, `side`, `count`, `price`, `time_in_force` and `self_trade_prevention_type`, and every V2 body sends all six. `self_trade_prevention_type` comes from `config.V2_SELF_TRADE_PREVENTION_TYPE`, `"taker_at_cross"`: an incoming order that would trade against another order on this account is cancelled at that point, where `"maker"` would cancel the account's resting order instead. The bot never leaves an order resting, so the only order it could meet is one placed outside the bot (by hand, or by another client on this account), and `taker_at_cross` leaves that order alone. What the endpoint reports for the bot's cancelled order has not been observed; the trader handles each shape through its existing paths — nothing filled is an ordinary non-fill, a part fill or an error response on a buy leg goes to the position-delta check (a part fill the account shows ends as `manual_review`), and either one on the unwind is `rollback_failed`. `v2_probe` checks only that the probe ticker's POSITION is flat, so cancel any resting orders of your own on that ticker before running it. `subaccount`, `cancel_order_on_pause`, `expiration_time` and `order_group_id` are still not sent and rely on server defaults. - Other fixed choices: the two buy legs are `fill_or_kill` (the whole count at or under the price cap, or nothing) and the unwind and a sale are `immediate_or_cancel` (the only time in force the endpoint accepts with `reduce_only` — see the rollback paragraph); prices are 4-decimal dollar strings (`_format_price`, exactly representing every grid point of every regime); counts are fixed-point strings (`_format_count`); each order body's `exchange_index` is that leg's OWN market's `exchange_index` (the NO leg and its rollback from the NO leg's market — `market_a` for same-title, `market_b` for time-series — and the YES leg from the YES leg's market; a pair's legs can sit on different shards) and never `-1` auto-route, so a wrong shard model is rejected loudly by the exchange instead of silently routed, and an explicit-shard write bills only that shard's rate-limit bucket where auto-route bills every nonzero shard's. `post_only` is always `False` (we are deliberate takers) and `reduce_only` is `True` only on the rollback and on a sale.
