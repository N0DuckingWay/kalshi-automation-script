**Interval-discount calibration (2026-09 follow-up) — `k` is measurable now, but only inside the backtest.** `config.time_series_profit_prob(spread, k=None)` takes an optional per-call override, resolved at call time (`discount = TIME_SERIES_INTERVAL_PROB_DISCOUNT if k is None else k`, so a test that monkeypatches the constant still takes effect whenever `k` is omitted — mandatory, since a `k: float = TIME_SERIES_INTERVAL_PROB_DISCOUNT` default would bind at def time instead), and `backtest.py` exposes it as `--interval-discount K` (`parser.error`s at or below 0 or above 1; omitted/`None`, the default, reads the config constant) plus `--no-sweep` (skips only the extra per-`k` re-simulation grid — the calibration measurement below still runs and logs either way). The live sizer is untouched by construction, not by discipline: it prices at the run's `LiveSettings.interval_discount` (`strategy._kelly_p_at` hands it to `time_series_profit_prob` as `k`, which the AST pin requires of every live call), and a live run's `LiveSettings` comes from the saved live defaults (only `main.py`'s own `--interval-discount` replaces their `k`, for one live run); no module on the live trading path imports a backtest module (the same pin; the read-only Live trading tab's `live_portfolio` imports `dashboard` for its Sharpe and Sortino, and nothing on that path imports it), so live sizing reads the saved `k` (or that flag) no matter what any backtest run passes — calibration writes a recommendation into the backtest log and the dashboard, and neither the backtester nor the dashboard writes `config.py` or the saved live defaults. `backtester.run_backtest()` keeps its positional parameters and `tuple[list[BacktestTrade], pd.DataFrame]` return (its one later parameter is the keyword-only `series_categories=None`, the /series listing the same-title sport check files by, DR-79) by becoming a thin wrapper split at the `k` boundary, so every pre-existing caller of `run_backtest()` (all of `tests/test_backtester.py`, unchanged) still gets byte-identical behavior: `_prepare_entries(hist_client, live_client, start_date, use_cache, max_horizon_days, same_event_ladders=None, *, depth_model=None, series_categories=None) -> tuple[list[dict] | None, OutcomeLabelCoverage | None]` is the `k`-INDEPENDENT prologue (the Monday-feasibility pre-check, `fetch_all_settled_markets`, the eligibility prefilter, both groupings, `_extract_pairs`, the parallel candlestick fetch, and the `_find_entry` sweep — none of it touches a probability model, so it runs exactly once no matter how many discounts get simulated), and `_simulate_at_discount(raw_entries, start_date, initial_balance, k=None, spread_band=None, population="all", *, tier_floors=True, size_cap=None, quiet=False, end_date=None, add_to_held=False, sell_at=None) -> SweepPoint` is the `k`-DEPENDENT tail (the Kelly gate, the outcome-validity and premise-violation checks, the one-pair-per-group dedup, `_drop_cross_type_duplicates`, chronological Pass 2, and `_build_equity_curve`; `run_backtest_sweep` does NOT call `_prepare_entries` — it runs `_prepare_candidates` once and then `_sweep_from_candidates`, which makes one `_entries_for_band` pass per spread band before any simulation. **The prologue's return is a PAIR, and the infeasibility sentinel lives on element 0** (DR-66b): a caller that forgets to unpack holds a 2-tuple, which is never `None`, so its `if raw_entries is None` guard silently goes false and an infeasible window walks into `_simulate_at_discount` holding a tuple. Element 1 is the run's `OutcomeLabelCoverage` census, carried out to the dashboard, and is `None` on exactly the feasibility-short-circuit path, where the fetch never ran — distinct from a censused corpus of zero records, which carries `total=0`. `run_backtest` unpacks and discards it (`raw_entries, _ = ...`), keeping its exact signature and two-tuple return. Each swept point of the primary band ANNOUNCES itself, and every simulation names its resolved `k` (and the band and population it simulated) on its `Backtest complete at k=..., band ..., <population>:` line, with `k` and each band bound printed exactly whenever the short form (`%.3f`, `%g`) would print two different values alike, so every prefix within one sweep is unique: that line is emitted once per swept discount — thirteen times on a run without the band sweep (`--no-band-sweep`, or `run_backtest_sweep`'s own `band_sweep=False` default), and once per band x `k` x population plus each split-half and ex-top run on a band sweep, which the CLI runs by default (with the tier-floors-off family, also on by default there, once more per binding band's cell and each of its checks, carrying " with the tier floors off" after the band) — and used to carry no `k` at all, while the primary's slot went unnumbered so the `Sweeping i/13` counter appeared to start at 2 (TS-21). The empirical measurement, `_interval_calibration(raw_entries, spread_min=None, *, tier_floors=True) -> IntervalCalibration | None` (`spread_min` only LABELS each gap band's tier with the band floor its entries were detected under, and `tier_floors=False` — a tier-off calibration's — labels it with that floor alone, so at a floor of 0 every bucket's tier is 0.0, which a renderer following the documented `tier <= 0` "no floor to print" sentinel would print as "-"/"—" like the pooled row; no tier-off calibration is logged — only the primary band's tier-on one is) (logged by `_log_interval_calibration` at INFO; since DR-72 `None` logs one explanatory line — "no time-series candidate entry with a readable settlement in this window — empirical k_hat is not measurable" — rather than nothing at all; the wording says "with a readable settlement" because the `None` branch also fires when time-series entries existed but every one was dropped for a non-binary outcome, though the sub-counts inside a non-`None` report, e.g. the excluded-premise-violations line, stay silent at zero), computes `k_hat = realised in-between rate / mean(mid spread)`, pooled and per deadline-gap band (`0-7d` / `8-15d` / `16-30d`, edged on `SHORT_DEADLINE_GAP_DAYS`/`MAX_DEADLINE_GAP_DAYS` so no band straddles a price tier) as `IntervalCalibrationBucket(label, tier, n, realised_rate, mean_implied, empirical_k)` rows, where `empirical_k` is `None` — not `0.0` — whenever `mean_implied <= 0`, since the ratio is undefined rather than zero. Each observation's `implied` is the pair's mid spread at its first qualifying Monday's four quotes, `config.time_series_mid_spread(pA, nA, pB, nB)` — the later market's midpoint minus the earlier one's, the very input the forecast multiplies by `k` (DR-78) — so `k̂` and `k` are fractions of one quantity; one pair's mid spread can be zero or negative only when its earlier market's quote is crossed (its YES ask below its own YES bid; on any other entry `_find_entry`'s fee check keeps the later book's width — its YES ask plus its NO ask, less 1 — under the YES-ask gap, which keeps the mid spread above half of it), and so can a bucket's mean, which then reports no `k̂`. **Every `k̂` recorded before DR-78 divided by the mean YES-ask gap `pB − pA` instead, and is not comparable with one measured since** — among them every `k̂` this file quotes from before it, such as the decision record's pooled 0.799 over 545 entries (0.45 / 0.996 / 0.994 by gap band), the entry-checkpoint A/B's 0.891 → 0.958 (0.884 → 0.927 with the tier floors off), DR-73's 0.87 on n=71 and the void 1.114, and every `k̂` in `config.TIME_SERIES_SAME_EVENT_LADDERS`' comment (DR-73's bands and the 365-day ladder run's 0.889), which says so. The report also carries the population it pooled: `IntervalCalibration.observations`, one frozen `CalibrationObservation(gap_days, implied, in_between, event_ticker, category)` per measured candidate in measurement order (market A's event ticker as the entry carries it, and `infer_category` of it — the fallback `BacktestTrade.category` carries), so `_calibration_bucket(label, 0.0, observations)` on that very tuple reproduces the pooled row exactly (a regrouped, reordered or reassembled copy agrees only to float rounding) and a report can regroup the same population through the same arithmetic instead of re-deriving which entries count — the dashboard's `k̂` breakdown does, by Kalshi category, tag and spread band. `event_ticker`/`category` are REQUIRED (the DR-71 reasoning: a forgotten field would file an observation under a category no market has), while `observations` defaults to `()` so hand-built calibrations still build — a consumer tells "not carried" from "no candidate" by comparing `len(observations)` with `pooled.n`, never by testing `observations == ()`. It holds strings and scalars only, at entry scale, never a market record, so the per-band calibrations a sweep keeps pin no record alive (TS-07) — which is why it does not collide with DR-66b's rule that `OutcomeLabelCoverage` must carry no per-category breakdown: that rule is about a CORPUS-scale census holding record examples. Its population is deliberately `k`-INDEPENDENT: read straight off the prepared entries (`_prepare_entries()`'s, or one band's `_entries_for_band()` output inside a sweep), never off `_simulate_at_discount()`'s Kelly-surviving candidates, because filtering by the Kelly gate first would make the estimate circular — a wrong `k` would confirm itself by excluding exactly the candidates that would have disproven it; this is also why an `IntervalCalibration` is computed ONCE per spread band (the primary band's as `calibration`, every swept band's in `calibrations_by_band`) and hangs off `BacktestSweep` rather than off any single `SweepPoint` — it is valid for every `k` at that band. Two same-shape, differently-named premise-violation counts now exist and must never be conflated: `_simulate_at_discount`'s own local `premise_violations` (its WARNING level — now a `logging.log(...)` that drops to DEBUG only on a `quiet` size-cap re-run — and its statement order unchanged from before the split; DR-72 rewrote the wording's named causes, not its position in the pipeline) counts candidates AFTER the Kelly gate — load-bearing statement order, preserved exactly — so it is itself `k`-DEPENDENT, since a different `k` changes which candidates even reach the check; `IntervalCalibration.excluded_premise_violations`, logged separately by `_log_interval_calibration` at INFO, counts over the WHOLE `k`-independent population instead, so it is generally the LARGER of the two.
