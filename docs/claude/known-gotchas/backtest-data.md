# Known Gotchas — the backtest's market fetch, caches, prefilter, candles and event titles

Moved word for word from the "Known Gotchas" section of the project's `CLAUDE.md` on 2026-10-26, when that file was cut down to a short root that indexes these notes. Where the text below says "this file", it means the project's notes as a whole: `CLAUDE.md` and the files in `docs/claude/`. In this file:

- Backtest fetch uses direct signed GETs — the pinned SDK has NO historical_api module.
- `fetch_all_settled_markets()` is sharded, parallel, and incrementally cached — don't serialize it again.
- The old fetch's multi-minute stalls were client-side memory/GC, not API throttling.
- The live-sweep `min_settled_ts` must track `start_date`, not just `cutoff_ts` (fixed 2026-07-13).
- Backtest cache semantics
- The Monday-feasibility pre-check measures its window in UTC.
- Every backtest window runs through today: a market settled after the archive cutoff is priced from Kalshi's live candlestick endpoint (2026-10).
- Daily candlesticks silently produced zero data for most markets — use hourly.
- Backtester pair-extraction eligibility prefilter — don't remove it.
- Event-title resolution is bounded, parallel, paced, and must stay loud.

**Backtest fetch uses direct signed GETs — the pinned SDK has NO historical_api module.** `historical.build_historical_client()` returns a plain prod `KalshiClient`; `/historical/cutoff`, `/historical/markets`, `/historical/markets/{ticker}/candlesticks`, the live API's `/series/{series}/markets/{ticker}/candlesticks` (a market settled after the archive cutoff — see the archive-cutoff gotcha), and `/events/{ticker}` are reached via `historical._signed_raw_get()` (KalshiAuth signs timestamp+method+path, the SDK's rest client executes) composed with `_http.fetch_json_page()` for status checks and `api_call_with_retry` for backoff. Hard-won facts about the archive endpoint (all live-verified 2026-07-13): (1) it IGNORES every server-side time filter (`min_settled_ts`, `max_settled_ts`, etc. all return the identical page); (2) its page size is hard-capped at 1000 (larger → HTTP 400); (3) it is ordered by **`created_time` DESC, ticker DESC — NOT by settlement time** (settlements interleave hours out of order, and long-lived markets created before a date can settle long after it); (4) its pagination cursor is a urlsafe-base64 **protobuf of the keyset position** (field 1 = Timestamp of `created_time`, field 2 = ticker), which `historical._encode_archive_cursor()` reproduces byte-for-byte — this is what makes sharded parallel fetching possible. The live `/markets` endpoint honors `min_settled_ts` AND `max_settled_ts` server-side (page size also capped at 1000), but does NOT serve pre-cutoff settlements — once markets migrate into the archive they disappear from `/markets` entirely. Candlestick candles now arrive with the dollar string in `yes_ask.close` (the old `close_dollars` field is gone); the parser prefers `close_dollars` when present so both formats read as dollars, never cents.

**`fetch_all_settled_markets()` is sharded, parallel, and incrementally cached — don't serialize it again.** A sequential walk of the settled-market history is tens of millions of records at 1000/page (live-measured 2026-07-13: 95+ minutes for 8,300 pages without finishing). The fetch therefore: (a) runtime-verifies archive cursor synthesis (`_archive_cursor_synthesis_ok` re-encodes page 1's last record and byte-compares against the server cursor); (b) fetches one slice per UTC **created-day** via synthesized cursors across `SETTLED_FETCH_MAX_WORKERS` (config.py, 8) threads, persisting each completed slice to `backtest_cache/archive_days/<day>.json.gz`; (c) starts those created-days at `ARCHIVE_FIRST_CREATED_DATE` (config.py, 2021-06-01, a month below the archive's oldest market; or at `start_date`, if a window starts earlier still), NOT at `start_date` — the archive is created-ordered and has no time filter (`/historical/markets` filters only by `tickers`, `event_ticker`, `series_ticker` and `mve_filter`), so a market created before start_date that settles in-window can be found only by reading its created-day, and the assembly's `settle >= start_ts` test drops the earlier days' other records. A sequential **tail** walk below `created_time == start_date` did this job until 2026-10-01 and stopped after `ARCHIVE_MAX_BARREN_PAGES` empty pages; on a 2025-10-01 start it stopped at page 2,813 and missed 60 in-window markets created in 2023-2024 (`LEAVEPOWELL-25-DEC31`, `GTA6-25DEC31`, …) behind runs of 56 and 59 empty pages. The days before the window are small (for a 2025-10-01 start, 1,583 days = 3,001 pages = 2.97M markets, about 58 MB of slices; the day workers fetched those 1,583 slices in 2 min 53 s on 2026-10-01, against the tail's 11 minutes), are reused like every archive slice while the cutoff holds, and are checked once per run: `_check_archive_floor` asks for the newest market created before the first day and WARNs if there is one. An assembled `settled_markets_*` cache built before this change lacks those markets and is still served on a hit — rebuild it with `--no-cache`; (d) sweeps the post-cutoff range as parallel per-**settled-day** windows via `min/max_settled_ts`, persisting fully-elapsed days to `backtest_cache/live_days/`. Any runtime-assumption failure raises `_ShardedFetchUnsupported` and falls back to the original sequential walks (which rely only on documented behavior) — never delete the fallbacks or the runtime checks. **The whole phase is skipped when `start_ts >= cutoff_ts`** (an INFO line says so): the archive holds only pre-cutoff settlements, so no record can satisfy such a window, and proving that by running the cursor-synthesis probe and the walk below start_date cost ~18 seconds and ~50,000 parsed records on every post-cutoff run. Note the skip also silences the synthesis probe on that path, so such a run reports on cursor synthesis at all (TS-25). **The `_fetch_archive_sequential` fallback stops on a barren-page counter, not on a settlement comparison.** No exact stop rule exists on a created-ordered walk: a market created arbitrarily early can settle in-window, so no page proves deeper pages are unproductive. The archive walks used to stop at the first page whose `page[0]` (the newest-*created* record on it, whose settlement time says nothing about the rest of the page) settled before `start_ts` — since most Kalshi markets are short-lived, that fired after one or two pages and silently dropped exactly the long-lived in-window settlers (BS-02). They now stop after `ARCHIVE_MAX_BARREN_PAGES` (config.py, 50) **consecutive** pages containing zero in-window settlements — the same productivity bail-out idiom as `EVENT_TITLE_LISTING_MAX_BARREN_PAGES` / `MVE_MAX_EMPTY_PAGES`, ~50k records of created-time depth past the last productive page. That rule is still not complete — it is what missed the 60 markets above — so the sharded path does not use it and reads every created-day instead; the fallback keeps it because a one-page-at-a-time walk of the whole archive would take hours, and it runs only when cursor synthesis fails. Productivity is judged on ANY in-window settlement on the page, deliberately **independent** of the binary-result and created-time keep filters, so a run of all-voided pages can't spuriously trip the counter. Don't reintroduce a `page[0]`-based stop, and don't judge productivity on "records kept". The test oracle used to replay the same flawed rule, so the parity tests structurally could not catch this; it is now `_expected_in_window`, a direct predicate over the fixture records (see `tests/test_historical.py`). The cursor-synthesis probe issues a real request, so **any** unexpected exception from it (auth, outage, unparseable body) is wrapped into `_ShardedFetchUnsupported` too — it used to escape the phase and kill the run with no warning logged. Both pool loops call `pool.shutdown(wait=False, cancel_futures=True)` when a worker raises: the executor's `__exit__` would otherwise drain every still-queued day (hundreds of them — hours) before the fallback is even reached. **Progress-line labels are load-bearing for diagnosis:** the sharded and sequential paths emit the same line shape, so they are suffixed `[sharded]`/`[windowed]` vs `[sequential]` — with identical labels (the pre-2026-08-03 state) a log cannot tell you which path a run actually took, and a live run was misdiagnosed exactly that way. Each completed slice also logs `N/M complete` with a rate and ETA; don't drop it, it's the only signal of how far a multi-hour fetch has actually got. Slice-reuse rules are load-bearing: archive day files are stamped with the `cutoff_ts` they were fetched under and are ONLY reused while it matches the current cutoff (a cutoff advance migrates markets archive-ward and OFF the live endpoint, so stale slices would silently miss them); live day files cover immutable fully-elapsed UTC days and are reused unconditionally; the frontier (current) day is always refetched and never persisted. Day slices are deliberately reused even under `--no-cache` (they cannot go stale by construction) — that's what makes refresh runs cheap, and an interrupted fetch resumes at day granularity. **Slice records are never accumulated in memory — not across days, and not within one day.** Each pool worker (`_fetch_and_store_archive_day` / `_fetch_and_store_live_window`) persists its own slice and returns only a count, and each phase then hands back a LAZY `_DaySliceStream` from `_assemble_day_slices()` — nothing is read at that point, and every later walk re-reads the slices off disk one record at a time, newest day first, which is the ordering the caller's first-wins ticker dedup depends on (the live phase returns a `_RecordChain` of its frontier spool followed by its stream, the old `frontier + [...]` order). Don't "simplify" by having workers return their records and flattening them: that is exactly what OOM'd a full-history run (2.7 GB RSS only 17% through, growing superlinearly with GC pressure), and it also drags gzip/JSON serialization back onto the main thread where it can't overlap. **The ASSEMBLED corpus is never accumulated either (SS-1 Commit C, 2026-09-24).** A 7-day window's past days held 18,061,549 fetched records of which 7,260,952 passed the backtester's prefilter, at 3,926 B/record (~28 GB), and the old assembly held them in a ticker-keyed `selected` dict, then a list copy, then one whole-list `json.dumps` — the run reached 19.9 GB of physical footprint in that silent phase and thrashed until killed. One generator, `_assembled_records`, now reproduces the old `_merge` EXACTLY — sources in the old order (archive day slices newest-first — every created-day from the first, so the days before the window come after the window's own, where the tail's records used to — below `cutoff_ts`; then live: frontier, then live day slices newest-first, unbounded above), `settle >= start_ts`, the prefilter BEFORE the first-wins ticker dedup, a fresh `seen` set per walk — and `fetch_all_settled_markets` walks it TWICE: walk A (`_count_assembled`) counts what the `Historical endpoint`/`Live endpoint` lines report (the same kept numbers, the same line order — since M9 each line also carries the endpoint's settled records and what the prefilter and the dedup removed, see the prefilter gotcha) and collects the event tickers for `_load_or_build_event_titles` (unchanged); walk B patches `event_title` exactly as before (only when `titles` is truthy) and streams each record straight into the assembled cache through `_DayStreamWriter` (new `write_record`), which is returned as a `SettledCorpus`. Walk B must reproduce walk A — same count and the same order-sensitive `_assembly_identity` over ticker and event_ticker — or `SettledCorpusError` is raised and the writer aborts, publishing nothing (a slice rewritten or pruned between the walks would otherwise write titles resolved for different records). Only tickers are held by a walk, never a record; what stays resident is a sequential fallback's list (as before), the walk's ticker set, the event-ticker set and the title map — the last three scale with the corpus (per-ticker strings, not records). Measured on the 2026-09-24 7-day run (3,989,846 event tickers): the fresh fetch peaked at 2,782 MiB before grouping against 895 MiB for the cache-hit rerun of the same window, and the watchdog placed the fresh run's peak (2,957 MB footprint) at the event-title merge and save, not in either walk — the cost DR-51 removed (see the event-title gotcha). On a synthetic 4,000,000-ticker request, building the set took the process's peak RSS from 51 to 673 MiB, and a steady-state (post-DR-51) title call added 145 MiB on top — mostly the returned title map, one entry per requested ticker (a 4,000,000-entry dict filled one key at a time measures 117 MiB by sys.getsizeof). Pinned by `tests/test_historical.py::TestStreamedAssemblyParity` (the old merge kept verbatim as an oracle, on list and stream sources and on the real phases with each fallback) and `::TestNothingIsMaterialized` (weakref-tracked: zero disk-parsed records alive while titles are resolved, at most the record in hand plus the open file's meta line at every cache write and every corpus step). Don't turn the corpus, a phase's stream or the assembly back into a list anywhere in the pipeline (`list(...)`, indexing, `frontier + [...]`), and don't give a mid-walk read failure a fallback or a skip. A worker no longer holds a whole day either (BS-15): at 2026-08 volumes one UTC day is ~4.4–4.8M markets, and buffering a day per worker sawtoothed RSS 3.4 → 4.3 → 7.89 GB on a 16 GB host. `_fetch_archive_day` / `_fetch_live_window` therefore take an optional `emit` callback; with it set they flush and drop their buffer every `SETTLED_FETCH_CHUNK_RECORDS` (config.py, 50k — the real bound is that plus the page in flight, since flushes land on page boundaries) and return a COUNT instead of a list. No production caller passes `emit=None` any more (SS-1, fixed 2026-09-24): past-day workers stream into their slice file, and the frontier (never-persisted, partial) day streams through `historical._extend_kept`, a sink that applies the caller's `keep` predicate (the backtester's `_can_ever_enter` prefilter) to each batch as its pages arrive and writes the survivors into a `historical._FrontierSpool`, so no frontier record — rejected or kept — is resident beyond the one batch in flight. The frontier used to be accumulated UNFILTERED and filtered only after the whole pool drained — the same records in the same order, but at a peak that grows through the UTC day (1.9M records at 07:30 UTC on 2026-09-24; a full day is up to 9.2M) whatever the window length, and that alone peaked a 7-day backtest at ~5.5 GiB RSS. Don't restore the post-hoc filter. The sink runs on the frontier's worker thread (so `keep` must be thread-safe — `_can_ever_enter` is pure) and the main thread seals and reads the spool only after the frontier future's `result()`. `frontier_future.result()` is LOAD-BEARING: it is the only place a frontier-window failure (an exhausted retry, a non-transient error, `keep` raising on the worker, a spool write failing) surfaces, and the pool's exit waits for the worker either way, so deleting it returns a silently SHORT frontier instead of raising — pinned by `TestFrontierStreamsThroughKeep`'s failure tests. Its return value, discarded until M9, is how many records the frontier window emitted BEFORE `keep`, so the gap to the spool's length is exactly what the prefilter dropped there; that count joins the assembly's `AssemblyCounts` only once the windowed path has succeeded, so a frontier the live fallback discards is never counted beside the sequential walk that refetches its day. **Why a spool and not a list (SS-1 review, fixed 2026-09-24):** filtering as pages arrive still left the keep-passing frontier resident as a list, and its size depends on the WEEKDAY, not on the window's length — `_can_ever_enter` admits every market open over a Monday checkpoint on/after `start_date` that closes at least a day later, so a frontier captured the day after a Monday can be mostly eligible (7,190,452 of the 9,176,306 records settled on Tuesday 2026-09-22 passed `_can_ever_enter(m, 2026-09-17)`, ~28 GB at 3,926 B/record on a 16 GB host). The spool is an ANONYMOUS temporary file (`tempfile.TemporaryFile` in `CACHE_DIR`, unlinked on creation): no later run can find it or reuse it as a complete day, and the OS reclaims it on close or on any process death, so a crash cannot leave a stale one. It carries the day slices' line framing and no meta block, is walked once per assembly walk (a newer walk invalidates a suspended one, which raises if resumed, since they share one file position; a complete walk that ends on a different count raises `SettledCorpusError`), and is closed by `fetch_all_settled_markets` in a `finally` (via `_RecordChain.close()` / `_close_records`) once its two walks are done, on success and failure alike — so the phase's result cannot be walked after the fetch returns. Don't turn it back into a list. Pinned by `tests/test_historical.py::TestFrontierSpool` (no kept frontier record alive at any page request or after the phase; exact old order on every walk; anonymous; closed on success, on a failed assembly and on a failed phase; lifecycle misuse loud). The list-returning `emit=None` form is retained for direct callers; the sequential fallbacks (`_fetch_archive_sequential`/`_fetch_live_sequential`) are separate walks with no sink that apply the same `keep` per record as each page arrives — exact, because the merge re-applies the prefilter before its first-wins dedup, and their progress lines still count records before `keep`; since M9 each also adds what it dropped to the assembly's counts, since the assembly never sees those records — but still hold their whole keep-passing result; a live-phase fallback first closes the partial frontier spool (freeing its disk), since the sequential sweep refetches today anyway. **Two slice formats exist on disk and both must stay readable:** the legacy single gzipped JSON document `{"meta":…, "markets":[…]}` written by `_day_store_save` (hundreds of MB already cached; refetching them costs hours), and the streamed `"jsonl-v1"` format written by `_DayStreamWriter` — meta line first, then one compact market dict per line, in fetch order (server newest-settled-first, which is what preserves the newest-first assembly / first-wins dedup contract). Both writers are kept: the streaming one for the workers, `_day_store_save` for callers already holding a full list, so neither format rots. `_DayStreamWriter` writes to `<path>.tmp` and only `commit()` renames it into place, same atomicity contract as `_day_store_save` — a killed worker leaves no visible slice. `_day_store_iter` is the ONE reader of the format (since SS-1's Commit C; `_day_store_load` is its all-or-nothing list form, `_DaySliceStream` and `SettledCorpus` its streaming users) and routes on file CONTENT (a first line that parses to a dict *without* a `"markets"` key is JSONL), **never on whether a whole-file parse succeeds**: an empty JSONL day is a lone meta line that parses fine as a document, so a parse-success test would misclassify every empty day. It parses JSONL one line at a time and yields each record, applying the optional `keep` predicate per record when a caller passes one (the prescan passes `_discard_all`; since M9 the phases pass none to their day-slice streams — see the prefilter gotcha), so a multi-million-record day is never materialized; the meta block is checked before the first record is yielded, and a fault found later — a malformed line, a truncated or damaged stream, including a damaged deflate block (`zlib.error`, which is NOT an `OSError` and used to escape the prescan as a crash), a non-object record or meta block — raises `_SliceUnreadable` AT the fault, after the records before it were yielded. So `_day_store_load` stays all-or-nothing (the WHOLE slice fails, `None` → refetch), while a streaming walk treats it as fatal: a slice that goes bad after its phase verified or wrote it raises `SettledCorpusError` naming the day and the remedy (re-run; the prescan then refetches it) — deliberately NOT the sequential fallback the old eager assembly took, which would hold the whole range in memory and could not take back records already yielded, and never a silently short corpus. An exception out of `keep` itself is not a file fault and propagates on both formats (before Commit C, a `keep` that raised `OSError`, `EOFError` or `ValueError` — the classes the old `except` caught — read as "slice unreadable" on the JSONL path only; any other exception already propagated). The prescan deliberately loads-and-discards to test slice validity (it passes `_discard_all`, so a streamed slice is fully parsed but nothing is retained), so reused days are decoded three times — the prescan and both assembly walks — which is minutes against a multi-hour fetch, and the alternative (partial-JSON meta peeking) is far more fragile. **The backtester's candlestick fetch (`backtester._fetch_candles_parallel`) is parallel for the same reasons**, across `CANDLESTICK_FETCH_MAX_WORKERS` (config.py, 8) threads, and uses the identical `pool.shutdown(wait=False, cancel_futures=True)` tear-down. It is safe because candle cache paths are strictly **per ticker**, so two workers can never target one path — `_save_gz_json_cache` writes atomically (tmp+replace, so a truncated file can never become visible), but its tmp name is derived from the destination, so a shared cache path would still collide between workers; never introduce a fetch whose cache path is shared across workers. Reads go through `_load_gz_json_cache`, which treats a corrupt/truncated file as a cache MISS (WARNING + refetch) rather than raising out of a worker. Worker exceptions must **propagate** out of `run_backtest`: `fetch_candlesticks` already fail-softs network errors to `[]` internally, so anything that still raises is a real defect (e.g. a market that should have been prefiltered out — the run_backtest tests rely on exactly that KeyError surfacing) and must not be degraded into "this ticker has no prices".

**The old fetch's multi-minute stalls were client-side memory/GC, not API throttling.** The 2026-07-13 live run showed growing pauses (up to ~14 minutes between page-100 log lines, growing roughly linearly with markets held) with ZERO retry warnings logged and consistent ~0.1–0.3s server latency — the cause was accumulating millions of RAW market payloads (30+ fields plus nested `mve_selected_legs` lists) in one Python list. The rewritten fetch normalizes every record to the compact `_market_to_dict()` form at keep-time and streams day slices to disk. Don't "optimize" by deferring normalization or accumulating raw pages again. The same failure recurred on 2026-08-03 in compact form — the phase functions still held every completed slice in a `results` dict *and* flattened it into a second list — so slices are now dropped as soon as they're persisted and re-read at assembly (see the sharded-fetch gotcha above). If a future run stalls again, check RSS before suspecting the API. **The failure class then moved one phase later, into the grouping/pairing step (TS-07).** `_prepare_candidates` (the first half of both `_prepare_entries` and `run_backtest_sweep`) held the whole eligible window as ONE list and built two group maps and two candidate-pair lists over it — until SS-1 (below), which stopped materializing the records that cannot group. Two measurements exist, both on a 16 GB host and both of the same 1,089,165-record FIVE-DAY window (the cheapest run the tool supports) — and they attribute the cost to two DIFFERENT places, so never quote one as if it explained the other. (1) **2026-09-12, cache MISS:** the fetch assembled the streamed day slices into that list and the recorded peak for the run is **6.05 GiB RSS**; that run predates the `_log_rss()` lines, so its own log carries no RSS line to confirm it — the figure was observed outside the log. (2) **2026-09-13, cache HIT:** `fetch_all_settled_markets` returned at its `use_cache` early return (`Loaded 1089165 settled markets from cache`) and assembled NOTHING; the memory went into `historical._load_json_cache`, which does `json.loads(path.read_text())` over the 1.43 GB assembled `settled_markets_*.json` — logged `Peak RSS before grouping: 3816 MiB` and `Peak RSS after pair extraction: 3977 MiB`, i.e. grouping and pair extraction added only 161 MiB to the high-water mark on that path. **That cache-load cost was a real, separate finding** (`_load_json_cache` materializes the whole file as one `str` and then every record from it); **SS-1's Commit C added the streaming reader** — new assembled caches are `settled_markets_*.jsonl.gz`, validated and then walked record by record through `historical.SettledCorpus` — so only a hit on a LEGACY `settled_markets_*.json` still pays it, exactly as before (those files keep loading, whole, as a list). The window is instrumented rather than invisible: `backtester._log_rss()` logs peak RSS in MiB (normalizing `ru_maxrss`, which is BYTES on macOS and KILOBYTES on Linux) at `before grouping` and `after pair extraction`. The `before grouping` line is logged **before** the RAM-budget warning so the two read in causal order: the RSS line is what the fetch or cache load — and, since SS-1, the two passes over the corpus — has ALREADY cost, and the warning (fired when the GROUPABLE subset exceeds `BACKTEST_MARKETS_RAM_WARN`; it counted every eligible market before SS-1) names that subset's share of it and what grouping adds on top. Two rules on that warning: it must not claim to precede the spend — by the time it fires every record it counts is already resident, which is why it counts the groupable records (what stays resident from the warning onward: the corpus is released just before it) and not the eligible ones — and it must print **only the running process's own numbers**, never a figure from another run, because nothing will ever prompt a reader to refresh a measurement baked into a string emitted on every run; the historical figures above belong in `config.py`'s comment and in this file, and nowhere else. `BACKTEST_RECORD_BYTES_ESTIMATE` (2,700) is the PARSED footprint of one cached record — what the list of dicts costs in memory — not its size on disk and not a peak-RSS predictor, since peak also covers whatever transients are live alongside it (the decoded JSON string on the cache-hit path; the group maps and pair lists during pairing). Two measurements on the real 2026-09-07 assembled cache bracket it: ~3.0 KB/record allocated when 195,038 sampled records are decoded under `tracemalloc`, and no more than ~2.4 KB/record resident once that 1.43 GB decoded string is subtracted from the 3,816 MiB pre-grouping peak — so it stays a round estimate between the two. The corpus (`markets`) and the first pass's key index are `del`'d right after the second pass, before any group map exists, and `ts_groups`, `same_groups` and `groupable` in ONE statement as soon as the pair lists are built, before the candlestick pool spawns its threads: nothing below reads any of them, and dropping the group maps ALONE frees no record dicts at all, because `groupable` still references every one of them. That release lowers RESIDENCY across grouping, the candlestick fetch and the `_find_entry` sweep; it does **not** lower peak RSS, which is a high-water mark already reached by that point. All of it is advisory — nothing is capped or dropped. **Known residual of that re-pointing:** when the corpus is a list (since Commit C, only on a LEGACY `.json` cache hit), every eligible record WAS resident up to its release and the `before grouping` RSS line includes all of them, yet the warning does not count them — so a run whose eligible count is far above the threshold but whose groupable count is not (the 7-day window below: 7,260,952 eligible, 184,255 groupable) gets no warning for the list that set its peak; the eligible count is still on the `Markets to analyze` and `Groupable subset` lines, and the cost on the RSS line. **SS-1 (2026-09-24): only the groupable eligible records are grouped, and `_prepare_candidates` builds no eligible list of its own.** A 7-day window (`--start-date 2026-09-17`) found 7,260,952 of 18,061,549 fetched past-day records eligible (99.75% of them MVE combos) at a measured 3,926 B/record under `tracemalloc` — ~28 GB for the eligible list alone — yet both grouping functions drop every single-member group, and only 184,255 of those records share a time-series OR same-title key with another eligible record; the rest can never appear in any pair of either type. `_prepare_candidates` therefore walks the corpus TWICE, treating it as any re-iterable of market dicts. **The corpus itself stopped being a list in SS-1's Commit C.** Until then `fetch_all_settled_markets` returned ONE list, and because the prefilter is applied during its assembly that list IS the eligible set — resident through both walks until `del markets`, and on that window alone ~28 GB. It now returns a `historical.SettledCorpus` (see the sharded-fetch gotcha) that streams the assembled `settled_markets_*.jsonl.gz` cache on every walk, fresh dicts each time, and holds its record count as `len()`: a walk that cannot read the file raises `SettledCorpusError` (a `RuntimeError`), and so does a complete walk that yields a different count. The passes needed no change for it — they were written for any corpus that re-iterates identically — and `tests/test_backtester.py::TestPrepareCandidatesOverASettledCorpus` pins that a real streamed corpus prepares exactly what the list does, in exactly two walks. Only a hit on a LEGACY `.json` cache still hands over a list. What the commit before it removed is the second, filtered copy the old code built and the grouping over every eligible record. Pass 1, `_index_eligible_keys`, counts every record (the `Markets to analyze` figure), applies `_can_ever_enter`, feeds the outcome-label census (an `_OutcomeLabelTally`, so the census costs no pass of its own), and appends `hash()` of each eligible record's two keys to `array('q')` buffers with validity flags — about 27 B per eligible record while the walk runs (187 MiB at 7,260,952 eligible records, measured on synthetic keys, 2026-09-24), plus a transient of about 74 B per record (515 MiB at that count) while `_shared_key_mask`'s `np.unique` computes the keep flags: small beside the records it stands in for, but not "a few bytes" — through `_ts_group_key`/`_st_group_key`, the SAME single definitions `_group_by_normalized_title`/`_group_by_exact_title` now group on (AST-pinned in `tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_both_finders_group_through_the_shared_key_helper`, which is a two-link chain since this change). `_shared_key_mask` (numpy) flags a hash that occurs at least twice among VALID keys of its kind. **Hashing is safe in exactly the direction that matters:** equal keys always hash equal, so a shared key is always kept, and a 64-bit collision can only keep an EXTRA record, which the exact grouping then drops as the singleton it is — results never move (pinned by forcing every hash to collide). Pass 2, `_materialize_groupable`, re-applies `_can_ever_enter` and keeps the flagged records BY POSITION among eligible records — the normalize_title-dominated keys are never recomputed for the records it drops — and **raises `RuntimeError`** if the corpus did not re-iterate identically in anything the mask was chosen from: a different eligible count, or at any eligible position a different `_corpus_identity` — one hash over the ticker and every field either grouping key reads (`event_title`, `title`, `subtitle`) — so a same-count reorder, or a grouping field changed between walks under unchanged tickers, is refused rather than silently misaligning the mask. No other field is compared, because none can change which records are grouped; eligibility is re-applied by pass 2 itself. Every member of every group of two or more is kept, in its original relative order, so the group maps (keys, members, member order, insertion order), both pair lists, the census and every reported number are exactly those of grouping the whole eligible list; the census still logs from its old position through `_report_outcome_label_coverage`, after the RAM warning. Log lines are unchanged in text and relative order except one new INFO line after pass 2 (`Groupable subset: materializing %d of %d eligible markets — ...`) and the reworded RAM warning (`%d groupable markets (of %d eligible) are materialized for grouping: ...`). Not changed: `_can_ever_enter`, both grouping keys, pairing, Kelly, fees and `SETTLED_PREFILTER_CACHE_TAG`. The per-eligible-record cost is unchanged too — pass 1 computes each key once, exactly as the old full-list grouping did — so a long window's pass 1 is as silent as its old grouping step was. **Pruning each market dict to the keys the backtester actually reads is a specified but UNLANDED follow-up**, deliberately gated on a profiling measurement (accept only if peak RSS ≤ 3 GB and the `Potential pairs` counts are byte-identical on the same assembled cache); don't land a pruning diff without it.

**The live-sweep `min_settled_ts` must track `start_date`, not just `cutoff_ts` (fixed 2026-07-13).** `fetch_all_settled_markets()`'s live phase used to always pass `min_settled_ts=cutoff_ts` — correct for the common case (`start_date` far in the past, e.g. the default `2024-01-01`, where the archive already covers everything before `cutoff_ts` anyway), but catastrophic for a narrow recent `start_date`: live-verified 2026-07-13, requesting the last 7 days scanned 20k+ pages (20M+ records) over ~5 hours because the server was asked for everything since `cutoff_ts` (which can trail `now` by a long way) and the existing client-side `settle_epoch < start_ts` check just silently discarded almost every page. Since the live endpoint DOES honor `min_settled_ts` server-side, the fix is `min_settled_ts=max(cutoff_ts, start_ts)` — strictly narrows the server-side window (never widens it, so it can't skip markets the client-side filter wasn't already going to drop) and collapses a multi-hour scan to a bounded one for recent windows. Don't revert to a bare `cutoff_ts` — that reintroduces the unbounded scan for any caller that passes a recent `start_date` (e.g. a quick verification run or a future `--recent-only` mode). In the windowed live sweep this bound survives as the floor of the settled-day windows at the **phase** level: `live_min_ts = max(cutoff_ts, start_ts)` is computed once and never goes below that bound. The *per-window* `min_settled_ts` the server actually sees can be up to 86,399s below it, though — the first window rounds `live_min_ts` down to UTC midnight (`first_lo = live_min_ts - (live_min_ts % _DAY_SECONDS)`) so windows align on day boundaries. This is harmless: the live endpoint serves nothing before the archive cutoff regardless of what `min_settled_ts` asks for, and the client-side `_merge` step still drops any record with `settle < start_ts`. The existing tests use a midnight cutoff, so they cannot observe the rounding; don't read "tests assert the minimum" as proof the per-window value never dips below `max(cutoff_ts, start_ts)`.

**Event-title resolution is bounded, parallel, paced, and must stay loud.** `_load_or_build_event_titles` resolves `event_ticker` → title in three phases: bulk `get_events` listings (settled/closed/open), the MVE listing (capped at `MVE_TITLE_LOOKUP_MAX_PAGES`), then a per-ticker `/events/{ticker}` fallback. That fallback costs **one HTTP round trip per ticker** and was written for a handful of stragglers — but a 21-day window measured **289,235 unresolved tickers** live (2026-08-03), and the 2026-09-24 7-day run 3,987,139, where the original sequential, uncapped loop ground for hours emitting nothing, which is indistinguishable from a hang. It is now capped at `EVENT_TITLE_FALLBACK_MAX_LOOKUPS` (5000) and run across `EVENT_TITLE_FALLBACK_MAX_WORKERS` (8) threads, each pausing `EVENT_TITLE_FALLBACK_RATE_LIMIT_SLEEP_SECONDS` (0.15 s) after every lookup, success or failure — the `fetch_candlesticks` idiom (DR-51). Unpaced, 5,000 lookups drew 268 retried HTTP 429s in 2m03s; pacing lowers the rate but does not guarantee zero 429s — the candlestick fetch paced the same way ran at about 24 requests/s and still drew them on 4–5% of requests. **How the cap is spent (DR-51):** when every still-unresolved ticker fits under it, all are looked up (sorted); when they do not, the cap goes to NON-combo tickers only, in ticker order with the tickers the accumulator has never answered first (then its stored pills, then tickers it already titles — only the first group exists with the cache on), and every combo ticker (the KXMVE family, read through `scanner.event_series`) is deferred. A combo's event title has no measured effect on which pairs form — DR-54/55 refuse every combo-vs-combo same-title pair, and on the 2026-09-08/09 day slices no combo shared even the time-series key with a non-combo — while a non-combo's does (TS-11). The old single sorted list spent the whole cap on whatever sorted before "KXMVE" plus the head of the combo block, and on the 2026-09-24 run skipped `KXNFLEVERYWEEKCOMPETE-27` (34 markets) among the 3,982,139 tickers it skipped. This decides which LOOKUPS to spend, never an MVE exclusion: combo markets are still fetched, cached, grouped and paired by the same rules. **What it does change is an input to those rules.** A combo the old sorted cap reached was looked up and titled — that run's census logged `event_title` on 27,934 of 7,274,215 eligible records, 18,671 of them among its 18,705 non-combo records, so 9,263 combo records carried a title — and a deferred combo now stays blank unless the accumulator already holds its title. That moves those markets' grouping keys and the `event_title` and deadline-phrasing census figures, so a post-DR-51 fresh backtest's outcome-label census is not comparable with a pre-DR-51 one; it does not change which pairs form, because the 2026-09-08/09 measurement above was taken on day-slice records, which carry no `event_title` at all (it is patched in at assembly). **A deferred ticker is not looked up and nothing is stored for it (DR-51)** — its return value is whatever the accumulator already holds (`""` unless an earlier run titled it), and a later run tries it again. For non-combo tickers that later run advances past this one's slice either way: with the cache on because every ticker this call answered is no longer unresolved, and under `--no-cache` (which re-resolves every requested ticker) because the tickers the accumulator has never answered take the cap first — a plainly sorted cap looked up the same head on every `--no-cache` run and never reached the tail. Only a genuine answer is stored: a title, or the `""` poison pill for a lookup that failed or an event listed without a title, so a genuinely unresolvable ticker is not re-paid every run (no failed lookup appears in any retained backtest log). A deferral that includes non-combo tickers is a WARNING naming both counts; a combo-only deferral, expected on every bulk window and without pairing effect, is INFO, so the WARNING keeps meaning something. Every phase logs progress, and one closing INFO line partitions every ticker the CALL was asked about — resolved by this run (bulk listings / per-ticker lookups), answered from the accumulator, recorded as unresolvable, deferred — and gives the accumulator's size before and after (DR-42; the old line printed the whole seeded accumulator as "this run" — 7,986,570 on a run that resolved at most about 7,525 — and "answered from the accumulator" as 0 by construction whenever the cache was on). **Never make this phase silent again, and never remove the cap** without replacing it with something else bounded. The bulk listings are bounded too, by a productivity bail-out (`EVENT_TITLE_LISTING_MAX_BARREN_PAGES`, 50 consecutive pages resolving nothing → move on), the same idiom as `MVE_MAX_EMPTY_PAGES`. That matters because a listing is an O(all events) scan for a specific ticker set, and `get_events` **excludes MVE events by API design** — so for an MVE-heavy miss set it can never resolve them no matter how long it pages. Live-measured 2026-08-03: the `settled` listing resolved 8,696 of 289,235 tickers in its first ~500 pages, then 9 more across the next 400.
