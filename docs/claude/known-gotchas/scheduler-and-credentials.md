**Every scheduled job is registered through `scheduler._guarded_job` (DR-59, fixed 2026-09).** `schedule.Job.run()` assigns `self.last_run` and calls `self._schedule_next_run()` only AFTER `job_func()` **RETURNS** (verified against the installed library's source), so an exception that ESCAPES a job leaves `next_run` in the past. `scheduler.main()`'s poll loop catches it (`Scheduler tick raised — daemon continues`) and keeps the daemon alive, but the job is still overdue — so `run_pending()` re-enters the SAME job on the very next 60-second poll tick, turning a weekly production trading run into a once-a-minute one for as long as the fault persists. `run_job` really can raise: the slot-CLAIM `_save_state()` sits OUTSIDE its `try`, the finalizing `_save_state()` sits after that `try` has closed, its two `except` clauses (`TimeoutExpired`, `OSError`) are scoped to the `subprocess.run` call alone, and `subprocess.run(..., capture_output=True, text=True)` decodes the child's streams strictly, so one non-UTF-8 byte raises `UnicodeDecodeError` (a `ValueError`, matching neither clause). The same mechanism defeats the blind-retry one-shot contract: `_blind_retry` signals "run me once" by RETURNING `schedule.CancelJob` — `schedule._run_job` cancels on the value RETURNED to it, never on the identity of the registered function — so a retry that raises returns nothing, is never deregistered, AND never advances the `SCHEDULER_BLIND_MAX_RETRIES` cap, which rides solely on the `retries` argument each attempt hands its successor. **The guard sits at the REGISTRATION boundary, not inside any one helper**, which is what makes it cover every escape path a job has rather than the ones an individual helper happens to know about; `.do(_guarded_job, job, *args, **kwargs)` forwards everything after the first argument through `functools.partial`, so the wrapper is transparent on the healthy path. Two registration sites, and both must stay wired: `main()`'s `_weekly_job().do(_guarded_job, run_job)` (no `on_error` — a RECURRING job must be rescheduled by a failure, never cancelled by one) and `run_job`'s blind retry `.do(_guarded_job, _blind_retry, retries + 1, on_error=schedule.CancelJob)` (a ONE-SHOT must deregister itself even when it raises). `_save_state`, `_load_state`, `_maybe_catch_up`, `_startup_catch_up`, `run_job`'s body, the exit-code mapping, the retry cap and BS-17 slot accounting are all deliberately unchanged — in particular `_save_state()` still RAISES, so a failed slot CLAIM still prevents the subprocess spawn (a real-money run with no recorded slot would break BS-17's invariant that a claimed slot always has a record). `KeyboardInterrupt`/`SystemExit` are not `Exception` subclasses and are deliberately not caught, so Ctrl-C still stops the daemon. **The weekly wiring is pinned by AST, and must stay pinned:** `main()` spawns a real prod run and is never invoked by the suite, so no runtime test can reach that line — without `tests/test_scheduler.py::TestGuardedJobRegistration::test_ast_weekly_job_is_registered_through_the_guard` (and its `on_error` sibling for the retry), an edit reverting to `.do(run_job)` restores DR-59 with a green suite. On a healthy host nothing changes; the only behaviour change is that a raising job abandons its slot and waits for the next scheduled fire instead of re-firing every minute. **That trade-off is deliberate and is the accepted cost:** a TRANSIENT fault at 09:00 that the old code would have re-entered 60 seconds later now costs the whole Monday slot, and a raising blind retry ENDS the retry chain for that slot (`on_error=CancelJob` deregisters it) — either is recoverable only by `_maybe_catch_up` on a daemon RESTART, never while the daemon keeps polling. It is still strictly better than the alternative it replaces, which is a real production trading run every 60 seconds for the duration of the fault.

**`KalshiClient` monkey-patch pattern:** The SDK does NOT accept `api_key_id` or `private_key_pem` as constructor parameters. They must be set as attributes on the `Configuration` object:
```python
cfg = Configuration(host=url)
cfg.api_key_id = key_id        # detected by hasattr() inside SDK
cfg.private_key_pem = pem_text
client = KalshiClient(configuration=cfg)
```
Do not "fix" this by moving them to the constructor — it will break silently.

**`secrets.json` may be missing outer braces.** `auth.py` wraps it if needed. New code must call `auth.build_client()` rather than reading `secrets.json` directly.

**Backtest uses prod credentials**, not sandbox. The Kalshi historical API endpoint doesn't exist on the sandbox. `historical.py` always calls `build_prod_live_client()`.

**Dev mode reads no positions (`get_held_positions`)** because the sandbox account is separate and has no positions from production. Don't add held-ticker filtering to `_run_dev()`; for the same reason a dev run never adds to a held pair, whatever its `rebalance` says (`main.py --help` says the flag is for production runs only), and has no positions-value check (`main._checked_positions_value` runs in production only). For the same reason it never calls `scanner.resolve_held_ladders` and hands the finder and `select_portfolio` no held ladders (DR-76); `select_portfolio`'s within-run rule — at most one time-series trade per ladder among the specs it picks — applies in dev as in prod, since it lives inside `select_portfolio`. Holding nothing, dev spends its virtual `--sandbox-balance` as both the portfolio value and the cash (`_run_dev` hands enrichment, `_compute_trade_specs` and `select_portfolio` the same number). Dev also never sells or trims, whatever its `sell_at` and `rebalance` say: it holds nothing, so `seller.plan_sales` and `seller.plan_trims` are never called there (`main.py --help` says `--sell-at` and `--rebalance` are for production runs only).
