# Known Gotchas — Kalshi API drift, exchange shards, balances and transfers

Moved word for word from the "Known Gotchas" section of the project's `CLAUDE.md` on 2026-10-26, when that file was cut down to a short root that indexes these notes. Where the text below says "this file", it means the project's notes as a whole: `CLAUDE.md` and the files in `docs/claude/`. Section names the code and README use ("Key Patterns", "Known Gotchas", "Module Map") name the folders of `docs/claude/`. Each paragraph is one line, some of them long: find one with `grep -n`, then read that line by number.

In this file:

- Live fetching bypasses the SDK's response models (2026-07 API drift).
- Exchange sharding — ingest tags every shard; only trading-inactive shards are dropped.
- Coverage is audited, never assumed.
- Sizing is cross-shard; collateral is made fungible before execution.
- Order routing is per leg.
- The balance read is raw, shard-aware, and returns PER SHARD — callers sum for gate/sizing (2026-08-14).
- Collateral transfers are centicent-denominated, asynchronous, and never retried.

**Live fetching bypasses the SDK's response models (2026-07 API drift).** The Kalshi API (a) rejects events page sizes above 200 with HTTP 400 (`MARKET_PAGE_SIZE` is now 200 and must stay ≤ 200), and (b) no longer populates the legacy integer fields the pinned SDK's response models type as required: markets lost `yes_ask`/`no_bid`/… (prices now only in `*_dollars` strings) and positions lost `position`/`market_exposure`/… (count now in the `position_fp` string) — so modeled calls that deserialize nested markets, any non-empty positions page, or any order (`Order` lost `yes_price`/`fill_count`/…) raise pydantic `ValidationError`. Therefore `scanner.fetch_open_events_with_markets()`, `scanner.get_held_positions()` (which `get_held_tickers()` reads) and `trader._position_count()` call the SDK's `*_without_preload_content` raw-response variants and parse the JSON themselves (markets into `scanner.ApiMarket` dataclasses). Order submission was the highest-stakes case: the modeled `create_order` (for the retired `/portfolio/orders` endpoint) would raise AFTER the order was placed, which would have pushed every real fill into the ambiguous-exception path; the V2 create-order route has no SDK method, so trader's `_build_no_order_v2`/`_build_yes_order_v2`/`_build_rollback_order_v2` build the JSON body by hand and `_submit_order_v2` signs and sends it through `_http.signed_request_json`. Two rules: (1) the raw variants do NOT raise on 4xx/5xx, so every raw call must go through `_http.fetch_json_page()`, which re-raises non-2xx as `ApiException` to keep prior error semantics (`api_call_with_retry`'s 429/5xx backoff for market data; order submission stays retry-free per the rule above); (2) don't "simplify" back to the modeled calls (`client.get_events(...)`, `client.get_positions(...)`) — they crash on live responses. **Event listings drifted too (2026-08).** They were previously safe through the modeled calls (no nested markets), but the live API now sends `category: null` on some events while the pinned SDK types `EventData.category` as a required `str` — so `get_events` and `get_multivariate_events` raise pydantic `ValidationError` mid-listing. Verified 2026-08-03: this killed a backtest *after* a successful 28-minute fetch. `historical._load_or_build_event_titles` therefore uses `get_events_without_preload_content` / `get_multivariate_events_without_preload_content` through `fetch_json_page` for BOTH bulk listings; the modeled `get_event` (singular) was already unusable — it embeds nested `Market` models — so the per-ticker fallback continues to use a raw GET. There is now no modeled SDK call left in the codebase at all — `verify_auth` (`auth.py`) was the last one, migrated to `get_balance_without_preload_content` for the same reason (BS-10); don't reintroduce a modeled call anywhere. Related drift: the MVE events listing is effectively unbounded (hundreds of thousands of auto-generated collection events) and on prod currently returns zero nested markets regardless of `with_nested_markets` — the MVE pull in `fetch_open_events_with_markets()` bails out after `MVE_MAX_EMPTY_PAGES` (25) consecutive pages that contribute no ACTIVE nested market, and the backtester's title lookup caps its MVE scan at `MVE_TITLE_LOOKUP_MAX_PAGES` (500); without those caps the scan hangs for hours (this is likely why the 2026-07-06 prod run logged nothing after auth). Don't remove the bail-outs. **Every cursor loop in `scanner.py` is bounded twice over (TS-05)** — the two in `fetch_open_events_with_markets()` and the one in `get_held_positions()`: each keeps a `seen_cursors` set, so a keyset that CYCLES (`A, B, A, B, …`) and therefore never repeats *consecutively* is caught as well as the plain stuck cursor the old `new_cursor == cursor` guard proved; and each stops unconditionally at `SCANNER_MAX_PAGES` (config.py, 5000 — ~1M markets at `MARKET_PAGE_SIZE`, against a ~135k-market prod ingest), which bounds the walk against any cursor pathology whether or not anyone enumerated it. These were the last unbounded scans in the ingest path, and `get_held_positions` runs before any pairing, so an unbounded walk there means the run never scans at all. `get_settlements` and `get_fill_times` carry the same two bounds. The MVE loop's `MVE_MAX_EMPTY_PAGES` productivity bail-out is independent of both and keeps its own counter and reset semantics — don't fold them together. The warning text still contains `cursor did not advance` (now "(repeated)"), which tests pin. **The counter must track productive (active-market) pages, not raw nested-market presence (fixed 2026-08, found live in sandbox).** The bail-out originally reset on the raw `len(markets)` per page regardless of status; on sandbox, the MVE listing serves thousands of pages whose nested markets exist but are all non-active (closed/settled/determined) — those pages kept resetting the counter forever, so the bail-out never fired and a sandbox validation run paged 4,600+ times flat at the same appended-market count. On prod this bug was invisible because prod happens to return zero nested markets per page either way. The fix counts only markets actually appended (status == "active") toward the reset decision. Same drift hits the orderbook: `scanner._fetch_orderbook()` also uses a raw GET, and the book arrives in one of two **matched** key generations tracked by `scanner._ORDERBOOK_SIDE_KEYS`, where each container key owns an ordered tuple of candidate `(yes_key, no_key, unit)` side-key sets and is NEVER read with another container's sets:
- `orderbook_fp` ⇒ `yes_dollars`/`no_dollars` only, **dollar strings**. This is what production actually receives today; its handling must stay behaviour-identical (a prod dry-run should log zero mismatch warnings).
- `orderbook` ⇒ `yes_dollars`/`no_dollars` (**dollars**) if present, else `true`/`false` (**integer cents**). Both shapes come straight from the pinned SDK's `models/orderbook.py`: the `Orderbook` model *requires* `yes_dollars`/`no_dollars` and aliases its legacy int arrays as `"true"`/`"false"` — it never had `yes`/`no`, which the table wrongly assumed until this was corrected (BS-03).

`_fetch_orderbook` picks the container by key *presence* (not truthiness), then takes the first candidate set of that container whose **both** keys exist — a set is only ever taken whole, so a unit can never be inferred from the wrong keys. Cents levels are validated (whole cent in `[1, 99]`) and converted `/100.0` to dollars **before** `_bids_to_ask_levels`, which stays dollars-only by contract; an invalid level is dropped with a WARNING naming the ticker and the raw value, because cents fed straight through that parser yield `1 - 45 = -44` and get silently discarded, turning a full book into a *silent* empty book (BS-12). Degenerate containers: present but `None` or `{}` ⇒ an **empty book** `{"yes": [], "no": []}` (a market with no resting bids, not drift — no warning, BS-28); a side key present but empty/`null` ⇒ that side has no resting bids, also fine; a **non-empty** container matching none of its own candidate sets (or a non-dict value) is logged as a **potential key mismatch** and returns `None` (fail-closed) rather than cross-reading another generation's keys. Don't collapse this back to a flat `data.get("orderbook_fp") or data.get("orderbook")` with an independent `yes_dollars or true` side lookup: that decoupling is exactly the cross-generation read this guards against. `TestFetchOrderbookKeyMapping` in `tests/test_scanner.py` pins every generation, unit, and degenerate container above against the SDK-documented shapes. **Context (from `main`, 2026-03-12):** Kalshi removed every legacy integer price field from its REST/WS payloads that day, and production serves `orderbook_fp` only — so the `orderbook` container and its cents arrays are not expected on the wire today. They are kept as SDK-shape-derived DEFENSE, not as a live code path (the pinned SDK still models exactly those shapes, and the alternative to parsing them correctly is not "no code" but a silently empty book, BS-12). Nothing about that weakens the fail-closed rule: an unknown container, or a known container matching none of its own candidate sets, still returns `None` with a mismatch warning.

**Exchange sharding — ingest tags every shard; only trading-inactive shards are dropped.** Kalshi has partitioned the exchange into parallel shards identified by an integer `exchange_index` on market payloads, in the account balance breakdown, and in `GET /exchange/status`'s `exchange_index_statuses` array. Each shard has its own markets, order books, and slice of account funds. **Market data is cross-shard** — the events/markets/orderbook endpoints return every shard's markets, tagged — so ingest LABELS and keeps them: `scanner._shard_index()` reads the field fail-safe (missing/null/unparseable => `config.DEFAULT_EXCHANGE_INDEX`, since absence is the pre-sharding/sandbox shape and must never empty the market list) and `scanner._market_from_dict()` stores it on `ApiMarket.exchange_index`. The sole ingest-time shard exclusion is `inactive_shards`, passed into `scanner.fetch_open_events_with_markets(client, inactive_shards=...)` by both `main._run_dev` and `main._run_prod` from `scanner.fetch_shard_statuses()` — and forwarded by `find_time_series_pairs`' own no-`markets` fallback fetch, which used to pass none (TS-27; that fallback is DEAD CODE today, unreachable in production and in the suite, so this closes a trap for a future caller rather than a live hole): nothing on a shard the exchange itself reports `trading_active=false` for can be traded, nor should it linger as a stale candidate. **`trading_active` is TRI-STATE on the parsed statuses — `True`, `False`, or `None` when the payload carried no such key — and only a `false` drops a shard at ingest (TS-04).** An absent or renamed field is "unknown", never "halted": coercing it to `False` (the old `bool(entry.get(...))`) marked every shard inactive, dropped every market, and still exited 0 claiming full coverage, so a single renamed field emptied the whole ingest — the same drift class that already hit markets, positions, orders, events and balance, and the same fail-safe policy `_shard_index` applies to a missing `exchange_index`. `fetch_shard_statuses` logs one summary WARNING naming how many shards carried no flag (silent at zero), and every consumer — `inactive_shard_indexes`, `check_shard_coverage`, `main._log_shard_coverage` — tests `is False` / `is not False`, never truthiness; one leftover truthiness test silently reintroduces the bug. `trader._transfers_active` reads a different key (`intra_exchange_transfers_active`) and keeps its `bool()` coercion, because a missing transfers flag correctly means "don't move money". **Absence is not the only drift shape: a RE-TYPED flag must keep its meaning too (TS-04b).** A JSON boolean that arrives as its string form is truthy in Python — `bool("false") is True` — so the old bare `bool()` coercion read a HALTED shard as open and kept scanning and trading it. Every flag in the parse therefore goes through `scanner._status_flag(raw)`, which resolves, in order: a real bool; the numeric spellings `0`/`1`; then, for strings, the closed token sets `config.EXCHANGE_FLAG_NULL_TOKENS` / `EXCHANGE_FLAG_FALSE_TOKENS` / `EXCHANGE_FLAG_TRUE_TOKENS` (stripped, lower-cased), where a stringified null (`"null"`, `"none"`, `"nil"`, `"undefined"`) reads as unknown rather than as open. An UNRECOGNISED value resolves by truthiness, in the one direction that cannot break a reading that is correct today: a falsy one (`0.0`, `""`, `[]`, `{}`) keeps the `False` that `bool()` already gave it — un-dropping a halted shard is the one change this must never make — while a truthy one (`2`, `"maybe"`) becomes `None`, which every `trading_active` consumer already treats exactly as it treated `True` (the shard stays ingested, audited and scannable). Do NOT "clean this up" into "any non-bool is unknown": that is a no-op for the drifted `"false"` (`None` and `True` are indistinguishable at every consumer, all of which test `is False`) AND it un-drops every falsy non-bool. The three flags then differ in what UNKNOWN means, which is why the final step is deliberately not uniform: `trading_active` stores the tri-state verdict as-is (unknown keeps the shard in the ingest — TS-04), while `exchange_active` and `intra_exchange_transfers_active` store `_status_flag(...) is True`, so anything but a recognised true — absent, null, false or unreadable — is stored as `False` and fails closed. That asymmetry is why the money flag matters at all: `trader._transfers_active` reads `intra_exchange_transfers_active`, and a drifted `"false"` read as `True` fires a real, non-idempotent, never-retried collateral POST at a shard whose transfers the exchange has disabled; `scanner.fetch_shard_statuses` is the single parse boundary, so the value reaching `trader` is always a real bool and the `bool()` there is a no-op on it. A second summary WARNING (separate from the absent-flag counter, silent at zero) names each drifted shard, flag and raw value, with the value's `repr` bounded by `config.EXCHANGE_FLAG_DRIFT_REPR_MAX_CHARS` so one drifted array cannot put a multi-KB line in the log on every run (the TS-02 failure class). The absent-flag counter still counts only genuinely ABSENT keys — a key that is present but unreadable is named by the drift line instead. A non-zero skip count logs `Skipped %d markets on trading-inactive exchange shards %s` (silent at zero), and the per-shard ingest census `Ingested markets by shard: {...}` is logged on EVERY fetch — it is the only signal of which shards a run actually saw, and is what makes a category migration visible. There is no `_on_routable_shard` any more; do not reintroduce a drop-at-ingest shard filter. **Migration facts:** shard 0 and shard 1 were both observed live on 2026-08-14; all combo/MVE markets moved to shard 1 on 2026-08-17; crypto moved to shard 2 and tennis/baseball to shard 3 on 2026-08-24. A shard-0-only scanner is therefore blind to most of the exchange — that is what this flip fixes.

**Coverage is audited, never assumed.** `scanner.check_shard_coverage(advertised, market_shards, balance_shards)` is a PURE comparison (no I/O, no logging) returning `(critical, warnings)`; `main._log_shard_coverage()` is the only thing that decides how loudly to report them and is called from both run modes immediately after the fetch, BEFORE held-ticker/horizon filtering (a blind spot must be measured against what ingest actually saw). The severity split is deliberate: an advertised `trading_active` shard that produced ZERO ingested markets is **CRITICAL** when it also holds account funds — money on a shard whose book we never scanned is a real blind spot — and only a **warning** when it holds none, because an advertised-but-empty shard is expected during the rollout and must not critical-alert every week. Markets ingested from a shard `/exchange/status` does not advertise are always critical (the two data sources disagree); funds on an unadvertised shard are a warning. A shard whose `trading_active` is explicitly `false` is never flagged — its ingest drop already warned — but a shard whose flag is absent (`None`, TS-04) IS still audited, because it stays in the ingest. `advertised is None` (sandbox / pre-sharding / any failure inside `fetch_shard_statuses`, which is fail-soft by design) returns `([], [])` and logs "coverage not assessable". **The check NEVER aborts a run** — it reports and trading continues on whatever was covered; the one run-ending verdict, the all-shards-inactive `EXIT_NO_TRADEABLE_SHARDS` short-circuit (TS-01), is decided in `main._run_dev`/`_run_prod`, never inside this pure helper. `balance_shards` must be pre-filtered to shards with a NONZERO balance by the caller (`{s for s, c in shard_balances.items() if c > 0}`); the function only tests set membership.

**Sizing is cross-shard; collateral is made fungible before execution.** `auth.read_account_balance()` returns each shard's cash as `dict[int, int]` (exchange_index -> cents, `AccountBalance.shard_cash_cents`) and `main._run_prod` spends `sum(...)` of it — the total across shards, not any one shard; Kelly fractions are taken of that sum plus the open positions' value (see the portfolio-value paragraph under Key Patterns) — because `trader.ensure_shard_collateral(client, portfolio, shard_balances, shard_statuses, dry_run=...)` runs after `pre_execution_check` and moves cash onto the shards the selected legs actually settle against (each leg charges its own market's shard). It degrades, never aborts: no deficit => untouched portfolio and zero API calls; `dry_run` => plan logged, never POSTed; transfers inactive on either endpoint shard, a failed POST (single-shot — the transfer endpoint is NOT idempotent, so never retry it), or funds that don't settle within `TRANSFER_SETTLE_TIMEOUT_SECONDS` => only the trades needing that shard are dropped, and `_run_prod` early-returns when nothing is left.

**Order routing is per leg.** Each V2 order body carries ITS OWN market's `exchange_index` (each `_Leg.market.exchange_index`: the NO leg's market for the NO leg and its rollback — `market_a` for same-title, `market_b` for time-series — and the YES leg's market for the YES leg), so a pair whose legs sit on different shards is now tradeable. It is always explicit and **never the `-1` auto-route sentinel**: an explicit shard makes the exchange reject loudly if our notion of a market's shard is wrong (rather than silently settling against an unmodelled shard), and it bills only that shard's rate-limit bucket where auto-route bills every nonzero shard's. `main.print_pairs_table`'s "Shards" column (`a/b`) shows which shard each leg's order routes to. The backtest path stores but does not filter: `historical._market_to_dict` passes `exchange_index` through raw into cache records (pre-existing caches read back `None`) so backtest data can distinguish shards, but no historical/backtester code drops markets by shard — all historical markets are shard 0, and filtering would silently change backtest results with no live-safety gain.

**The balance read is raw, shard-aware, and returns PER SHARD — callers sum for gate/sizing (2026-08-14).** `auth.verify_auth()` no longer calls the modeled `client.get_balance()` — that deserializes through the pinned SDK's strict pydantic model (`balance`/`portfolio_value`/`updated_ts` all required ints), the exact drift-fragile pattern that already broke events, orders, and positions. It now calls `get_balance_without_preload_content` through `_http.fetch_json_page()` (wrapped in `api_call_with_retry`, since it's a read-only GET), so non-2xx still raises `ApiException` and bad credentials still fail loudly. Don't "simplify" it back to the modeled call. `verify_auth()` returns `dict[int, int]` — spendable cents keyed by `exchange_index` — not a scalar. `auth._balance_cents_by_shard()` builds that dict from the raw body: (1) every parseable `balance_breakdown` entry, keyed by ITS OWN `exchange_index` (no shard-0 preference — a later collateral-transfer planner and a shard-coverage check both need every shard's balance, not just the routable one); (2) only when the breakdown is missing or entirely unparseable, top-level `balance_dollars` (the cross-shard aggregate) attributed to `config.DEFAULT_EXCHANGE_INDEX`; (3) same fallback tier, legacy top-level integer `balance`, also attributed to `config.DEFAULT_EXCHANGE_INDEX` — this is the sandbox shape. A breakdown that exists but yields no parseable entries at all logs a WARNING and falls through to the aggregate rather than reading `$0` (a false `MIN_BALANCE_CENTS` abort); a malformed or non-dict breakdown entry is skipped rather than aborting the scan of the good ones. A skipped entry's cash is missing from the dict, which only makes a purchase smaller, but a Kelly trim grows as the value it is sized on shrinks: so each entry whose cash is not counted (no readable shard or balance, or the earlier of two entries for one shard) is named in the keyword-only `left_out` list, filled only when the breakdown's entries are what is returned (the aggregate counts every shard), `read_account_balance()` carries those texts as `AccountBalance.cash_left_out` (so `cash_complete` is False), and `main._run_prod` trims nothing that run, its WARNING naming the first entry left out (pinned by `tests/test_auth.py::TestReadAccountBalance::test_cash_complete_says_whether_every_entry_was_counted` and `tests/test_main.py::TestRunProdTrimsInADryRun::test_cash_on_a_shard_that_cannot_be_read_trims_nothing`). If nothing parses, it raises `ValueError` — a deliberate loud-failure carve-out to the return-`None`-on-validation-failure convention, because sizing real trades against an unknown balance is worse than aborting the run. **There is deliberately no scalar-returning wrapper.** A single number would hide funds parked on other shards, and every caller's actual need is either the full per-shard map or its sum, never one shard in isolation — the `MIN_BALANCE_CENTS` gate and Kelly sizing read that sum plus the open positions' value, the portfolio selection spends the sum, and the shard-coverage check and the collateral transfer read the per-shard map; a dual API would invite a future caller to size against the wrong (single-shard) number. The read itself is `auth.read_account_balance()`, which returns an `AccountBalance` — this per-shard cash dict plus Kalshi's value of the open positions (`positions_value_cents`, see the money-units paragraph) — from the same one GET and the same `Auth OK` line; `verify_auth()` is that read returning only the cash dict, so `read_account_balance()` is the one definition of the balance read and `verify_auth()` is not a second one. `main._run_prod()` reads `account = read_account_balance(client)`, keeps `shard_balances = account.shard_cash_cents` for the coverage check and the transfer planner, spends `cash_cents = sum(shard_balances.values())` — the total across shards, because collateral is made fungible across shards by the pre-execution transfers — and sizes on that sum plus `account.positions_value_cents` (`main._bankroll_cents`; see the portfolio-value paragraph under Key Patterns); the post-trade balance line for the Excel log sums the cash the same way. **Same-key-different-units trap:** inside a `balance_breakdown` entry, `"balance"` is a fixed-point DOLLAR STRING (live: `"1.1407"`); at the TOP level, `"balance"` is legacy INTEGER CENTS (live: `114`). Never route the top-level field through `auth._dollar_str_to_cents()` and never return an entry's field as-is. Within an entry the field is chosen by **presence, not truthiness** (`"balance_dollars" in entry`, never `a or b`): a numeric `0` is a real answer, and an `or` would discard it and read the stale legacy field, reporting a genuinely-empty shard as funded — the one OVER-statement this function can produce, against the flooring and drop-with-a-WARNING rules that exist to guarantee the opposite (TS-16). A repeated `exchange_index` keeps the last entry and WARNs; silently last-winning hid a changed payload shape. Dollar strings are converted with `Decimal` and **floored, not rounded** (`ROUND_FLOOR`), so the bot is never told it holds a sub-cent it cannot spend; float parsing would reintroduce the truncation noise the `*_dollars` fields exist to avoid.

**Collateral transfers are centicent-denominated, asynchronous, and never retried.** A run spends the SUM of every shard's cash (Kelly fractions are taken of that sum plus the open positions' value) but an order settles against its own market's shard only, so `trader.ensure_shard_collateral()` moves cash onto the shards a selected portfolio actually draws from before execution: it totals each shard's requirement from the legs' `cost_with_fees_a`/`cost_with_fees_b` (`_required_cents_by_shard`, through `config.leg_cash_cents` — `math.ceil(round(cost * 100, 6))`, the one rounding `strategy.select_portfolio` spends the cash with, so a portfolio it admitted is never a cent short on any shard — ceiling because under-funding a shard by a fraction of a cent gets the order rejected for insufficient collateral, while over-funding by a cent costs nothing; the `round()` first stops binary float noise claiming an extra cent, same idiom as `fee_leg_exact`), plans a pure deterministic greedy fill out of surplus shards (`_plan_transfers` — deficits in ascending shard order, sources ranked by largest REMAINING surplus, so the number of non-idempotent POSTs is minimized), POSTs each planned transfer to `config.TRANSFER_PATH`, and confirms it actually settled. Three rules are load-bearing. (1) **Centicents are the codebase's THIRD money unit** — the endpoint's `amount` field is 1/100 of a cent (dollars for contract prices, integer cents for balances, centicents here and nowhere else). The conversion lives ONLY in `trader._cents_to_centicents()`; never inline the factor, because a missing ×100 moves 1% of the intended collateral (surfacing much later as an unexplained insufficient-funds rejection) and a doubled one moves 100× out of a shard. (2) **A 2xx means accepted, not settled** — the endpoint is asynchronous, so an order submitted immediately after could still be rejected for insufficient collateral. `_await_transfer_settlement()` re-reads the per-shard balance through `auth.read_shard_balances` — the SINGLE-SHOT (retry-free) variant of `verify_auth`'s parse, because `verify_auth`'s `api_call_with_retry` backoff could hold one read for ~60s and silently stretch the "bounded" wait — every `TRANSFER_POLL_INTERVAL_SECONDS` (2) against a `time.monotonic` deadline of `TRANSFER_SETTLE_TIMEOUT_SECONDS` (30); a balance read that raises is treated as "nothing observed", never as success, and the await targets ONLY the shards accepted transfers were headed for (an unfundable deficit shard must not burn the timeout or miscast settled transfers as in-flight). `trader.py` imports the reader at module scope — layering-legal (`config`/`_http` → `auth`/`scanner` → `strategy` → `reporter` → `trader`) — and tests substitute it by monkeypatching `trader.read_shard_balances`. (3) **A retried transfer moves the money twice** — the endpoint is not idempotent, so `_execute_transfer` submits through `_http.signed_request_json` (single-shot by construction, never `api_call_with_retry`, which `_execute_transfer` deliberately does not use — `trader.py` DOES import `api_call_with_retry` at module scope, for the retried `_position_count` reads; the no-retry rule is asserted per-function on the submission/transfer sources and at `_submit_order_v2`'s two call sites, never as a module-wide import ban) and one failed POST is logged and abandoned, never re-sent. An **accepted-but-unparseable** response is NOT a failed POST: `_check_and_parse` validates the status before parsing, so a `JSONDecodeError` out of that call proves a 2xx and therefore that the money moved. `_execute_transfer` catches it, logs `logging.critical` naming MONEY IS IN FLIGHT, and returns `None` — the value that already means "accepted, id unknown" — so the shard is still awaited and still eligible for the in-flight critical. Letting it propagate instead reported a FAILED POST, skipped the settlement poll entirely and suppressed that critical (TS-17). Nor is an **accepted-but-non-object** response a failed POST: `_check_and_parse` does not narrow the parsed body to a `dict` (both `_http.fetch_json_page` and `_http.signed_request_json` are annotated `-> Any` and say so in their Returns), so a 2xx body of `"accepted"`, `[]`, `123`, `true` or a literal `null` reaches `_execute_transfer` as a `str`/`list`/`int`/`bool`/`None` and `data.get("transfer_id")` raised `AttributeError` into the very same generic handler — the same misreport, one exception type over (DR-05). An `isinstance(data, dict)` guard now logs its own MONEY IS IN FLIGHT critical (naming the type, so payload-shape drift is distinguishable from a parse failure) and returns `None` on the same in-flight contract; an id-less but genuine JSON OBJECT is untouched and still returns `None` with no critical. The other readers of a 2xx body are deliberately left loud, for two different reasons. The read-only ones have moved no money by the time they parse: the `.get(...)` readers (`auth._balance_cents_by_shard`, `scanner.fetch_open_events_with_markets` and the other scanner cursor loops) raise the same `AttributeError`, and `historical`'s subscripting `/historical/cutoff` read (`cutoff["market_settled_ts"]`) raises `TypeError`. The ORDER-submission reader **in `trader.py`** is the exception to that rationale and still must NOT get this guard: a 2xx there can mean a FILL, so money HAS moved — `_submit_order_v2` reads through `_v2_fill_status`'s `data.get("order")` and raises `AttributeError`, and stays loud precisely because raising is what routes `_execute_one` into its ambiguous-submission path, where the outcome is resolved against the account's position DELTA — a stronger remedy than an in-flight critical. **`v2_probe.py` is the named carve-out to that carve-out and DOES get the guard (DR-58).** Its submissions are order submissions, but nothing resembling `_execute_one` sits above them: the probe IS the top of its own call stack, so raising resolves nothing and merely kills the process mid-step — after a real ask has been submitted, before the position read, before any "FLATTEN IT MANUALLY" line, and (in `_step_no_mapping`, the only step that has one) before the reduce-only close, leaving a real position open with nothing to tell the operator it exists. `v2_probe._non_object_body_fail` therefore guards both submission-response READERS — `_step_no_mapping`'s NO buy and `_step_unfillable_ask`'s ask — printing a FAIL that names the body type, reading the position and telling the operator what to flatten. **READERS, not submissions: the probe makes THREE submissions and only two of them read their body.** `_step_no_mapping`'s reduce-only NO CLOSE needs no guard because its 2xx body is only handed to `_emit` (typed `Any`, it just pretty-prints) and the verdict comes from `trader._position_count`, so there is no `.get(...)` on it to raise — add a guard there only if a future edit starts reading fill fields off `close_data`. `_non_object_body_fail` **re-reads once on a flat OR unreadable first read**, which EXTENDS DR-21 rather than restating it: DR-21's own re-read fires only on an exactly-zero read, and a bare truthiness test here would collapse `None` (lookup failed) into `0` (genuinely flat) in exactly the window where both are expected — the three outcomes stay distinguishable in the output. It deliberately does NOT submit the close: that order rests on the mapping the unreadable body proves nothing about, so the position is left for a human, as a disproven mapping already leaves it. The probe's own read-only 2xx readers (`_fetch_market`'s `data.get("market")`) stay loud like every other read-only one — nothing has been submitted by then. So: three call sites carry the guard across two modules — `trader._execute_transfer` and `v2_probe`'s two submission readers; `_execute_transfer` is the one site in the PIPELINE with neither property — no ledger reconciles a transfer after the fact, and its caller's generic handler would report a FAILED POST. Do not generalise the guard to any of the others. (`scanner._fetch_held_market` — `resolve_held_ladders`' lookup of a held market, DR-76 — also type-checks its 2xx body, but that is not this guard: a non-object body there is a failed read that makes the run skip its time-series pairs, with no money-in-flight claim, since nothing has been submitted.) `_check_and_parse` itself keeps raising on an empty 2xx: returning `{}` there would make `trader._read_position` answer "account flat" when the truth is unknown, and would make every cursor loop read a falsy page as a clean finish. Every failure mode **degrades, never aborts the run**: a shard whose `intra_exchange_transfers_active` is false (checked on BOTH endpoints of a transfer, and a shard absent from `scanner.fetch_shard_statuses()` counts as inactive) warns the operator to move the funds manually in the Kalshi UI; a failed POST logs an error; an accepted transfer whose money is not OBSERVED to arrive logs `logging.critical` naming the in-flight `transfer_ids`. **That critical's trigger is the settlement OBSERVATION, never a shard's membership in `accepted_cents` (DR-65).** `ensure_shard_collateral` compares each still-unfunded shard's `confirmed` balance against `awaitable` — the same `min(required, prior + moved)` map the settle wait targeted, i.e. exactly what the accepted transfers could deliver. Below it, cents were accepted and did not land, so the critical fires; at or above it the money demonstrably arrived and the shard is still short — because a planned leg was blocked, its POST failed, or there was no surplus to cover the rest — which gets a WARNING naming the shortfall instead. **The warning reports only what was observed and asserts no cause**, because the code observed exactly one thing (`confirmed >= awaitable`) and knows nothing about why the shard is still short, nor about transfers whose POST raised — a raised POST the server had already accepted leaves that shard out of `accepted_cents` entirely, so an affirmative "nothing is in flight" there would be a false denial. The two verdicts partition the unfunded shards an accepted transfer was headed for, and no shard is ever reported both ways; a shard whose transfer was never accepted is in NEITHER and was already warned about at its skip or POST-failure site. Do not "simplify" `settled_short` to `unfunded - in_flight` — that would tell the operator a never-sent transfer had "SETTLED". One known residual: "landed" is inferred from a balance THRESHOLD against the run's opening `shard_balances`, so an unrelated credit to the deficit shard of at least the accepted cents, arriving inside the poll while the transfer is genuinely stuck, would suppress the critical (the inverse, a debit, only over-reports, which is the safe direction). The membership test fired the critical on a plan that settled in full and in zero wait, with the same log line's own `confirmed` map showing the money had arrived — telling the operator funds were unaccounted for when none were. In every case only the specs whose shards remain unfunded are dropped — a spec dies if EITHER leg's shard is short, since a funded NO leg with an unpayable YES leg is precisely the unhedged half-fill the rollback machinery exists to avoid — and the rest execute normally. `dry_run` plans and logs but NEVER POSTs, returning the portfolio unchanged. The zero-deficit fast path keys off the deficit set, not off the plan being empty: an empty plan is ambiguous ("nothing needed" vs. "nothing movable"), and reading it as the former would let underfunded specs sail through. `main._run_prod` wires it in right after `pre_execution_check`.
