Moved word for word from the "Key Patterns — Always Follow These" section of the project's `CLAUDE.md` on 2026-10-26, when that file was cut down to a short root that indexes these notes. Where the text below says "this file", it means the project's notes as a whole: `CLAUDE.md` and the files in `docs/claude/`. Section names the code and README use ("Key Patterns", "Known Gotchas", "Module Map") name the folders of `docs/claude/`. Each paragraph is one line, some of them long: find one with `grep -n`, then read that line by number.

In this file:

- Constants live in `config.py` exclusively.
- Use `@dataclass` for all data transfer objects.
- Return `None` for validation failures; don't raise.
- Two-stage fee calculation
- Each leg's fee uses its own market's series fee multiplier, and only a confirmed one counts.
- Retry pattern
- Order and transfer POSTs are paced, never retried (2026-09-28).
- Compare prices with `config.PRICE_EPSILON`, never bare (TS-09).
- Use `pathlib.Path` for all file paths.
- Monetary values
- Process exit-code contract (BS-14).

**Two-stage fee calculation:**
1. `fee_per_pair_approx(price_a, price_b, *, multiplier_a, multiplier_b)` — continuous approximation over the two LEG prices (`scanner.leg_prices(pair)`: `(nA, pB)` for same-title, `(pA, nB)` for time-series); use during pair *filtering* before the integer contract count `n` is known.
2. `fee_leg_exact(n, p, *, multiplier)` — ceiling-rounded exact fee; use for *final validation* once `n` is determined.
Never swap these — the approximation underestimates and will let bad trades through if used for final validation.

**Each leg's fee uses its own market's series fee multiplier, and only a confirmed one counts.** Kalshi's /series listing gives each series a `fee_multiplier` (0.5 for MLB game series, 0 for a few fee-free ones), which every live market carries as `_fee_multiplier` (`main._attach_series_labels`) and every backtest pair market's record carries under `backtester._LISTED_FEE_KEY` (`_prepare_candidates`, written only when it is not 1.0). **Retry pattern:** Use `api_call_with_retry()` from `_http.py` for all new market-data API calls (this includes read-only portfolio calls like the balance read in `auth.read_account_balance()` and the positions listing in `scanner.get_held_positions`, which `get_held_tickers` reads; both now go through `fetch_json_page` on the SDK's raw `*_without_preload_content` variant rather than the modeled call — see the shard-balance gotcha). It handles HTTP 429 and 5xx with exponential backoff doubling 2s → 32s across 6 attempts (`_MAX_DELAY = 60s` is only a defensive ceiling). It ALSO retries status-less transport failures — `urllib3.ProtocolError`, `ReadTimeoutError`, `http.client.IncompleteRead`, and the builtin `ConnectionError`/`TimeoutError` — matched through a bounded `__cause__`/`__context__` walk (`_is_transient_network_error`), because urllib3 wraps the real error (a `ProtocolError: Connection broken: IncompleteRead` from `resp.read()` killed a multi-hour backtest fetch on 2026-08-03; it carries no `.status`, so the old status-only classifier treated it as fatal). Retrying these is safe *because* every caller of this wrapper is a read-only GET. Do NOT add retry logic to order submission in `trader.py` NOR to the collateral transfer POST — `_submit_order_v2` / `_submit_sale_v2` / `_execute_transfer` deliberately call `_http.signed_request_json` directly (which itself contains no retry logic, precisely so those call sites stay single-shot); a failed leg means the price moved, not a transient error, and a retried transfer moves the money twice. `trader._position_count()` **is** wrapped (it's a read-only GET like the rest): the no-retry rule covers submission only, and an unretried transient 429 there reads as "fill state unknown", escalating a recoverable ambiguity into a rollback or `manual_review`. Don't "unify" `_position_count` with `_submit_order_v2`/`_submit_sale_v2`/`_execute_transfer` in either direction — the asymmetry is the rule, and `trader.py` therefore DOES import `api_call_with_retry` (for the position lookups only); the no-retry rule is asserted per-function on the submission/transfer sources, and at `_submit_order_v2`'s two call sites (`_execute_one`, `_rollback_no_leg`), never as a module-wide import ban. The position reads that are deliberately unretried go through `trader._position_count_once`, and both sit inside the window where the NO leg MAY be filled (on the re-read path that is exactly what is being determined) and is certainly unhedged, because the YES leg has not been submitted: `_confirm_v2_no_mapping`'s mapping check (see the V2 backstop bullet) and `_execute_one`'s NO-leg ledger-lag RE-READ (DR-64 — see the delta bullet). It shares `_read_position`'s parse with `_position_count`, so only the retry policy differs; the YES-leg re-read is deliberately the RETRIED reader, because the first read beside it is already retried and a single-shot re-read that fails yields an unknown delta, i.e. `manual_review`, which leaves the NO leg unhedged INDEFINITELY — strictly worse than a bounded wait followed by a correct unwind. The accepted residual is that in the branch where the YES leg genuinely did not fill, that retried re-read can hold the loss-floored unwind for up to ~62s of backoff on top of the 1s pause, which can turn a `rolled_back` into a `rollback_failed` orphan; the pre-existing read beside it already carried that same exposure. One consequence to respect: the cause-chain walk means anything raised *inside* an `except` block that is handling a `TimeoutError` inherits it as `__context__` and is misclassified as transient, so `_execute_one` takes its post-failure position snapshots **outside** the `except` clause (on the NO leg and the YES leg alike) — otherwise a fatal lookup error stalls an urgent decision for the full ~62s backoff. `trader._sell_leg` follows the same rule for a sale: when its POST raised, or its reply says nothing, it reads the position after the `except` clause has ended (the retried read, read again after each pause of `config.V2_MAPPING_ZERO_RECHECK_DELAYS_SECONDS` while the move is short of the whole count).

**Order and transfer POSTs are paced, never retried (2026-09-28).** Kalshi limits an account's writes with a token bucket that refills continuously rather than per window, and a request over the limit gets HTTP 429 and is rejected outright, not processed (Kalshi's rate-limit docs, docs.kalshi.com/getting_started/rate_limits), with no `Retry-After` header. `GET /account/limits` on this account (2026-09-28) returned `usage_tier` basic with a write `bucket_capacity` of 100 and a `refill_rate` of 100 a second, and `GET /account/endpoint_costs` (2026-09-28) lists no override for `POST /trade-api/v2/portfolio/events/orders`, `POST /trade-api/v2/portfolio/orders` or the `intra_exchange_instance_transfer` path, so each costs the default 10 tokens: 10 orders a second and 10 back to back. (The legacy `/portfolio/orders` endpoint takes no orders; see the order-path bullet under the V2 order semantics gotcha.) The first live production run (2026-09-28 02:26 PDT) ran 7 pairs on `execute_trades`' concurrent workers and POSTed all 7 NO legs and then the YES legs inside about one second; two YES legs came back 429, `_execute_one` read each as ambiguous (retried position read, delta 0, 1 s pause, re-read, delta 0) and rolled its NO leg back, and both unwinds filled — 5 pairs executed, 2 rolled back, about $2.40 lost to spread and fees. That fits the continuous model: 12 of the 14 accepted means the 14 went out within about 0.2 s (10 + 10 × 0.2 = 12). The same burst could have given a ROLLBACK a 429, i.e. `rollback_failed` with an open NO position, and a YES leg the exchange kills with its HTTP 409 is unwound at once, with no pause to spread the writes. So `_submit_order_v2`, `_submit_sale_v2` (in turn: `_ORDER_WRITE_PACER.acquire()`, before its `Submitting V2 sale order` line; sales run one position at a time before any buy, so none competes with a hedge write) and `_execute_transfer` each take exactly one place on `trader._ORDER_WRITE_PACER` immediately before their one POST (in `_submit_order_v2` before the `Submitting V2 order` line too, so the log time is the send time) — the order submitter through a keyword-only `pace` hook (`_execute_one` and `_rollback_no_leg` pass it on), `_ORDER_WRITE_PACER.acquire` when none is given: one `trader._WritePacer`, a thread-safe token bucket shared by every worker, at `config.ORDER_WRITES_PER_SECOND` (8) with bursts of at most `config.ORDER_WRITE_BURST` (8, and at least 2 — the constructor refuses less, since a pair's NO leg takes two places at once) — 20% under the Basic budget, for writes the bot does not see (another client on the account, a manual order, a probe). A caller joins one of two lines under a `threading.Condition`, each first come, first served in the order callers take its lock (a lock does not promise strict arrival order): the hedge lane (`acquire_hedge`), served first, and the in-turn line (`acquire`, `acquire_with_hold`). The balance never goes negative: the front of the line is served once the refill covers it — by whichever waiting thread wakes first, and none behind it goes first — waits happen in `Condition.wait` with the lock released, a caller that stops waiting (Ctrl-C) leaves the line, and one INFO line (`Paced an order or transfer write …`) is logged after a wait over 0.25 s. Under a continuous bucket the pacer's at most 8 + 8·T sends in any T seconds never exceed the exchange's 10 + 10·T. **Pacing is not a retry**: each submission, sale and transfer is still sent exactly once and the no-retry rule above is unchanged. A 429 that comes back anyway takes the path it always took, which differs by write: on a buy leg it raises into `_execute_one`'s ambiguous path (the live run's two YES-leg 429s were resolved that way and rolled back, the $2.40 above); on the unwind it is `rollback_failed`, an open NO position; on a sale order it raises into `_sell_leg`, which asks the account how many contracts sold; on a collateral transfer it is a failed POST, and the trades needing that shard are dropped. **Residuals:** pacing controls when a request is sent, not when it arrives, so large network jitter could still bunch arrivals over the limit (and the pacer counts a write as sent when its place is granted, a few milliseconds before the POST leaves — the 20% headroom covers up to 0.25 s of either); and the pacer is per process, so a second process writing to the account (`v2_probe`'s transfer step, or a run on another computer — two real-money runs on one machine never overlap, since `run_lock` stops the second with exit 50) has its own full-rate pacer. A 429 from either takes the paths just listed. **Hedge writes go ahead of opening NO legs (2026-09-28, the pacer's follow-up).** With one first-come-first-served line, each hedge write — the YES leg, and the unwind — waited for the pacer while its NO leg was filled and unhedged, behind other pairs' opening NO legs, up to `TRADER_MAX_WORKERS / ORDER_WRITES_PER_SECOND` (1 s) per write: in simulation at the shipped values (8 workers, 50–300 ms per POST and 100 ms per position read), NO fill to YES sent took up to 0.45–0.95 s and NO fill to unwind sent up to 1.3–1.95 s, with 7 and 14 pairs. Now each pair's places come from one `trader._PairWrites`. The NO leg's POST takes `acquire_with_hold`: it waits in turn until two tokens are free together, sends one and HOLDS the other (`_HeldWrite`). The YES leg sends the held place with no wait. An unwind takes `acquire_hedge`, the hedge lane, ahead of every waiting opening NO leg (it would send the held place instead only if the YES leg's submission raised before taking it). The held place goes back (`_PairWrites.close`) as soon as the NO leg's POST raises — working out whether that leg filled can take a minute of retried position reads (plus the 1 s ledger-lag pause and re-read), and a place held through them kept room from every other pair: with `burst − 1` pairs stuck there during a transport failure, every other pair's opening waited about 60 s (reproduced by the adversary critic; fixed before merge) — so the unwind of an unclear NO leg takes the hedge lane too; otherwise `_execute_one` gives an unsent held place back in a `finally` (its body is `_execute_legs`), whether the pair filled, was killed, stopped for review or raised. In the same simulation NO fill to YES sent is 0.000 s in every case. When every YES leg is killed, YES return to unwind sent is at most 0.40–0.45 s (0.575–0.95 s before), and NO fill to unwind sent — the measure quoted above for before — at most 0.45–0.70 s, which includes the YES leg's own round trip (four unwinds land in the hedge lane at once and the k-th waits for k tokens; one unwind alone waits at most 1/8 s). The cost is throughput, because each pair's NO leg now waits for two free tokens and holds the second through its whole round trip — and, until the V2 NO-leg mapping latches (the first V2 fills of a process), through `_confirm_v2_no_mapping`'s single-shot reads and their pauses (1, 2 and 4 s when the ledger reads unchanged). While the mapping is unsettled `execute_trades` runs pairs one at a time (see the runtime-backstop bullet under V2 order semantics), so that hold keeps room from no other pair; only once the phase has lasted `V2_MAPPING_CHECK_SERIAL_BUDGET_SECONDS` do pairs run together again, each still holding its place through its own check. The verifier's measurement of this cost (14 pairs with a lagging ledger: last return 3.2 s → 3.475 s) was taken when unverified pairs still ran together, before the one-at-a-time phase and the longer re-read schedule. Keeping the hold there is deliberate, since releasing it would put the YES leg in the hedge lane: a run's total time grew by up to 0.475 s at 50–300 ms per POST (7 pairs, every YES leg killed, 300 ms) and by 0.55–0.75 s at 1 s per POST, where the old pacer had put no wait in the window at all. **Why a held place is safe to send late, and why it must count against the bucket.** A write sent later than its admission can overdraw a plain token bucket: its token was taken from the pacer's balance at admission while the exchange's bucket, never having spent it, sat at its cap and gained nothing from the refill, so without a cap a held write could go out at the same instant as a full bucket of other writes and, in some stretch, the sends would exceed burst + rate × stretch by as many writes as were held. So the refill stops at `burst` minus the held writes. With free tokens L, held writes H and a bucket X at the pacer's rate and burst that is charged at each actual send: L + H ≤ burst always, and X ≥ L + H is kept by every event (a grant takes from L what X loses at the send, a hold moves a token from L to H, a held send takes one from H and from X, a release moves one from H back to L, and X refills no slower than L while L + H is under the cap), so X ≥ H ≥ 1 whenever a held write is sent, however late. `acquire_with_hold` needs two free tokens, so at most `burst − 1` writes are ever held: a hedge-lane write can always be served by the refill alone, a pair waiting for room is woken by any hold's send or release, and no caller waits on the pacer while it holds a write, so there is no deadlock whatever `TRADER_MAX_WORKERS` is. Raising the two constants is safe only up to the account tier's own write budget divided by the order cost (10 tokens). `v2_probe` is human-paced and does not call `_submit_order_v2` for its orders (its transfer step goes through `_execute_transfer`, one POST). Position and balance reads are GETs on the separate read bucket and are not paced. `tests/conftest.py` gives every test a fresh pacer; `tests/test_trader.py::TestWritePacer`, `::TestHeldWrites`, `::TestHedgeLane`, `::TestWritesArePaced`, `::TestPairWrites` and `::TestExecuteTradesArePaced` pin the bucket (its balance read under the lock, the wait handed the lock to release, a caller that stops waiting leaving the line, and by AST the module's one `_WritePacer(ORDER_WRITES_PER_SECOND, ORDER_WRITE_BURST)` construction), the held write (two places taken, counted against the bucket until it is sent or released, its room freed only after the balance is brought up to date when it is sent late, ended once, given back by the pacer when its caller stops just after being served, at most `burst − 1` held, a pair waiting for room woken by a send on real threads, and — on 12 seeded random mixes of late held sends, releases, single and hedge-lane writes, each caller's plan drawn before the threads start — sends never exceeding `burst + rate · T`), the hedge lane (served ahead of a waiting pair, with the in-turn control), a caller that stops waiting removing its own place and not an equal-looking one (`_PaceRequest` is `eq=False`), one place per POST before the POST (a 409 kill, a 429 and a place the caller hands in included), each `_execute_one` path's places, read as the number held at each POST and the hedge-lane places handed out (the held place sent by the YES leg; the hedge lane for every unwind; the held place given back before the first read after the NO leg's POST raises, on a killed NO leg, a disproven mapping and an escaping exception), and concurrent pairs at the shipped rate and burst whose YES legs go out the moment their NO legs return (7 and 14 pairs), whose opening NO legs are spread to the limit (7), and whose unwinds never let an opening NO leg go first (7 and 14). Apart from two real-thread tests, the multi-thread cases run in simulated time (`_SimTime`: time stands still while any thread runs and jumps to the earliest deadline once all are blocked, so the times are exact and do not depend on the machine); `tests/test_config.py::TestOrderWriteBudget` pins the shipped rate and burst inside the Basic-tier budget.

**Compare prices with `config.PRICE_EPSILON`, never bare (TS-09).** Every price is a float parsed from a cent-quantized dollar string, so `0.35 - 0.30 == 0.04999999999999999` and a bare `< 0.05` rejects pairs that sit exactly on a documented threshold — measured over live books: the same-title 5c test rejected 50 of 94 qualifying pairs, the 15c tier 21 of 84, the 30c tier 15 of 69. `PRICE_EPSILON` is `1e-6`, at most 1% of the finest tick ($0.0001), so it can only absorb representation noise, never a real one-tick difference. **Do not tune it upward** — it is an ABSOLUTE tolerance, so its weight relative to the compared quantity grows as that quantity shrinks. Six scanner comparisons carry it: the same-title finder's threshold test, enrichment's and `validate_pair_price`'s qualifying filters, DR-67's reject-side `pA + nB >= 1.0 - PRICE_EPSILON` guard in `find_time_series_pairs`, `validate_pair_price`'s reachability-cap check (its two epsilon terms, one per side of the book, are one logical comparison: is this level reachable at the FoK limit), and enrichment's crossed-book guard (`ref_yes + no_levels[0][0] < 1.0 - PRICE_EPSILON`). The time-series threshold test itself now lives in `config.time_series_spread_refusal`, the live spread rule the finder, enrichment and `validate_pair_price` share, which carries three more in `_find_entry`'s placement: positivity (`spread <= PRICE_EPSILON`, on the REJECT side, which TIGHTENS — a zero spread that evaluates a hair above 0 is still refused), the floor (`spread < floor - PRICE_EPSILON`), and the band's ceiling through `time_series_spread_too_wide` (keep side, like the floor). The subtractions don't all move the same way: the same-title threshold test, the time-series floor test and the crossed-book guard subtract on the KEEP side of a reject test (`pA - pB < SAME_TITLE_MIN_PRICE_DIFF - PRICE_EPSILON`, `spread < floor - PRICE_EPSILON`, `ref_yes + no_levels[0][0] < 1.0 - PRICE_EPSILON`), which LOOSENS acceptance — a boundary pair (a spread exactly on the floor, a YES ask exactly at the YES bid) is kept rather than dropped, which is the whole point of TS-09. The pA+nB guard subtracts from the reject side's own bound (`pA + nB >= 1.0 - PRICE_EPSILON`), which TIGHTENS it — a sum that is really 1.0 but evaluates a shade under it must still be refused (see the pA+nB skip note above). Do not "fix" any of the three keep-side subtractions to an add: that would re-narrow the keep bound and reintroduce the measured TS-09 rejections above. `backtester._find_entry` mirrors it at three: `gap < threshold` and `price_a + price_b > 1 - threshold` directly, and the spread-band ceiling through `config.time_series_spread_too_wide` — the one place that ceiling's epsilon lives, on the keep side like the floor's (`0.90 - 0.30 == 0.6000000000000001` is kept at a 0.60 ceiling). A fourth is the refusal of a time-series Monday whose spread is not strictly positive (`gap <= PRICE_EPSILON`), which sits on the REJECT side and TIGHTENS, like DR-67's pA + nB guard; its live twin is `time_series_spread_refusal`'s positivity test. It is inert with the tiers on and bites only with them off at a floor of 0 (the backtest's tier-floors-off family, or a live run with `LiveSettings.tier_floors` off). `tests/test_backtester.py::TestLiveBacktestSpreadParity` pins the live rule and these tests to one verdict on every boundary's float-noise neighbours. **The AST parity pins do NOT check this constant**, so a missed mirror is silent divergence between live and backtest.
**Use `pathlib.Path` for all file paths.** Never `os.path` or string concatenation.

**Monetary values:** Three units, not two. Contract prices are **dollars** (float, or `Decimal` on the V2 order-price path, range 0–1). Balances and order costs are integer **cents** — except that inside `auth._balance_cents_by_shard()`'s per-shard `balance_breakdown`, the API's own `"balance"` field is a fixed-point **dollar string** (converted with `Decimal`, floored not rounded — see the shard-balance gotcha); only the top-level legacy `"balance"` field and the sandbox fallback are plain integer cents. The balance reply's top-level `"portfolio_value"` is plain integer cents too, and it is the open positions' value ALONE — it never includes cash (two live replies with positions held put it below the cash balance, and the pinned SDK's model describes it as "the current value of all positions held") — read by `auth._positions_value_cents()`, which prefers a `"portfolio_value_dollars"` dollar string by presence (floored, like every balance; no reply seen and not the SDK's model carries that spelling, so it is read only in case Kalshi adds one, as it added `balance_dollars`) and returns `None`, never 0 and never an error, for a missing, negative or unreadable value, for a dollar value that is not a string or a plain number (refused before it is turned into text), and for anything above 2**53 cents (about $90 trillion, and every whole number of cents up to it is exact in a float), checked before any conversion so a huge exponent never builds a huge integer. It does not catch a value in the wrong unit (say 100x) itself, since the balance reply does not list the positions: `main._checked_positions_value` checks the value against them once `_run_prod` has read the positions listing (accepted risk (4) in the portfolio-value paragraph under Key Patterns says what it keeps and what still passes). The collateral-transfer endpoint's `amount` is **centicents** (1/100 of a cent), converted only by `trader._cents_to_centicents()` — see the collateral-transfer gotcha. Don't mix units, and don't assume every "balance" field on the wire is the same shape.

**Process exit-code contract (BS-14).** `main()`'s process exit code is the only signal `scheduler.run_job()` — a separate subprocess — has for what happened in a run, beyond generic pass/fail. `_run_prod`/`_run_dev` return one of five `config.py` codes instead of a bare `None`: `EXIT_OK` (0, the normal case), `EXIT_SKIPPED_LOW_BALANCE` (10, the short-circuit when the portfolio value — the cash on every shard plus Kalshi's value of the open positions, or the cash alone when that value is unread or refused — is below `MIN_BALANCE_CENTS`, which used to `return` and exit 0 just like a clean run, silently burying the reason nothing happened; cash alone below the minimum is only a WARNING, and the run goes on), `EXIT_TRADES_NEED_ATTENTION` (20, any `execute_trades()` result with status `"rollback_failed"` or `"manual_review"`, and any sale from `trader.sell_positions` left `"unbalanced"` or `"manual_review"`, or turned into `"manual_review"` by `main._flag_sales_sold_more` because the positions listing read back shows more sold than an account reading recorded — `main._SALE_ATTENTION_STATUSES`), and `EXIT_NO_TRADEABLE_SHARDS` (30 — NOTHING was scanned: every advertised shard reported `trading_active=false` so ingest dropped every market (TS-01), or ingest produced zero markets for a cause `/exchange/status` could not name (VI-02); both are decided by the single helper `main._blind_run_reason`, which both run modes call), and `EXIT_TIME_SERIES_SKIPPED` (40, production only — `scanner.resolve_held_ladders` could not identify a held market, so the run made no time-series trade but still searched, sized and traded same-title pairs; `EXIT_TRADES_NEED_ATTENTION` wins over it — DR-76). `main()` itself exits with a sixth, `EXIT_RUN_IN_PROGRESS` (50), without entering either run mode: a production run that sends orders found the machine-wide live-run lock (`run_lock`) still held by another run after `LIVE_RUN_LOCK_WAIT_SECONDS`, so it stopped before building a client or making any request. `main()` ends with `sys.exit(code)`; an unhandled exception is not covered here and still propagates to the interpreter's normal exit 1. A usage error exits `2` before either run mode is entered — argparse's code, from `parser.error` — for an invalid flag, for any `config.ORDER_API_VERSION` but `"v2"` (`config.order_api_version_error`, checked first, since 2026-09-28) and, since the saved live defaults, for no saved defaults or a refused `live_defaults.json` (`main._resolve_live_settings` reads them through `config.live_defaults()` before logging is configured; an invalid config.py toggle constant no longer stops a live run), so even a SCHEDULED run, which passes no toggle flag, can exit `2`: its `kalshi_arb.log` records nothing, the reason is on stderr, which `scheduler.run_job` logs under `Job failed (exit 2)`, and like any failed run it satisfies the weekly slot (only `30` reopens one) — which is why `scheduler._check_live_defaults` warns at daemon start. `scheduler.run_job()` maps all six to a distinct log level and message so a skipped or attention-needed run is visible in the scheduler's own log, not just buried in `kalshi_arb.log`. Don't collapse these back into a bare `return`/exit 0 — that's exactly the bug this fixed. **30 is deliberately not 0.** An exchange-wide halt (observed live 2026-09-03 00:29 PDT) makes `inactive_shard_indexes` return every shard, `fetch_open_events_with_markets` drop every market, and both loops of `check_shard_coverage` run empty — so it returned `([], [])`, which `_log_shard_coverage` read as success and reported as `Full shard coverage: shards [...] scanned`, indistinguishable from a healthy full ingest. Both run modes therefore short-circuit with 30 on `main._blind_run_reason(markets, shard_statuses, inactive_shards)` (placed after the markets fetch, which is where `inactive_shards` and the ingest census exist, and, in prod, after the `MIN_BALANCE_CENTS` gate, which still runs first, and BEFORE the held-ticker and horizon filters, which legitimately empty the list on a healthy exchange). That helper keeps the halt test — `shard_statuses and inactive_shards == set(shard_statuses)` — as its OWN disjunct and adds a second one, `not markets`, rather than replacing it with the census: the two are NOT equivalent, because a halt that still leaves one stray market ingested (one tagged with a shard `/exchange/status` does not advertise — `scanner._shard_index` only defaults a MISSING index to `DEFAULT_EXCHANGE_INDEX`) would pass a bare census test while every advertised book is shut, carrying the run into pair discovery, sizing and, on a live Monday run, order submission during an exchange-wide halt. The `not markets` disjunct exists because `fetch_shard_statuses` is fail-soft and returns `None` on ANY internal failure, which makes the halt test unevaluable exactly when something has gone wrong: a run that ingested zero markets then exited 0 claiming a clean scan (VI-02). A blind DEV run short-circuits before `write_dev_simulation` on both causes — the empty simulation file records a run that SCANNED and found no pairs, never one that never looked. Independently of the gate, `_log_shard_coverage` claims coverage only over shards that were actually scannable (`trading_active is not False`, so a `None` flag still counts as scanned) — the "Full shard coverage" line names those shards, not every advertised one. On the scheduler side, 30 is the one code that does NOT satisfy the weekly slot. Because 30 now covers both causes and the exit code alone cannot separate them, `scheduler.py`'s retry WARNING and give-up ERROR name both possibilities and point the operator at `kalshi_arb.log`, where `_blind_run_reason`'s line says which one fired — they must never assert the halt as the cause (`tests/test_scheduler.py::TestBlindRunRetry` pins that wording). `run_job(retries=0)` registers a one-shot retry on the `schedule` library's global scheduler (`_blind_retry`, which returns `schedule.CancelJob` so it can never become a recurring job — and, since DR-59, is registered through `scheduler._guarded_job` with `on_error=schedule.CancelJob`, because a retry that RAISES returns nothing and would otherwise stay registered, re-fire on every poll tick and never advance the cap) every `SCHEDULER_BLIND_RETRY_SECONDS` (3600), at most `SCHEDULER_BLIND_MAX_RETRIES` (4) times, and `_maybe_catch_up` re-runs a slot whose recorded attempt exited 30 — its old test was purely temporal and never read the exit code. The cap is enforced by the `retries` argument each attempt carries, never by the caller, because a retry that exits 30 again schedules its own successor; it is persisted as `scheduler_state.json`'s optional `"retries"` key, which pre-existing state files lack and every reader treats as 0 (`_load_state` now also validates the optional `retries`/`exit_code` keys, degrading a bad value IN PLACE rather than discarding the whole state the way an unparseable `last_slot` does: a PRESENT but non-int `retries` — a hand-edited string, `null` — degrades to 0 with a WARNING instead of reaching `_maybe_catch_up`'s `retries < SCHEDULER_BLIND_MAX_RETRIES` comparison unvalidated and raising `TypeError` out of `main()` before the weekly job was ever registered (DR-24); a non-int `exit_code` is typed to `None` the same way, which is hygiene rather than a crash fix — its `==` comparison never raised, it only ever compared unequal and left the slot unretried. `main()` additionally runs the whole startup catch-up check through `_startup_catch_up()`, a `try`/`except Exception: logging.exception(...)` guard around `_maybe_catch_up()`, as a backstop for whatever else that check might still raise). A run that merely FAILED still does not reopen its slot — that is BS-17's deliberate behaviour. **40 is deliberately not 0, and deliberately not 30 (DR-76).** A production run whose `scanner.resolve_held_ladders` cannot identify a held market makes no time-series pair but still searches, sizes and trades same-title. Returning `EXIT_OK` for it (the first cut of DR-76) left the scheduler's own log showing a clean run, so a lookup that failed every week would have stopped time-series trading week after week with only the ERROR in `kalshi_arb.log` to say so — and that lookup path is routine rather than rare, since every held market that has closed but not yet paid out is absent from the active-market ingest and is looked up on every run until it pays out. So it has its own code, which `run_job` logs as an ERROR (`Job made NO time-series trade (exit 40) …`, pointing at the ERROR in `kalshi_arb.log` that names the market). It is not 30: the run DID scan, so 40 satisfies the weekly slot like 10 and 20 — no hourly retry, and `_maybe_catch_up` does not re-run it — because a retry an hour later would most likely fail the same lookup. `_run_prod` picks its clean exit once, after the resolver and the sale block (`clean_exit`: 20 when a sale was left unbalanced or of unknown outcome, else 0, or 40 when a held market could not be identified), and every later clean return uses it; `EXIT_TRADES_NEED_ATTENTION` is the one return after it that does not, so a trade or a sale needing a human wins over 40. A dev run never returns 40 (it holds nothing and never calls the resolver). Pinned by `tests/test_main.py::TestRunProdTimeSeriesSkippedCode` (the dry-run, live, no-pair and attention paths, and an AST check that every return after `clean_exit` is set returns it or 20) and `tests/test_scheduler.py::TestRunJobExitCodeMapping::test_time_series_skipped_logs_error` / `::test_every_exit_code_has_a_message_of_its_own` (every `EXIT_*` code is distinct, none is 1 or 2, and none reaches the catch-all `Job failed` branch) and `::TestCatchUp::test_a_run_that_skipped_time_series_is_not_retried`. **50 satisfies the slot too, and is never retried.** A real-money run was already trading when the scheduled run stopped, and a retry an hour later could stack a second same-title trade that week, so `run_job` finalizes the slot with exit 50 and `_maybe_catch_up` does not re-run it. `run_job` logs a WARNING naming the run in the way (`run_lock.holder().describe()`: process, checkout, start time), or an ERROR when that run's recorded start is over `SCHEDULER_JOB_TIMEOUT_SECONDS` old or not recorded — it may be hung or stopped, no trade was made that week, and every scheduled run will stop the same way until it ends. Only `--mode prod` without `--dry-run` takes the lock: a dry run or a dev run sends no orders, so it neither takes the lock nor waits for it, and never blocks the Monday run. The lock's record is read only for messages; the flock alone decides who trades, and the operating system drops it however its holder ends.
