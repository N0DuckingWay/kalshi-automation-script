**Saved live defaults (live_defaults.json) — no file, no live run.** Every live run, prod and dev, scheduled or by hand, starts from `config.LIVE_DEFAULTS_FILE` (`live_defaults.json` in the repo root, gitignored operator state like `scheduler_state.json`), and from nothing else. **Deploy consequence: every live run — the Monday 09:00 scheduled one included, and a hand run with toggle flags — exits 2 until a usable file exists in the checkout the scheduler runs from, and a file saved before Rebalance (one holding `add_to_held_pairs`, `trim_to_kelly` or `trim_min_rise`, the three settings `rebalance` and `min_price_move` replaced) is not usable, nor is one saved before the category filter became a list of categories to exclude (one holding `categories`, the old list of categories to trade, which `exclude_categories` replaced), nor one saved before the tag filter became a list of tags to exclude (one holding `tags`, the old list of tags to trade, which `exclude_tags` replaced — EVERY file saved before that change, since the key was required): each is refused as outdated, and nothing trades from it until it is saved again.** After pulling this change there, in that checkout: (1) stop and start `./start_dashboard.sh` (a server still running older code is refused) and save the defaults. For a file saved before Rebalance, open `http://127.0.0.1:8765/`, follow its red notice to the confirmation page, check the table — the file's values in their new form: Rebalance yes when both old switches were on, with the old `trim_min_rise` as its Min. price movement, otherwise Rebalance no with no minimum, every other setting as saved — and click Confirm and save, which replaces the file; do not delete it, since the server offers its values only while it is there. A file that both added to held pairs and trimmed reads as Rebalance yes, so its runs go on doing both; one that did only one of the two reads as Rebalance no, so its runs stop doing either: save it that way, since Rebalance yes would start the half the account never did (Kelly trims, real reduce-only sale orders, for a file that only added; add-ons for one that only trimmed), and turn it on only through the first-run order for rebalancing from its step (2): `v2_probe --step yes-close` must PASS and the `--dry-run --rebalance` check must hold before (4) saves Rebalance yes. For a file saved before the category filter became a list of categories to exclude, or before the tag filter became a list of tags to exclude, the same notice and page offer its values with no category excluded (in place of `categories`) and no tag excluded (in place of `tags`), every other setting as saved (a file that predates several changes gets them all at once). One whose `categories` or `tags` was `null` traded every category, or every tag, and still does. One whose `categories` or `tags` listed names has no exact reading as a list to exclude, so its values as offered trade EVERY category, or EVERY tag: a red paragraph on every page that offers them names the old categories, or the tags it limited trading to (a tied "Category · Tag" having limited that category alone), and says how to keep that filter — add `&exclude_category=<name>` or `&exclude_tag=<name>` to the address for each category or tag to leave out, or save from the rebuilt dashboard with those categories and tags ticked in its Exclude categories and Exclude tags menus — and only then click Confirm and save. One whose old `categories` or `tags` the older version would itself have refused (not `null` or a list of names, a tied tag with a blank half, or one tied to a category the older version did not allow) gets no offer: save new defaults from the seed values or the dashboard. While the file is there, a confirmation link that names only some fields keeps the rest as the file had them (`defaults_server._kept_base`), and the page's red sell-more warning compares the proposal with those values. With no file at all, follow the first-run order for rebalancing (the paragraph after the live-trimming one), whose step (1) saves the seed values with rebalancing off; it does not start with `./start_dashboard.sh --seed`, because the seed turns Rebalance yes. Either way, check that `/saved` names that checkout's `live_defaults.json`. (2) Rebuild the dashboard with the `--start-date` it was built from (for the 365-day window, `python3 -m kalshi_betting.backtest --start-date 2025-09-24`, about 23 minutes and 2.1 GB when that window's corpus is already cached — measured before the Rebalance family, whose cells the dashboard step also simulates, and not re-measured — one heavy process at a time; without `--start-date` it runs from 2024-01-01, a far longer fetch; it is a full run, since `--dashboard-only` refuses a saved sweep from before this change, `BACKTEST_SWEEP_FORMAT` `backtest-sweep-v4`) — until then the old page may save no category or tag exclusion (a page built before the category change sends none, and one built before the tag change sends no tag, which the server reads as nothing excluded), and it may not save a scenario at all: on a page that shows adding to held pairs, trimming or Rebalance, its Save button sends the settings Rebalance replaced, which the defaults server refuses (`this link was built before Rebalance …`), and a page built before the Save and Trade buttons has neither (the defaults server WARNs so; run on its own it opens its index; through the launcher it opens nothing, and the Backtest tab shows the old page); meanwhile `http://127.0.0.1:8765/trade` trades the saved defaults. (3) If the scheduler daemon runs, restart it after the pull so it has the exit-50 message, and do (1) before starting it, since on start it can run a missed slot at once (it logs an ERROR at start while the file is missing, refused or outdated). Code from before this change refuses a file this change saves (it requires `tags`, or, older still, `categories`), so pull in every checkout that trades and restart its servers and scheduler daemon together. Later saves go through the same server: the backtest dashboard's "Save as live defaults…" button. **Precedence:** the file, then `main.py`'s toggle flags for one run; there is no fallback to config.py's toggle constants. `main._resolve_live_settings` reads the file once per run through `config.live_defaults()` — its only live caller — and that read travels as the run's `reference`, with where it came from on `LiveSettings.origin` (`live_defaults.json, saved <UTC time>[ from <source note>]`), which is `compare=False`, so `settings != reference` still reads only the twelve toggles and no run-mode signature changed (a counting spy on the reader and on config's parse of the file's bytes pins the one read: `tests/test_main.py::TestSavedLiveDefaults`). **A missing file raises `LiveDefaultsMissing`, a refused one `LiveDefaultsError`, and one an older version saved `LiveDefaultsOutdated`** (all `ValueError`s, the last two `LiveDefaultsError`s; refused means anything at the path that is not a usable file — see the config.py Module Map row), and `_resolve_live_settings` turns each into `parser.error`: exit 2 before logging is configured, any client is built or any request is made, the stderr naming the file and, for a missing file, the two ways to save one; for a refused file, the reason and the remedy: fix the file, or delete it before saving new defaults — `defaults_server` answers 409 and saves nothing while the file is refused; and for an outdated one, `the saved live defaults are out of date, and no run trades them: <the file, the old settings it holds and how the defaults server's pages offer them>; do not delete the file: a Confirm and save on those pages replaces it`, whatever flags are given (`tests/test_main.py::TestLiveDefaultsRequired`, `::test_a_file_an_older_version_saved_exits_2_with_the_remedy`). A scheduled run that exits 2 is `Job failed (exit 2)` in the scheduler's log and spends its slot (only 30 reopens one), so `scheduler._check_live_defaults` logs an ERROR as soon as the daemon starts whenever no usable file is saved — naming, for an outdated file, that every scheduled run will exit 2 until it is saved again through the defaults server and that it must not be deleted (`tests/test_scheduler.py::TestCheckLiveDefaults::test_an_outdated_file_logs_how_to_save_it_again`), and, for a missing file, the checkout (`PROJECT_ROOT`) the defaults must be saved in, since `python3 -m` run from another checkout's root (a worktree) saves that checkout's file, and run from any directory that is no checkout's root saves the pip-installed checkout's (the defaults server's first log line names the file it saves to) — and never raising, since the weekly job must still be registered. **The mark rule:** `describe_live_settings` marks each field a flag moved `(default: X)` against saved defaults and `(config: X)` against a reference built from config.py's constants (origin `config.LIVE_DEFAULTS_FROM_CONFIG`, which only a test or direct call hands a run mode); every live run logs `Live defaults: <origin>` before its `Live settings:` line, a production run that submits orders under a flag WARNs that it overrides the saved live defaults, and the trade log's separator note ends `| defaults: <origin>`. **config.py's twelve toggle constants are no live run's defaults.** They remain the backtest's `k` and caps (`backtester` and `backtest` bind them by value) and what `config.live_settings()` returns: the fallback a whitelisted live entry point reads when a caller hands it no settings — tests and direct library calls only, since the AST pin makes every live call path hand the run's settings. Do not "fix" that fallback into `live_defaults()`: hundreds of tests call the finders and the sizer without settings under monkeypatched constants. **So a backtest sizes at config.py's `k` and caps, not the saved defaults'**: its report names the saved defaults (`BacktestSweep`'s thirteen `live_*` fields, from one fail-soft pre-fetch read, `backtester._live_settings_for_report`), labelled `(saved live defaults)`, and says so whenever the saved `k` or caps differ from the run's primary (`backtester._live_sizing_note`, and on the page where the filter bar shows that sizing, `dashboard._live_sizing_bar_clause`); with no usable file it reads "none recorded — no usable live defaults were saved when this run started, and live runs refuse to start without them" (an INFO line with none saved, one WARNING with a refused file) and the run goes ahead. `backtest.py`'s pre-fetch echo is a separate read of its own (`live rule=<rule> (<origin>)`, `none saved (live runs refuse to start)`, or `not recorded — the saved live defaults are refused (...)`). **The seed** (`config.LIVE_DEFAULTS_SEED`): tier floors off, spread band 0–0.5, `k` 0.80, a 10% per-trade cap, a 20% same-title cap (which never binds under the 10% cap), no category or tag excluded, Rebalance yes with no minimum price movement, selling off — one new pair stakes at most 10% and `live_rule_warnings` is empty (an add-on never stakes more than a new pair, and never takes its whole position — the held pair at today's prices plus the fees paid for it, and the add-on — above 10% of the portfolio value; a Kelly trim only sells); nothing trades on it until it is saved. **A saved file that leaves `rebalance` out reads it as off** (`config._OPTIONAL_TOGGLES`: `rebalance`, `min_price_move`, `rebalance_min_days_to_maturity`, `sell_at` and `sell_min_days` may each be left out, and then take their `LiveSettings` default: no rebalancing, no minimum price movement, rebalancing at any distance from maturity, never selling, no minimum of days), though config.py (`REBALANCE`) and the seed ship it on: nobody confirmed a value for that file, so a file that leaves the key out starts every live run with no rebalancing. A missing required toggle, an extra key or a non-bool (`1`, `"true"`, `null`) is still refused. The writer leaves each optional key out while it is at its default, so a file with all five off holds only the other seven toggles; code from before the tag filter became a list to exclude (a revert, or a defaults server still running old code) requires `tags` where this file holds `exclude_tags` (code older still requires `categories` too), and refuses it; a file saved with rebalancing on carries `"rebalance": true` (and `"min_price_move": 0.1`, then `"rebalance_min_days_to_maturity": 7` when set) right after `exclude_tags`, before `sell_at`, and is refused by code from before Rebalance (exit 2 until it is saved again there). `LiveSettings` refuses a `rebalance` that is not a real bool, a `min_price_move` off the 5c grid (`PRICE_MOVE_STEP_CENTS`) or outside 5c to $1 (`min_price_move must be a multiple of 5c from 5c to $1, got X`, checked first), and a minimum with rebalancing off (`min_price_move needs rebalance on, got min_price_move X with rebalance off`); it also refuses a `rebalance_min_days_to_maturity` that is not 0 (stored as `None`), 1 or 7 (`rebalance_min_days_to_maturity must be 0, 1 or 7, got X`) and days with rebalancing off (`rebalance_min_days_to_maturity needs rebalance on, got rebalance_min_days_to_maturity X with rebalance off`); the reader refuses a JSON `true`/`false` for the minimum or the days and names the field. The confirmation page's address carries `rebalance` (`on`/`off`), `min_price_move` (`off` or dollars such as `0.1`) and `rebalance_min_days_to_maturity` (`0` for "maturity", `1` or `7`); a link that leaves one out keeps the saved value (the seed's, with none saved; a link naming `rebalance=off` clears the days), the seed page proposes rebalancing on with every other seed value, and the dashboard's save button sends the Rebalance choice and minimum only from a page that shows it, otherwise keeping what is saved. The dashboard's "Rebalance until" select shows each choice's run while Rebalance is yes (the backtest's walk applies the days through `_simulate_at_discount(rebalance_min_days_to_maturity=)`, and the page carries every choice's runs, read through `RebalanceSweep.maturity_grid` into its base block's `grid_maturity`): from a page with the choices its Save button sends the choice shown as `rebalance_min_days_to_maturity` (`0`, no days limit, for maturity and whenever Rebalance is no; `tests/test_dashboard.py::TestUntilScript` and `::TestSaveLiveDefaultsButton::test_the_rebalance_until_choice_on_screen_is_what_the_defaults_server_reads`), and from a page without them it leaves the days as saved (Rebalance no clears them) (pinned by `tests/test_config.py::TestSavedLiveDefaults::test_a_seven_toggle_file_reads_with_rebalancing_off`, `::test_the_written_text_is_pinned`, `::test_an_on_save_writes_the_key_after_the_filters`, `::test_the_writer_never_writes_a_retired_key` and `::TestLiveSettings::test_every_optional_toggle_is_a_field_with_a_default_at_the_end`). **A file an older version saved is refused as outdated.** Settings holding any of `config._RETIRED_TOGGLES` (`add_to_held_pairs`, `trim_to_kelly`, `trim_min_rise`: two switches and a minimum, where this version has `rebalance` and `min_price_move`; `categories`, a list of categories to trade, where this version has `exclude_categories`, a list of categories not to trade; and `tags`, a list of tags to trade, where this version has `exclude_tags`, a list of tags not to trade) are never read as the new settings: `_saved_settings` checks the file's keys, format, save time and source note first, then raises an internal `_RetiredSettings` carrying the proposal, which `read_saved_live_defaults` turns into `LiveDefaultsOutdated` naming the file (see the config.py Module Map row for the proposal's rule). Rebalance does both old jobs together, so the proposal turns it on only when both old switches were on, with the old `trim_min_rise` as its minimum; with either off it is Rebalance no with no minimum. In place of `categories` the proposal excludes no category: exact for a `null` `categories` (any category), while a listed one has no exact reading as an exclusion (what it left out depends on every category Kalshi lists), so its names ride on `LiveDefaultsOutdated.old_categories` and every defaults-server page that offers the proposal says in red that it trades every category; `tags` is read the same way, its names riding on `LiveDefaultsOutdated.old_tags`. No live run trades the proposal: `main._resolve_live_settings` exits 2, `scheduler._check_live_defaults` logs an ERROR, and only the defaults server offers it, on a confirmation page where one Confirm and save replaces the file (see the `defaults_server.py` Module Map row); a `backtest.py` run reads such a file as refused, so its report records no live rule (pinned by `tests/test_config.py::TestOutdatedSavedFile`, `::TestCategoriesRetirement` and `::TestTagsRetirement`, `tests/test_main.py::TestLiveDefaultsRequired::test_a_file_an_older_version_saved_exits_2_with_the_remedy`, `tests/test_scheduler.py::TestCheckLiveDefaults::test_an_outdated_file_logs_how_to_save_it_again` and `tests/test_defaults_server.py::TestOutdatedFile`). **The sell level and its minimum of days are optional keys too (2026-10-08).** A saved file that leaves `sell_at` or `sell_min_days` out, or holds `null` there, reads it as off (never selling, no minimum), and the writer leaves each out while it is off, so a file with rebalancing and selling all off is still the seven-toggle file; one that sells carries `"sell_at": 0.85` (and `"sell_min_days": 7`) after `rebalance`, `min_price_move` and `rebalance_min_days_to_maturity`, and code from before them refuses it as a file with an extra key (exit 2 until it is saved again there). The reader refuses a JSON `true`/`false` for either key and names the field; `LiveSettings` refuses a level off the 1% grid (`SELL_AT_STEP`) or outside (0, 1], a minimum that is not a whole number of days from 1 (a bool, `1.0` or a numpy integer included) and a minimum with no level. Nothing sells until a level is saved: the seed's and config.py's are off, and a file saved before the setting existed sells nothing, exactly as it traded. The confirmation page's address carries `sell_at` (`off` or a share such as `0.85`) and `sell_min_days` (`off` or a number of days); a link that leaves either out keeps the saved value (the seed's, with none saved). The first-run order for turning selling on is in the live-selling paragraph below, and for turning rebalancing on in the paragraph after the live-trimming one. **The AST pin** (`tests/test_strategy.py::TestTimeSeriesKellyParity::test_ast_live_path_reads_toggles_only_through_live_settings`) allows no direct `live_settings()` call anywhere on the live path (`_DIRECT_RESOLVERS` is empty), allows each saved-defaults reader only where `_DEFAULTS_READERS` names it (`live_defaults` in `main._resolve_live_settings`, `read_saved_live_defaults` in `scheduler._check_live_defaults` and `defaults_server._current_defaults`, each called exactly once, every allowed function found), allows `save_live_defaults` only in `defaults_server._App._post_confirm` (`_DEFAULTS_WRITERS`: the confirmation page's Confirm and save, and its Confirm and trade, which saves before it starts a run), and forbids in every walked module the saved file's path, config's private parse of it and the seed (`_SAVED_FILE_INTERNALS`: `LIVE_DEFAULTS_FILE`, `_settings_from_bytes`, `_saved_settings`, `LIVE_DEFAULTS_SEED`), so no second read can slip past the readers table — but for `_SAVED_FILE_EXEMPT`, which lets `defaults_server` alone read `LIVE_DEFAULTS_SEED` (the values `--seed` proposes; `_SAVED_FILE_IMPORTABLE`, so it may be imported by value) and print `LIVE_DEFAULTS_FILE` (the path its pages and log show; `_SAVED_FILE_PRINT_ONLY`: only as `config.LIVE_DEFAULTS_FILE` in a logging message call (`logging.info` and its siblings, never a handler), or its `.name` or `.absolute()` passed straight to `str()`, `html.escape()` or an f-string field, with every call around it in its statement one that prints or builds text — `str()`, `html.escape()`, a logging message call or one of the server's own functions — so `config.LIVE_DEFAULTS_FILE.read_bytes()`, `Path(str(config.LIVE_DEFAULTS_FILE.absolute())).write_text(...)` and `logging.FileHandler(config.LIVE_DEFAULTS_FILE)` fail, each checked by appending it to the server's source (`::test_ast_the_print_only_path_is_never_used_to_reach_the_file`); its sibling `::test_ast_the_reports_never_write_the_saved_live_defaults` pins that `backtester`, `backtest` and `dashboard` name none of those nor the writer (`save_live_defaults` and its helpers), so a report can never change what live runs trade. **Tests:** conftest's two redirects (`_isolate_live_defaults_for_the_session`, an empty session directory in force during class setup, and `_isolate_live_defaults`, each test's own `tmp_path`) keep every test off the real file; **Trading from the defaults server.** The defaults server's pages run the live bot from a browser: on `/confirm`, Confirm and trade saves the page's settings (exactly as Confirm and save does) and then starts one production run with them, and Dry run starts the same run with `--dry-run` and saves nothing; `/trade` does the same with the saved defaults. Each run is its own `python -m kalshi_betting.main --mode prod` process, started by `defaults_server._App._start_run` with all twelve toggles as explicit flags (`config.live_settings_argv`), so it trades exactly what its page showed whatever the saved file says by then, with `--result-file` in its own folder under `config.LIVE_RUNS_DIR` (`live_runs/`, gitignored), from `config.PROJECT_ROOT`, in a new session — so it starts with fresh process-level latches (the V2 mapping latches) as a scheduled run does, takes the machine-wide live-run lock like any real-money run, and nothing done in the server's terminal reaches it. Because every press starts a process whose V2 mapping latches are clear, the stop-trading remedy (`trader`'s two V2 NO-leg mapping-disproof CRITICALs, and `v2_probe._STOP_TRADING`, which the probe prints after a FAIL) says, beside stopping the scheduler daemon and not running `main.py --mode prod`, to stop the server with Ctrl-C in the terminal running `./start_dashboard.sh` or `python3 -m kalshi_betting.defaults_server` and not to press Confirm and trade. The dashboard reaches these pages through its filter bar ("Save as live defaults…" → `/confirm`, "Trade using defaults…" → `/trade`, each in a new tab), with the server started by `./start_dashboard.sh` (which also starts the live dashboard, whose Backtest tab is that page); a second start in the same checkout reuses the running server when it runs the checkout's current code (it opens the page and exits, starting nothing), and a start on a port held by that server running older code, or by another checkout's server, is refused (see the `defaults_server.py` Module Map row). Five rules are load-bearing. (1) **The server never places an order itself and never imports the pipeline:** it imports `config` and `run_lock` only (besides the standard library), and it starts a process only through the `start_process` it was built with — `subprocess.Popen`, which `main()` alone passes; the default `None` refuses every run (the pages say why), so no test and no other `_App` can start `main.py`. (2) **Every check before a save or a start runs first:** the used-nonce check right after the token check (a second POST of one page — a double click, a resubmit — is sent to what the first produced, and nothing is done twice), then the stale-page check, then the run's blockers (a run started from this checkout's server that is still going, found after a restart of the server too; `run_lock.held()`, a momentary shared lock that `acquire()`'s `LIVE_RUN_LOCK_WAIT_SECONDS` retry rides out, for a real-money run only) and, for a trade, the attention acknowledgement — all before `save_live_defaults`, so a refused trade saves nothing. (3) **A failed save means no trade:** Confirm and trade starts the run only after `save_live_defaults` has written the file, read it back and matched it. Nothing runs from a saved file an older version wrote (`LiveDefaultsOutdated`): `/trade` refuses it, and on `/confirm` Dry run waits for the save while Confirm and trade saves the page's settings first, so a run only ever trades settings saved in their new form. (4) **Every run's outcome is readable:** its page reads `result.json` strictly (a damaged file reads "result could not be read", never a crash) beside the exit code the server collected, checks exit 2 with no result (a usage error: "refused to start", nothing sent) before "ended without writing a result", tells a real-money run that ended without a result, or stopped while sending orders (`submission_started` true, no trades, an error), to check positions before trading again, and has a rule of its own for every `config.EXIT_*` code (`tests/test_defaults_server.py::TestRunPage::test_every_exit_code_has_a_rule_of_its_own`). (5) **The real-money button is always last and never moves:** a button that does not apply is a disabled placeholder with its reason, and the page script arms only the ids of `_ARMED_BUTTONS` present and stops re-arming once the form is sent. When the newest finished real-money run that says anything about the account — one the server started or the scheduler's; a run that stopped before it could send an order (exit 2, 10, 30 or 50) or a dry run is passed over — exited `EXIT_TRADES_NEED_ATTENTION` (a pair or a sale left for a person) or ended without a clean result (no result, a signal, an error after it began sending orders, a scheduled run stopped at the time limit), both trade pages show a red banner (it says to read that run's result — a scheduled run, which has no run page, is named with `kalshi_arb.log`, where its result is — and, if the result reports a V2 order-mapping disproof, to stop trading — stop the scheduler daemon, do not run `main.py --mode prod` and do not press Confirm and trade — and then undo by hand in the Kalshi UI what its CRITICAL names: close out a market the account did not hold before the run, and put one it did hold back to what it held (`defaults_server._ATTENTION_TAIL`)) and a real-money run needs a ticked box; only a newer clean run (exit 0 or 40) clears it, and a failure to read the records fails closed, with the banner. The server never stops a run (killing one mid-trade can orphan a leg), runs have no time limit, and a page calls a run possibly hung past `SCHEDULER_JOB_TIMEOUT_SECONDS`. **Residuals, recorded rather than fixed:** the server does not authenticate local programs (anything that can connect to 127.0.0.1:8765 can start a run with valid settings, as it could already save them for the next scheduled run — stop the server when done); a crafted link can open `/confirm` with attacker-chosen valid settings, and one armed click on Confirm and trade then saves and trades them (every change is highlighted, the source note is restricted, and the real-money button is last); nothing keeps the Mac awake during a run (the run page says to); a run stopped by a kill signal writes no result (its page says so, and for real money says to check positions); the attention banner reads only this checkout's `live_runs/` and scheduler state, so a hand-run terminal run or `v2_probe` leaves nothing it can read, and a scheduled run whose daemon stopped mid-run records no finish time, so the banner passes over it; category and tag names are checked for form only, however many a link names (a name that no series in Kalshi's /series listing carries and no pair of the run was filed under matches nothing, and the run's own typo WARNING, shown on its run page, says so), so a crafted link can name a look-alike of a real category (a homoglyph such as a Cyrillic "о", or an NFC and an NFD spelling of one name) in place of the real one, excluding the look-alike and leaving the real category (or tag) trading; a server running code from before the exclude lists refuses a link naming `exclude_category` or `exclude_tag` (an unknown field), and code from before them refuses every file this code saves (it requires `tags`, or `categories`), so restart the scheduler daemon and the servers and pull everywhere together; and pair choice is unchanged — a run started here is an ordinary production run, so same-title pairs can still stack across runs, and one open time-series pair per ladder still holds. Pinned by `tests/test_defaults_server.py` (`TestRenderStates`, `TestTokenAndNonce`, `TestActions`, `TestBlockers`, `TestAttention`, `TestRunPage`, `TestIsolation`, and `TestOverASocket`'s dry-run round trip, whose stand-in starts a tiny Python child through the real `subprocess.Popen` in place of `main.py`).

**The Live trading tab.** `./start_dashboard.sh` opens the page on its Live trading tab, served by `live_dashboard.py` and worked out by `live_portfolio.py` (their Module Map rows give the details); it reads the account from Kalshi on every page load and is reporting only — nothing on it trades, sizes or saves anything, and it imports no order-path module. Ten rules are load-bearing. (1) **Who owns what, and how the bot's orders are found.** The trade log (`reporter.PROD_LOG_PATH`, `trade_log.xlsx`, plus reporter's own fallback copies beside it, matched by their exact name pattern, never a copy you made) lists the bot's purchases and, for a run that sells, the held positions it sold before buying: a sale row (its Notes start `[sale: `, `live_portfolio._SALE_NOTE`; a Kelly trim's row does too) is read as that run's row, under a banner and log time of its own (so the purchases that follow are looked for after the sales' log time), but never as a purchase and never as a status the page does not know (`tests/test_live_portfolio.py::TestReadTradeLogs::test_a_runs_sales_are_a_log_time_of_their_own`, `::TestBuildLiveView::test_a_run_that_sells_then_buys`). Each executed leg is matched to one Kalshi order of exactly its market, direction and size, in two passes: first inside its run's own window — after the previous real run's log time (at most `LIVE_BOT_RUN_WINDOW_SECONDS`, 6 h, before its own) and up to its own — taking the latest order there, since a run's orders come just before it writes the log; then, for legs still unmatched, up to `LIVE_BOT_RUN_CLOCK_SLACK_SECONDS` past the log time, taking the earliest. A log time is read as the END of its second (`LIVE_TRADE_LOG_TIME_STEP_SECONDS`: the Time cell rounds down, and a run's last orders can land inside that second). A rolled-back or failed-unwind row matches its NO leg and then the bids that bought it back; every other fill is `OTHER_BETS` (your own trades, `v2_probe` included, and the bot's sale orders, which are read as sales by hand: a held pair's two sale orders, within `LIVE_MANUAL_PAIR_SECONDS` of each other, close that pair's purchase first, so what they bring in goes to it, and a lone held market's sale closes your own contracts in that market first, then the bot's). (2) **The cash model.** A fill's direction comes from its `book_side` alone — a bid buys YES or closes NO held, an ask sells YES held or opens NO — and the running position in that market decides how much of it closes and how much opens; Kalshi's `side` and `action` are never read, since they contradict its own documents (a NO purchase arrives with `action` "sell"). A close is paid the fill's price of the side closed and an open costs the price of the side opened, so the ledger's cash equals a plain running-position formula exactly; replayed oldest first, it rebuilds each run's logged "Balance before" (the cash check on the page: a banner above purchases is checked just before the run's first bot fill, and the banner above a run's sales, the cash before its sale orders, just before the run's first fill on the markets it sold, `::TestCheckLoggedCash::test_a_sales_banner_is_checked_just_before_its_first_sale`) and each market's held count, a market whose count differs from Kalshi's position being a warning. (3) **Rebuilt payouts.** Kalshi lists only recent settlements, so a market whose fills leave contracts held, which Kalshi neither holds nor lists a settlement for, has its payout rebuilt from the market itself (`/historical/markets`: its result, settlement time and YES value); a market it cannot read is a warning, and its contracts stay held. A settlement's `fee_cost` is the trading fees already charged and is never subtracted again. (4) **Valuation.** A holding is worth its decided result; else the midpoint of its quote, where Kalshi's placeholder for an empty side counts at its edge (a bid of 0, an ask of 1), so a one-sided quote is halfway from its real side to that edge; with both sides empty, the last trade, when strictly between 0 and 1; else the latest earlier daily price; else what it cost. (5) **Return.** The account is valued just before the bot's first fill, at each of Kalshi's daily closes (midnight New York), at each deposit or withdrawal — at the moment it lands, with it counted in — and now. The total return chains those step returns with each deposit or withdrawal taken out at the end of the step it lands in (time-weighted), so new money's gain or loss is never credited to the money already there; Profit is the value's change less deposits plus withdrawals. (6) **Ratios.** Sharpe and Sortino are the backtest page's own `dashboard._sharpe`/`_sortino` at `CALENDAR_DAYS_PER_YEAR`, over whole days only (one daily close to the next, the part-days at either end of the period left out; with fewer than `LIVE_RATIO_MIN_WHOLE_DAYS` they show "—"), less the 8-week T-bill yield on the share of the account held in positions at each day's opening close — the backtest page's rule of charging the yield on deployed capital only. (7) **Trades and categories.** Mean and median trade are pair-weighted (each contract pair counted once) over every executed or manual-review purchase whose two orders were both found and that was opened in the period, each at (cash back + value now − spent) ÷ spent, fees, sales and payouts included and open pairs at today's value; a rolled-back attempt is no pair, but its money counts in its category. A category's return over a period is its profit — value plus net cash at the end, less the same at the start — over what it put in: its value at the start plus the most cash it had out at any moment since, so a payout put back to work is not counted twice and a sale is cash back, never a loss. A bot purchase's category is its market A's Kalshi category (`historical.series_labels`, the backtest page's filing rule). (8) **Two ports, read-only.** The tab page and `/api/live` are on 127.0.0.1:8766 and the backtest page with its chunk files, and the Data page (`/eda/`, the third tab, which `eda.py` writes after each backtest), on 127.0.0.1:8767: two web origins, so neither of those pages nor the Plotly they load can read the account, and neither page can press the defaults server's buttons on 8765. The server sends Kalshi GETs only (its client's transport refuses any other method before anything is sent, with timeouts on every request), never loads the order path, answers only its own Host and only GET and HEAD, and refuses `/api/live` without the page's own header or from another site, and `/` when another site sent the browser there; the backtest port may be framed only by 8766, each of its pages in a sandboxed frame of its own that cannot navigate the tab page, and no other site may load its files except by navigating to them. (9) **The snapshot log.** Each read appends one JSON line to `LIVE_PORTFOLIO_LOG_FILE` (`live_portfolio_log.jsonl`, gitignored: the read's time, the cash, Kalshi's positions value, every holding with its value; a line it cannot write is a WARNING) and one INFO line to `LIVE_DASHBOARD_LOG_FILE` (`kalshi_live_dashboard.log`). The one thing cached is the daily prices of finalized markets read from Kalshi's archive (`LIVE_MARKS_CACHE_DIR`), which can never change; everything else is read fresh. (10) **Stable colors.** The categories are ordered by when each first appeared — its first bot purchase — ties by name, Other bets last (`live_portfolio._group_order`), and take the six palette slots in that order, the rest drawn together in gray as More categories (a lone one past the six by its own name, in that gray), so a category keeps its color from one load to the next — while each purchase's category and the set of matched purchases stay the same: Kalshi refiling a series, a /series listing that cannot be read with no copy cached (the categories then fall back to `infer_category`), or an older trade log found later can rename or reorder them — and a later category, however large, never takes an earlier one's slot (`tests/test_live_portfolio.py::TestBuildLiveView::test_a_later_bigger_category_does_not_take_an_earlier_ones_place`, `tests/test_live_dashboard.py::TestArea::test_a_later_bigger_category_does_not_take_an_earlier_ones_color`). **Residuals, recorded rather than fixed:** a deposit's fee is assumed to come out of the deposit and a withdrawal's to be charged on top of it (unverified, since no money has moved in or out since the bot's first live trade on 2026-09-28; the cash check would show the first mismatch); interest and fee rebates have no endpoint and are not counted as income, so they show only as a cash-check gap; a run whose trade-log write failed (only RESCUE lines in `kalshi_arb.log`) leaves its orders counted as Other bets; the trade log's times are this computer's local time, so reading it on a computer in another time zone shifts the windows; your sale of a bot pair is recognised only when you sell both its markets within `LIVE_MANUAL_PAIR_SECONDS` (10 minutes) of each other, and otherwise the oldest lots go first (the same holds for the bot's own two sale orders of a pair, should a slow reply ever hold them that far apart); a read has no overall deadline (each request has its timeouts, but their retries can stretch one read past `LIVE_DASHBOARD_BUILD_WAIT_SECONDS`, and a request arriving meanwhile gets 503); a dry run's sale row whose plan could not be used ("not sold") or whose sale raised ("check") is not simulated, so it opens a window and has its banner checked as a real run's does (its cash is the cash read then, so it matches); your own fill on a market a run sold, inside that run's window and before its first sale order, sets the time its banner is checked at, which can then read as a miss; and with a short history Sharpe and Sortino are noisy (each card says how many whole days it used). Pinned by `tests/test_live_portfolio.py` and `tests/test_live_dashboard.py`, the launcher by `tests/test_launcher.py`.
