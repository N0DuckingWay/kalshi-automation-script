This is a **production prediction-market pair-trading bot** (the "Kalshi Arbitrage Bot" is its product name; the time-series pairs it trades are a directional bet, not an arbitrage) that trades real money via RSA-signed Kalshi REST API calls. Read this file in full before making any changes to trading, fee, or order-submission logic.

The bot finds one type of mispriced binary contract pair on Kalshi (time-series pairs), sizes positions using the Kelly criterion, and submits fill-or-kill orders leg-by-leg (there is no batch order endpoint), unwinding the first leg if the second doesn't fill. With a sell level saved (`LiveSettings.sell_at`), a production run first sells the held positions that have reached it, by the take-profit rule the backtest uses and before it buys anything (see the live-selling paragraph under Key Patterns); with rebalancing on (`LiveSettings.rebalance`) it also sells part of each exact held time-series pair, and of each lone leg whose earlier market paid out $0, that has outgrown its Kelly share, in the same step (see the live-trimming paragraph), and may add to the pairs the account holds (DR-77). A separate backtesting pipeline replays the same strategy on the full history of settled markets.

**Time-series pairs:** Two contracts asking the same question at different deadlines (e.g. "Will BTC exceed $80k by March?" vs. "by June?"). `market_a` is always the EARLIER contract — earlier by `close_time`, except for a same-event ladder (DR-73), where it is earlier by STATED deadline and the pair carries that gap on `CandidatePair.stated_gap_days`. A later deadline can only add probability, so the later contract's YES ask normally sits above the earlier's, and the gap `pB − pA` measures the market-implied probability that the event first happens *between* the two deadlines — plus half the later book's width less half the earlier book's (a book's width, its YES ask plus its NO ask less 1, is a cost of trading rather than a view of the odds), which is why the forecast reads that probability at the midpoints instead (the mid spread, DR-78; see its gotcha below). The bot disputes that number when it is large: when `pB − pA` passes the run's live spread rule (`config.time_series_spread_refusal`: strictly positive, at least the entry floor — the band floor alone with the tier floors off, as the seed saves them and config.py ships them since the operator decision of 2026-09-27 (a floor of 0, so any strictly positive spread), or the deadline-gap tier `min_price_diff_for_gap(gap_days)` with the band floor layered on it with the tier floors on, as before that decision — and within the spread band's ceiling, 0.5 in the seed; a live run reads both from the saved live defaults, `live_defaults.json`; see the saved-live-defaults and directional-filter paragraphs and the live-defaults decision record of 2026-09-27 under Key Patterns) it buys YES on the earlier contract (at `pA`) and NO on the later one (at `nB`). Exactly three settlement cells exist: the event happens by the earlier deadline (A=YES ⇒ B=YES; the YES on A pays), it never happens by the later deadline (A=NO, B=NO; the NO on B pays), or it happens in between (A=NO, B=YES; both legs expire worthless — the full stake is lost). A=YES with B=NO is impossible for a cumulative-deadline pair. **That premise is now screened on WORDING at pair formation (a heuristic) rather than assumed (DR-67):** both the live finder and the backtest's refuse a pair unless both legs' WORDING states a cumulative "by <date>" deadline and the two deadlines DIFFER — `scanner.deadline_phrasing` / `scanner.cumulative_deadline_pair`, one definition shared by `find_time_series_pairs` and `backtester._extract_pairs` (see the cumulative-deadline gotcha below). The backtester still treats a pair that settled A=YES/B=NO as a premise violation and excludes it with a counted WARNING, never pays it — but that counter is no longer the ONLY signal, it is defence in depth behind a text heuristic, and a non-zero count now means one of the WARNING's named causes fired — most likely a wording false negative, though legs ordered on an early REALIZED close (cross-event pairs only — a same-event ladder is ordered on its stated deadlines), or strike-blind grouping on a cache without subtitles, can also produce it (DR-72 widened the WARNING beyond "the wording screen missed it" — see the strategy-change gotcha below for the full cause list). A wording heuristic has residuals: recurring rolling-window series ("before <date>" families that publish a new deadline every week) pass the screen without genuinely nesting, but checked against real prices they are co-quoted only in the earlier leg's final hours at a YES ask near $0.01, where the trade reduces to a NO bet on the later window regardless — measured harmless; see the Known residuals list in the cumulative-deadline gotcha below. This is a **directional bet, not an arbitrage**: at market prices its expected value is zero minus fees, and it only profits if the market systematically overstates the in-between mass. Kelly sizes it with `config.time_series_profit_prob(spread)` = `1 − k·spread`, where `spread` is the MID spread — the later market's midpoint minus the earlier one's, a midpoint being halfway between a market's YES ask and its YES bid (`config.time_series_mid_spread`; DR-78) — and `k = TIME_SERIES_INTERVAL_PROB_DISCOUNT` (0.80 since the operator decision of 2026-09-27; 0.75 before it) is the fraction of that market-implied in-between mass the operator believes ("prices converge by 20%"; by 25% at 0.75) — an operator-tunable estimate, not a measured quantity. With no per-trade cap in config.py since that decision, `k` also bounds every time-series trade: `f* < 1 − k` = 0.20 (the seed adds a 10% per-trade cap; a live run reads `k` and its per-trade cap from the saved live defaults). Two contracts are only "the same question at two deadlines" when they ask about the same OUTCOME, so the grouping key is `scanner.time_series_group_key(pair_key(m), m.subtitle)` — the date-stripped `event_title | market_title` PLUS the market's outcome label — not the title alone: a daily price family lists dozens of strikes under ONE title and differs only in the subtitle (DR-01, see the cross-strike gotcha below). Two contracts of ONE event ticker were refused outright until DR-73, on the rationale that a shared event is a multi-choice OPTION set; that is true of an MVE event's labels and false of a deadline LADDER, so `config.TIME_SERIES_SAME_EVENT_LADDERS` (ON by operator decision of 2026-09-26; it shipped OFF) admits two dated cumulative rungs of one event, ordered and tiered on their stated deadlines — see the same-event-ladder gotcha below. And two contracts whose RAW wording is identical — same `title`, same `subtitle`, same event title — across two event tickers of ONE series are not a cumulative-deadline pair at all: the deadline lives outside the wording, so they are two instances of one recurring fixture and the finder skips them (DR-02, DR-54 — see the one-series gotcha below). The one-series rule is checked first, so it is the rule that refuses and counts those skips; since DR-67 identical wording also fails the cumulative-deadline rule (it states one deadline, or none). The outcome label (`subtitle`) is the intra-title outcome discriminator and is sourced from the API's `yes_sub_title` field (see the subtitle-drift gotcha below) — it is load-bearing, not cosmetic: since DR-01 it is part of the time-series key `scanner.time_series_group_key`, and two markets are worded identically (`scanner._identical_wording`) only when their subtitles match too.

**Same-title pairs, which the bot no longer trades:** Two contracts with identical title, subtitle and event title on two events of DIFFERENT series: one question listed twice. Until November 2026 the bot bought No on the pricier and Yes on the cheaper when their Yes prices differed by 5¢ or more, sized on a fixed 95% chance that both settle alike. A pair also had to pass three checks: its two series differ, since two events of one series are two instances of one recurring fixture (DR-02/54, which stays and now protects time-series pairs; see the one-series gotcha in `known-gotchas/time-series-pairing.md`); its two markets close within an hour of each other (DR-74); and its two series are filed under one Kalshi category and first tag, and its two events name the same competition, or neither names one (DR-79). The bot no longer looks for, prices, sizes, buys or backtests them. Every place a pair comes in refuses any pair that is not time-series, with one log line and before any order (`scanner._enrich_pair`, `scanner.validate_pair_price`, `HeldPair.matches`, `strategy.compute_trade` and `strategy.select_portfolio`; `scanner.leg_sides`, `scanner.leg_prices` and `trader._ordered_legs` raise `ValueError` for another type, and the backtest refuses any entry that is not time-series). Same-title pairs the account bought earlier are left to settle on their own: live rebalancing never trims one (`scanner.held_pair_kind` gives two identically worded markets no kind, and it does not read two held markets on two events as a time-series pair when a stated deadline cannot be read and they close within an hour of each other; see the held-pair close bound gotcha in `known-gotchas/time-series-pairing.md`), but a saved sell level can still sell one whole (`seller.plan_sales` never asks a position's kind), and the time-series finder can still add to two rare same-title holdings (the DR-77 residuals in `known-gotchas/ladders-and-held-pairs.md`). Old trade-log rows that name a same-title pair are still read. A saved `live_defaults.json` that holds the retired `same_title_size_cap` is refused as outdated, so every live run exits 2 until one Confirm and save on the defaults page, and the old command-line flag for that cap exits 2 too.

**Multivariate (MVE) markets:** **Neither live runs nor the backtest read combo (MVE) markets since 2026-11-10** (`INCLUDE_MVE_MARKETS=False` in `config.py`). The combo listing had grown to 36 minutes of a 37-minute live run (5,475 pages, 639,261 combos, and still only part of the 7,114,381 open ones, because the walk stops at `MVE_MAX_EMPTY_PAGES`), and none of it forms a pair: of the 7.1 million, 6,457 had a YES ask of 1c to 99c (the rest list $0.00 / $1.00, since combos trade by request for quote), every one a parlay of sports games or races (2 to 21 legs) whose wording, event title included, names no deadline, so the cumulative-deadline rule refuses each; the live time-series finder returned the same 26 pairs with and without them. The live fetch skips the combo events listing, the shard coverage check leaves out the shard the exchange labels `COMBO_SHARD_DESCRIPTION` ("Combos") when it yields no markets (`scanner.unread_combo_shards`, one INFO line), and the backtest passes `mve_filter="exclude"` and names its assembled cache `_nomve` (DR-57). The rest of this paragraph describes how combos are handled when `INCLUDE_MVE_MARKETS` is turned back on. Time-series pairs include MVE markets (option markets within a multi-choice event, e.g. "Trump" inside "2024 Election Winner") when `INCLUDE_MVE_MARKETS=True`. Pairs are grouped by `event_title + market_title` (see `scanner.pair_key`) so option labels like "Trump" or "Above $80k" can't false-positive across unrelated events; the time-series finder keys on that PLUS the subtitle (`scanner.time_series_group_key`), which still leaves one option label at two deadlines in a single group but splits two different labels. Since DR-54 two identically worded MVE combo tickets are never paired: Kalshi lists combos under several series prefixes, all beginning `KXMVE` (`KXMVECROSSCATEGORY`, `KXMVESPORTSMULTIGAMEEXTENDED`, `KXMVECROSSCATEGORY0`, `KXMVENBASINGLEGAME`), and since DR-55 `scanner.event_series` collapses that whole family onto one series (`config.MVE_SERIES_FAMILY_PREFIX`) so the one-series rule treats any two combo tickets as two instances of one recurring fixture — a combo ticket's wording names its legs but never its date, so one wording recurs across fixture instances and two tickets with identical leg wording are two DIFFERENT tickets. That is a pairing rule, not an ingest exclusion: with `INCLUDE_MVE_MARKETS` on, MVE markets are fetched, grouped and eligible as time-series pairs. **DR-73 does not open MVE option labels to pairing either, and for the same reason the cumulative-deadline rule does not: it turns on WORDING.** Two markets of one event pair only when both are worded as cumulative deadlines reading to two DIFFERENT calendar dates, which an option set ("Trump" / "Harris" under one election event) never is — so the branch admits a deadline ladder and still refuses the multi-choice options this exclusion was written for. **The cumulative-deadline rule (DR-67) does not change that, because it turns on WORDING rather than on a market being MVE:** an MVE market whose sub-contract label carries a "by <date>" deadline ("$80,000 by June 30") is eligible like any other, and so is one whose parent EVENT title carries it ("Presidential Election Winner by March 2026") — those two routes are pinned by `tests/test_scanner.py::TestOutcomeDiscriminator::test_dated_outcome_label_is_one_key` and `::test_mve_option_label_at_two_deadlines_still_pairs`. The event-title route survives DR-69's deciding-field spans because there the event title IS the deciding field (the option label and title carry no marker), so it supplies the spans itself (`tests/test_scanner.py::TestSpansFromDecidingField::test_mve_event_title_route_still_pairs`). What that rule does refuse is the narrower case of a combo/parlay ticket whose wording names its legs but no date at all ("Parlay" / "All legs hit"), which classifies `unknown` and fails closed — correct, since such a pair never had a cumulative-deadline premise either. On the LIVE path no combo reaches this rule now, since none is read; on 2026-11-10, when the live listing still returned 639,261 combos, every priced one classified `unknown`, which this rule refuses. The CLASSIFIER does run routinely in the BACKTEST — cached day slices built while combos were read do carry combo records, and `_extract_pairs` classifies every member of a >=2-member time-series group up front, combo or not — but no combo PAIR ever reaches this refusal there either: two combos landing in one time-series group are always identically-worded duplicates of one KXMVE ticket, so the one-series conjunct (checked first) drops them a line earlier, before `cumulative_deadline_pair` is ever asked (measured on the 2026-09-08/09 day slices: 0 of 856,513 combo records share a group key with a differently-worded combo or with any non-combo). Since DR-68 the classifier does read combos worded "by Decision" (fight-method legs), which used to read as a "by Dec" deadline — on those same slices that was every one of the 525 combo records classified cumulative, and none remains. On those same 2026-09-08/09 day slices, the time-series pairs DR-67 removes from `main`'s set were mostly snapshot families (97.3% of 943,450 non-MVE pairs, per the verifier), plus dateless non-MVE look-alikes (2.7%) — combos contributed ZERO time-series candidates before and after this change (DR-02/54/55 already excluded them). Set `INCLUDE_MVE_MARKETS=False` to fall back to binary-only behaviour. With the flag off, event titles are still resolved and attached in both the scanner and the backtester — the flag narrows which markets are fetched, never how the remaining ones are grouped.
